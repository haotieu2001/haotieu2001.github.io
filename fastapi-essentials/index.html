FastAPI Essentials

FastAPI is a Python framework for building web APIs. You write a normal Python function, add type hints to it, and FastAPI turns those hints into request parsing, validation, error messages and live documentation - for free. This page walks the whole path: the request lifecycle, Pydantic validation, async, dependencies, talking to PostgreSQL with SQLAlchemy and Alembic, JWT auth, testing, a React frontend, packaging with Docker, splitting into microservices, and deploying the finished stack on AWS.

The short version

  • A route is a Python function with type hints. FastAPI reads the hints and derives parsing, validation, error responses and OpenAPI docs from them. You write the hints once and get four things.
  • Pydantic is the contract. One model class describes what comes in, another describes what goes out. Anything not in the outgoing model never reaches the client - that is your accidental-password-leak insurance.
  • Use async def only when the body awaits something. A blocking call inside async def freezes every other request on that worker. That single mistake causes most "FastAPI is slow" reports.
  • Depends() is the seam. Database sessions, the current user, settings and feature flags all arrive as arguments, so tests can swap them out with one line.
  • Postgres talks to you through a connection pool. One session per request, opened by a dependency, always closed - even when the handler raises.
  • Deployment is boring on purpose: one container image, many identical tasks behind a load balancer, a managed database next to them, and secrets injected at start-up rather than baked into the image.

01. What FastAPI is, and why it caught on

FastAPI is a Python library for building HTTP APIs. Its one big idea: the type hints you already write are enough information to build the whole request layer automatically.

An API is a program other programs talk to over HTTP. A phone app asks for a list of orders, a React page submits a form, another service checks whether a user exists. Each of those is an HTTP request with a method (GET, POST, PUT, DELETE), a path (/orders/42), sometimes a body of JSON, and a response with a status code and JSON back.

Writing that by hand is repetitive in a very specific way. For every single endpoint you find yourself doing the same six chores:

  • Pull values out of the URL and the query string, which arrive as strings.
  • Convert them to the types you actually want - an int, a UUID, a date.
  • Check they are valid, and return a clear 422 error when they are not.
  • Parse the JSON body into an object, and validate that too.
  • Turn your Python return value back into JSON.
  • Document all of the above so the frontend team knows what to send.

FastAPI does all six from the function signature. Here is the entire idea in five lines:

python
from fastapi import FastAPI

app = FastAPI()

@app.get("/orders/{order_id}")
def read_order(order_id: int, include_items: bool = False):
    return {"id": order_id, "items": [] if include_items else None}

Because order_id is annotated int and appears in the path, FastAPI knows to read it from the URL and convert it. Because include_items is annotated bool with a default and does not appear in the path, FastAPI knows it is an optional query parameter. Request /orders/abc and you get a 422 with a precise message, without writing a single line of checking code. Open /docs in a browser and there is a full interactive API reference you never wrote.

Two words worth defining before we go further, because they show up constantly.

Two terms you need up front

ASGI
Asynchronous Server Gateway Interface. The agreed contract between a Python web framework and the server process that runs it. WSGI, the older contract, could only handle one request per worker at a time. ASGI can hold thousands of requests open at once, which is what makes async possible.
Uvicorn
The ASGI server almost everyone uses with FastAPI. FastAPI describes what your endpoints do; Uvicorn is the process that actually listens on a TCP port and speaks HTTP. You always run both together.

The mental model to keep

FastAPI is a thin, clever layer over two libraries: Starlette handles routing, middleware and the HTTP mechanics; Pydantic handles validation and serialisation. When you hit a problem, ask which of the two owns it. "Why is my body rejected?" is a Pydantic question. "Why does my middleware not see the response?" is a Starlette question. Knowing which library to search is half the debugging.

02. Your first app, line by line

Install two packages, write ten lines, run one command. Then read the four things that just happened.

bash
# A virtual environment keeps this project's packages separate from the system Python
python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate

pip install "fastapi[standard]"
# the [standard] extra pulls in uvicorn, the CLI, and a few useful helpers
python
# main.py
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="Orders API", version="1.0.0")


class Order(BaseModel):
    id: int
    customer: str
    total_cents: int


@app.get("/health")
def health():
    return {"status": "ok"}


@app.get("/orders/{order_id}", response_model=Order)
def read_order(order_id: int):
    return Order(id=order_id, customer="ada", total_cents=1999)
bash
fastapi dev main.py        # development: auto-reload on file save
# or the explicit form, which is what you run in production:
uvicorn main:app --host 0.0.0.0 --port 8000

In main:app, the part before the colon is the Python module (the file main.py) and the part after is the variable inside it. Uvicorn imports the module and looks for that object. Getting this string wrong is the single most common first-run error.

The four things you now have

1
A working API. curl localhost:8000/orders/42 returns JSON. curl localhost:8000/orders/abc returns a 422 explaining that order_id must be an integer.
2
Interactive docs at /docs. A Swagger UI page listing every endpoint with a "Try it out" button that fires real requests. Nothing to configure.
3
A machine-readable schema at /openapi.json. This is the file that later generates your TypeScript client in §15. It is the contract between backend and frontend, and it is generated, so it cannot drift out of date.
4
A guaranteed response shape. response_model=Order means the response is validated on the way out too. Return a dict with an extra internal_notes key and it is silently dropped rather than leaked.

Route order matters

FastAPI matches routes top to bottom and stops at the first hit. If /orders/{order_id} is declared before /orders/summary, then a request to /orders/summary matches the first route, tries to parse "summary" as an int, and returns 422. Always declare fixed paths before parameterised ones.

03. Path, query and body parameters

There are only three places data can arrive from, plus headers and cookies. FastAPI decides which is which by a simple rule you can hold in your head.

The rule, in order:

  1. If the parameter name appears inside the path string, it is a path parameter.
  2. Otherwise, if its type is a simple scalar (int, str, bool, float, UUID, date, Enum), it is a query parameter.
  3. Otherwise, if its type is a Pydantic model, it is the request body.
python
from datetime import date
from typing import Annotated
from fastapi import FastAPI, Path, Query, Header
from pydantic import BaseModel, Field

app = FastAPI()


class OrderCreate(BaseModel):
    customer: str
    total_cents: int = Field(gt=0)


@app.post("/customers/{customer_id}/orders")
def create_order(
    # 1. in the path string -> path parameter, always required
    customer_id: Annotated[int, Path(ge=1)],

    # 2. Pydantic model -> the JSON body
    payload: OrderCreate,

    # 3. scalars with defaults -> optional query parameters
    notify: bool = False,
    placed_on: date | None = None,

    # 4. explicit metadata: constraints plus docs text
    coupon: Annotated[str | None, Query(max_length=16, description="Promo code")] = None,

    # 5. headers: underscores become dashes automatically
    x_request_id: Annotated[str | None, Header()] = None,
):
    return {"customer_id": customer_id, "notify": notify, "body": payload}

That endpoint handles a request like POST /customers/7/orders?notify=true&coupon=SUMMER with a JSON body. Every value is parsed, converted and range-checked before your function starts running.

Why Annotated instead of a default value

You will see both styles in tutorials. q: str = Query(max_length=50) works, but it puts a FastAPI object where Python expects a default value, which confuses type checkers and makes the function awkward to call directly from a test. q: Annotated[str, Query(max_length=50)] = "x" keeps the default in the normal place and the metadata in the annotation. Prefer Annotated in new code - it is the documented style and it composes with the dependency system in §6.

Required, optional, and nullable are three different things

DeclarationClient must send it?Can it be null?
q: strYesNo
q: str = "abc"No, defaults to "abc"No
q: str | None = NoneNo, defaults to NoneYes
q: str | NoneYes, but may be nullYes

The last row surprises people. Writing | None does not make a field optional; leaving off the default is what makes it required. They are separate switches.

04. Pydantic: the validation layer

Pydantic turns a class definition into a parser, a validator, a serialiser and a JSON Schema document. It is the piece doing most of the work, so it is worth understanding on its own.

A Pydantic model looks like a dataclass but behaves very differently: creating one runs the type annotations rather than ignoring them.

python
from datetime import datetime
from decimal import Decimal
from pydantic import BaseModel, EmailStr, Field, field_validator, ConfigDict


class CustomerIn(BaseModel):
    # forbid unknown keys: a typo in the client is now a 422, not a silent no-op
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    name: str = Field(min_length=1, max_length=120)
    email: EmailStr
    credit_limit: Decimal = Field(ge=0, decimal_places=2)
    signed_up_at: datetime | None = None

    @field_validator("name")
    @classmethod
    def no_digits(cls, v: str) -> str:
        if any(ch.isdigit() for ch in v):
            raise ValueError("name must not contain digits")
        return v.title()

Send {"name": "ada 3", "email": "not-an-email", "credit_limit": -5} and you get a single 422 listing all three problems with the exact field path for each. You did not write an if statement.

The three-model pattern

This is the most useful convention in the whole framework, and beginners usually discover it the hard way. Do not use one model for everything. The data a client is allowed to send, the data stored in the database, and the data you send back are three different shapes.

python
class CustomerBase(BaseModel):
    name: str
    email: EmailStr


class CustomerCreate(CustomerBase):
    # only ever arrives; never leaves
    password: str = Field(min_length=12)


class CustomerUpdate(BaseModel):
    # every field optional, so PATCH can send just one
    name: str | None = None
    email: EmailStr | None = None


class CustomerOut(CustomerBase):
    # what the client is allowed to see - note: no password, no internal flags
    id: int
    created_at: datetime
    model_config = ConfigDict(from_attributes=True)   # can read a SQLAlchemy row

from_attributes=True is the switch that lets Pydantic build a model from an object with attributes, such as a SQLAlchemy row, instead of only from a dict. Without it, returning a database row from a handler raises a confusing validation error. With it, response_model=CustomerOut converts the row and drops everything not listed.

This is a security control, not a style preference

Because response_model drops any field it does not know about, a separate *Out model is what stops a password hash, an internal fraud score or another tenant's identifier from reaching the browser the day someone adds a column to the table. One model for everything means every new column is published by default. Default to closed.

Any FastAPI version from 0.100 onward uses Pydantic v2, but a lot of search results still show v1. The renames that trip people up: @validator is now @field_validator, class Config is now model_config = ConfigDict(...), orm_mode is now from_attributes, .dict() is now .model_dump(), and .parse_obj() is now .model_validate(). If a snippet uses the left-hand name, it is v1 - translate it before pasting.

05. async def vs def, and the event loop

This is the one section where a wrong choice quietly destroys your performance. The rule is short, but you need the picture underneath it to remember which way round it goes.

What the event loop actually does

A typical API handler spends most of its life doing nothing. It sends a query to Postgres and waits 20 milliseconds for the answer. During that wait the CPU is idle. The event loop's whole job is to notice that wait and use it to make progress on another request.

The catch is that the loop can only notice a wait if you tell it about one. The word that tells it is await. When your code says await session.execute(...), control returns to the loop, which picks up another request. When your code instead calls a normal blocking function - requests.get(), time.sleep(), a synchronous database driver - the loop never gets control back. It sits frozen until that call finishes, and every other request on that worker waits with it.

The rule

Choose by what is inside the function

If the body contains await, write async def. If the body calls anything blocking that you cannot await, write plain def and let FastAPI move it to a thread pool for you. The only broken combination is async def with a blocking call inside. When in doubt, plain def is the safe default - it is never catastrophic, only slightly slower.

python
# CORRECT: async all the way down
@app.get("/orders/{oid}")
async def read_order(oid: int, db: AsyncSession = Depends(get_db)):
    row = await db.get(Order, oid)          # async driver, awaited
    return row

# CORRECT: blocking work, declared sync - FastAPI runs it in a thread
@app.get("/report")
def build_report():
    return pandas.read_parquet("s3://bucket/big.parquet").describe().to_dict()

# BROKEN: async promise, blocking body - freezes every other request
@app.get("/rates")
async def rates():
    return requests.get("https://api.example.com/rates").json()   # no await!

# FIXED, option 1: use an async HTTP client
@app.get("/rates")
async def rates(client: httpx.AsyncClient = Depends(get_client)):
    r = await client.get("https://api.example.com/rates")
    return r.json()

# FIXED, option 2: push the blocking call off the loop explicitly
from starlette.concurrency import run_in_threadpool

@app.get("/rates")
async def rates():
    r = await run_in_threadpool(requests.get, "https://api.example.com/rates")
    return r.json()

Doing several waits at once

Once a handler is async, you get concurrency inside a single request almost for free. Three independent calls that each take 100 ms take 300 ms in sequence and 100 ms together:

python
import asyncio

@app.get("/dashboard")
async def dashboard(db: DbSession, http: HttpClient):
    # one database call and two network calls - none of them need each other
    orders, rates, weather = await asyncio.gather(
        count_orders(db),                        # uses the request's session
        http.get("https://api.example.com/rates"),
        http.get("https://api.example.com/weather"),
    )
    return {"orders": orders, "rates": rates.json(), "weather": weather.json()}

Do not share one database session across gathered tasks

A SQLAlchemy AsyncSession is not safe to use from two coroutines at once. The example above is fine because only one of the three gathered tasks touches the database. Put count_orders(db) and count_invoices(db) in the same gather and you get InterfaceError: another operation is in progress. If you really need two queries in parallel, open a second session from the pool for the second task - or just run them one after the other, which is usually fast enough.

How many processes to run

One Uvicorn process uses one CPU core, because of Python's global interpreter lock. To use a whole machine you run several processes, each with its own event loop, behind a single port. In containers the usual answer is one process per container and let the orchestrator scale containers - it keeps memory accounting, health checks and rolling deploys simple. The rough starting point when you do run several in one box is workers = (2 × cores) + 1, then measure.

06. Dependency injection with Depends

A dependency is just a function whose result FastAPI computes and hands to your handler as an argument. That small idea is what keeps a growing codebase from turning into copy-pasted boilerplate.

Every endpoint needs the same few things: a database session, the logged-in user, the app settings. Without dependencies you fetch them at the top of every handler and remember to clean them up at the bottom. With dependencies you declare them in the signature and FastAPI resolves the whole tree before your function runs.

python
from typing import Annotated
from fastapi import Depends

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    # everything before `yield` runs before the handler
    async with SessionLocal() as session:
        yield session
    # everything after `yield` runs after the response is built - even on error

# give the annotation a name so you write it once, not fifty times
DbSession = Annotated[AsyncSession, Depends(get_db)]


@app.get("/orders")
async def list_orders(db: DbSession):
    return (await db.execute(select(Order))).scalars().all()

Dependencies depend on other dependencies

This is where the pattern earns its keep. A dependency can itself declare dependencies, so FastAPI builds a graph and resolves it in the right order, once per request.

The four shapes a dependency can take

python
# 1. plain function - runs, returns a value
def pagination(limit: int = 50, offset: int = 0) -> dict:
    return {"limit": min(limit, 200), "offset": offset}

# 2. generator - has setup AND teardown, like a context manager
async def get_db():
    async with SessionLocal() as s:
        yield s

# 3. class - the instance itself is the dependency, __init__ takes the params
class Paginator:
    def __init__(self, limit: int = 50, offset: int = 0):
        self.limit, self.offset = min(limit, 200), offset

@app.get("/items")
def items(page: Annotated[Paginator, Depends()]):   # no argument needed
    return {"limit": page.limit}

# 4. side-effect only - the return value is ignored, it just has to not raise
async def verify_api_key(x_api_key: Annotated[str, Header()]):
    if x_api_key != settings.api_key:
        raise HTTPException(status_code=401, detail="bad api key")

# attach it to a whole router, or the whole app
router = APIRouter(dependencies=[Depends(verify_api_key)])

Why this matters for testing

Because every external thing enters through Depends, a test can replace it with one line. No monkey-patching, no import-order tricks:

python
app.dependency_overrides[get_db] = lambda: fake_session
app.dependency_overrides[get_current_user] = lambda: User(id=1, is_admin=True)
# ... run tests ...
app.dependency_overrides.clear()

This is the practical reason to route all shared state through dependencies, including things that feel too small to bother with, like "what time is it now". The day you need to test the month-end job, you will be glad the clock was injectable.

07. Errors, status codes and handlers

An API is judged by its error responses as much as its happy path. The goal is one predictable JSON shape for every failure, so the frontend has exactly one thing to handle.

Raising an error from a handler

python
from fastapi import HTTPException, status

@app.get("/orders/{oid}", response_model=OrderOut)
async def read_order(oid: int, db: DbSession):
    order = await db.get(Order, oid)
    if order is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail="Order not found",
        )
    return order

raise, not return. Raising means every dependency's teardown still runs - the database session still closes, the transaction still rolls back - and the exception can bubble to a handler that logs it. Returning a hand-built error response skips all of that.

One error shape for the whole API

FastAPI's defaults are two different shapes: {"detail": "..."} for HTTPException and {"detail": [ ... ]} for validation errors. Normalise them once, at the app level, and the frontend never has to guess:

python
import logging, uuid
from fastapi import Request
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError

log = logging.getLogger("api")


def problem(status_code: int, code: str, message: str, **extra) -> JSONResponse:
    return JSONResponse(
        status_code=status_code,
        content={"error": {"code": code, "message": message, **extra}},
    )


@app.exception_handler(HTTPException)
async def on_http_error(request: Request, exc: HTTPException):
    return problem(exc.status_code, "http_error", str(exc.detail))


@app.exception_handler(RequestValidationError)
async def on_validation_error(request: Request, exc: RequestValidationError):
    # exc.errors() gives loc / msg / type per bad field - pass it through
    return problem(422, "validation_error", "Request body is invalid",
                   fields=jsonable_encoder(exc.errors()))


@app.exception_handler(Exception)
async def on_unhandled(request: Request, exc: Exception):
    # log the real cause with an id; give the client only the id
    incident = str(uuid.uuid4())
    log.exception("unhandled", extra={"incident": incident, "path": request.url.path})
    return problem(500, "internal_error",
                   "Something went wrong on our side.", incident=incident)

Now every failure looks the same, and a support ticket saying "I got incident 4f3c..." maps to one exact line in your logs.

Translating database errors

A duplicate email should be a clean 409, not a 500 with a Postgres error string in it. Catch the driver's exception at the edge of your data layer and re-raise something meaningful:

python
from sqlalchemy.exc import IntegrityError

try:
    db.add(customer)
    await db.flush()
except IntegrityError as exc:
    await db.rollback()
    if "customers_email_key" in str(exc.orig):
        raise HTTPException(409, "That email is already registered") from exc
    raise

08. Project structure that scales

A single main.py is perfect for the first week. Past that, use a layout that separates the four concerns: routes, business logic, data access, and configuration.

text
orders-api/
├── app/
│   ├── main.py              # create_app(), middleware, lifespan, router wiring
│   ├── config.py            # Settings, read once from the environment
│   ├── deps.py              # shared dependencies: DbSession, CurrentUser
│   ├── api/
│   │   ├── health.py        # APIRouter for /health and /ready
│   │   └── v1/
│   │       ├── orders.py    # APIRouter, prefix="/orders"
│   │       └── customers.py
│   ├── schemas/             # Pydantic models - the wire format
│   │   └── order.py         #   OrderCreate / OrderUpdate / OrderOut
│   ├── models/              # SQLAlchemy models - the table format
│   │   └── order.py
│   ├── services/            # business rules; no HTTP, no framework imports
│   │   └── ordering.py
│   ├── repositories/        # all the SQL lives here
│   │   └── orders.py
│   └── db.py                # engine + session factory
├── alembic/                 # migration scripts

│   ├── conftest.py
│   └── test_orders.py
├── Dockerfile
├── docker-compose.yml
└── pyproject.toml

The important rule is the direction of imports: api imports services, services import repositories, and nothing ever imports back up. Your services/ code should not import fastapi at all. That is what lets you reuse the same logic in a scheduled job or a message consumer later, and it is what makes splitting into microservices a move rather than a rewrite.

Settings from the environment, validated

python
# app/config.py
from functools import lru_cache
from pydantic import PostgresDsn, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    environment: str = "local"
    database_url: PostgresDsn
    jwt_secret: SecretStr
    jwt_ttl_minutes: int = 30
    cors_origins: list[str] = []
    db_pool_size: int = 5


@lru_cache
def get_settings() -> Settings:
    return Settings()          # parsed once; every caller shares this object

Two things this buys you. First, a missing DATABASE_URL crashes the container at start-up with a clear message, instead of causing a mysterious 500 at 3am. Second, SecretStr means the secret cannot accidentally appear in a log line or a traceback.

Lifespan: start-up and shutdown

Things that must exist for the whole life of the process - a connection pool, an HTTP client, a cache client - belong in the lifespan context manager, not at import time. Anything created at import time also gets created when a test or an Alembic script imports the module, which is rarely what you want.

python
# app/main.py
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    # --- start-up: runs once, before the first request ---
    app.state.http = httpx.AsyncClient(timeout=5.0)
    yield
    # --- shutdown: runs once, after the last request ---
    await app.state.http.aclose()
    await engine.dispose()


def create_app() -> FastAPI:
    app = FastAPI(title="Orders API", version="1.0.0", lifespan=lifespan)
    app.include_router(health.router)
    app.include_router(orders.router, prefix="/api/v1", tags=["orders"])
    app.include_router(customers.router, prefix="/api/v1", tags=["customers"])
    return app


app = create_app()

The create_app() factory is worth the extra three lines: tests can build a fresh app with different settings, and nothing happens merely because a module was imported.

Version your API from day one

Mounting routers under /api/v1 costs nothing today. The day you need a breaking change, you add /api/v2 and run both while clients migrate. Retrofitting a version prefix onto a live API means changing every caller at the same instant, which is not a thing you can actually do.

09. PostgreSQL part 1: engine, session, models

Almost every FastAPI service talks to Postgres, and almost every production incident with one traces back to the same thing: connections. Start there, then the code is easy.

The three layers between you and the database

Driver, engine, session

Driver (asyncpg)
Speaks the Postgres wire protocol over a TCP socket. Low level. asyncpg is the async one; psycopg is the traditional synchronous one. You rarely call it directly.
Engine
Created once when the app starts. It owns the connection pool - a small set of open connections that are handed out and returned rather than opened per query. Opening a Postgres connection takes tens of milliseconds, so the pool is the whole point.
Session
Created once per request. It borrows a connection from the pool, tracks the objects you loaded and changed, and wraps your work in one transaction. Closing it returns the connection.

The arithmetic that prevents the outage

replicas × workers_per_replica × (pool_size + max_overflow) < max_connections − headroom. Scale to 20 replicas with a default pool and you will exhaust a small RDS instance long before you exhaust its CPU. When the numbers stop working, put PgBouncer in transaction mode in front of Postgres: hundreds of client connections get multiplexed onto a few dozen real ones.

Engine and session factory

python
# app/db.py
from collections.abc import AsyncGenerator
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession
from sqlalchemy.orm import DeclarativeBase

from app.config import get_settings

settings = get_settings()

# note the +asyncpg: postgresql+asyncpg://user:pass@host:5432/dbname
engine = create_async_engine(
    str(settings.database_url),
    pool_size=settings.db_pool_size,   # connections kept open
    max_overflow=10,                    # extra ones allowed at a burst
    pool_timeout=30,                    # seconds to wait for a free connection
    pool_recycle=1800,                  # drop connections older than 30 min
    pool_pre_ping=True,                 # cheap SELECT 1 before reuse
    echo=settings.environment == "local",
)

SessionLocal = async_sessionmaker(
    engine, expire_on_commit=False, class_=AsyncSession
)


class Base(DeclarativeBase):
    pass


async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with SessionLocal() as session:
        try:
            yield session
            await session.commit()      # handler finished cleanly -> commit
        except Exception:
            await session.rollback()    # anything raised -> undo everything
            raise

Two settings deserve a note. pool_pre_ping=True costs one tiny round trip but saves you from the classic "server closed the connection unexpectedly" that happens when a load balancer or the database silently drops an idle connection - very common on AWS RDS. expire_on_commit=False means the objects you loaded stay usable after the commit; without it, touching order.id after committing triggers a fresh query, which then fails because the session is closing.

Commit in the dependency, not in the handler

The get_db above gives you one transaction per request, for free, everywhere. A handler that creates an order and writes an audit row either produces both or neither - no half-finished state to clean up. Handlers use await db.flush() when they need a generated id mid-request, and never call commit() themselves.

Foreign key columns are not indexed automatically

Postgres indexes the primary key for you. It does not index the foreign key side. Without index=True on customer_id, every "orders for this customer" query scans the whole table, and every delete of a customer scans it too. This is the number one cause of a query that was instant with 1,000 rows and takes 40 seconds with 10 million.

Two model families, on purpose

You now have Order in models/ (a table row) and OrderOut in schemas/ (a JSON document). Duplicating the field names feels wasteful for about a week, and then you rename a column, or add an internal risk_score, and you understand why they are separate. The bridge between them is one line:

10. PostgreSQL part 2: queries that behave

Modern SQLAlchemy uses one query style for everything: build a select(), hand it to the session, ask for the shape you want back.

The query patterns you will use every day

python

from sqlalchemy.orm import selectinload

# one row by primary key - checks the session's identity map first
order = await db.get(Order, order_id)

# one row by any condition; None if there is no match
stmt = select(Customer).where(Customer.email == email)
customer = (await db.execute(stmt)).scalar_one_or_none()

# a filtered, sorted, paged list
stmt = (
    select(Order)
    .where(Order.customer_id == cid, Order.status == "paid")
    .order_by(Order.created_at.desc())
    .limit(50)

orders = (await db.execute(stmt)).scalars().all()

# aggregate
stmt = select(func.count()).select_from(Order).where(Order.status == "paid")
total = (await db.execute(stmt)).scalar_one()

# join and return columns rather than whole objects
stmt = (
    select(Customer.name, func.sum(Order.total).label("lifetime"))
    .join(Order, Order.customer_id == Customer.id)
    .group_by(Customer.name)
    .having(func.sum(Order.total) > 1000)
)
rows = (await db.execute(stmt)).all()      # list of (name, lifetime) tuples

# bulk update without loading anything into Python
await db.execute(
    update(Order).where(Order.status == "pending").values(status="expired")
)

The N+1 problem, and the one-word fix

This is the single most common performance bug in any ORM, and it is invisible in code review because the code looks fine.

python
# SLOW: 1 query for the customers, then 1 more per customer = 101 queries
customers = (await db.execute(select(Customer).limit(100))).scalars().all()
for c in customers:
    print(len(c.orders))     # each attribute touch fires a fresh SELECT

# FAST: 2 queries total, no matter how many customers
stmt = select(Customer).options(selectinload(Customer.orders)).limit(100)
customers = (await db.execute(stmt)).scalars().all()

selectinload issues a second query with WHERE customer_id IN (...) and stitches the results together. Use it for one-to-many relationships. Use joinedload for many-to-one, where a single LEFT JOIN is cheaper than a second round trip.

With an async session, lazy loading does not merely slow down - it crashes

Under AsyncSession, touching an unloaded relationship raises MissingGreenlet, because the implicit query would need to run I/O from a place that cannot await. That sounds annoying and is actually a gift: the N+1 bug becomes a loud error in development instead of a silent 40× slowdown in production. The fix is always the same - name what you need with selectinload or joinedload up front.

# keyset pagination: the client sends back the cursor we gave it
@router.get("/orders", response_model=Page[OrderOut])
async def list_orders(db: DbSession, after: str | None = None, limit: int = 50):
    stmt = select(Order).order_by(Order.created_at.desc(), Order.id.desc())
    if after:
        ts, last_id = decode_cursor(after)
        # row-value comparison - one index seek, not a scan
        stmt = stmt.where(tuple_(Order.created_at, Order.id) < (ts, last_id))
    rows = (await db.execute(stmt.limit(min(limit, 200)))).scalars().all()
    next_cursor = encode_cursor(rows[-1]) if len(rows) == limit else None
    return {"items": rows, "next": next_cursor}

Note min(limit, 200). Always cap a client-supplied limit. Otherwise the first curious person to send ?limit=999999999 takes your service down for everybody.

Check-then-act is a bug unless the database is holding a lock

"Read the balance, decide, then write" works perfectly until two requests arrive in the same millisecond, both read 100, and both subtract 80. The fixes, in order of preference: let a unique constraint reject the duplicate and translate the error to a 409; use ON CONFLICT so insert-or-update is a single statement; use SELECT ... FOR UPDATE when you truly must read, think, and then write.

Keeping SQL out of your handlers

Handlers should read like a description of the endpoint, not like a query plan. Push queries into a repository module - it makes them reusable, testable, and easy to find when one gets slow.

python
# app/repositories/orders.py - the ONLY place that knows about tables
class OrderRepository:
    def __init__(self, db: AsyncSession) -> None:
        self.db = db

    async def get(self, order_id: int) -> Order | None:
        return await self.db.get(Order, order_id)

    async def recent_for_customer(self, cid: int, limit: int = 50) -> list[Order]:
        stmt = (select(Order).where(Order.customer_id == cid)
                              .order_by(Order.created_at.desc()).limit(limit))
        return list((await self.db.execute(stmt)).scalars().all())


# app/deps.py
def order_repo(db: DbSession) -> OrderRepository:
    return OrderRepository(db)

OrderRepo = Annotated[OrderRepository, Depends(order_repo)]

11. Alembic: changing the schema safely

Your models describe the tables you want. Alembic is the tool that gets an existing database from the shape it has to the shape you want, one reviewable step at a time.

The tempting shortcut is Base.metadata.create_all(). It creates missing tables and is genuinely fine for a throwaway test database. It will never alter an existing column, never backfill data, and never tell you what changed - so it is not a migration tool. Use Alembic from the first commit.

bash
pip install alembic
alembic init -t async alembic        # async template, matches our engine

# after editing a model, generate a migration by comparing models to the DB
alembic revision --autogenerate -m "add status to orders"

# READ the generated file, then apply it
alembic upgrade head

alembic current                      # which revision is this database on?
alembic history --verbose            # the full chain
alembic downgrade -1                  # step back one (test this before you need it)

Point alembic/env.py at your metadata so autogenerate can see the models, and read the URL from the same settings object the app uses:

python
# alembic/env.py (the two lines that matter)
from app.db import Base
import app.models.order, app.models.customer   # import so classes register

target_metadata = Base.metadata
config.set_main_option("sqlalchemy.url", str(get_settings().database_url))

Autogenerate is a first draft, not an answer

It reliably misses: renames (it emits a DROP plus an ADD, which deletes your data), CHECK constraints, enum value changes, index renames, and anything about server defaults. It also never writes the data backfill you need. Open every generated file and read it before running it.

Adding a required column without downtime

Adding a NOT NULL column with no default to a live table fails, because existing rows have nothing to put in it. The safe recipe is three deploys, and it is worth learning once because you will use it constantly:

1
Deploy 1 - add it nullable. ALTER TABLE orders ADD COLUMN currency VARCHAR(3). Existing rows get NULL; nothing breaks. Ship application code that writes the new column but does not require it.
2
Backfill in batches. A single UPDATE over 50 million rows locks the table for minutes. Loop in chunks of a few thousand with a commit between them, so other queries keep flowing.
3
Deploy 2 - tighten it. Once every row has a value, SET NOT NULL. Now the model can declare it required.
python
# alembic/versions/8f2a_add_currency.py
def upgrade() -> None:
    op.add_column("orders", sa.Column("currency", sa.String(3), nullable=True))

    # batched backfill - never one giant UPDATE on a big table
    conn = op.get_bind()
    while True:
        result = conn.execute(sa.text("""
            UPDATE orders SET currency = 'USD'
            WHERE id IN (SELECT id FROM orders WHERE currency IS NULL LIMIT 5000)
        """))
        if result.rowcount == 0:
            break


def downgrade() -> None:
    op.drop_column("orders", "currency")

Build indexes concurrently on a live table

A plain CREATE INDEX takes a lock that blocks writes for the whole build - potentially many minutes on a large table. Postgres offers CREATE INDEX CONCURRENTLY, which does not. In Alembic: op.create_index(..., postgresql_concurrently=True), and mark the migration with with op.get_context().autocommit_block(): because concurrent index builds cannot run inside a transaction.

Where migrations should run

Not in your application's start-up code. If ten containers start at once, ten of them race to migrate the same database. Run alembic upgrade head as a separate one-off task that must finish before the new version rolls out - an ECS run-task step, a Kubernetes Job, or a CI job with database access. Alembic takes a lock on its version table, so a race is more likely to hang your deploy than to corrupt data, but a clean pipeline order avoids the question entirely.

12. Authentication with OAuth2 and JWT

Two separate questions, often confused. Authentication asks who you are. Authorization asks what you may do. FastAPI helps with the plumbing of both; the policy is yours.

What a JWT actually is

A JSON Web Token is three base64 chunks joined by dots: a header, a payload of claims, and a signature. The payload is readable by anyone - it is encoded, not encrypted. The signature proves the server issued it and that nobody changed a character since. So: never put a secret in a JWT, and never trust one you did not verify.

text
eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiI0MiIsImV4cCI6MTc...  .  4f9Xc2H1kQ...
└──── header ─────┘     └──────── payload ──────────┘     └── signature ──┘
  alg: HS256              sub: "42"      who it is        HMAC-SHA256 over
  typ: JWT                exp: 1735689600 when it dies    header.payload
                          role: "admin"  what it may do   using your secret

The big trade-off: because verification is pure arithmetic, no database call is needed to check a token. That is what makes JWTs so good for microservices - any service with the public key can validate a caller. The cost is that you cannot un-issue one. A token stays valid until it expires, so keep access tokens short (15-30 minutes) and pair them with a refresh token you can revoke, because that one is checked against a table.

# app/security.py
from datetime import datetime, timedelta, timezone
from jose import jwt, JWTError
from passlib.context import CryptContext

pwd = CryptContext(schemes=["bcrypt"], deprecated="auto")
ALGORITHM = "HS256"


def hash_password(raw: str) -> str:
    return pwd.hash(raw)


def verify_password(raw: str, hashed: str) -> bool:
    return pwd.verify(raw, hashed)


def create_access_token(subject: str, minutes: int, secret: str) -> str:
    now = datetime.now(timezone.utc)
    claims = {
        "sub": subject,                                  # who
        "exp": now + timedelta(minutes=minutes),         # until when
        "iat": now,                                      # issued at
        "iss": "orders-api",                              # who issued it
    }
    return jwt.encode(claims, secret, algorithm=ALGORITHM)

    db: DbSession,

        detail="Could not validate credentials",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        payload = jwt.decode(
            token,
            settings.jwt_secret.get_secret_value(),

            issuer="orders-api",

    user = await db.get(User, int(payload["sub"]))
    if user is None or not user.is_active:
        raise credentials_error
    return user

Five ways JWT auth goes wrong

  • Accepting any algorithm. Always pass an explicit algorithms=["HS256"]. Letting the token's own header pick the algorithm is the classic alg: none forgery.
  • No expiry. A token without exp is a password that never changes and cannot be taken back.
  • A guessable secret. Generate it with openssl rand -hex 32 and load it from AWS Secrets Manager, never from the repository.
  • Trusting a claim you did not verify. Decoding the payload without checking the signature is reading a document someone else wrote.
  • Storing the token in localStorage. Any injected script can read it. Prefer an httpOnly, Secure, SameSite=Lax cookie - see §15.

Ownership checks are your job, not the framework's

A valid token proves who the caller is. It says nothing about whether this order belongs to them. Forgetting that check is the most common real-world API vulnerability, and the automated scanners have a name for it: broken object-level authorization.

python
# WRONG: any logged-in user can read anyone's order by guessing an id
@router.get("/orders/{oid}")
async def read(oid: int, user: CurrentUser, repo: OrderRepo):
    return await repo.get(oid)

# RIGHT: scope the lookup to the caller, and 404 rather than 403
@router.get("/orders/{oid}")
async def read(oid: int, user: CurrentUser, repo: OrderRepo):
    order = await repo.get_for_customer(oid, user.id)
    if order is None:
        raise HTTPException(404, "Order not found")   # do not confirm it exists
    return order

13. Middleware, CORS and background tasks

Middleware wraps every request. Use it for things that must happen for all of them, and nothing else - it is on the hot path.

python
import time, uuid
from fastapi import Request

@app.middleware("http")
async def add_request_context(request: Request, call_next):
    request_id = request.headers.get("x-request-id") or str(uuid.uuid4())
    started = time.perf_counter()

    response = await call_next(request)      # the rest of the app runs here

    elapsed_ms = (time.perf_counter() - started) * 1000
    response.headers["x-request-id"] = request_id
    response.headers["x-response-time-ms"] = f"{elapsed_ms:.1f}"
    log.info("request", extra={
        "request_id": request_id, "method": request.method,
        "path": request.url.path, "status": response.status_code,
        "ms": round(elapsed_ms, 1),
    })
    return response

Middleware runs in the reverse order it is added: the last one added is the outermost wrapper. That matters when a logging middleware needs to see the response that an error-handling middleware produced.

CORS, explained properly

Browsers refuse to let JavaScript on app.example.com read a response from api.example.com unless the API explicitly allows it. This is a browser rule, enforced in the browser - curl and your mobile app never see it, which is why "it works in Postman but not in the browser" is always a CORS problem.

For anything except a simple GET, the browser first sends an OPTIONS "preflight" request asking permission, and only sends the real request if the answer allows the method, the headers and the origin.

python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.cors_origins,   # ["https://app.example.com"]
    allow_credentials=True,                # needed for cookie auth
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
    max_age=600,                           # cache the preflight for 10 minutes
)

allow_origins=["*"] plus allow_credentials=True silently does nothing

The browser specification forbids that combination outright, so the browser drops the response and you get a confusing console error rather than a clear one. With credentials you must list real origins. And "*" in production is a bad idea anyway: it lets any website on the internet call your API with the visitor's browser.

Test against real Postgres, not SQLite

SQLite is tempting because it needs no server. It also has no JSONB, no ON CONFLICT the same way, different NULL ordering, weaker type checking and no real concurrency - so a green test suite tells you very little. Run a throwaway Postgres in Docker for tests (§16) or use Testcontainers to start one per test session. The extra few seconds buy you tests that mean something.

Three tests are worth writing for every endpoint before anything clever: the happy path, one validation failure, and one authorization failure. That trio catches the overwhelming majority of regressions, and it takes about five minutes per endpoint.

One small API client, and nothing else

Resist the urge to install a heavyweight HTTP wrapper. Thirty lines around fetch gives you the base URL, the token, JSON parsing and consistent errors - and you can read all of it.

typescript
// src/api/client.ts
import type { paths } from "./types.gen";

const BASE = import.meta.env.VITE_API_URL ?? "http://localhost:8000";

export class ApiError extends Error {
  constructor(public status: number, public code: string, message: string) {
    super(message);
  }
}

export async function apiFetch<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`${BASE}${path}`, {
    ...init,
    credentials: "include",          // send the httpOnly auth cookie
    headers: { "Content-Type": "application/json", ...init.headers },
  });

  if (res.status === 204) return undefined as T;

  const body = await res.json().catch(() => ({}));

  if (!res.ok) {
    // the single error shape we standardised on in §07
    const e = body.error ?? {};
    throw new ApiError(res.status, e.code ?? "unknown", e.message ?? res.statusText);
  }
  return body as T;
}

// the response type comes straight from the backend - zero hand-written types
export type Order =
  paths["/api/v1/orders/{oid}"]["get"]["responses"][200]["content"]["application/json"];

17. Splitting into microservices

Microservices trade a simple problem you understand for a distributed problem you probably do not. Sometimes that trade is worth it. Start by being honest about when.

Start with one service. Really.

A well-structured FastAPI monolith - the layout from §08, with clean module boundaries - takes most teams a very long way. Split when you have a concrete reason: two parts need wildly different scaling (a GPU inference endpoint next to a CRUD API), separate teams keep blocking each other on releases, or one part has different compliance rules. "It is more modern" is not a reason, and neither is a diagram.

# synchronous: orders-svc asks payments-svc, and waits
class PaymentsClient:
    def __init__(self, http: httpx.AsyncClient, base: str) -> None:
        self.http, self.base = http, base

    async def charge(self, order_id: int, cents: int, key: str) -> ChargeResult:
        r = await self.http.post(
            f"{self.base}/charges",
            json={"order_id": order_id, "cents": cents},
            # the key that makes a retry safe - see the box below
            headers={"Idempotency-Key": key},
            timeout=3.0,           # ALWAYS set a timeout. Always.
        )
        if r.status_code >= 500:
            raise HTTPException(503, "Payments unavailable, try again shortly")
        r.raise_for_status()
        return ChargeResult.model_validate(r.json())


# asynchronous: orders-svc announces, and does not care who listens
async def publish_order_paid(sns, order: Order) -> None:
    await sns.publish(
        TopicArn=settings.orders_topic_arn,
        Message=json.dumps({
            "event": "order.paid",
            "version": 1,                     # version events from day one
            "event_id": str(uuid.uuid4()),      # consumers dedupe on this
            "occurred_at": order.paid_at.isoformat(),
            "data": {"order_id": order.id, "total": str(order.total)},
        }),
    )

Idempotency: the one habit that makes distributed systems survivable

Networks fail after the work is done as often as before it. A timeout does not tell you whether the charge went through. So every write endpoint accepts an Idempotency-Key, stores it with the result, and returns the stored result if the key comes back. Now a retry is free, and "did we charge them twice?" stops being a question anyone has to ask.

The two problems you inherit on day one

You cannot use a transaction across services

In the monolith, "create the order and charge the card" was one transaction: both happen or neither does. Across two services there is no such thing. The standard replacement is a saga: a sequence of local transactions where each step has a compensating step that undoes it.

text
happy path      order.created  →  payment.charged  →  stock.reserved  →  order.confirmed
                     ok                 ok                 FAILS

compensate      order.cancelled  ←  payment.refunded  ←  ─────────────────┘
                (undo step 1)       (undo step 2)

Note what this means for the user: for a short window the order exists and the card is charged, but the item is not reserved. The system is eventually consistent, and the product has to be designed for that - "your order is being confirmed" rather than a claim that is briefly false.

One request now spans several logs

Generate a correlation id at the gateway, pass it through every hop in a header, and log it everywhere. Without it, debugging means grepping four services by timestamp and hoping. With it, one search shows the whole journey.

python
# in every service: accept the id if present, create it if not, and pass it on
@app.middleware("http")
async def correlation(request: Request, call_next):
    cid = request.headers.get("x-correlation-id") or str(uuid.uuid4())
    correlation_id.set(cid)               # a contextvar the logger reads
    response = await call_next(request)
    response.headers["x-correlation-id"] = cid
    return response

A sensible splitting order

1
Draw the seams inside the monolith first. Separate modules, separate schemas, no cross-module imports, no cross-schema joins. Enforce it in code review. This is 80% of the work and none of the risk.
2
Extract the piece with the most different needs. Usually the one that is GPU-bound, or bursty, or under separate compliance rules. Not the one that is easiest.
3
Give it its own database and copy the data it needs. Duplication is now correct, not a smell. The new service keeps its own read model, updated from events.
4
Put a gateway in front before you extract the second one, so clients never learn the internal topology and you can keep moving routes without breaking anyone.

Two roles, two purposes, and mixing them up is a common security mistake. The execution role is what ECS itself uses to pull the image and read the secrets before your container starts. The task role is what your code uses to call AWS at runtime - reading an S3 bucket, publishing to SNS. Your application should never have permission to read the secrets it was already given.

Two health endpoints, not one

python
# app/api/health.py

@router.get("/health")                 # LIVENESS: am I running?
async def health():
    # must NOT touch the database. If the DB blips and this returns 503,
    # the load balancer kills every task and you have an outage, not a blip.
    return {"status": "ok"}


@router.get("/ready")                  # READINESS: can I serve traffic?
async def ready(db: DbSession):
    try:
        await db.execute(text("SELECT 1"))
    except Exception:
        raise HTTPException(503, "database unreachable")
    return {"status": "ready"}

Point the load balancer at the liveness check

If the ALB health check queries the database and the database has a two-second hiccup, every task fails its check at the same moment, all get replaced at once, and a two-second blip becomes a five-minute outage. Liveness must be cheap and local. Use /ready for deployment gating and dashboards instead.

The deployment pipeline

1
Test. Lint, type-check and run pytest against a real Postgres service container. Nothing ships that has not passed.
2
Build and push. One image, tagged with the git SHA. The SHA is what makes a rollback exact: you can name the artefact that was running yesterday.
3
Migrate. Run alembic upgrade head as a one-off ECS task and wait for it to succeed. Because migrations are backward-compatible (§11), the old code keeps working while this runs.
4
Roll out. Update the service; ECS starts new tasks, waits for their health checks, shifts traffic, then drains the old ones. If the new tasks never go healthy, the deployment circuit breaker rolls back automatically.
5
Publish the frontend. Sync the build to S3, then invalidate the CloudFront cache for /index.html. Hashed asset files never need invalidating - that is the point of hashing them.

Right-size the scaling policy, not the instance

An API that waits on a database is rarely CPU-bound, so a CPU-based scaling rule fires late or never. Scale on ALB request count per target or on p95 latency instead. 19. Observability and going live

Once the service is running somewhere you cannot attach a debugger to, the only thing you have is what it tells you about itself. Make that worth reading.

Log JSON, not sentences

A human-readable log line is unsearchable at scale. Structured JSON lets CloudWatch Logs Insights answer questions like "show me every 500 for this customer in the last hour" in one query.

python
import json, logging, sys
from contextvars import ContextVar

correlation_id: ContextVar[str] = ContextVar("correlation_id", default="-")


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S%z"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "correlation_id": correlation_id.get(),
        }
        # anything passed as extra={...} rides along as its own field
        payload.update(getattr(record, "context", {}))
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        return json.dumps(payload)


handler = logging.StreamHandler(sys.stdout)   # stdout - the container ships it
handler.setFormatter(JsonFormatter())
logging.basicConfig(handlers=[handler], level=logging.INFO)

Never log the request body

It is the fastest route to passwords, card numbers and personal data sitting in a log store with a much broader access list than your database. Log the method, path, status, duration, user id and correlation id. Log field names when validation fails, never field values. And put a retention policy on the log group before the first deploy, not after the first bill.

The go-live checklist

Before the first real user

Secrets
Nothing sensitive in the repository, the image or a plain environment variable. All of it in Secrets Manager, injected at start-up. A rotation plan exists.
HTTPS everywhere
TLS terminated at CloudFront and the ALB. HTTP redirects to HTTPS. HSTS set.
Docs
Decide deliberately whether /docs and /openapi.json are public. For an internal API, pass docs_url=None in production or put them behind auth.
Database
Automated backups on, retention set, and a restore you have actually performed once. An untested backup is a hope.
Connections
The §09 arithmetic checked against your maximum task count, not your current one.
Timeouts
Every outbound HTTP call has one. Every database statement has statement_timeout. A hung dependency should fail fast, not pile up.
Graceful shutdown
On SIGTERM, stop accepting new work, finish in-flight requests, close the pool. Set the ALB deregistration delay above your slowest request.
Alarms that page
Error rate, p95 latency, and database connections. Everything else is a dashboard, and a dashboard nobody watches is fine.
Rollback
You can name the previous image tag and redeploy it in one command. You have done this once, on purpose, in business hours.

Where do I put shared state?A dependency. Always. It is the only thing a test can replace cleanly
One Pydantic model or three?Three: Create, Update, Out. The Out model is a security control
Where does commit() go?In the get_db dependency, so one request is one transaction

Every term used on this page

ASGI
The contract between a Python web framework and its server that allows many requests to be in flight at once. The async successor to WSGI.
Uvicorn
The ASGI server that actually listens on a port and runs your FastAPI app.
Starlette
The library underneath FastAPI providing routing, middleware, requests and responses.
Pydantic
The validation and serialisation library FastAPI uses. Turns type hints into runtime parsing and JSON Schema.
Event loop
The scheduler that runs many coroutines on one thread by switching between them at every await.
Coroutine
A function defined with async def. Calling it returns an object that does nothing until awaited.
Blocking call
Any function that occupies the thread until it returns. Fatal inside async def, fine inside plain def.
Dependency injection
Declaring what a function needs in its signature and letting the framework supply it. In FastAPI, Depends().
response_model
The Pydantic model a response is validated and filtered through on the way out. Unlisted fields are dropped.
OpenAPI
The standard JSON description of an API. FastAPI generates yours; /docs renders it and code generators consume it.
SQLAlchemy
Python's main database toolkit. The ORM maps classes to tables; Core builds SQL statements.
Session
A SQLAlchemy unit of work: one per request, wrapping one transaction, holding the objects you loaded.
Connection pool
A small set of open database connections reused across requests, because opening one is expensive.
N+1 query
Loading a list, then firing one extra query per item. Fixed with selectinload or joinedload.
Eager loading
Fetching related rows in the same trip as the parents, on purpose, instead of on first access.
Migration
A versioned, reviewable script that moves a database schema from one shape to the next. Alembic manages them.
Keyset pagination
Paging with WHERE key < last_seen instead of OFFSET, so deep pages stay fast.
JWT
A signed, base64-encoded token carrying claims. Readable by anyone, forgeable by nobody without the key.
Claim
One field inside a JWT payload: sub (who), exp (until when), iss (who issued it).
OAuth2 password flow
Exchanging a username and password at a token endpoint for an access token. What OAuth2PasswordBearer wires up.
CORS
The browser rule that stops JavaScript on one origin from reading a response from another unless the server allows it.
Preflight
The automatic OPTIONS request a browser sends before a non-simple cross-origin request, asking permission.
Idempotency
The property that doing something twice has the same effect as doing it once. What makes a retry safe.
Saga
A multi-service workflow built from local transactions, each with a compensating action to undo it.
Eventual consistency
Different services hold briefly different views of the same fact, converging shortly after.
Correlation id
One identifier attached to a request and passed to every service it touches, so the logs can be joined.
Liveness vs readiness
Liveness: the process is alive - restart it if not. Readiness: it can serve traffic - send requests only if so.
ECS Fargate
AWS's serverless container runtime: you supply an image and a size, AWS supplies the machines.
Task definition
The JSON blueprint for a container in ECS: image, CPU, memory, secrets, logging, health check.
ALB
Application Load Balancer. One HTTPS front door that spreads requests across healthy tasks.
RDS
AWS's managed relational database. Backups, patching and failover are handled for you.
ECR
AWS's private container image registry, where your built images live.
OIDC (in CI)
Letting GitHub Actions assume an AWS role with a short-lived token, so no long-lived AWS keys are stored anywhere.
Blast radius
How much breaks when one thing fails. Non-root containers, private subnets and narrow IAM roles all shrink it.
