DSA Patterns Sheet for Data Engineers

The revision sheet that pairs with the full DSA guide. Eighteen patterns, and for each one the phrase that signals it, the template to write, what it costs, and the trap that fails people. Nothing outside what a data engineering interview actually asks.

~12 min read · Sep 2026 · 18 patterns · 18 runnable snippets · a sheet to skim, not a course

❯ How to use this sheet

1. Listen for the signal. Interview questions are worded in a small set of phrases, and each phrase maps to one pattern. 2. Write the template. Every snippet is the short version you should be able to type from memory. 3. Say the cost and the trap. Naming the complexity and the failure mode out loud is most of what separates a pass from a fail.

Scope is the same as the guide: TIER 1 · MUST KNOW TIER 2 · GOOD TO KNOW. The overkill list (grid and bitmask DP, max flow, segment trees, contest maths) is deliberately left out.

Name your own loop first

Before any pattern, say what your loop does. One pass over the data is O(n). A loop inside a loop is O(n²). Halving the search space each step is O(log n). A sort is O(n log n). A dict or set lookup is O(1) on average. If your first answer is nested loops, the fix is nearly always a hashmap.

02.Tier 1 patterns

Fourteen patterns. This is most of the bar.

P01 · Count, group, dedupe

Signal: "how many times", "most common", "per customer", "unique", "have we seen this"

In DE · Status counts in a log file, rows per user, dropping the replayed rows of a re-delivered batch.

Cost · O(n) time · O(distinct keys) memory

from collections import Counter, defaultdict

def count_group_dedup(rows):
    status = Counter(r["status"] for r in rows)  # counting
    by_user = defaultdict(list)                  # grouping
    for r in rows:
        by_user[r["user"]].append(r)
    seen, unique = set(), []                     # dedup, keep first
    for r in rows:
        if r["id"] not in seen:
            seen.add(r["id"])
            unique.append(r)
    return status, by_user, unique

Trap: Quote the distinct-key count as memory, not n. One hot key is the single-machine form of a skewed partition. Full walkthrough: §05

P02 · Hash join (build, then probe)

Signal: "join these two datasets", "enrich events with the customer", "look up each row in a reference table"

In DE · What a Spark broadcast hash join does: hold the small table in memory, stream the big one past it.

Cost · O(n + m) time · O(small side) memory, versus O(n × m) for a nested loop

def hash_join(orders, customers, key="cust_id"):
    by_id = {c[key]: c for c in customers}  # BUILD: the small side, once
    for o in orders:                        # PROBE: stream the big side
        c = by_id.get(o[key])
        if c is not None:                   # no match: skip (left join: keep o)
            yield {**o, **c}

Trap: The dict keeps one row per key, so a duplicate key on the build side silently overwrites. If the build side is not unique, store a list per key. Full walkthrough: §05

P03 · One-pass parse and aggregate

Signal: "parse this file and give me a metric", "average latency per endpoint", "errors per hour"

In DE · The most common DE coding question: read a log line by line, split it, fold it into dict aggregates.

Cost · O(n) time · O(distinct keys) memory

from collections import defaultdict

def avg_latency(lines):      # "2026-01-01T00:00:01 GET /users 120"
    total, count, bad = defaultdict(float), defaultdict(int), 0
    for line in lines:
        parts = line.split()
        if len(parts) != 4:  # malformed: count it, keep going
            bad += 1
            continue
        _, _, path, ms = parts
        total[path] += float(ms)
        count[path] += 1
    return {p: total[p] / count[p] for p in total}, bad

Trap: Malformed lines are normal input. Count them and move on, never crash. Iterate the file object instead of reading it all into a list. Full walkthrough: §03

P04 · Two pointers

Signal: "a pair that sums to", "reverse in place", "palindrome", "remove duplicates from sorted data"

In DE · Find two ledger amounts that reconcile to a target. Compact a sorted key column in place without a second array.

Cost · O(n) time · O(1) memory

def pair_summing_to(a, target):  # a MUST be sorted
    i, j = 0, len(a) - 1
    while i < j:
        s = a[i] + a[j]
        if s == target:
            return a[i], a[j]
        if s < target:
            i += 1               # too small: raise the low end
        else:
            j -= 1               # too big: lower the high end
    return None

def compact_sorted(a):           # same direction: read ahead, write behind
    if not a:
        return 0
    w = 1
    for r in range(1, len(a)):
        if a[r] != a[w - 1]:
            a[w] = a[r]
            w += 1
    return w                     # a[:w] is the unique prefix

Trap: Squeezing from both ends only works on sorted input, and on unsorted input it is silently wrong rather than loudly broken. Full walkthrough: §03

P05 · Binary search on a predicate

Signal: "first one at or after", "the cutoff", "find the boundary", "which partition holds this timestamp"

In DE · First event after a watermark in a time-sorted file. Which sorted partition boundary a key falls into.

Cost · O(log n) time · O(1) memory

from bisect import bisect_left

def first_true(lo, hi, pred):  # pred flips once: F..FT..T
    while lo < hi:
        mid = (lo + hi) // 2
        if pred(mid):
            hi = mid           # mid may be the answer: keep it
        else:
            lo = mid + 1       # mid is not: discard it
    return lo                  # equals hi if nothing matched

# library form, for a sorted list ts:
#   bisect_left(ts, x) == first_true(0, len(ts), lambda k: ts[k] >= x)

Trap: Write hi = mid and lo = mid + 1, never lo = mid, which loops forever. The predicate must flip once, from False to True. Full walkthrough: §03

P06 · Merge two sorted streams

Signal: "combine two sorted files", "join two already-sorted datasets", "union then keep order"

In DE · The core of an external merge sort, and of a sort-merge join when both inputs arrive sorted on the key.

Cost · O(n + m) time · O(n + m) for the output list, O(1) if you stream it out

def merge(a, b):
    i = j = 0
    out = []
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:  # <= keeps it stable: ties come from a
            out.append(a[i]); i += 1
        else:
            out.append(b[j]); j += 1
    out.extend(a[i:])     # drain the tails - the classic miss
    out.extend(b[j:])
    return out

Trap: Forgetting to drain whichever side still has rows left. For a join, duplicates on both sides need a cross product per key group. Full walkthrough: §06

P07 · Latest row per key

Signal: "latest record per key", "current state from a change stream", "keep the newest duplicate"

In DE · Collapse a CDC feed to the current row per primary key before a MERGE. Deduplicate an at-least-once source.

Cost · O(n) time · O(distinct keys) memory

def latest_per_id(rows, ts="updated_at"):    # rows: dicts with id + timestamp
    best = {}
    for r in rows:
        cur = best.get(r["id"])
        if cur is None or r[ts] >= cur[ts]:  # >= : a later arrival wins ties
            best[r["id"]] = r
    return list(best.values())

Trap: Decide the tie-break on equal timestamps out loud. The one-pass max never needs a sort, and sorted() is stable if you do sort. Full walkthrough: §06

P08 · Stack

Signal: "validate nesting", "matching brackets", "undo", "the most recent unfinished thing"

In DE · Validate brackets in a SQL fragment or a hand-rolled config. Anything where the last thing opened must be the first thing closed.

Cost · O(n) time · O(n) memory

def is_balanced(s):
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in s:
        if ch in "([{":
            stack.append(ch)
        elif ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False  # closer with no matching opener
    return not stack          # leftovers mean an unclosed opener

Trap: Two easy misses: popping from an empty stack, and returning True while openers are still left on it. Full walkthrough: §07

P09 · Queue with deque

Signal: "process in arrival order", "first in first out", "work through a backlog"

In DE · A retry backlog, a work list that grows as it is processed, the frontier of a BFS.

Cost · O(1) per enqueue and dequeue · O(n) memory

from collections import deque

def process_in_order(events, handle):
    q = deque(events)
    while q:
        e = q.popleft()              # O(1); list.pop(0) would be O(n)
        for follow_up in handle(e):  # handling may create more work
            q.append(follow_up)

Trap: list.pop(0) is O(n), so a loop of it is a silent O(n²). Use collections.deque and popleft(). Full walkthrough: §07

P10 · Linked list: reverse

Signal: "reverse this chain", "walk to the Nth node", "remove this node given a reference to it"

In DE · Rarely built at work, but it is the mental model under queues, LRU caches and the call stack. Doubly linked gives O(1) removal of a node you already hold.

Cost · O(n) time · O(1) memory

class Node:
    def __init__(self, val, nxt=None):
        self.val, self.next = val, nxt

def reverse(head):
    prev = None
    while head:
        nxt = head.next         # 1. save the rest BEFORE cutting it
        head.next = prev        # 2. flip the arrow
        prev, head = head, nxt  # 3. step forward
    return prev                 # the old tail is the new head

Trap: Save head.next before you overwrite it, or you lose the rest of the chain. There is no random access: reaching node k costs k steps. Full walkthrough: §04

P11 · Recursion

Signal: "nested JSON", "break it into a smaller version of itself", "each child is the same shape as the parent"

In DE · Flatten a nested API payload into flat columns before loading it to a table.

Cost · O(size of the document) time · O(depth) call stack

def flatten(obj, prefix=""):
    out = {}
    for k, v in obj.items():
        key = f"{prefix}.{k}" if prefix else k
        if isinstance(v, dict):
            out.update(flatten(v, key))  # recursive case: a smaller document
        else:
            out[key] = v                 # base case: a leaf value
    return out

Trap: Write the base case first. Python stops at about 1000 frames, so very deep data needs an explicit stack, which is the same code as a DFS. Full walkthrough: §08

P12 · Tree traversal: pre, in, post

Signal: "walk the hierarchy", "org chart or category tree", "roll totals up from the children"

In DE · Pre-order visits a parent before its children (copy, serialise). In-order on a search tree gives sorted output. Post-order handles children first (delete, roll up sizes).

Cost · O(n) time · O(height) stack

class T:
    def __init__(self, val, left=None, right=None):
        self.val, self.left, self.right = val, left, right

def walk(n, order="pre"):
    if n is None:
        return
    if order == "pre":  yield n.val  # parent first
    yield from walk(n.left, order)
    if order == "in":   yield n.val  # parent between the children
    yield from walk(n.right, order)
    if order == "post": yield n.val  # parent last

Trap: A degenerate tree has height n, so recursion can hit the limit. Building a list by concatenating sub-lists is quietly worse than yielding. Full walkthrough: §09

P13 · BFS / DFS on a graph

Signal: "what breaks if this table is late", "everything downstream of", "fewest steps", "is X reachable from Y"

In DE · Impact analysis over a lineage graph: every table that eventually reads from a source.

Cost · O(V + E) time · O(V) memory

from collections import deque

def downstream(graph, start):  # graph: {table: [tables that read it]}
    seen, q = {start}, deque([start])
    while q:
        node = q.popleft()
        for nxt in graph.get(node, []):
            if nxt not in seen:
                seen.add(nxt)  # mark on enqueue
                q.append(nxt)
    return seen - {start}

Trap: seen must be a set, and mark a node seen when you enqueue it, not when you pop it, or it gets queued many times. Swap popleft() for pop() to get DFS. BFS gives the fewest hops when edges are unweighted. Full walkthrough: §09

P14 · 1-D dynamic programming

Signal: "how many ways to", "fewest or most such that", a brute-force recursion that keeps recomputing the same sub-answers

In DE · Staircase and coin change are the two the screens ask. The DP-shaped work in a real pipeline (running totals, sessions, gaps and islands) is window functions in SQL.

Cost · O(n) or O(amount × coins) time · O(1) to O(n) memory

def climb(n):                  # ways to climb n stairs, 1 or 2 at a time
    a, b = 1, 1
    for _ in range(n - 1):
        a, b = b, a + b        # keep only the last two cells
    return b

def coin_change(coins, amount):
    INF = float("inf")
    dp = [0] + [INF] * amount  # dp[x] = fewest coins that make x
    for x in range(1, amount + 1):
        for c in coins:
            if c <= x and dp[x - c] + 1 < dp[x]:
                dp[x] = dp[x - c] + 1
    return dp[amount] if dp[amount] != INF else -1

Trap: Only read cells that are already finished. Greedy is not always optimal for coin change, which is exactly why the table exists. Full walkthrough: §10

03.Tier 2 patterns

Four patterns. Worth it once tier 1 is automatic.

P15 · Heap: top-K and k-way merge

Signal: "top 10 by", "the worst N", "largest K of a stream", "merge these sorted files"

In DE · Top 10 users by spend without sorting all of them. Merge many sorted part-files into one sorted stream.

Cost · O(n log K) time · O(K) memory

import heapq

def top_k(stream, k):
    h = []              # min-heap of the k best seen so far
    for x in stream:
        if len(h) < k:
            heapq.heappush(h, x)
        elif x > h[0]:  # beats the weakest of the current best
            heapq.heapreplace(h, x)
    return sorted(h, reverse=True)

# k-way merge of sorted inputs, lazy: heapq.merge(*sorted_iterables)

Trap: The K largest need a MIN-heap, so the weakest of the current best is always at h[0]. A heap is not sorted, only its root is meaningful. For a one-off in memory, heapq.nlargest(k, xs, key=f) is enough. Full walkthrough: §11

P16 · Sliding window

Signal: "longest run where", "rolling N-day total", "max sum of k consecutive", "in any window of"

In DE · Rolling metrics over an ordered stream, and the longest stretch of events that satisfies a rule.

Cost · O(n) time · O(1) memory, and a fixed window does O(1) work per step whatever k is

def max_sum_window(a, k):       # fixed size k
    s = best = sum(a[:k])
    for i in range(k, len(a)):
        s += a[i] - a[i - k]    # add the newcomer, drop the leaver
        best = max(best, s)
    return best

def longest_unique(items):      # variable size: grow right, shrink left
    last, left, best = {}, 0, 0
    for right, x in enumerate(items):
        if x in last and last[x] >= left:
            left = last[x] + 1  # jump past the earlier copy
        last[x] = right
        best = max(best, right - left + 1)
    return best

Trap: A variable window only works when the condition is monotone: growing it can only break the rule, shrinking it can only repair it. For a fixed window, add the newcomer and drop the leaver, never re-sum. Full walkthrough: §12

P17 · Prefix sums

Signal: "sum between any two points", "range query", "running total", "how many subarrays sum to k"

In DE · Answer many range-sum questions over a fixed column after a single pass. Pair with a dict to count subarrays with a target sum.

Cost · O(n) build · O(1) per query · O(n) memory

from itertools import accumulate

def build(a):
    return [0, *accumulate(a)]     # P[i] = sum of a[:i]

def range_sum(P, lo, hi):          # sum of a[lo..hi], inclusive
    return P[hi + 1] - P[lo]

def count_subarrays(a, k):         # prefix sum + hashmap
    seen, run, n = {0: 1}, 0, 0
    for x in a:
        run += x
        n += seen.get(run - k, 0)  # an earlier prefix that leaves exactly k
        seen[run] = seen.get(run, 0) + 1
    return n

Trap: The range is P[hi + 1] - P[lo]: the off-by-one is the whole question. It assumes the data does not change, since an update means a rebuild. Full walkthrough: §12

P18 · Topological sort (Kahn)

Signal: "what order should these run in", "dependencies", "is there a circular dependency"

In DE · Literally what Airflow, dbt and any orchestrator do to your DAG before running it.

Cost · O(V + E) time · O(V) memory

from collections import defaultdict, deque

def topo_order(edges):             # edges: [(upstream, downstream)]
    out, indeg, nodes = defaultdict(list), defaultdict(int), set()
    for u, v in edges:
        out[u].append(v)
        indeg[v] += 1
        nodes |= {u, v}
    # start from every node that has nothing upstream
    q = deque(sorted(n for n in nodes if indeg[n] == 0))
    order = []
    while q:
        n = q.popleft()
        order.append(n)
        for m in out[n]:
            indeg[m] -= 1
            if indeg[m] == 0:      # its last dependency finished
                q.append(m)
    if len(order) < len(nodes):
        raise ValueError("cycle")  # some nodes never became ready
    return order

Trap: If fewer nodes come out than went in, there is a cycle. Ties are unordered, so any valid order is a correct answer. Full walkthrough: §13

06.Say it out loud, and what to skip

Four sentences to have ready, and the topics that are not worth your hours

Four sentences to have ready

On cost: "That is O(n) time and O(distinct keys) memory: one pass over the file, constant work per row."

On joins: "The small side fits in memory, so a hash join: build from the small side, probe once. If both sides are already sorted on the key, a sort-merge join uses no extra memory."

On latest per key: "One pass keeping the newest row per key. I would confirm the tie-break for equal timestamps."

On dependencies: "That is a topological sort. If fewer nodes come out than went in, there is a cycle."

Skip unless a role asks for it

Grid, tree and bitmask DP · max flow and min cut · Bellman-Ford and minimum spanning trees · segment trees, Fenwick trees and tries · contest maths tricks · writing a hash table or heap from scratch. Union-find is the one exception if you work on entity resolution. The full reasoning is in §14 of the guide, and the honest ordering of prep hours is in §15: hard SQL, data modelling and system design come first.
