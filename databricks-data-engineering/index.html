01. The Data Engineering Lifecycle & the Six Undercurrents

Every "design a data platform" question is easier when you have a spine to hang the answer on. The most useful one comes from Fundamentals of Data Engineering (Joe Reis and Matt Housley): a lifecycle of stages that data moves through, and six undercurrents that cut across every stage. Walk the stages to make sure the data flows; sweep the undercurrents to make sure it is safe, governed, reliable and maintainable. Interviewers reward candidates who do both, because most weak answers only cover the flow.

How to Use the Framework in a System-Design Answer

  1. Clarify requirements first (consumers, freshness, volume, retention, compliance). Every later choice is justified against them.
  2. Walk the stages left to right with a concrete component per stage, saying why (for example "bronze via Auto Loader because the source drops files; silver via a declarative pipeline with expectations").
  3. Sweep the six undercurrents as a closing checklist: how it is secured, governed, monitored and deployed, how it is orchestrated, how the code is tested and versioned, and how the architecture can change later.
  4. Name trade-offs and failure modes. "What if the source sends duplicates, or the job fails at 3am, or the schema changes?" is the follow-up you pre-empt.
Interview angle "Design a data platform for X." Open with the lifecycle as your outline, and finish by explicitly touching all six undercurrents. Candidates who only describe the pipeline (generation to serving) sound like implementers; candidates who add security, data management, DataOps, architecture trade-offs, orchestration and engineering practice sound like owners.

02. Platform Overview & Architecture

Before any pipeline code, an interviewer wants to hear that you understand what Databricks is made of: who owns which layer, where your data physically lives, and where your code physically runs. Most "system design on Databricks" answers are really answers to those three questions.

What "Unified Data Analytics Platform" Actually Means

Databricks' own one-line definition is a unified, open analytics platform for building, deploying, sharing and maintaining enterprise-grade data, analytics and AI solutions at scale. Two words carry the weight: unified means one copy of the data and one governance model (Unity Catalog, §05) shared by every role; open means the data sits in open formats (Delta/Parquet, Iceberg-compatible) in your own cloud storage, not in a proprietary store.

Data engineers

Build batch and streaming pipelines: ingestion, transformation, the bronze/silver/gold layers, orchestration. This guide's main audience.

Data scientists / ML engineers

Develop, deploy and monitor models and AI agents on the data engineers' governed tables (MLflow, Model Serving, Vector Search).

Analysts and business users

Query with SQL warehouses, build AI/BI dashboards, ask questions in natural language through Genie, all against the same governed data.

Account, Workspace and Metastore

Everything starts at the account: one per organization, managed in the account console. Under it live workspaces and Unity Catalog metastores, and the account is where identity and money are managed.

LevelWhat it isManaged here
AccountThe organization-wide container. One console covers every region and workspace.Identity (users, groups, service principals), creating/deleting workspaces, metastores, usage and billing, account-level policies and settings.
WorkspaceThe collaboration environment: the web UI where people write code, run compute, build jobs and dashboards. Many workspaces per account, many per region.Notebooks, repos, jobs, clusters/warehouses, workspace-level permissions and settings, personal access tokens.

The practical consequence: because identity and the metastore live at the account level, three workspaces (dev, staging, prod) in one region can share one metastore and one set of groups, while environment isolation is done with separate catalogs (restaurant_dev, restaurant_prod) bound to specific workspaces. A user with the account admin role sees the "Manage account" entry in the workspace menu.

Control Plane vs. Compute Plane

  • Control plane - the web app you log into, the storage of your notebooks/queries/job definitions, the cluster manager that asks the cloud for VMs, and the Unity Catalog service. Fully managed by Databricks.
  • Classic compute plane - all-purpose clusters, job clusters and classic SQL warehouses run as VMs in your cloud account, so the data is processed inside your network boundary. You pay the cloud provider for the VMs and Databricks for DBUs (two bills).
  • Serverless compute plane - Databricks runs the compute in its account. You configure nothing and pay a single all-in DBU price, but you have less visibility into and control over the infrastructure. Network access to your storage is secured with a Network Connectivity Configuration (NCC) and private endpoints (see §03).
  • Serverless workspace - a workspace type (introduced late 2025) that is serverless only: no classic clusters, and it can use Databricks-provided default storage, so you can start without setting up any cloud resources.

Free Edition: What You Can and Cannot Practice

Databricks Free Edition (sign up at the Databricks login page with Google/Microsoft/email) is a genuine, no-cost workspace and is enough to practice almost everything in this guide. Know its shape so you are not surprised:

The classic interview follow-up is "the same code on an all-purpose and a job cluster uses the same number of DBUs, so why is the job cluster cheaper?" Answer: two reasons. The per-DBU rate for jobs compute is lower than for all-purpose, and a job cluster has no idle time because it dies with the run. Illustrative math (rates vary by cloud, tier and region, so always read them from system.billing.list_prices):

Job uses 100 DBU
  on all-purpose compute @ ~$0.50 per DBU  ->  ~$50   (plus idle minutes)
  on jobs compute        @ ~$0.33 per DBU  ->  ~$33   (no idle time)

SQL Warehouses

A SQL warehouse is compute purpose-built for SQL and BI. You pick a type (Serverless, Pro or Classic), a t-shirt size (2X-Small up to 4X-Large, each step roughly doubling the compute and the DBU per hour), min/max clusters for concurrency scaling, and an auto-stop timeout. Size drives the speed of one query; cluster count drives how many queries run at once. Serverless warehouses start in seconds, which is why they are the default recommendation for dashboards and Genie. The warehouse used for a dashboard refresh or a Genie space is a real cost lever: under-sizing makes dashboards slow, over-sizing burns DBUs.

Serverless Compute

Serverless removes cluster management entirely: there is nothing to create, you just pick "Serverless" on a notebook, job task, pipeline or warehouse. Databricks provisions and scales instantly, upgrades the runtime for you, and bills a single usage price. Two flavors of jobs matter: performance-optimized (fast start, higher price) and standard (cheaper, tolerates a longer start), a genuine cost knob for non-urgent batch.

04. Notebooks, DBUtils & Development Workflow

The notebook is where a data engineer spends most of the day, so interviewers probe it for fluency: magic commands, parameterization, calling one notebook from another, handling files and secrets, and debugging. None of it is hard, but it is all "have you actually done this" material, so each topic below comes with the runnable snippet.

Notebook Basics Worth Knowing Cold

  • Default language and per-cell override. A notebook has a default language (Python, SQL, Scala or R); any cell can override it with a magic command on its first line.
  • Running cells. Run cell, run all, run all above / below, and run only the selected text. Shift+Enter runs and advances, Ctrl/Cmd+Enter runs in place.
  • Autosave and version history. Every edit is saved as you type. The revision history lists changes with a diff and a Restore this version button, which is how you recover an accidentally deleted cell. For real version control use Git folders (below).
  • Markdown headings build a table of contents. A %md cell starting with # or ## becomes a clickable outline in the left panel. A long notebook without headings is unnavigable.
  • Comments and sharing. Comment on a cell for review; share with per-user permissions (Can View, Can Run, Can Edit, Can Manage). Sharing a notebook does not grant access to the tables it reads: that is Unity Catalog's job.
  • Results. display(df) renders an interactive table with a + tab for visualizations and data profiling, and a download button (CSV/Excel). The result of a %sql cell is also available in Python as the DataFrame _sqldf.
  • Variable explorer. The right panel lists every variable and its current value, useful for debugging and for seeing DataFrame schemas without printSchema().
  • Import / export. DBC archive (Databricks' native format), source .py, HTML (viewable anywhere with outputs) and .ipynb (Jupyter).

Widgets: Parameterizing a Notebook

Widgets are the notebook's input parameters and the bridge between a Job and a notebook: a job passes a parameter, the widget with the same name receives it. Four types exist: text, dropdown, combobox (dropdown that also accepts free text) and multiselect.

dbutils.widgets.removeAll()                                   # clean slate while developing
dbutils.widgets.text("table_name", "sales_customers", "Table name")
dbutils.widgets.dropdown("env", "dev", ["dev", "staging", "prod"], "Environment")
dbutils.widgets.multiselect("regions", "EU", ["EU", "US", "APAC"], "Regions")

table_name = dbutils.widgets.get("table_name")                # always returns a string
env        = dbutils.widgets.get("env")
regions    = dbutils.widgets.get("regions").split(",")        # multiselect comes back comma-separated

# In SQL cells the same widget is read with the parameter marker syntax:
#   SELECT * FROM IDENTIFIER(:env || '_catalog.sales.orders') LIMIT 10

Best practice: define all widgets in the first cell, give every one a sensible default so the notebook runs interactively, and remember values are always strings, so cast numbers and dates explicitly.

Managing Files and Folders with dbutils.fs

Files live in Unity Catalog volumes (§05): a volume is a governed folder inside catalog.schema, addressed as /Volumes/<catalog>/<schema>/<volume>/<path>. A volume can be managed, or external and mapped onto an S3/ADLS/GCS path, which is why the same commands copy data between storage accounts with no cloud SDK. The legacy DBFS root and mounts are deprecated for new work; use volumes.

base = "/Volumes/main/landing/raw/input"

display(spark.createDataFrame(files))

dbutils.fs.mkdirs(f"{base}/../archive/2026/09")            # creates the full path, parents included
dbutils.fs.cp(f"{base}/sales_1.csv", f"{base}/../archive/sales_1.csv")     # copy one file (overwrites the target)
dbutils.fs.cp(base, f"{base}/../backup", recurse=True)     # copy a whole directory tree
dbutils.fs.mv(f"{base}/sales_2.csv", f"{base}/../archive/sales_2.csv")     # move = copy + delete source

And never use it to "clean" a Delta table's folder: delete Delta data with DELETE and VACUUM so the transaction log stays consistent.

Secrets and Secret Scopes

Never hardcode a password or token in a notebook, in a job definition or in Git. A secret scope is a named, access-controlled vault; inside it, secrets are key/value pairs. Two backends: Databricks-backed (stored in Databricks) and, on Azure, Azure Key Vault-backed (the scope is a live view of a Key Vault).

  • For cloud storage access, prefer Unity Catalog storage credentials and external locations over embedding keys, and use service principals with OAuth for automation (§08).

05. Unity Catalog for Data Engineers

Unity Catalog (UC) is the governance layer every table, volume, and function on Databricks lives under. As a data engineer you touch it constantly: every table you create is governed by it, every grant you write goes through it, and most access-denied bugs in an interview scenario trace back to a missing grant somewhere in this hierarchy.

The Securable Object Hierarchy

Everything in UC nests inside a single account-level metastore (one per region, attached to a workspace). Below that, four levels matter day to day:

Managed vs. External Tables and Volumes

A managed table stores its data files in storage that UC owns and controls (under the catalog's or schema's managed storage location) - you never specify a path, and DROP TABLE deletes the underlying data. An external table points at a path you specify, backed by an external location that UC has been granted access to; DROP TABLE only drops the metadata, the files stay put. The same distinction exists for volumes, which govern access to non-tabular files (images, PDFs, arbitrary CSVs an ingestion job lands before it's a table, model checkpoints) the same way tables govern access to structured data.

-- Managed: Databricks owns the storage path
CREATE CATALOG IF NOT EXISTS restaurant_prod;
CREATE SCHEMA IF NOT EXISTS restaurant_prod.silver;
CREATE TABLE restaurant_prod.silver.orders_clean (
  order_id STRING, restaurant_id STRING, order_amount DECIMAL(10,2), order_ts TIMESTAMP
);

-- External: you own the storage path, UC just governs access to it
CREATE STORAGE CREDENTIAL restaurant_s3_cred
  WITH (AWS_IAM_ROLE = 'arn:aws:iam::123456789012:role/uc-access-role');

CREATE EXTERNAL LOCATION restaurant_landing
  URL 's3://restaurant-landing-zone/raw/'
  WITH (STORAGE CREDENTIAL restaurant_s3_cred);

CREATE TABLE restaurant_prod.bronze.orders_raw
  LOCATION 's3://restaurant-landing-zone/raw/orders/'
  AS SELECT * FROM json.`s3://restaurant-landing-zone/raw/orders/`;

-- A volume for arbitrary files an Auto Loader job will pick up
CREATE VOLUME restaurant_prod.bronze.incoming_files;
-- Path form: /Volumes/restaurant_prod/bronze/incoming_files/orders/2026-09-17.json
Interview angle "When would you use an external table over a managed one?" - when data must live in a specific bucket for cost/compliance reasons, when another system also writes to the same path, when migrating an existing lake into UC without moving petabytes of files, or when you need the data to survive a DROP TABLE by design. Default to managed tables otherwise: they get automatic file layout optimization and you never have to think about storage paths.

Grants & Privilege Model

UC uses standard SQL GRANT/REVOKE syntax. Privileges are additive and inherit downward: a USE CATALOG + USE SCHEMA + SELECT grant chain is the minimum to read a table you don't own.

GRANT USE CATALOG ON CATALOG restaurant_prod TO `analysts`;
GRANT USE SCHEMA ON SCHEMA restaurant_prod.gold TO `analysts`;
GRANT SELECT ON SCHEMA restaurant_prod.gold TO `analysts`;

GRANT CREATE TABLE, MODIFY ON SCHEMA restaurant_prod.silver TO `data-engineers`;
GRANT ALL PRIVILEGES ON CATALOG restaurant_prod TO `platform-admins`;

REVOKE SELECT ON TABLE restaurant_prod.gold.customer_pii FROM `analysts`;

Common privileges: USE CATALOG/USE SCHEMA (a "can see inside" gate with no data access on its own), SELECT, MODIFY (insert/update/delete/merge), CREATE TABLE/CREATE SCHEMA, EXECUTE (for functions/models), and ALL PRIVILEGES. Ownership (ALTER ... OWNER TO) is separate from grants - the owner can always grant/revoke on the object regardless of their own explicit privileges.

Row Filters & Column Masks

Rather than maintaining separate "safe" views by hand, UC lets you attach a filter/mask function directly to a table so every query - SQL, PySpark, BI tool - is filtered the same way with no way to bypass it.

-- Column mask: analysts see a redacted email, engineers on the "pii-access" group see it raw
CREATE FUNCTION restaurant_prod.silver.mask_email(email STRING)
RETURNS STRING
RETURN CASE WHEN is_account_group_member('pii-access') THEN email ELSE '***redacted***' END;

ALTER TABLE restaurant_prod.silver.customers
  ALTER COLUMN email SET MASK restaurant_prod.silver.mask_email;

-- Row filter: each restaurant chain only sees its own rows
CREATE FUNCTION restaurant_prod.silver.filter_by_chain(chain_id STRING)
RETURNS BOOLEAN
RETURN chain_id = current_user_chain() OR is_account_group_member('platform-admins');

ALTER TABLE restaurant_prod.silver.orders_clean
  SET ROW FILTER restaurant_prod.silver.filter_by_chain ON (chain_id);

Before this native feature, the standard pattern was a dynamic view wrapping the base table with CASE WHEN is_member(...) logic and granting access to the view instead of the table - still valid, still common in older codebases and worth recognizing, but row filters/column masks are the current best practice since they attach to the table itself rather than requiring everyone to remember to query the view.

Lineage & System Tables

UC automatically captures table- and column-level lineage for anything that reads and writes through Spark or Databricks SQL - no extra instrumentation needed. It's visible in Catalog Explorer's lineage graph, and queryable directly:

-- Which tables feed restaurant_prod.gold.daily_sales?
SELECT source_table_full_name, target_table_full_name
FROM system.access.table_lineage
WHERE target_table_full_name = 'restaurant_prod.gold.daily_sales';

-- Who queried a sensitive table in the last 7 days?
SELECT user_identity.email, request_params.full_name_arg, event_time
FROM system.access.audit
WHERE action_name = 'getTable' AND event_time > current_timestamp() - INTERVAL 7 DAYS;

The system catalog is UC's built-in operational data warehouse: system.access.audit (every action, by whom), system.access.table_lineage/column_lineage, system.billing.usage (DBU consumption by workspace/SKU/job), system.compute.clusters, and system.lakeflow.job_run_timeline. These are covered in more depth in §23, but knowing they exist - and that they're just Delta tables you can query with SQL - is a strong interview signal.

Environment Strategy: Catalogs, Not Just Workspaces

Because a metastore spans workspaces, the clean way to separate environments is by catalog: restaurant_dev, restaurant_staging, restaurant_prod, each bound to the workspaces allowed to use it (a dev workspace cannot even see the prod catalog). Inside each catalog, schemas by layer (bronze, silver, gold) or domain. Give production catalogs to service principals for writes and to groups for reads; developers get write access only in dev. The environment name then becomes a bundle variable (§20), so the same code runs everywhere against a different catalog.

06. PII & Sensitive Data Protection

Any customer-facing platform holds personal data, so "how do you handle PII?" is a standard system-design question. A weak answer names one technique ("we mask it"). A strong answer walks a lifecycle, picks a technique per column from the actual requirement, and explains erasure. This section gives you that framework and the Databricks code for every step.

What Counts as PII

PII is any data that can identify a specific individual. Direct PII identifies a person on its own: full name, email, phone number, SSN or national ID, passport number, exact address. Indirect PII identifies a person only in combination: date of birth, IP address, device ID, ZIP code, job title. Combining just date of birth, ZIP code and gender is enough to uniquely identify a large share of people, which is why indirect PII is still sensitive. PHI (protected health information) is health data tied to an individual; the same techniques apply, only the regulation (HIPAA) differs.

Why it matters: breaches are expensive, regulation is mandatory (GDPR in the EU, CCPA/CPRA in California, HIPAA for US health data, PCI DSS for card data, DPDPA in India, and others), and a leak destroys trust.

The PII Lifecycle

Stage 1 and 2: Minimize and Classify

Minimize. If the analytics question is "customers per country," you need customer_id, city, country, not name, email and phone. Select only the non-PII columns during ingestion and the whole problem disappears for that dataset.

slim = spark.table("pii_demo.source.customers").select("customer_id", "city", "country")
slim.write.mode("overwrite").saveAsTable("pii_demo.target.customers_minimized")

Classify. When you must keep PII, label every column so tools and policies can find it. Tags are key/value metadata on tables and columns, searchable through information_schema:

ALTER TABLE pii_demo.target.customers ALTER COLUMN email
  SET TAGS ('pii' = 'true', 'pii_type' = 'direct', 'classification' = 'email');
ALTER TABLE pii_demo.target.customers ALTER COLUMN date_of_birth
  SET TAGS ('pii' = 'true', 'pii_type' = 'indirect', 'classification' = 'dob');
ALTER TABLE pii_demo.target.customers ALTER COLUMN country SET TAGS ('pii' = 'false');

-- Discovery: every PII column in the catalog
SELECT table_schema, table_name, column_name, tag_value AS classification
FROM pii_demo.information_schema.column_tags
WHERE tag_name = 'classification';

Automatic classification. Data Classification is an agentic scanner you enable per catalog (catalog Details tab, needs MANAGE on the catalog). It runs incrementally in the background, tags detected columns with system governed tags such as class.email_address and class.name, and records findings, with sample values, in system.data_classification.results (account-admin access by default). Because the tags are standard across organizations, policies you write against them are portable. It recognizes categories mapped to GDPR, HIPAA, PCI DSS and others.

Stage 3: Protect - Choosing the Technique

Hashing, done safely

from pyspark.sql import functions as F
salt = dbutils.secrets.get("pii", "hash-salt")        # a secret, never in code or in the table

hashed = spark.table("pii_demo.source.customers").select(
    "customer_id",
    F.sha2(F.concat_ws("|", F.lit(salt), F.col("email")), 256).alias("email_hash"),
    F.sha2(F.concat_ws("|", F.lit(salt), F.col("ssn")), 512).alias("ssn_hash"),
    "country",
)

SHA2 takes the bit length (224/256/384/512); md5 and sha1 are shorter and weaker. The classic pitfall: an unsalted hash of a phone number or SSN can be reversed by hashing every possible value (a rainbow table), because the input space is tiny. Add a secret salt (a "pepper" kept in a secret scope) so an attacker who steals the table cannot precompute. Rotate deliberately: changing the salt changes every hash and breaks joins against old data.

Tokenization with a vault table

vault_tbl = "pii_vault.tokens.email_tokens"          # restricted schema: only privileged groups
src = spark.table("pii_demo.source.customers")

# 1) mint tokens ONLY for values not seen before (idempotent: reruns do not re-key existing emails)
existing = spark.table(vault_tbl) if spark.catalog.tableExists(vault_tbl) else None
new_vals = src.select("email").where("email IS NOT NULL").distinct()
if existing is not None:
    new_vals = new_vals.join(existing.select("email"), "email", "left_anti")
new_vals.withColumn("token", F.expr("uuid()")).write.mode("append").saveAsTable(vault_tbl)

# 2) analytics table carries only the token
tokenized = (src.join(spark.table(vault_tbl), "email", "left")
                .withColumnRenamed("token", "email_token").drop("email"))
tokenized.write.mode("overwrite").saveAsTable("pii_demo.target.customers_tokenized")

Analysts get the tokenized table and can still join or count distinct emails via the token. Admins with grants on the vault schema can join back to recover the email. Minting tokens only for unseen values matters: a naive uuid() over the full table would re-key everything each run. A vault is one lookup table, so the security of tokenization is the security of that table's grants.

Generalization patterns

-- categorical generalization: exact job title -> broad family
CASE WHEN job_title IN ('Software Engineer','Data Engineer') THEN 'Engineering'
     WHEN job_title IN ('Product Manager','HR Manager')      THEN 'Management'
     ELSE 'Other' END AS job_family

-- binning: date of birth -> age band
CASE WHEN age < 18 THEN 'under 18' WHEN age <= 25 THEN '18-25' WHEN age <= 40 THEN '26-40' ELSE '41+' END AS age_band
  -- where age = floor(months_between(current_date(), date_of_birth) / 12)

-- IP truncation: zero the last octet so it no longer pinpoints a device
regexp_replace(ip_address, '\\.\\d+$', '.0') AS ip_truncated

-- rounding: keep the magnitude, lose the exact figure
round(salary, -4) AS salary_rounded          -- 87,342 -> 90,000

Generalization has a formal cousin, k-anonymity: every combination of quasi-identifiers (age band, ZIP, gender) must appear at least k times so no one is unique. Worth naming in an interview when asked how you would share a dataset externally.

Column encryption

-- key comes from a secret scope; must be exactly 16, 24 or 32 bytes for AES-128/192/256
SELECT customer_id,
       base64(aes_encrypt(email, secret('pii', 'aes-key'))) AS email_enc,     -- default mode GCM, random IV
       country
FROM pii_demo.source.customers;

-- decrypt (fails or returns NULL with a wrong key; try_aes_decrypt returns NULL instead of erroring)
SELECT cast(try_aes_decrypt(unbase64(email_enc), secret('pii', 'aes-key')) AS STRING) AS email
FROM pii_demo.target.customers_encrypted;

-- make decryption a governed object instead of copying the call everywhere
CREATE FUNCTION pii_demo.security.decrypt_pii(v STRING) RETURNS STRING
RETURN cast(aes_decrypt(unbase64(v), secret('pii', 'aes-key')) AS STRING);
GRANT EXECUTE ON FUNCTION pii_demo.security.decrypt_pii TO `pii-admins`;
  • Encryption at rest is provided by the cloud storage layer by default with provider-managed keys; for stricter control use customer-managed keys (a key in AWS KMS / Azure Key Vault / Google KMS that you can rotate or revoke). This protects the disks, not a user with SELECT.
  • Encryption in transit is TLS everywhere by default; nothing to configure.
  • Column encryption protects against anyone who can read the table but should not read that column. Lose the key and the data is gone, so key management (a secret scope or KMS, rotation, backup) is the real work.

Stage 4: Control Access

Four tools, usually combined:

  • RBAC. GRANT SELECT to groups at catalog, schema or table level (§05).
  • Column masks. A function attached to a column; the result depends on who is asking. Use is_account_group_member() (account-level groups) rather than the workspace-scoped is_member() in Unity Catalog functions.
  • Row filters. A boolean function attached to a table; rows for which it returns false are invisible.
  • ABAC. Attribute-based policies that apply masks and filters to every column or table carrying a governed tag, so one policy protects hundreds of tables and new tagged columns are protected automatically.
-- Different masks for different data shapes (each returns the real value only to the privileged group)
CREATE FUNCTION pii_demo.security.mask_email(v STRING) RETURNS STRING
RETURN CASE WHEN is_account_group_member('pii-admins') THEN v
            ELSE concat(left(v, 1), '***', substring(v, instr(v, '@'))) END;   -- a***@example.com

CREATE FUNCTION pii_demo.security.mask_phone(v STRING) RETURNS STRING
RETURN CASE WHEN is_account_group_member('pii-admins') THEN v
            ELSE concat('******', right(v, 4)) END;                            -- last four digits only

CREATE FUNCTION pii_demo.security.mask_dob(v DATE) RETURNS DATE
RETURN CASE WHEN is_account_group_member('pii-admins') THEN v
            ELSE make_date(year(v), 1, 1) END;                                 -- keep the year

ALTER TABLE pii_demo.target.customers ALTER COLUMN email SET MASK pii_demo.security.mask_email;
ALTER TABLE pii_demo.target.customers ALTER COLUMN phone SET MASK pii_demo.security.mask_phone;

-- Row filter: managers see everything, everyone else only India
CREATE FUNCTION pii_demo.security.filter_country(country STRING) RETURNS BOOLEAN
RETURN is_account_group_member('managers') OR country = 'India';
ALTER TABLE pii_demo.target.customers SET ROW FILTER pii_demo.security.filter_country ON (country);

-- ABAC: one policy masks every column tagged pii=ssn (a governed tag), across the whole schema, for one group.
-- pii_demo.security.mask_ssn is a mask UDF written like mask_phone above.
CREATE POLICY mask_ssn
  ON SCHEMA pii_demo.target
  COLUMN MASK pii_demo.security.mask_ssn
  TO `us_analysts` EXCEPT `pii-admins`
  FOR TABLES
  MATCH COLUMNS has_tag_value('pii', 'ssn') AS ssn
  ON COLUMN ssn;

Two cautions. A mask or filter that calls a function per row adds cost, so keep the functions simple. And these policies protect data in queries; they do nothing for someone with direct read access to the underlying storage files, which is why managed tables and external-location grants matter.

Stage 5: Monitor

Stage 6: Delete (Right to Erasure)

Some regulations require deleting a person's data within a deadline (for example 30 days). In Delta this is more subtle than DELETE because old files stay readable through time travel and, with deletion vectors, even the "deleted" row can still sit in the original file.

-- 1) retention must fit inside the compliance window
ALTER TABLE silver.customers SET TBLPROPERTIES (
  'delta.deletedFileRetentionDuration' = 'interval 30 days',   -- default 7 days
  'delta.logRetentionDuration'         = 'interval 30 days');  -- default 30 days (time-travel history)

-- 2) logically delete the subject everywhere they exist
DELETE FROM silver.customers  WHERE customer_id = 'C-10293';
DELETE FROM silver.orders     WHERE customer_id = 'C-10293';

-- 3) with deletion vectors ON, the row is only masked in its file. Rewrite so it is physically gone
REORG TABLE silver.customers APPLY (PURGE);

-- 4) after the retention window passes, remove old file versions for good
VACUUM silver.customers;
  • Every copy counts: bronze raw files (Auto Loader landing volume), silver and gold tables, aggregates derived from the person, Change Data Feed history (it keeps pre-images), ML feature tables, vector indexes, streaming checkpoints, clones and backups, exported files, logs.
  • Build a deletion pipeline, not a one-off script: a governed request table of subject IDs, a job that fans out over every table holding the key, a scheduled VACUUM, and an audit row proving completion.
  • Crypto-shredding is the elegant alternative for hard cases: encrypt each subject's PII with a per-subject key, and "delete" the person by destroying the key. Every copy, including backups, becomes unreadable at once.

Picking the Technique: A Decision Table

Ask these questions in order, per column. Stop at the first "yes."

#QuestionIf yes
1Does the platform need this column at all?No: minimize (drop it at ingestion). Done.
2Are summaries or aggregates enough for the use case?Generalize (bin, category, round, truncate).
3Is an irreversible fingerprint enough (joins, distinct counts)?Salted hash.
4Must authorized people recover the value, and do you want PII in a separate, tightly-governed table?Tokenize with a vault.
5Must the exact value be stored, but unreadable without a key?Column-encrypt, govern the key and the decrypt function.
6Must the exact value be stored in the clear for some users but hidden from others?RBAC + column mask + row filter (or ABAC at scale).

The techniques stack: an encrypted column can also carry a mask; a tokenized table still needs RBAC. In practice each column gets its own row in a "PII handling register" (column, classification, technique, who may see it, retention), and that register is the artifact a design review should ask for.

Interview angle "Design PII handling for a customer 360 platform." Walk the lifecycle: minimize what you ingest; tag and auto-classify so nothing is missed; per column choose salted hash / token / generalization / encryption from the actual requirement; enforce with UC grants, ABAC masks on tags and row filters for regional access; audit through system.access with alerts; an erasure pipeline that handles DELETE, PURGE, VACUUM, downstream copies and CDF. Then name the trade-offs (mask cost, key management, hash-salt rotation) and you have answered the whole question.

Data Contracts

A data contract is an explicit, versioned agreement between a producer and its consumers about a dataset: schema, meaning, quality expectations, freshness, ownership and how changes are announced. It converts "the upstream team changed a column and broke us" from a surprise into a process. Keep the contract in Git next to the pipeline and check it in CI:

# contracts/orders.v2.yaml
dataset: prod.silver.orders
version: 2.1.0
owner: orders-team@company.com
freshness: {max_lag_hours: 2}
schema:
  - {name: order_id,     type: string,        required: true,  unique: true}
  - {name: order_amount, type: "decimal(12,2)", required: true, min: 0}
  - {name: status,       type: string,        allowed: [OPEN, SHIPPED, CANCELLED]}
change_policy: "additive changes minor; removals and type changes major with 30 days notice"
def check_contract(contract: dict, df):
    problems = []
    cols = {f.name: f.dataType.simpleString() for f in df.schema.fields}
    for c in contract["schema"]:
        if c["name"] not in cols:
            problems.append(f"missing column {c['name']}")
        elif c["type"].replace(" ", "") != cols[c["name"]]:
            problems.append(f"type drift on {c['name']}: {cols[c['name']]} != {c['type']}")
        if c.get("required") and c["name"] in cols and df.where(f"{c['name']} IS NULL").limit(1).count():
            problems.append(f"nulls in required column {c['name']}")
    return problems

Enforcement points, cheapest first: schema enforcement and the rescued-data column at ingestion, expectations at write time, contract tests in CI on producer changes, and monitoring in production. The organizational half matters as much: a named owner, a version number, a deprecation window and a place consumers are notified.

Ownership: the Human Side

  • Every governed table has a named owner (accountable for meaning and quality) and a steward or team on call.
  • Organize by domain (catalogs or schemas per business area) so ownership follows the business, not the platform team.

Interview angle "How do you make sure data across the company can be trusted?" 08. Security & Governance Operations

Beyond the grants covered in §05, a data engineer needs to know how credentials, identities, and network boundaries actually work day to day.

Secrets

# Databricks-managed secret scope (or an Azure Key Vault-backed scope)

databricks secrets put-secret orders-db password

# Referenced from a notebook - the value is redacted from logs/output automatically
password = dbutils.secrets.get(scope="orders-db", key="password")

Secrets referenced this way are automatically redacted (shown as [REDACTED]) anywhere they'd otherwise appear in notebook output or logs - never hardcode a credential in a notebook cell, and never pass a secret value into a plain print()/string concatenation, which can defeat the redaction.

Service Principals vs. Users

A service principal is a non-human identity for automation - every production job, every CI/CD deploy, every scheduled pipeline should run as one, not as an individual's personal identity. This is what makes "an engineer leaves the company" a non-event operationally: nothing production depends on their personal account, OAuth token, or PAT. Grant a service principal exactly the UC privileges its job needs (§05), scoped as narrowly as the pipeline allows.

Network: Where Compute Actually Runs

Recall the control-plane/data-plane split (see the overview guide): clusters run inside your own cloud VPC/VNet, not Databricks'. For stricter environments, PrivateLink (AWS) or private endpoints (Azure) keep all traffic between the control plane and data plane off the public internet, and IP access lists restrict which networks can reach the workspace UI/API at all. Knowing these exist - and that "your data never leaves your cloud account" is the underlying reason they're even possible - is usually enough depth for a DE interview; the fine network configuration is typically a platform/cloud team's job.

A Deprecation Worth Knowing: Credential Passthrough

Table access control lists via credential passthrough (a cluster inheriting the logged-in user's own cloud IAM identity to enforce access at the storage layer) predates Unity Catalog and is deprecated in its favor. If asked about it, the correct framing is historical: "that was the pre-Unity-Catalog way to enforce fine-grained access; UC's grant model (§05) replaced it and is what any new workspace should use."

External Metastore Migration

Workspaces that predate Unity Catalog often ran on the legacy Hive metastore (per-workspace, no cross-workspace governance, no lineage, no row/column security). Migrating existing Hive-metastore tables into UC (SYNC TABLE, or Databricks' bundled migration tooling) is a common real-world project - worth knowing it's a named, common undertaking rather than a rare edge case, since many production environments are mid-migration at any given time.

Duplicates, late events, mutable rows, silent schema changes and fragile APIs are properties of the source, and the ingestion design is where you absorb them. Before picking a tool (§10, §11), evaluate the source and decide the ingestion pattern. That evaluation is the difference between a pipeline that works in the demo and one that survives production.

The Source-Evaluation Checklist

Ask these before designing anything; each answer maps to a design decision.

QuestionWhy it matters
Who owns it, and is there a contact and a change process?You need someone to call when the schema changes. Ownership is the start of a data contract (§07).
How does data change: append-only, or updated and deleted in place?Append-only is trivial. Mutable data needs CDC, MERGE or snapshots, plus a plan for deletes (§15).
Is there a reliable change indicator (an updated_at, a version, a log)?Decides watermark pulls vs. log-based CDC vs. full snapshots. Timestamps set by applications are often not monotonic.
What are the volume, velocity and growth?Sizing, trigger choice and whether streaming is justified at all.

Does it contain PII or regulated fields?Classify and protect at ingestion (§06).

Design Dimensions of Ingestion

DimensionOptions and trade-offs
Batch vs. streamingA continuum, not a switch: daily batch, hourly, micro-batch (availableNow every few minutes), continuous streaming. Pick the slowest cadence that satisfies the requirement, because every step towards real time adds cost and operational burden.
Push vs. pullPull: you fetch on a schedule (simple, you control load). Push: the source sends events (lower latency, but you must be always available and handle bursts).

Idempotent Bronze: Metadata and Deduplication

Land data exactly as received, and add lineage metadata so any row can be traced and a bad load can be identified and removed:

from pyspark.sql import functions as F

          .option("cloudFiles.format", "json")
          .option("cloudFiles.schemaLocation", "/Volumes/prod/bronze/_schemas/orders")

          .withColumn("_ingest_ts",   F.current_timestamp())
          .withColumn("_source_file", F.col("_metadata.file_path"))
          .withColumn("_source",      F.lit("orders_api_v2")))

# silver: dedupe on the business key, keeping the latest version, so replays and duplicates are harmless
from pyspark.sql import Window
w = Window.partitionBy("order_id").orderBy(F.col("updated_at").desc(), F.col("_ingest_ts").desc())

Two rules follow: never mutate bronze (it is your replay source), and make every downstream write idempotent so that re-running a day produces the same result instead of a second copy.

Contracts at the Boundary

The cheapest place to catch a bad change is the ingestion boundary. Agree the schema, semantics and delivery expectations with the source owner in a data contract, and check them automatically on every load (§07). When you cannot negotiate one (third-party data), the rescued-data column and schema-drift alerts are your fallback.

Interview angle "Ingest an orders table from a production Postgres into the lakehouse." Start with source questions: is there a replica, a change log, deletes, a reliable timestamp? Then choose log-based CDC (Lakeflow Connect or Debezium) if deletes matter and load must stay low, or a watermark pull from a replica if not. Land raw in bronze with lineage columns, dedupe on key and sequence in silver, and say how you would detect and recover from a missed or duplicated change (periodic reconciliation, replay from bronze).

10. Auto Loader Deep Dive

Auto Loader (cloudFiles) is the default way to incrementally ingest files landing in cloud storage into a Delta table. It's a Structured Streaming source under the hood, which means it inherits checkpointing, exactly-once semantics, and everything else in §12 - the part that's genuinely new is how it discovers files and infers schema.

The Core Pattern

raw_stream = (spark.readStream
  .format("cloudFiles")
  .option("cloudFiles.format", "json")
  .option("cloudFiles.schemaLocation", "/Volumes/restaurant_prod/bronze/_schemas/orders")
  .option("cloudFiles.inferColumnTypes", "true")
  .load("/Volumes/restaurant_prod/bronze/incoming_files/orders/"))

(raw_stream.writeStream
  .option("checkpointLocation", "/Volumes/restaurant_prod/bronze/_checkpoints/orders")
  .trigger(availableNow=True)
  .toTable("restaurant_prod.bronze.orders_raw"))

Two File-Discovery Modes

Directory Listing (default)

Lists the target directory each trigger and diffs against a tracked state (RocksDB-backed) to find new files. Zero setup, works everywhere, scales to millions of files with incremental listing. Default and usually sufficient.

File Notification

cloudFiles.useNotifications=true sets up a cloud-native event queue (S3 event notifications + SQS, or ADLS + Event Grid/Queue Storage) so new files are pushed instead of polled. Set up once per source with cloudFiles.region/IAM permissions; worth it at very high file-arrival rates or very deep/wide directory trees where listing itself becomes the bottleneck.

Schema Inference & Evolution

On first run, Auto Loader samples the data to infer a schema and persists it to cloudFiles.schemaLocation so restarts don't have to re-infer. cloudFiles.schemaEvolutionMode controls what happens when new files show a schema change:

ModeBehavior
addNewColumns (default)Stream fails once, schema is updated with the new column, then the stream is restarted (manually, or automatically under Lakeflow Declarative Pipelines) and continues.
rescueUnrecognized fields are captured in a _rescued_data JSON string column instead of failing the stream - nothing is silently dropped, but the pipeline never breaks on new fields.
failOnNewColumnsStream fails and stays failed until you update the schema by hand. Use when an unexpected new column should be a human decision, not an automatic one.
noneNew columns are silently ignored. Rarely what you want - usually paired with an explicit schema and rescue for anything unexpected instead.
The Rescued Data Column Even with an explicit schema, mismatched types (a string where a number was expected) or extra columns land in _rescued_data rather than causing a failed row or a silent null. This is the single most interview-relevant Auto Loader detail: it's the mechanism that makes "what happens when upstream sends a malformed record?" answerable with "nothing breaks, and nothing is lost - check _rescued_data."

Key Options Worth Knowing Cold

Triggers for Batch-Like Ingestion

Auto Loader is almost always run with trigger(availableNow=True) rather than a continuously running stream: it processes everything currently available, then stops - behaving like an incremental batch job you can schedule every 15 minutes via Workflows, without paying for an always-on cluster. Auto Loader Patterns from the Projects

Three small, real Auto Loader uses (a CSV transactions drop, JSON files carrying a fraud watchlist, and partner CSV extracts) show the details that separate a working demo from a dependable load:

          .option("cloudFiles.inferColumnTypes", "true")
          .load(src)
          .withColumn("source_file", F.col("_metadata.file_path"))           # lineage: which file did this row come from
          .withColumn("ingestion_timestamp", F.current_timestamp()))

q = (stream.writeStream.format("delta").outputMode("append")
     .option("checkpointLocation", "/Volumes/finguard/source/fraud_watchlist/_checkpoint/")
     .trigger(availableNow=True)                                              # process what is there, then stop
     .toTable("finguard.bronze.fraud_watchlist"))

  • CSV arrives as strings. Even with inferSchema, numeric and timestamp columns often land as strings (especially with formats like dd-MMM-yyyy HH:mm:ss). Bronze stays as landed; silver casts explicitly (cast("int"), to_timestamp(col, "MM/dd/yyyy hh:mm:ss a")) and derives simple columns (gross amount = quantity x price).
  • Schema and checkpoint locations belong next to the data (in the volume), one pair per source, so each source has independent state and can be reset on its own.
  • _rescued_data is your safety net. A row whose values do not fit the schema does not fail the stream; the unmatched fields go to _rescued_data. Count non-null rescued rows as a data-quality signal.
  • Incremental means "new files only." Upload a second file and rerun: only the new file is read, tracked by the checkpoint. It does not detect changes inside an already processed file, so agree with the source that files are immutable.
  • An AI assistant will happily write a query that never ends. Generated Auto Loader code often used a continuous trigger, so the cell ran forever until it was stopped and re-prompted for "process the available files and exit." Always check the trigger and add awaitTermination() for scheduled runs (§29).
  • Simulating file streams for practice: a small generator that writes one JSON file per record into the volume, resuming from the highest id already written, lets you rehearse late and incremental arrival without a real source.

11. COPY INTO, Lakeflow Connect & Choosing a Tool

Auto Loader isn't the only ingestion path, and picking the wrong one for the scenario is a common interview trip-up.

COPY INTO

A simpler, SQL-native, idempotent bulk-load statement. Databricks tracks which files have already been loaded (metadata-only, no streaming infrastructure), so re-running the same statement is safe and only new files are loaded.

COPY INTO restaurant_prod.bronze.orders_raw
FROM '/Volumes/restaurant_prod/bronze/incoming_files/orders/'
FILEFORMAT = JSON
FORMAT_OPTIONS ('inferSchema' = 'true')
COPY_OPTIONS ('mergeSchema' = 'true');

COPY INTO is the right call for occasional or ad hoc loads and when you don't want streaming checkpoint infrastructure at all. It doesn't scale to millions of small files or very high-frequency micro-batches nearly as well as Auto Loader - that tracking metadata grows unbounded and eventually becomes the bottleneck. Rule of thumb: COPY INTO for thousands of files loaded occasionally, Auto Loader for continuous or high-volume arrival.

12. Structured Streaming on Databricks

Structured Streaming treats a stream as an unbounded table that keeps growing, and re-runs the same DataFrame logic you'd write for a batch job against each new chunk. This "batch code, streaming execution" model is why so much Databricks ingestion - Auto Loader included - is a streaming query underneath, even when the intent is closer to "run this incrementally every 15 minutes."

The Micro-Batch Model

Under the default execution engine, Spark repeatedly: (1) checks the source for new data, (2) processes it as one micro-batch through the same query plan, (3) writes results, (4) records progress in the checkpoint, (5) waits for the next trigger. Each cycle is atomic - a crash mid-batch just replays that batch on restart, using the checkpoint to know exactly where it left off.

Triggers: Controlling the Cadence

Interview angle "Is Auto Loader batch or streaming?" - it's a streaming source almost always run with availableNow triggers, which is why people call the same pipeline both "batch" and "streaming" and both answers are defensible. The precise answer: it uses the Structured Streaming engine (checkpointing, exactly-once, incremental state) but is scheduled and billed like a batch job.

Checkpoints & Exactly-Once

The checkpointLocation stores two things: offsets (what's been read from the source) and a write-ahead log of what's been committed to the sink. Together, these let Spark guarantee end-to-end exactly-once processing for idempotent sinks like Delta tables, even across driver failures - a restarted stream replays only the uncommitted portion of the last micro-batch, never double-processes committed data. This is the mechanism that makes "what happens if the cluster dies mid-write?" answerable with "nothing, it resumes exactly where it left off" rather than "you get duplicates."

A checkpoint is tied to one query Changing the transformation logic in incompatible ways (adding a stateful aggregation, changing partition columns) after a checkpoint exists can break the stream on restart. Never point two different streaming queries at the same checkpoint location, and never delete/move a checkpoint you intend to keep running - that's equivalent to restarting the pipeline from scratch.

Stateful Operations, Watermarking & Late Data

Aggregations, joins, and deduplication across a streaming DataFrame require Spark to keep state between micro-batches (e.g. "the running total for restaurant X so far"). Left unbounded, that state grows forever. A watermark tells Spark how late data is allowed to arrive before it's considered droppable, which bounds state size and lets Spark clean up state for windows that will never see another update.

from pyspark.sql.functions import window, col

windowed = (orders_stream
  .withWatermark("order_ts", "10 minutes")           # tolerate up to 10 min of lateness
  .groupBy(window(col("order_ts"), "5 minutes"), col("restaurant_id"))
  .sum("order_amount"))

# Streaming deduplication - also needs a watermark to bound the dedup state
deduped = (orders_stream
  .withWatermark("order_ts", "1 hour")
  .dropDuplicatesWithinWatermark(["order_id"]))

A row arriving more than 10 minutes late (per the watermark above) relative to the max event time already seen is silently dropped from that aggregation - a direct trade of correctness-for-arbitrarily-late-data against bounded memory. Setting the watermark is a business decision as much as a technical one: too short and you drop legitimately late data (a mobile order synced after being offline); too long and state balloons, slowing every micro-batch.

foreachBatch: The Escape Hatch

foreachBatch hands each micro-batch to you as an ordinary (static) DataFrame, which is how you do anything the streaming write API doesn't support natively - most commonly, a streaming MERGE for upserts (see §15), writing to multiple sinks, or per-batch custom logic.

def upsert_batch(microBatchDf, batchId):
    (microBatchDf.createOrReplaceTempView("updates"))
    microBatchDf.sparkSession.sql("""
        MERGE INTO restaurant_prod.silver.orders_clean t
        USING updates s ON t.order_id = s.order_id
        WHEN MATCHED THEN UPDATE SET *
        WHEN NOT MATCHED THEN INSERT *
    """)

(orders_stream.writeStream
  .foreachBatch(upsert_batch)
  .option("checkpointLocation", "/Volumes/restaurant_prod/silver/_checkpoints/orders")
  .trigger(availableNow=True)
  .start())

Kafka is the most common streaming source you will meet, so an interviewer expects you to explain it without notes. It is a distributed, durable, append-only log. Producers append records; consumers read them at their own pace and can rewind.

Alerting Sinks and Idempotency

An alert (an email, a page, a call to an API) is a side effect, and side effects are not covered by Delta's exactly-once guarantee. A micro-batch that fails halfway is retried, so anything that sends to the outside world must tolerate running twice. 13. Delta Lake Internals

Knowing Delta Lake as "ACID transactions and time travel" gets you through a definitions question. Knowing what's actually in the _delta_log folder gets you through the follow-up.

What's Actually on Disk

restaurant_prod.db/orders_clean/
├── part-00000-....snappy.parquet         ← the actual data, plain Parquet
├── part-00001-....snappy.parquet
├── ...
└── _delta_log/
    ├── 00000000000000000000.json        ← commit 0: CREATE TABLE
    ├── 00000000000000000001.json        ← commit 1: a MERGE
    ├── 00000000000000000002.json        ← commit 2: an OPTIMIZE
    ├── 00000000000000000010.checkpoint.parquet   ← periodic full-state snapshot
    └── _last_checkpoint                 ← pointer to the latest checkpoint

Each commit is one JSON file containing an ordered list of actions: add (a new data file, with stats), remove (a file logically removed, tombstoned rather than deleted from disk immediately), metaData (schema/partitioning changes), protocol (minimum reader/writer version), and commitInfo (who/when/what operation). The current state of the table at any version is just "replay every commit up to that version and keep the surviving add files" - which is exactly what makes time travel possible: VERSION AS OF 5 replays the log up to commit 5.

Because replaying thousands of small JSON commits from scratch would be slow, Delta writes a checkpoint (a Parquet snapshot of the fully-reconciled state) every 10 commits by default, so a reader only needs the latest checkpoint plus any commits after it.

Optimistic Concurrency Control

Delta doesn't use locks. A writer reads the table version it started from, computes its changes, and tries to commit the next sequential version number. If another writer already committed that version first, the loser re-reads the new state, checks whether its changes still conflict (not just "someone else wrote something," but "did they touch the same files/partitions"), and retries if safe, or fails if a genuine conflict exists (e.g. two concurrent MERGEs touching overlapping rows).

Interview angle "How does Delta handle two jobs writing to the same table at once?" - optimistic concurrency control via atomic commit-file creation on the metastore/storage layer, not pessimistic locking. Non-overlapping writes (different partitions, blind appends) succeed concurrently with automatic retry; truly conflicting writes to the same rows fail one of the transactions, which the caller must retry.

ACID Guarantees, Concretely

Atomicity

A commit JSON either lands in full or not at all - readers never see a partially-written set of files as "the table."

Consistency

Schema enforcement rejects writes that violate the declared schema before they're ever committed.

Isolation

Snapshot isolation: every reader sees a single consistent version for the duration of its query, never a version that changes mid-read.

Durability

Once a commit file exists in cloud storage (itself durable, replicated object storage), the write is permanent.

Table Features & Protocol Versions

Newer capabilities (deletion vectors, column mapping, liquid clustering, change data feed) are gated behind a reader/writer protocol version recorded in the log's protocol action. A table using a feature your client doesn't support simply refuses to open - this is why an older open-source Spark/Delta client sometimes can't read a table a newer Databricks Runtime just wrote to, and why DESCRIBE DETAIL and SHOW TBLPROPERTIES are useful first commands when debugging a compatibility error.

DESCRIBE DETAIL restaurant_prod.silver.orders_clean;
SHOW TBLPROPERTIES restaurant_prod.silver.orders_clean;
-- delta.minReaderVersion, delta.minWriterVersion, delta.feature.deletionVectors, etc.

Deletion Vectors

Historically, a single-row DELETE or UPDATE rewrote the entire Parquet file that row lived in - correct, but expensive at scale. Deletion vectors (enabled by default on newer Databricks Runtime versions) instead record "row N in file X is deleted" in a small side file, leaving the original Parquet untouched. Reads transparently apply the deletion vector to filter those rows out. This turns row-level DELETE/UPDATE/MERGE from an "O(file size)" operation into something closer to "O(rows changed)" - a large part of why MERGE performance improved substantially on recent runtimes. Deletion vectors are eventually reconciled away by a subsequent OPTIMIZE, which does the full file rewrite once, in bulk.

14. Delta Lake Performance

Every Delta performance feature is really solving one of two problems: too many small files, or scanning data you don't need. Keep that framing and the whole feature set organizes itself.

The Small-Files Problem

Streaming and frequent-micro-batch writes naturally produce many small files (one small write, one small file). Small files hurt because listing and opening thousands of tiny files has fixed per-file overhead that swamps the actual I/O, and because Spark schedules roughly one task per file/split - too many tiny tasks means the cluster spends more time on scheduling overhead than computation.

OPTIMIZE restaurant_prod.silver.orders_clean;

-- Or automatically: enable on the table so small writes get compacted continuously
ALTER TABLE restaurant_prod.silver.orders_clean
SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',   -- coalesce output files at write time
  'delta.autoOptimize.autoCompact'   = 'true'    -- opportunistically compact small files after writes
);

OPTIMIZE compacts many small files into fewer, right-sized ones (target ~1 GB per file by default) by rewriting them - it does not change query results, only file layout, and old files are only removed from the live table version (still recoverable via time travel until VACUUM runs).

Z-Ordering vs. Liquid Clustering

Both exist to answer the same question: "when a query filters on column X, how do we avoid scanning files that couldn't possibly contain a match?" Delta tracks min/max stats per file per column; if a query's filter range doesn't overlap a file's stats, that file is skipped entirely (data skipping). Both features work by physically co-locating similar values into the same files so those min/max ranges stay narrow and useful.

-- Z-Order: co-locate by columns, computed at OPTIMIZE time
OPTIMIZE restaurant_prod.silver.orders_clean
ZORDER BY (restaurant_id, order_ts);

-- Liquid Clustering: declared once, maintained incrementally on every write
CREATE TABLE restaurant_prod.silver.orders_clean (...)
CLUSTER BY (restaurant_id, order_ts);
-- or on an existing table:
ALTER TABLE restaurant_prod.silver.orders_clean CLUSTER BY (restaurant_id, order_ts);

Partitioning: When It Helps and When It Hurts

Classic Hive-style partitioning (PARTITIONED BY (order_date)) physically splits data into subdirectories per partition value. It's a coarse, powerful pruning tool for a well-chosen, moderate-cardinality column (a date) that most queries filter on - but the classic interview trap is over-partitioning: partitioning by a high-cardinality column (a customer ID, a UUID) creates thousands of tiny partition directories, each with its own small-file problem, and defeats the whole point. The current best practice for most new Databricks tables is to skip explicit partitioning altogether and use liquid clustering instead, which avoids this failure mode entirely.

Common mistake Partitioning a large fact table by customer_id or another near-unique column "for faster customer lookups." This produces one file per customer, catastrophic write amplification, and a directory listing problem at scale. Use Z-Order/liquid clustering on that column instead of partitioning by it.

VACUUM & Retention

OPTIMIZE and DELETE/UPDATE/MERGE leave old, no-longer-referenced Parquet files on disk (still needed for time travel to older versions). VACUUM permanently deletes files older than the retention threshold that are no longer referenced by any version within that window.

VACUUM restaurant_prod.silver.orders_clean;               -- default 7-day retention
VACUUM restaurant_prod.silver.orders_clean RETAIN 168 HOURS;
VACUUM restaurant_prod.silver.orders_clean DRY RUN;        -- list what would be deleted, delete nothing
Interview angle Setting retention below 7 days (Databricks requires explicitly disabling a safety check to go lower) risks corrupting a table for anyone with a still-running query or a concurrent writer that started before the VACUUM and is reading files it assumes still exist. Never shorten retention just to save storage cost without confirming no long-running readers/writers span that window.

Table Statistics & ANALYZE

Delta automatically collects min/max/null-count statistics for the first 32 columns of every file at write time (used for data skipping); for the cost-based optimizer's join and aggregation planning more broadly, keep table-level statistics fresh with ANALYZE TABLE ... COMPUTE STATISTICS after large data changes, especially before a query with several joins where the optimizer has to choose a join strategy (see §18).

15. CDC & Incremental Patterns

Almost every real pipeline is incremental: new rows arrive, existing rows change, some rows are deleted. This section is the single most interview-tested area of Databricks data engineering - expect to write MERGE from memory.

MERGE INTO, Clause by Clause

MERGE INTO restaurant_prod.silver.orders_clean AS target
USING staged_updates AS source
  ON target.order_id = source.order_id
WHEN MATCHED AND source.op = 'DELETE' THEN DELETE
WHEN MATCHED AND source.updated_at > target.updated_at THEN
  UPDATE SET target.status = source.status, target.updated_at = source.updated_at
WHEN NOT MATCHED THEN
  INSERT (order_id, restaurant_id, status, updated_at)
  VALUES (source.order_id, source.restaurant_id, source.status, source.updated_at);

Each WHEN clause can carry its own extra condition, and clauses are evaluated in order - the first matching clause wins for a given row. WHEN NOT MATCHED BY SOURCE (matched in the target but absent from the source) is the fourth clause type, used to detect deletions when a full snapshot is the source rather than a stream of explicit delete events.

The classic MERGE bug If source contains more than one row per join key (duplicate events, or a source batch that wasn't deduplicated), MERGE throws UnsupportedOperationException: multiple source rows matched for the UPDATE/DELETE clauses. Always deduplicate the source batch on the join key before merging - typically by keeping only the latest event per key with a window function, exactly the fix shown in the deduplication subsection below.

Change Data Feed (CDF)

CDF turns a Delta table into a source of row-level changes - not just its current state - so downstream tables can process only what changed since they last looked, instead of re-scanning everything.

ALTER TABLE restaurant_prod.silver.orders_clean
SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

-- Downstream: read only what changed between two versions
SELECT * FROM table_changes('restaurant_prod.silver.orders_clean', 10, 20);

-- Or as a stream, continuously
spark.readStream.format("delta") \
  .option("readChangeFeed", "true") \
  .option("startingVersion", 10) \
  .table("restaurant_prod.silver.orders_clean")

Each CDF row carries a _change_type column (insert, update_preimage, update_postimage, delete), plus _commit_version and _commit_timestamp. This is the mechanism that makes it practical to propagate an upstream UPDATE/DELETE all the way to a gold table without re-processing the whole table - and it's exactly what APPLY CHANGES INTO in Lakeflow Declarative Pipelines uses under the hood (§16).

Slowly Changing Dimensions: Type 1 vs. Type 2

SCD Type 1 overwrites the old value - you lose history, but the table stays simple. That's exactly what the plain MERGE above does for the status column. SCD Type 2 keeps every historical version as its own row, with validity date ranges, so you can ask "what was this customer's address on March 3rd?"

-- SCD Type 2: expire the old row, insert the new one, in a single MERGE
MERGE INTO restaurant_prod.silver.customer_dim AS target
USING (
  SELECT customer_id, address, city, current_timestamp() AS effective_ts
  FROM staged_customer_updates
) AS source
ON target.customer_id = source.customer_id AND target.is_current = true
WHEN MATCHED AND (target.address != source.address OR target.city != source.city) THEN
  UPDATE SET target.is_current = false, target.valid_to = source.effective_ts
WHEN NOT MATCHED THEN
  INSERT (customer_id, address, city, valid_from, valid_to, is_current)
  VALUES (source.customer_id, source.address, source.city, source.effective_ts, NULL, true);

-- Note: a plain MERGE can only touch each existing row once per statement, so a genuine
-- "expire old + insert new" SCD2 in one pass typically needs the source pre-joined against
-- the current row (as above) or two statements/passes for expire vs. insert; Lakeflow
-- Declarative Pipelines' AUTO CDC APPLY AS SCD TYPE 2 (see §16) handles this natively.

Deduplication Patterns

# Batch: keep the latest event per key
from pyspark.sql import Window
from pyspark.sql.functions import row_number, col

w = Window.partitionBy("order_id").orderBy(col("updated_at").desc())
deduped = (raw_events
  .withColumn("rn", row_number().over(w))
  .filter("rn = 1")
  .drop("rn"))

# Or, when you truly only need first-seen-wins across the whole table history:
deduped_table = spark.read.table("bronze.orders_raw").dropDuplicates(["order_id"])

For streaming, use dropDuplicatesWithinWatermark (shown in §12) rather than plain dropDuplicates, which would otherwise have to retain state for every key ever seen, forever.

Idempotent Writes

A pipeline that might reprocess the same micro-batch (after a failure, or via manual backfill) needs writes that are safe to repeat. MERGE keyed on a natural or event ID is idempotent by construction - running it twice with the same input produces the same result. A plain append is not: reprocessing produces duplicate rows unless the source is deduplicated first or the sink itself de-duplicates (e.g. foreachBatch using MERGE, as in §12, is the standard way to make a streaming append workload idempotent).

16. Lakeflow Declarative Pipelines (Delta Live Tables)

Lakeflow Declarative Pipelines - the current name for what was branded Delta Live Tables (DLT); both names are in active use and refer to the same engine - let you declare what each table should contain and let Databricks work out dependency ordering, incremental processing, retries, and cluster management, instead of hand-writing an imperative script that calls tables in the right order.

The Three Table Types

Streaming Table

Processes each input row exactly once, incrementally. Backed by Auto Loader or another streaming source. The default choice for bronze/silver ingestion.

Materialized View

Recomputed (fully or incrementally, when possible) from its query whenever its inputs change. The default choice for gold-layer aggregations that need to reflect the full current state.

View

Not persisted at all - a named, reusable query, recomputed on every read. Useful for intermediate logic you don't want materialized as its own table.

Python Syntax

import dlt
from pyspark.sql.functions import col

@dlt.table(
  comment="Raw orders landed via Auto Loader",
  table_properties={"quality": "bronze"}
)
def orders_raw():
    return (spark.readStream.format("cloudFiles")
        .option("cloudFiles.format", "json")
        .load("/Volumes/restaurant_prod/bronze/incoming_files/orders/"))

@dlt.table(comment="Cleaned, validated orders")
@dlt.expect_or_drop("valid_amount", "order_amount > 0")
@dlt.expect_or_fail("has_order_id", "order_id IS NOT NULL")
def orders_clean():
    return (dlt.read_stream("orders_raw")
        .filter(col("status").isNotNull())
        .select("order_id", "restaurant_id", "order_amount", "status", "updated_at"))

@dlt.table(comment="Daily sales per restaurant")
def daily_sales():
    return (dlt.read("orders_clean")
        .groupBy("restaurant_id")
        .sum("order_amount"))

SQL Syntax

CREATE OR REFRESH STREAMING TABLE orders_raw
AS SELECT * FROM STREAM read_files(
  '/Volumes/restaurant_prod/bronze/incoming_files/orders/', format => 'json'
);

CREATE OR REFRESH STREAMING TABLE orders_clean (
  CONSTRAINT valid_amount EXPECT (order_amount > 0) ON VIOLATION DROP ROW,
  CONSTRAINT has_order_id EXPECT (order_id IS NOT NULL) ON VIOLATION FAIL UPDATE
)
AS SELECT order_id, restaurant_id, order_amount, status, updated_at
FROM STREAM orders_raw
WHERE status IS NOT NULL;

CREATE OR REFRESH MATERIALIZED VIEW daily_sales
AS SELECT restaurant_id, sum(order_amount) AS total
FROM orders_clean GROUP BY restaurant_id;

Rather than hand-writing the MERGE from §15, a declarative pipeline can consume a CDC feed (from Lakeflow Connect, CDF, or a Debezium-style stream) directly, including out-of-order events and SCD Type 2 history, in one declaration:

import dlt

dlt.create_streaming_table("customer_dim")

dlt.apply_changes(
  target="customer_dim",
  source="customer_cdc_events",
  keys=["customer_id"],
  sequence_by="updated_at",       # resolves out-of-order events correctly
  apply_as_deletes="op = 'DELETE'",
  except_column_list=["op"],
  stored_as_scd_type=2            # or 1 - handles history automatically
)

This single declaration replaces the hand-rolled SCD Type 2 MERGE pattern from §15 - sequence_by makes it correct even when CDC events arrive out of order (a real-world guarantee that's genuinely hard to hand-code correctly).

Pipeline Modes & Unity Catalog Integration

A pipeline runs in triggered mode (processes available data, then stops - the common case, scheduled via Workflows) or continuous mode (stays running, picking up new data with low latency, at the cost of an always-on cluster). Every table a pipeline creates is a normal Unity Catalog-governed Delta table - queryable with plain SQL from outside the pipeline the moment it's written, and covered by the same grants, lineage, and row filters described in §05.

Working with a pipeline day to day

  • Source layout. A pipeline is a folder of files (commonly transformations/ with bronze.py, silver.sql, gold.sql); the engine reads all of them and infers the dependency graph from which tables read which. File order does not matter.
  • Dry run validates the whole graph (syntax, schemas, missing tables) without processing data or updating tables: run it before every real run and in CI.
  • Selective runs. Run or refresh only chosen tables while developing. Full refresh reprocesses a table from scratch: for a streaming table that reads a source with limited retention (Kafka, a landing zone you clean up), a full refresh can permanently lose data, so protect such tables with TBLPROPERTIES ('pipelines.reset.allowed' = 'false').
  • Development vs. production mode. Development keeps the compute warm for fast iteration and disables retries so errors surface immediately; production mode terminates compute after the update and retries on failure.
  • Compute. Serverless pipelines (no cluster config, automatic optimization) are the default recommendation; classic pipelines give control over node types and libraries.
  • Materialized views refresh incrementally when the engine can, and fall back to a full recompute when it cannot; that decision is visible in the event log.

The event log: the pipeline's own telemetry

Interview angle "Why use Lakeflow Declarative Pipelines instead of hand-written PySpark jobs orchestrated by Workflows?" - you get automatic dependency resolution from the query graph (no manually ordering tasks), built-in data quality enforcement (expectations), automatic incremental processing for streaming tables, and a managed pipeline UI showing data quality and lineage per run. The trade-off: less imperative control, and a learning curve around its specific decorators/clauses. For simple, mostly-independent jobs, plain Workflows tasks are often still simpler.

Expectations: what "warn" and "drop" look like in practice

In a build with six rules on a product table, the run showed 23 rows written, one dropped and one allowed with a violation. The one dropped failed an expect_or_drop (a null product name); the one allowed failed a plain expect (a zero price). The pipeline UI lists every rule with its pass and fail counts, which is your data-quality dashboard for free. Design guidance:

  • Drop when a row is unusable (null key). Warn when it is suspicious but you would rather see it than lose it (price of zero, unknown category). Fail the update only for invariants where wrong output is worse than none.
  • Prefer several individual rules to one grouped rule so metrics say which check failed and each can carry its own action.
  • Derive, do not just copy, in silver: is_active from a null end date of an SCD2 source, deal_size from an amount band, inventory_status from stock versus reorder level, gross_amount from quantity and price. Business rules encoded once, near the data.

Project structure and gotchas

  • Folders group files, files hold datasets. A typical layout is transformations/bronze_to_silver/ (one file per table) and transformations/silver_to_gold/. The engine builds the dependency graph from the reads, so a gold table automatically runs after the silver tables it reads, with no ordering configuration.
  • A file must be included as pipeline source. A file created outside the configured source folders shows a "skipped" icon and silently does not run; include it as pipeline source code (or create it inside the right folder). This is a classic "why is my table missing?" cause.
  • Set the default catalog and schema in the pipeline settings so unqualified names land where you expect.
  • Dry run before run. It catches wrong column names and missing tables without moving data.
  • Reruns are incremental. Running the whole pipeline again reprocesses only new source data for streaming tables; existing tables report zero new rows.
  • Gold dimensions as views. When silver already is the clean, standardized dimension (one row per customer, active only), a view over silver avoids copying data; it always reflects current silver. Use a table when you need a snapshot, indexes on hot columns, or to protect consumers from silver changes.
  • Review AI-generated pipeline code. A generated pipeline was structurally right but had grouped expectations, unnecessary trim/upper, and (in one case) a fact table missing the customer key that the semantic layer later needed. Prompt for a dry run, then read every expectation and every join key.

17. Data Modeling on Databricks

The medallion architecture tells you where data is in its journey; data modeling tells you what shape the gold layer takes so people can query it correctly and fast. The concepts (grain, facts, dimensions, keys) are platform-independent and are covered in depth in Data Modeling for Data Engineers. This section is the Databricks-specific layer: how to implement a star schema on Delta and Unity Catalog, and which platform features replace old warehouse habits.

Modeling Style vs. Medallion Layer

Star Schema in Five Rules

  1. Declare the grain first. One sentence: "one row per order line." Every fact column and every dimension must be true at that grain. Mixed grains are the most common modeling bug and the source of double counting.
  2. Facts hold numeric measures (quantity, amount) and foreign keys to dimensions. Types: transaction (one row per event), periodic snapshot (one row per entity per period, e.g. daily account balance), accumulating snapshot (one row per process instance, updated as milestones occur, e.g. order placed/shipped/delivered).
  3. Dimensions hold descriptive attributes (customer, product, store, date) with a surrogate key. Special kinds: conformed (shared across facts, e.g. one dim_customer), role-playing (date used as order date and ship date), degenerate (order number kept on the fact), junk (bundle of low-cardinality flags), bridge tables for many-to-many.
  4. Surrogate keys insulate the model from source-key changes and make SCD Type 2 possible. Generate them with an identity column or a deterministic hash of the business key plus effective date.
  5. Add an "unknown" member (key -1) to each dimension so late-arriving or missing dimension rows do not drop fact rows in an inner join.

Implementing It on Delta and Unity Catalog

CREATE TABLE retail_prod.gold.dim_customer (
  customer_sk    BIGINT GENERATED ALWAYS AS IDENTITY,      -- surrogate key, assigned by Delta
  customer_id    STRING NOT NULL,                          -- business key from the source
  customer_name  STRING,
  segment        STRING,
  country        STRING,
  valid_from     TIMESTAMP NOT NULL,                       -- SCD Type 2 validity window
  valid_to       TIMESTAMP,
  is_current     BOOLEAN NOT NULL,

)

CREATE TABLE retail_prod.gold.fact_sales (
  sale_id        STRING NOT NULL,                          -- degenerate key
  sale_date      DATE   NOT NULL,
  customer_sk    BIGINT NOT NULL,
  product_sk     BIGINT NOT NULL,
  quantity       INT,
  net_amount     DECIMAL(18,2),
  CONSTRAINT fact_sales_pk  PRIMARY KEY (sale_id),
  CONSTRAINT fk_customer    FOREIGN KEY (customer_sk) REFERENCES retail_prod.gold.dim_customer (customer_sk),
  CONSTRAINT chk_qty        CHECK (quantity > 0)            -- enforced on every write
)
CLUSTER BY (sale_date, customer_sk);

Enforced constraints

NOT NULL and CHECK are enforced by Delta at write time: a violating batch fails, which makes them real data-quality gates. In pipelines, the equivalent is an expectation (§16).

Informational constraints

PRIMARY KEY and FOREIGN KEY are not enforced: they document the model, feed lineage, BI tools and metric-view joins, and (with RELY) let the optimizer eliminate redundant joins. You are responsible for uniqueness, so test it.

Identity columns (GENERATED ALWAYS AS IDENTITY) give unique, increasing, not gap-free surrogate keys, but they force a writer that cannot be parallelized in some patterns and cannot be used with every MERGE shape. A common alternative in pipelines is a deterministic hash key such as xxhash64(customer_id, valid_from), which is stable across reloads and needs no coordination. Generated columns (GENERATED ALWAYS AS (year(sale_date))) derive a column on write, useful for partition-like pruning.

Physical Layout: Liquid Clustering, Not Partitioning

Cluster the fact table on the columns most used in filters and joins (sale_date, then a high-cardinality key), and dimensions on their business key. Use CLUSTER BY AUTO to let predictive optimization choose and evolve the keys from real query patterns. Avoid Hive-style partitioning unless the table is truly multi-terabyte and always filtered by the partition column (§14). Enable predictive optimization so OPTIMIZE, VACUUM and statistics run without a schedule.

Loading a Type 2 Dimension

The whole pattern is "close the old row, insert the new one." You can hand-write it as a two-statement MERGE (§15) or let a declarative pipeline do it:

-- Lakeflow Declarative Pipelines (SQL): SCD Type 2 in one declaration
CREATE OR REFRESH STREAMING TABLE dim_customer_scd2;

CREATE FLOW customer_flow AS AUTO CDC INTO dim_customer_scd2
FROM STREAM(retail_prod.silver.customers_changes)
KEYS (customer_id)
SEQUENCE BY updated_at
STORED AS SCD TYPE 2;         -- adds __START_AT / __END_AT; current row has __END_AT IS NULL

The fact load then joins to the dimension as of the event time so history is honored: ON f.customer_id = d.customer_id AND f.event_ts >= d.valid_from AND (f.event_ts < d.valid_to OR d.valid_to IS NULL). Anything without a match is assigned the unknown member, and a data-quality check counts how many.

Validating the Model

-- grain check: the declared primary key really is unique
SELECT sale_id, count(*) FROM retail_prod.gold.fact_sales GROUP BY sale_id HAVING count(*) > 1;

-- referential integrity: no orphan foreign keys
SELECT count(*) AS orphans
FROM retail_prod.gold.fact_sales f
LEFT JOIN retail_prod.gold.dim_customer d USING (customer_sk)
WHERE d.customer_sk IS NULL;

-- exactly one current row per business key
SELECT customer_id FROM retail_prod.gold.dim_customer WHERE is_current GROUP BY customer_id HAVING count(*) > 1;

18. Spark Performance Tuning on Databricks

The Spark guide covers the execution model in full; this is the condensed, Databricks-specific checklist for when a job is slow and you have five minutes to diagnose it.

Adaptive Query Execution (AQE)

AQE (on by default) re-optimizes the query plan mid-execution using real runtime statistics instead of only static pre-execution estimates. Three concrete things it does:

Coalesce shuffle partitions

Merges many small post-shuffle partitions into fewer, right-sized ones, fixing the classic "200 shuffle partitions for a tiny dataset" overhead problem automatically.

Switch join strategy

Converts a sort-merge join to a broadcast join mid-plan once actual data size (not just the estimate) proves one side is small enough.

Skew join optimization

Detects a disproportionately large partition after a shuffle and automatically splits it into smaller sub-partitions processed in parallel.

Joins: Broadcast vs. Shuffle

from pyspark.sql.functions import broadcast

# Force a broadcast join when you know one side is small (or AQE's estimate is wrong)
result = orders.join(broadcast(restaurants), "restaurant_id")

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 100 * 1024 * 1024)  # default 10MB

A broadcast join ships the entire smaller table to every executor, avoiding a shuffle of the (usually much larger) other side entirely - the single biggest join speedup available, but only viable when one side fits comfortably in executor memory. Two large tables force a sort-merge join, which shuffles both sides by join key - expensive, but unavoidable at that scale.

Data Skew

Skew is when one partition key holds vastly more rows than others (one restaurant chain with 40% of all orders), so one task takes far longer than the rest and the whole stage waits on it. AQE's automatic skew join handling covers many cases; when it doesn't (a skewed groupBy rather than a join, for instance), the manual fix is salting: append a random suffix to the skewed key to spread it across more partitions, then aggregate again to remove the salt.

from pyspark.sql.functions import concat, lit, rand, floor

salted = orders.withColumn("salted_key",
    concat(col("restaurant_id"), lit("_"), floor(rand() * 10).cast("int")))
partial = salted.groupBy("salted_key", "restaurant_id").sum("order_amount")
final = partial.groupBy("restaurant_id").sum("sum(order_amount)")

Caching

.cache()/.persist() keeps a DataFrame's computed result in memory/disk across multiple actions, which only pays off when you actually re-read the same DataFrame more than once (an interactive notebook exploring the same intermediate result repeatedly; a table read by several downstream branches of the same job). Caching something read exactly once is pure overhead. Always .unpersist() when done, and remember Delta's own file-level caching (disk cache on Databricks clusters) already accelerates repeated reads of unmodified cloud files without any code change.

Reading the Spark UI / Query Profile

The fastest diagnostic loop for "why is this slow": open the query's Query Profile (or Spark UI's SQL tab), find the stage with the longest wall-clock time, and check for (1) a huge shuffle read/write size relative to input - a join or aggregation exploding row counts; (2) a large skew between min/median/max task duration in that stage - data skew; (3) heavy spill (data written to disk because it didn't fit in executor memory) - undersized executors or too few shuffle partitions for the data volume.

Photon

Photon (see also the overview guide) is a vectorized native-code execution engine, a drop-in replacement for Spark's row-at-a-time JVM execution for supported operators - scans, filters, joins, aggregations, most write paths. It requires zero code changes; enable it on the cluster (or use it by default on SQL warehouses/serverless) and eligible operators run faster. Not every operator is Photon-eligible yet (some UDFs and complex data types fall back to standard Spark), which is why the Query Profile shows exactly which operators ran on Photon versus the JVM engine for a given query - useful when Photon is enabled but a job isn't seeing the expected speedup.

Interview angle "A job got slower after adding a UDF." - Python UDFs force row-by-row serialization between the JVM and a Python process for every row (and are not Photon-eligible), which is often dramatically slower than an equivalent built-in Spark SQL function or a vectorized Pandas UDF (@pandas_udf, which batches rows and uses Arrow for serialization). Always prefer a built-in function first, a Pandas UDF second, and a plain row-at-a-time Python UDF last.

19. Orchestration: Jobs & Workflows

Databricks Jobs (the UI/product is called Workflows, part of the broader Lakeflow Jobs branding) is the native scheduler: a DAG of tasks, each with its own compute, retries, and dependencies, triggered on a schedule, a file arrival, or another job's completion.

Task Types

Notebook / Python script / Python wheel

The most common task: run a notebook, a .py file, or an installed wheel's entry point.

Lakeflow Declarative Pipeline

Trigger a full pipeline run (§16) as one task, with the pipeline's own internal DAG hidden inside it.

SQL task

Run a query, a dashboard refresh, or an alert check against a SQL warehouse.

dbt task

Run a dbt project's models directly as a job task, with dbt's own DAG respected.

Run Job task

Trigger another job as a task - the mechanism for composing large pipelines out of smaller, independently-testable jobs.

Condition / For Each

Branch on a value, or fan out the same task across a list of inputs (e.g. one set of transformations per restaurant chain) without duplicating task definitions.

Dependencies, Parameters & Task Values

Tasks declare depends_on another task by key, forming a DAG (fan-out and fan-in both supported). Two ways data flows between tasks:

# Inside an upstream task's notebook - pass a small value forward
dbutils.jobs.taskValues.set(key="row_count", value=42193)

# Inside a downstream task - read it back
upstream_count = dbutils.jobs.taskValues.get(taskKey="ingest_orders", key="row_count")

# Job-level parameters, referenced anywhere as {{job.parameters.env}}
# set at trigger time (UI, API, or a scheduled trigger's fixed value)

Task values are for small pieces of metadata (a row count, a computed file path, a flag) - not a substitute for writing actual data to a table between tasks.

Retries, Timeouts & Alerts

{

Set retries on tasks that hit genuinely transient failures (a flaky upstream API, a brief cloud storage throttling event) - not on tasks with a logic bug, where retrying just delays the failure notification. alert_on_last_attempt avoids paging someone on the first of three retries when the second or third might still succeed.

Compute per Task

Each task can run on its own job cluster (created for the run, torn down after - the default and usually cheapest for production), a shared job cluster reused across the run's tasks (faster startup for a chain of small tasks, at the cost of resource contention between them), an existing all-purpose cluster (fast for development iteration, not recommended for production), or serverless compute (no cluster configuration at all).

Triggering: Schedule, File Arrival, Continuous

A file arrival trigger starts a job shortly after new files land in a path - useful for event-driven ingestion without a tight polling schedule, and complementary to (not a replacement for) Auto Loader's own incremental file tracking once the job is running.

Repair runs, retries and notifications

  • Repair run. After a failure, fix the cause (code or data), open the failed run and choose Repair run. Only the failed tasks and the tasks downstream of them re-execute; completed tasks are kept. Inside a For Each, only the failed iterations re-run (say one of 200 tables failed: you re-run one), and you can override parameters for the repair.
  • Retries are per task and automatic (count, interval, retry-on-timeout). They complement repair: retries absorb transient errors, repair handles errors you had to fix.
  • Notifications at job level: on start, success, failure, and duration warning; destinations are email, Slack, Teams, PagerDuty and webhooks. Subscribers on a Dashboard task get their own refreshed-snapshot email, separate from job notifications.
  • Parameters. Job-level parameters are visible to every task and overridable at trigger time; task-level parameters are scoped to one task. Reference dynamic values with {{job.parameters.env}}, {{tasks.<key>.values.<name>}}, {{job.run_id}} and, inside a loop, {{input}}. A typo in a reference (an extra letter in the key) does not fail loudly: the task simply receives the wrong value, which is why the job-run page's parameter view is the first place to look.
  • Every run is audited in system.lakeflow tables (jobs, tasks, run timelines, with parameters and compute), which is how you build a fleet-wide reliability dashboard (§23).

Job Patterns from the Projects: Nested Jobs, Run Ids and "All Done"

Three production habits appear in every good orchestration design, and each comes with a limit worth knowing.

1. For Each wraps exactly one task, so nest a job

A For Each task loops one inner task over a list. If the per-item work is a sequence (read parameters, load to bronze, merge to silver), you cannot put three tasks inside the loop. The pattern: make the sequence its own inner job with parameters, and have the For Each's single inner task be a Run Job task that calls it once per item, passing {{input}}.

resources:
  jobs:
    source_to_silver:                                  # the OUTER job for one source system
      parameters: [{name: source_system, default: sql_server}, {name: run_id, default: "0"}]
      tasks:
        - task_key: get_list_of_tables                 # publishes a JSON array with dbutils.jobs.taskValues.set
          notebook_task: {notebook_path: ../src/get_tables.py, base_parameters: {source_system: "{{job.parameters.source_system}}"}}
        - task_key: ingest_each
          depends_on: [{task_key: get_list_of_tables}]
          for_each_task:
            inputs: "{{tasks.get_list_of_tables.values.tables_metadata}}"
            concurrency: 4
            task:
              task_key: ingest_one
              run_job_task:
                job_id: ${resources.jobs.source_to_silver_inner.id}
                job_parameters: {table_metadata: "{{input}}", run_id: "{{job.parameters.run_id}}"}

    source_to_silver_inner:                            # ONE table: three notebooks in sequence
      parameters: [{name: table_metadata}, {name: run_id}]
      tasks:
        - task_key: read_table_parameters
          notebook_task: {notebook_path: ../src/read_params.py}
        - task_key: source_to_bronze
          depends_on: [{task_key: read_table_parameters}]
          notebook_task:
            notebook_path: ../src/source_to_bronze.py
            base_parameters: {table_parameters: "{{tasks.read_table_parameters.values.table_parameters}}"}
        - task_key: bronze_to_silver
          depends_on: [{task_key: source_to_bronze}]
          notebook_task: {notebook_path: ../src/bronze_to_silver.py}

The names in base_parameters must match the notebook's widgets exactly, or the value silently does not arrive. Set the For Each concurrency deliberately: it is a cap on parallel iterations (and the platform enforces a maximum), and each iteration starts its own run, so it multiplies compute.

2. Propagate one run id end to end

A master job should pass {{job.run_id}} (its own run id) into every child as a parameter. Every child writes that id into the audit table, so one query answers "what happened in last night's run across all sources and layers?" and the summary email can be built from a single id. Give the run id a harmless default (for example "0") so children can be run alone in testing.

3. "Run if" choices are design decisions, not defaults

tasks:
  - {task_key: sql_server_to_silver, run_job_task: {job_id: ${resources.jobs.source_to_silver.id}, job_parameters: {source_system: sql_server, run_id: "{{job.run_id}}"}}}
  - {task_key: blob_to_silver,       run_job_task: {job_id: ${resources.jobs.source_to_silver.id}, job_parameters: {source_system: blob,       run_id: "{{job.run_id}}"}}}
  - task_key: silver_to_gold
    depends_on: [{task_key: sql_server_to_silver}, {task_key: blob_to_silver}]
    run_if: ALL_DONE                                   # rebuild gold from whatever silver holds, even if one source failed
    run_job_task: {job_id: ${resources.jobs.silver_to_gold.id}, job_parameters: {source_system: silver, run_id: "{{job.run_id}}"}}
  - task_key: send_email
    depends_on: [{task_key: silver_to_gold}]
    run_if: ALL_DONE                                   # always send the summary, success or failure
    notebook_task: {notebook_path: ../src/send_email.py, base_parameters: {run_id: "{{job.run_id}}"}}
ChoiceEffectTrade-off
ALL_SUCCESS (default)Gold runs only if both sources loaded.Safe and consistent, but one flaky source blocks the whole platform.
ALL_DONEGold and the email run regardless of upstream outcome.Right for the notification. For gold it favors availability over consistency: dashboards may combine fresh and stale data, so surface freshness in the output and in the email.

Other details from the same builds: a first attempt may fail against a database that is waking up, so the default retries (about three, immediately) usually rescue it; keep the audit write idempotent on (run_id, table_id) so a retried task updates its own row instead of adding a second one; a dashboard refresh is just another task (with a warehouse and optional subscribers) placed after gold; and views and metric views need no refresh task, because they read current data at query time (§28).

Orchestration Principles (Tool-Independent)

Orchestration is the undercurrent that runs the whole pipeline in the right order at the right time. Whatever tool you use, good orchestration rests on the same ideas, which is exactly what an interviewer probes when they ask "Airflow or Databricks Jobs?":

  • Dependencies as a DAG. Express what must finish before what, with no cycles; let the scheduler run independent branches in parallel.
  • Idempotent, deterministic tasks. Any task can be retried or re-run for a past date and give the same result. This is what makes retries, repairs and backfills safe.
  • Time-based and event-based triggers. Schedules for regular cadence, sensors or file-arrival triggers for data that arrives when it arrives, and dataset or table triggers for cross-pipeline dependencies. Avoid polling with sleeps.
  • Retries with backoff, timeouts and SLAs. Retry transient faults only; every task has a timeout; a missed SLA raises an alert, not silence.
  • Backfills are first-class. Running a range of past dates with the same code and parameters must be routine and safe.
  • Separate orchestration from computation. The orchestrator triggers and observes work; it should not run heavy processing itself.
  • High availability and observability. The scheduler is itself a critical service: it needs redundancy, run history, logs, and alerting on its own health.
  • Keep the DAG small and readable. A pipeline of pipelines, each independently testable, beats one enormous graph.

What Can Live in a Bundle

Almost everything in a data project: jobs and their compute settings, Lakeflow Declarative Pipelines and ingestion pipelines, notebooks and Python files (the code itself), Python wheels, dashboards, ML models and serving endpoints, unit and integration tests, and workspace/cluster settings such as policies. The point is that "the project" is one versioned directory that can be deployed to any workspace. Before bundles you could keep notebooks in Git, but jobs and dashboards were clicked into existence and drifted between environments.

Branching and Release Flow

  1. Link the repo. Create the GitHub repository (default branch main), attach it in the workspace as a Git folder, and cut dev from main.
  2. Develop on a feature branch cut from dev. Deploy it to your own dev target (mode: development prefixes resource names with your username and pauses schedules), run it, and iterate.
  3. Pull request into dev with a senior reviewer. Parallel features on separate branches merge independently.
  4. Deploy dev to the dev workspace (manually with a button, or by Action; both are legitimate choices) and run the job or integration tests against real dev data.
  5. Pull request dev to main with required reviewers. On merge, a GitHub Action authenticates as a service principal and runs databricks bundle deploy -t prod. Do the very first production deploy by hand to confirm the end-to-end setup, then automate it.
  6. Hotfix. For a production incident, branch from main, fix, test, merge straight back to main (deploy fires), then back-merge into dev so the fix is not lost. Skipping the dev round trip is the entire point of a hotfix, which is why it must still go through review.

It is a non-breaking rename: the databricks bundle CLI commands and existing databricks.yml files are unchanged, and both names still appear in blogs, courses and interviews. Say "Declarative Automation Bundles (formerly Asset Bundles, DABs)" and you are covered either way.

21. Testing Data Pipelines

Data pipeline testing has the same pyramid shape as any software: fast unit tests for pure logic, slower integration tests against real (dev) infrastructure, and declarative data-quality checks running continuously in production.

Unit Testing PySpark Transformations

The core trick: write transformation functions that take and return DataFrames, with no I/O inside them, so tests can pass in small in-memory DataFrames and assert on the output - no cluster, no real table, no cloud storage required.

# src/transforms.py
def clean_orders(df):
    return df.filter(df.order_amount > 0).dropDuplicates(["order_id"])

# tests/test_transforms.py
import pytest
from chispa.dataframe_comparer import assert_df_equality
from src.transforms import clean_orders

def test_clean_orders_filters_negative_amounts(spark):
    input_df = spark.createDataFrame(
        [("o1", 10.0), ("o2", -5.0)], ["order_id", "order_amount"])
    expected = spark.createDataFrame([("o1", 10.0)], ["order_id", "order_amount"])
    assert_df_equality(clean_orders(input_df), expected, ignore_row_order=True)

chispa (a PySpark-native assertion library) gives readable diffs on DataFrame mismatches instead of a generic assertion error. A local SparkSession fixture (started once per test session, not per test, for speed) is all the infrastructure this needs - it runs in CI without touching Databricks at all.

def test_merge_upserts_existing_and_inserts_new(spark, tmp_path):
    table_path = str(tmp_path / "orders")
    spark.createDataFrame([("o1", "pending")], ["order_id", "status"]) \
        .write.format("delta").save(table_path)

    updates = spark.createDataFrame(
        [("o1", "shipped"), ("o2", "pending")], ["order_id", "status"])
    updates.createOrReplaceTempView("updates")
    spark.sql(f"""
        MERGE INTO delta.`{table_path}` t USING updates s ON t.order_id = s.order_id
        WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *
    """)

    result = spark.read.format("delta").load(table_path)

    assert result.filter("order_id = 'o1'").first().status == "shipped"

The expectations from §16 are effectively assertions that run on every pipeline update in production, not just in CI - a form of testing that never goes stale because it can't be skipped or forgotten before a deploy.

Integration Testing

For logic that genuinely needs Databricks (Unity Catalog grants, a real Auto Loader run against cloud storage, an actual Job's task dependencies), run the real thing against an isolated dev catalog/schema created and torn down per test run - exactly what a DAB's mode: development target (§20) is designed to make cheap and collision-free between developers and CI runs.

22. Software Engineering for Data Pipelines

Data engineering is software engineering with unusually stateful, unusually expensive-to-rerun programs. The field has moved from GUI-driven ETL to pipelines written as code, so the practices that keep any codebase healthy apply: version control, review, modular design, automated tests, packaging and infrastructure as code. Interviewers ask about these because they separate someone who writes a working notebook from someone who can keep a hundred pipelines working for years. Testing details are in §21 and deployment in §20; this section is the engineering discipline around them.

Notebooks vs. Code: Pick the Right Tool

Notebooks are excellent for exploration, prototyping and documentation, and poor as the unit of production code: hidden execution order and state, hard to unit test, hard to diff and review, easy to copy-paste. The pragmatic rule: explore in notebooks, ship in modules. Move logic into functions in a package, keep a thin notebook or script that wires them together, and deploy through a bundle. Source-format notebooks in Git and Git folders reduce the pain where notebooks remain.

Functional Core, Imperative Shell

Keep business logic in pure functions that take DataFrames and return DataFrames, and push reads, writes and configuration to the edges. Pure functions are trivially testable and reusable; the shell is small enough to cover with one integration test.

# transforms.py : pure, no I/O, no global state
from pyspark.sql import DataFrame, functions as F

def clean_orders(df: DataFrame) -> DataFrame:
    return (df.where(F.col("order_id").isNotNull())
              .withColumn("order_amount", F.col("order_amount").cast("decimal(12,2)"))
              .dropDuplicates(["order_id"]))

# jobs/ingest_orders.py : the shell wires reads, transforms and writes
def run(spark, cfg):
    raw = spark.table(f"{cfg.catalog}.bronze.orders")
    clean_orders(raw).write.mode("overwrite").saveAsTable(f"{cfg.catalog}.silver.orders")

# tests/unit/test_transforms.py
def test_clean_orders_drops_null_keys_and_dupes(spark):
    df = spark.createDataFrame([("a", "10.5"), ("a", "10.5"), (None, "1")], "order_id string, order_amount string")
    out = clean_orders(df)
    assert out.count() == 1 and out.first().order_amount == Decimal("10.50")

Technical Debt in Data Systems

Data code accumulates debt in recognizable ways: copy-pasted notebooks, undocumented business rules, tables nobody dares delete, hard-coded dates and paths, pipelines with no tests, and logic duplicated across dashboards. Manage it deliberately: keep a visible backlog, delete unused tables using lineage and usage data, refactor when you touch code, and reserve capacity for it. Ignoring it does not save time, it borrows from your future incident rate.

Interview angle "How do you make pipeline code maintainable?" Modules over notebooks; pure transformation functions with unit tests and thin I/O shells; config and bundle variables instead of hard-coded values; linting, type checks and tests as CI gates; bundles for project resources and Terraform for platform; idempotent writes; structured logs with a run id; and code review against a data-specific checklist. Concrete beats abstract: name the layout and the gates you would put in CI.

Job Alerts & SQL Alerts

Beyond the email_notifications/on_failure config shown in §19, a Databricks SQL alert runs a query on a schedule and notifies when a threshold condition is met - the natural tool for "alert me if yesterday's order count drops by more than 20%" business-logic monitoring, as distinct from "alert me if the job itself crashed."

Lakehouse Monitoring automatically computes and tracks statistical profiles (null rates, distinct counts, distributions) of a table over time in two generated tables (a profile table and a drift table), so a silent upstream schema/semantic change - a currency field switching units, a category suddenly all-null - shows up as a metric change you can alert on, rather than a customer noticing a wrong number in a dashboard weeks later.

Worked Example: What Did This Job Run Cost?

Cost questions come up in every senior interview, and the answer is a two-table join. system.billing.usage records consumption in DBUs, one row per hour per SKU per run, tagged with the job and run that caused it. system.billing.list_prices holds the price per DBU per SKU, with a validity period because prices change over time. Multiply and sum.

-- Cost of ONE job run
SELECT u.usage_metadata.job_run_id                            AS run_id,
       sum(u.usage_quantity)                                  AS dbus,
       sum(u.usage_quantity * p.pricing.effective_list.default) AS cost_usd
FROM system.billing.usage u
JOIN system.billing.list_prices p
  ON  u.sku_name = p.sku_name
  AND u.cloud    = p.cloud
  AND u.usage_start_time >= p.price_start_time                    -- price valid at the time of usage
  AND (p.price_end_time IS NULL OR u.usage_start_time < p.price_end_time)
WHERE u.usage_metadata.job_run_id = '1234567890123456'
GROUP BY 1;

-- Cost per job per day: the basis of a cost dashboard
SELECT u.usage_date, u.usage_metadata.job_id AS job_id, j.name,
       round(sum(u.usage_quantity * p.pricing.effective_list.default), 2) AS cost_usd
FROM system.billing.usage u
JOIN system.billing.list_prices p
  ON u.sku_name = p.sku_name AND u.cloud = p.cloud
 AND u.usage_start_time >= p.price_start_time
 AND (p.price_end_time IS NULL OR u.usage_start_time < p.price_end_time)
LEFT JOIN (SELECT job_id, max_by(name, change_time) AS name FROM system.lakeflow.jobs GROUP BY job_id) j
  ON u.usage_metadata.job_id = j.job_id
WHERE u.usage_metadata.job_id IS NOT NULL AND u.usage_date >= current_date() - 30
GROUP BY 1, 2, 3
ORDER BY cost_usd DESC;
  • Why hourly rows. A two-hour run produces two or three usage rows (the run straddles hour boundaries), each with its own DBU quantity. That is why you sum.
  • Why the time-aware join. A shortcut that filters prices to price_end_time IS NULL (the current price) prices historical usage at today's rate; joining on the validity window prices each hour at the rate in force then.
  • Which price column. The pricing struct has default, promotional.default and effective_list.default. Use effective_list: it is the price after any promotion.
  • Limits. These are list prices. A negotiated discount will not appear, and the cloud provider's VM cost on classic compute is a separate bill, so treat the number as the Databricks share and reconcile with finance before quoting it externally. Billing rows can lag by hours.
  • The optimization habit. Before tuning a job, record duration and cost; after tuning, record both again. "Reduced runtime 40% and cost 35%" is a defensible result; "made it faster" is not.
  • Where the job facts live. system.lakeflow.jobs (definitions), job_tasks, job_run_timeline and job_task_run_timeline (every run and task: start, end, result state, parameters, compute). Join them to billing on job_id and run_id for cost-per-outcome analysis.

Data Quality Monitoring: Freshness and Completeness

Beyond expectations and Lakehouse Monitoring above, Databricks offers schema-level data quality monitoring that you enable once and that learns each table's normal behavior:

Freshness

Was the table updated when its history says it normally is? A table that usually updates hourly and has been silent for six hours is flagged, without you writing a rule.

Completeness

Did the expected volume arrive? A table that normally gains about a million rows a day and gained ten thousand (or ten million) is flagged.

Results surface as a health indicator on the table (green for healthy, amber for an anomaly) and in a results table you can alert on. A companion data profiling feature computes summary statistics (min, max, mean, median, distinct counts, null rates). Use them together: expectations enforce rules you know, anomaly detection catches the failure you did not think of.

Interview angle "How would you know if an upstream source silently started sending bad data?" - the layered answer: DLT/pipeline expectations catch known invariants at write time (§16); Lakehouse Monitoring catches unknown drift in distributions/nulls over time; system tables catch operational failures (a job stopped running at all). A strong answer names all three rather than reaching for one.

24. DataOps: SLOs, Observability & Incident Response

DataOps applies the habits of DevOps, agile and lean manufacturing to data: build and release quickly and safely, watch the system continuously, and recover fast when it breaks. It rests on three technical pillars (automation, observability and monitoring, incident response) and one cultural one (people communicate, own outcomes and learn from failures without blame). The mechanics of CI/CD and monitoring are in §20 and §23; this section is the operating model that ties them into a reliable service, which is exactly what an interviewer means by "how do you run this in production?"

Start with Service Level Objectives

"The pipeline is reliable" means nothing until you say what reliable means. Define a few service level indicators (SLIs, the measurements) and objectives (SLOs, the targets) per data product, agreed with consumers:

-- Freshness SLI: hours since each certified table was last written, against its own target
SELECT t.table_catalog, t.table_schema, t.table_name,
       round((unix_timestamp(current_timestamp()) - unix_timestamp(t.last_altered)) / 3600, 1) AS hours_stale,
       CAST(tag.tag_value AS INT) AS slo_hours
FROM system.information_schema.tables t
JOIN system.information_schema.table_tags tag
  ON tag.catalog_name = t.table_catalog AND tag.schema_name = t.table_schema AND tag.table_name = t.table_name
 AND tag.tag_name = 'freshness_slo_hours'
WHERE (unix_timestamp(current_timestamp()) - unix_timestamp(t.last_altered)) / 3600 > CAST(tag.tag_value AS INT);

A non-empty result is an alert. The error budget idea from site reliability engineering applies: a 99% freshness SLO permits about seven hours of staleness a month; when the budget is spent, reliability work outranks new features.

Automation: Shrink the Distance from Commit to Production

  • Everything as code: pipelines, jobs, dashboards, permissions and infrastructure in Git, deployed by CI (§20, §22).
  • Automated gates on every change: lint, unit tests, bundle validation, a dry run of pipelines, contract checks, and integration tests in a dev environment (§21).
  • Environment parity: the same bundle in dev, staging and prod with different targets, so "works in dev" means something.
  • Safe releases: deploy to production by service principal, keep changes small, and know the rollback before you ship (below).
  • Self-healing where safe: task retries for transient faults, auto-restart for streams, repair runs for partial failures; never auto-retry a logic bug.

Incident Response: the 3 a.m. Runbook

1

Detect

An alert (job failure, freshness SLO breach, anomaly), or worse, a consumer report. Track how often consumers find problems before you do: that ratio is your monitoring quality.

2

Triage and contain

Decide the severity by consumer impact. Stop the bleeding first: pause downstream jobs and dashboard refreshes, or flag the affected tables as suspect, so wrong data does not spread. Use lineage to find what is affected.

3

Mitigate and recover

Pick the fastest safe fix: repair run for a failed task once the cause is fixed; RESTORE TABLE to undo a bad write; roll back the deployment; or a targeted backfill of the affected dates from bronze.

DESCRIBE HISTORY retail_prod.silver.orders;                       -- find the last good version
RESTORE TABLE retail_prod.silver.orders TO VERSION AS OF 412;     -- undo the bad write (within retention)

-- Idempotent backfill: rewrite only the affected dates from bronze
INSERT INTO retail_prod.silver.orders REPLACE WHERE order_date BETWEEN '2026-09-20' AND '2026-09-22'
SELECT * FROM retail_prod.silver.orders_rebuilt WHERE order_date BETWEEN '2026-09-20' AND '2026-09-22';
4

Communicate

Tell consumers what is wrong, what is affected, and when to expect a fix; tell them again when it is resolved. Silence destroys trust faster than the outage does.

5

Learn: a blameless postmortem

Write down the timeline, the root cause (the system, not a person), what worked, what did not, and the follow-ups with owners and dates: a missing test, a missing alert, an unclear contract. Fix the class of problem, not just the instance.

Backfills, Reprocessing and Change Management

  • Design for reprocessing from day one: parameterize jobs by date range, keep bronze immutable, and make writes idempotent (replaceWhere, MERGE), so a backfill is a normal run with different parameters.
  • Backfill safely: throttle so you do not starve production, run in a separate compute, and invalidate or refresh downstream aggregates that included the wrong data.
  • Schema changes use expand and contract: add the new column (compatible), migrate consumers, then remove the old one after a deprecation window, announced through the contract and located with lineage.
  • Keep a change log: what shipped when, so an incident can be correlated with a release.

Culture: the Part Tools Cannot Buy

Teams that run reliable data services share a few habits: a clear owner per dataset and pipeline, an on-call rotation with a runbook, blameless postmortems, a habit of talking to consumers, and the discipline to spend error budget on reliability. Without them, the best monitoring stack simply produces alerts nobody owns.

Interview angle "A dashboard shows wrong revenue this morning. Walk me through it." Contain (pause refresh, flag the table), triage with lineage to the first bad table, fix the cause, restore or backfill idempotently, verify against a control total, communicate, then write the postmortem and add the missing test or alert. Stating SLOs, error budgets and the blameless review shows you run data as a service, not as a set of scripts.

25. Cost Optimization

Databricks bills for two things: the underlying cloud VM cost, and DBUs (Databricks Units) - a per-second usage metric that varies by compute type and workload tier. Most cost optimization is really "use the cheapest compute type/shape that meets the latency requirement," which is a much smaller set of levers than it first appears.

Job Clusters vs. All-Purpose Clusters

An all-purpose cluster left running for interactive development is billed continuously whether or not it's doing useful work; a job cluster is created for a run and torn down immediately after. Every scheduled production workload should run on a job cluster (or serverless), never on a shared all-purpose cluster - this single practice is the most common cost-review finding in real Databricks accounts.

Serverless vs. Spot vs. On-Demand

Serverless

No cluster to size at all; near-instant start; a usage-based price that bundles infrastructure overhead in. Best when engineering time saved on sizing/tuning outweighs a potentially higher per-DBU rate, and for spiky/unpredictable workloads.

Spot / Preemptible

Spare cloud capacity at a steep discount, revocable with short notice. Good for fault-tolerant, retryable batch jobs (Spark re-schedules lost tasks); risky for anything with a hard SLA, since the whole point is that it can be pulled back at any time.

On-Demand

Guaranteed availability at full price. The right choice for the driver node always (losing the driver kills the whole job) and for latency-sensitive production workloads.

A common pattern: on-demand driver, spot workers with a fallback to on-demand if spot capacity isn't available - balancing cost against the risk of losing worker capacity mid-job.

Cluster Policies

An admin-defined policy (see the overview guide's cluster section) restricts which cluster shapes users can even create - capping max node count, pinning approved instance types, forcing autoscaling within a bounded range, or requiring spot for non-production. This turns cost governance into a platform-level control instead of a per-engineer discipline that erodes over time.

Autoscaling: min/max Tuning

An autoscaling range that's too wide (min: 1, max: 20 "just in case") means Spark spends real time scaling up mid-job when the workload is predictable and could just start at the right size; a range that's too narrow throttles genuinely spiky workloads. For a recurring job with stable, known data volume, a fixed-size cluster (no autoscaling at all) is often both cheaper and faster than badly-tuned autoscaling, because there's no scale-up latency to pay every run.

Right-Sizing from Actual Usage

-- Find clusters that are consistently over-provisioned (low CPU utilization)
SELECT cluster_id, avg(cpu_user_percent + cpu_system_percent) AS avg_cpu_pct
FROM system.compute.node_timeline
WHERE start_time > current_timestamp() - INTERVAL 7 DAYS
GROUP BY cluster_id
HAVING avg_cpu_pct < 30
ORDER BY avg_cpu_pct;

Pair this with system.billing.usage (tag-based cost attribution) to find the specific jobs/teams driving spend, rather than guessing. This is the direct, boring, and highly effective answer to "how would you reduce our Databricks bill by 30%": look at the actual utilization and billing system tables before touching any code.

Serving Machine Learning

ML consumers need consistent features between training and inference. Compute features in the pipeline once, register them as governed tables, and reuse the same definitions for offline training (batch reads from Delta) and online inference (a low-latency store synced from the same tables). Point-in-time correctness matters: training rows must only see feature values that existed at their event time, or the model learns from the future. Vector indexes and agent tools (§30) are the same idea for retrieval.

Reverse ETL: Pushing Data Back into Operational Tools

Reverse ETL moves curated warehouse data (a customer's lifetime value, a churn score, a segment) into the systems where people act on it: a CRM, an ad platform, a support desk. It looks easy and is full of production traps:

  • Idempotency: the API will be called again after a partial failure. Send upserts keyed on the target's id, never blind inserts.
  • Diffing: push only what changed (compare to the last successful sync) to respect rate limits and avoid flooding the tool with no-ops.
  • Rate limits and batching: throttle, batch, and back off on 429s; make the job resumable from a checkpoint table.
  • Auditability and privacy: record what was sent and when; send only the fields the destination needs (§06).
  • Ownership: the destination team owns the meaning of the field; agree a contract (§07).
def push_batch(batch_df, batch_id):
    changed = (batch_df.alias("n")
        .join(spark.table("prod.ops.crm_sync_state").alias("s"), "account_id", "left")
        .where("s.payload_hash IS NULL OR s.payload_hash != n.payload_hash"))     # only what changed
    for chunk in changed.toLocalIterator():                                        # small result: safe to iterate
        crm_client.upsert(external_id=chunk.account_id, fields=chunk.payload)      # idempotent upsert by key
    # record success ONLY after the API accepted the data
    changed.select("account_id", "payload_hash").write.mode("append").saveAsTable("prod.ops.crm_sync_state_updates")

27. Metric Views & the Semantic Layer

Gold tables are clean, but they do not say what "revenue" or "active customer" means. Ten analysts write ten slightly different SQL definitions and the CEO sees ten numbers. A semantic layer puts the business definitions (dimensions and measures) in one governed place; in Databricks that object is the metric view. It is also the layer that makes Genie's natural-language answers trustworthy.

The Problem It Solves

  • KPI drift. "Number of patients" is count(*) to one person, count(distinct patient_id) to another, with or without cancelled visits to a third.
  • SQL duplication. The same join and filter logic is copy-pasted into dashboards, notebooks and reports, and diverges.
  • View explosion. One regular view per grain (by day, by month, by region, by product) so that the aggregation is fixed at definition time.
  • Untrusted AI answers. An LLM asked "total revenue by country" has to guess which column, join and filter to use.

A metric view separates what you measure (measures) from how you slice it (dimensions), and applies the aggregation at query time: define total_revenue once, then group it by day, country, or anything else without new objects.

Anatomy of a Metric View

A metric view is a Unity Catalog object (a view of a special type) whose body is YAML. You can build one in the UI (pick a source table and add measures and dimensions with a builder or free SQL expressions) and the UI shows the resulting YAML under Details; in real projects you author the YAML and create it with SQL so it lives in version control.

CREATE OR REPLACE VIEW retail_prod.semantic.order_metrics
WITH METRICS
LANGUAGE YAML
AS $$
version: 1.1                                  # the YAML spec version, not your revision
comment: "Order revenue KPIs, one row per order"
source: samples.tpch.orders                   # a table, view, another metric view, or a SQL query
filter: o_totalprice > 0                      # applied to every query

joins:                                        # star schema; nest 'joins' for a snowflake
  - name: customer
    source: samples.tpch.customer
    on: source.o_custkey = customer.c_custkey
    joins:
      - name: nation
        source: samples.tpch.nation
        on: customer.c_nationkey = nation.n_nationkey

dimensions:                                   # 'fields' is the newer synonym
  - name: order_date
    expr: o_orderdate
    display_name: Order Date
  - name: order_year
    expr: year(o_orderdate)
  - name: order_status
    expr: |
      CASE o_orderstatus WHEN 'F' THEN 'Fulfilled' WHEN 'O' THEN 'Open' WHEN 'P' THEN 'Processing' END
  - name: customer_name
    expr: customer.c_name                     # a column from a joined table needs its alias
  - name: country
    expr: customer.nation.n_name              # nested join: alias path

measures:
  - name: total_revenue                       # ATOMIC: a direct aggregate on source columns
    expr: SUM(o_totalprice)
    display_name: Total Revenue
    synonyms: [sales, revenue, total sales]   # helps Genie and other AI tools map words to this measure
    format: {type: currency, currency_code: USD, decimal_places: 0, abbreviation: compact}
  - name: order_count
    expr: COUNT(1)
  - name: avg_order_value                     # COMPOSED: built from other measures
    expr: MEASURE(total_revenue) / MEASURE(order_count)
  - name: customers_last_7_days               # WINDOW measure (experimental)
    expr: COUNT(DISTINCT o_custkey)
    window:
      - order: order_date
        range: trailing 7 day
        semiadditive: last
$$;

Things people trip over: the version is a format version; a column from a joined table must be referenced through its alias (customer.c_name, or customer.nation.n_name through a nested join), otherwise it is resolved against the source and fails; the multi-line | block scalar is how you write a CASE expression; and YAML is indentation-sensitive, which is why an AI assistant (§29) is genuinely useful for authoring it, provided you check the result against the docs.

Querying: MEASURE() and GROUP BY

SELECT order_year,
       country,
       MEASURE(total_revenue)   AS revenue,
       MEASURE(avg_order_value) AS aov
FROM retail_prod.semantic.order_metrics
WHERE order_status = 'Fulfilled'
GROUP BY ALL                      -- group by every dimension in the SELECT
ORDER BY order_year, revenue DESC;

Measures can only be read through MEASURE(), dimensions are selected and grouped normally, and SELECT * is not supported (it has no meaning: a measure needs a grouping). Change the dimensions in the SELECT and the aggregation changes with them, with no new view. Because the engine knows the joins, it only executes the joins a given query actually needs.

Measure Types and Window Measures

TypeDefinitionExample
AtomicA direct aggregate over columns; the building block.SUM(o_totalprice)
ComposedCombines other measures with MEASURE(); reuse instead of repeating aggregates.MEASURE(total_revenue) / MEASURE(order_count)
Window (experimental)An aggregate over a moving frame ordered by a dimension, like a SQL window function.customers in the last 7 days

A window measure needs three things: order (a dimension to order by), range, and semiadditive (what to show when the query does not group by the ordering dimension: first or last value in the window). Range values: trailing 7 day (backward), leading 7 day (forward), cumulative (everything up to the current row, a running total), current (just this row's value) and all (the whole set on every row).

Semantic Metadata for Humans and AI

  • display_name - the readable label shown in dashboards and Genie (Total Revenue, not total_revenue).
  • synonyms - other words users say ("sales", "turnover") so an LLM maps the phrase to the right measure. Up to ten per field.
  • format - currency, number, percent, date formats with decimal places and compact abbreviations (172B is readable, 172319004467.98 is not).
  • comment - a description, used as context by AI tools.

Display names, formats and synonyms need a recent runtime (metric views are supported from Databricks Runtime 14.3, with newer YAML features requiring newer runtimes and SQL warehouse versions), so check the version table in the docs when a feature "does nothing."

Materialization: Trading Cost for Speed

materialization:
  schedule: every 6 hours
  mode: relaxed                       # the only mode today
  materialized_views:
    - name: daily_summary
      type: aggregated                # precompute chosen dimensions x measures
      dimensions: [order_date, order_status]
      measures: [total_revenue, order_count]

When a query's dimensions and measures are covered by a materialized view, the engine reads the precomputed data; anything not covered is computed from the source and combined (an aggregate-aware rewrite that is invisible to the user). An unaggregated materialization instead stores the fully joined, unaggregated model (only one per metric view). Under the hood Databricks runs a Lakeflow Declarative Pipeline to refresh it incrementally, so it costs compute and storage. The rule of thumb: do not materialize up front. Ship the metric view, watch which measures and dimensions users actually query, then materialize those. Materialization and window measures are flagged experimental, so expect changes.

Governance, Limits and Where It Fits

  • Governed like any UC object: grants, lineage, tags and certification, and an Insights tab showing who uses it. As with a regular view, consumers need SELECT on the metric view rather than on every source table.
  • Consumers: AI/BI dashboards, Genie spaces, alerts, notebooks and SQL. Third-party BI tools depend on connector support, and Power BI's compatibility mode was removed, so verify your BI tool before promising it.
  • Limits to know: the special MEASURE() / GROUP BY query syntax needs a short training for SQL users; Delta Sharing of metric views was not supported at the time of writing.
  • Versus alternatives: a regular view fixes the grain; a materialized view stores one fixed result; a metric view stores definitions and computes the grain per query. dbt's semantic layer and a BI tool's own model solve the same problem in other places, but definitions defined inside Unity Catalog are usable by every Databricks consumer at once.
Interview angle "How do you make sure 'revenue' means the same thing in the dashboard, the notebook and the AI assistant?" Define it once as a measure in a metric view over the gold star schema, expose only the metric view to consumers, add display names and synonyms so Genie resolves words correctly, certify it, and materialize only after usage data shows which slices are hot. Then contrast it with the alternative (definitions duplicated per tool) and name the trade-offs: query syntax, experimental features, and one more object to maintain.

28. AI/BI Dashboards, Genie & Databricks One

The consumption layer is where your pipelines meet the business. As a data engineer you are rarely asked to make a chart look pretty, but you are expected to know how dashboards are built, refreshed, secured and deployed, how a Genie space is set up so it answers correctly, and what compute they run on. This section covers all three surfaces and how they connect to the semantic layer (§27).

AI/BI Dashboards

AI/BI dashboards (the product formerly called Lakeview) are built from two things: datasets (a query or table) and visualizations placed on a canvas.

1

Data tab: define datasets

Add a table or write SQL. Each dataset is a named query the widgets read from. Add parameters for user-driven values. Keep datasets thin and pointed at gold tables or a metric view; heavy joins here run on every refresh.

2

Canvas: build pages and widgets

Add counters (KPI tiles), bar/line/area/pie charts, tables, pivots, maps, plus text widgets for titles and explanations. Use multiple pages to separate audiences (executive overview vs. customer and product detail). Add filters (a field filter such as country or payment method; one filter can drive several datasets) and cross-filtering between charts.

3

Build visuals with the AI assistant

Type "show revenue by franchise country" into a widget. The assistant knows the dashboard's datasets and the Unity Catalog metadata, writes the SQL (including any join the current dataset lacks, which it proposes as a new dataset you approve) and configures the chart. Always read the generated SQL: it is a draft, and a wrong join silently double-counts.

4

Publish, share, schedule

A dashboard has a draft (where you edit) and a published version (what viewers see; use "Edit draft" to change it and republish). At publish you choose the credentials: viewer credentials (each reader's own Unity Catalog permissions apply, so row filters and masks work) or embedded credentials (the publisher's identity runs the queries, so readers need no table access but see what the publisher can see). Add a refresh schedule and subscribers who receive an emailed snapshot. Viewers also get "Ask Genie" on a published dashboard for follow-up questions.

Engineering concerns for dashboards

  • Compute. Datasets execute on a SQL warehouse chosen at build time; serverless is the default recommendation (fast start, concurrency scaling). Cost is driven by how many widgets refresh and how heavy each query is.
  • Refresh in a pipeline. A Job can contain a Dashboard task that refreshes a published dashboard on a warehouse and notifies subscribers, so the dashboard updates immediately after the gold tables do (§19) instead of on an unrelated clock.
  • Dashboards as code. A dashboard serializes to a JSON file (.lvdash.json) that can live in Git and be deployed as a bundle resource across dev and prod (§20), with the dataset catalog parameterized per environment.
  • Performance. Point datasets at aggregated gold tables or a metric view, select only the needed columns, avoid SELECT *, and push filters into the dataset so the warehouse prunes data. A dashboard that "is slow" is almost always a dataset problem, not a chart problem.
  • Operational visibility. Dashboard and warehouse activity appear in system.query.history and billing tables, so you can find which dashboard drives your warehouse bill.

SQL alerts complete the picture: a saved query plus a condition (e.g. "revenue dropped more than 20% vs. yesterday"), a schedule and recipients. Alerts watch business signals; job notifications watch pipeline health (§23).

Genie: Natural-Language Analytics

Genie lets a business user ask a question in plain English and get a SQL query run for them, a table, a summary and, where sensible, a chart. The product line has three layers as of 2026:

Genie space / Genie Agent

A curated, domain-specific agent over a chosen set of tables, views and metric views (spaces evolved into "Genie Agents", which can also reason over unstructured content and run multi-step work). This is what you configure as a data engineer.

Genie One

The business-user product: ask questions and delegate tasks from the web, Slack, Teams, mobile or an MCP-compatible assistant, backed by agents.

Genie Ontology

The context layer beneath both: a continuously updated map of business meaning (public preview). It combines what you model in Unity Catalog with meaning inferred from dashboards, queries and agents.

How Genie produces an answer

A compound AI system: it interprets the question, retrieves relevant tables, columns, instructions and example queries (your configuration and Unity Catalog metadata), generates SQL, executes it on a SQL warehouse under the asking user's Unity Catalog permissions by default (so grants, row filters and masks apply), then summarizes and visualizes the result. It always shows the SQL it ran so users can inspect it, and users can rate answers.

29. AI-Assisted Development: Genie Code

Genie Code (the evolution of the Databricks Assistant) is Databricks' in-workspace AI coding agent. It is asked about in interviews for two reasons: it is now part of a data engineer's daily tooling, and how you use it (context, review, guardrails) reveals your engineering judgment. The differentiator versus general coding agents is that it is integrated with Unity Catalog, so it knows your tables, lineage, permissions and conventions.

Two Modes

Chat mode

A Databricks-tuned chatbot. It answers, explains, finds documentation and suggests code, but executes nothing. Good for "how do I read this format" and "what does this error mean."

Plans a multi-step task and does it: creates and edits notebooks, runs cells and reads the output, fixes its own errors, builds pipelines (dry-run then run), dashboards and jobs, and edits your existing artifacts. You review and accept or reject each change.

Its scope of action in a notebook: it can add markdown cells before each code cell, reorganize, comment, optimize, rename variables and convert between SQL dialects across the whole notebook (not only the selected cell), because it sees the notebook's full context.

What Agent Mode Can Build (and the Guardrails Around It)

  • Notebooks: reads table structure, writes and executes cells, adds markdown, fixes errors.
  • Lakeflow Declarative Pipelines: creates a pipeline with bronze/silver/gold files, adds data-quality expectations, runs a dry run to validate, then runs it.
  • Dashboards and jobs: creates datasets and visuals, wires a job with notebook and dashboard tasks (it uses the CLI/API under the hood, and may need to publish the dashboard before a refresh task works).

Using It Well: Best Practices

  1. Be specific. Name the table, the steps, the output. "Read @samples.tpch.orders, filter 1995 onwards, write to silver_orders" beats "clean the orders."

  3. Break down complex work. A notebook, then the pipeline, then the dashboard, then the job, verifying each. One giant prompt that builds everything is a demo trick, not a workflow.
  4. Iterate and refine. Follow up with corrections; it is a model, not an oracle.
  5. Always review. Read diffs, run tests, check generated SQL for wrong joins and grain. You own the code, however it was written.

The assistant itself carries no separate charge; the compute its code runs on is billed normally.

Building the Knowledge Base (Where the DE Work Is)

Unstructured: documents to a vector index

  1. Land and parse. PDFs go in a Unity Catalog volume; ai_parse_document (or a parser library) turns them into text and structure. Store one row per document with path, product/tenant metadata and the extracted text.
  2. Chunk. Whole documents are too big and too vague to retrieve. Split into pieces: fixed-size (e.g. 500 to 1000 tokens with 10-20% overlap, simple and robust), structure-aware (by heading or paragraph), or semantic. Small documents can stay one chunk. Keep metadata (source, page, section, ACL group) on every chunk. Chunking is the biggest lever on answer quality and it is a pipeline you own.
  3. Embed and index. An embedding model turns each chunk into a vector. The chunk table must have Change Data Feed enabled for a Delta Sync index.

Index types

Delta Sync: follows a Delta table; managed embeddings (Databricks embeds for you) or self-managed (you supply a vector column). Direct Access: you upsert vectors through the API, for data that does not live in Delta.

Retrieval quality knobs

Chunk size and overlap, metadata filters, hybrid search (vector plus keyword, better for IDs and product codes), a reranker, number of chunks returned, and the embedding model.

Keeping it fresh: a new or corrected document must reach the index. Run the parse and chunk pipeline as a job (file-arrival trigger, §19), update the chunk table with MERGE so deletions propagate, and trigger the index sync after it. A stale or "ghost" chunk (from a deleted document) is a correctness and compliance bug (§06).

Structured: tables to tools

An agent cannot safely run arbitrary SQL, so you give it narrow, parameterized functions. The function's COMMENT is not decoration: the LLM reads it to decide when to call the tool.

CREATE OR REPLACE FUNCTION agentic.tools.get_customer_returns(customer_email STRING)
RETURNS TABLE (order_id STRING, return_date DATE, reason STRING, status STRING)
COMMENT 'Returns every return request filed by a customer, looked up by email. Use when the user asks about the status or history of their returns.'
RETURN SELECT order_id, return_date, reason, status
       FROM agentic.crm.returns
       WHERE email = customer_email;

GRANT EXECUTE ON FUNCTION agentic.tools.get_customer_returns TO `support-agent-sp`;

Least privilege applies to agents too: the agent's identity (a service principal, or the end user when acting on their behalf) gets EXECUTE on exactly the tools it needs and nothing else.

From Prototype to Production

1

Prototype in the Playground

Choose a model, write a system prompt, add tools (the vector index, UC functions), and chat. Ask something that needs a document, something that needs a table, and something that needs both. Fix tool comments and prompts until behavior is right.

2

Export as an agent notebook

Get code → Create agent notebook generates a notebook that defines the agent (an MLflow agent class wrapping the model and tools), logs it to MLflow, registers it in Unity Catalog and deploys it to a serving endpoint. You then own the code in Git.

3

Evaluate

Build an evaluation set of questions with expected facts, run MLflow evaluation with LLM judges (correctness, groundedness to the retrieved chunks, relevance, safety), and gate releases on the scores, exactly like a test suite. Traces show the sequence of tool calls, latency and tokens per step, which is how you debug "it gave a wrong answer yesterday."

4

Serve and expose

The serving endpoint is the API. A Databricks App gives users a chat UI; grant the app permission to query the endpoint and configure user-authorization scopes so the app calls it on behalf of the signed-in user. Put AI Gateway in front for rate limits, usage tracking, guardrails and payload logging (inference tables) so you can audit and bound spend.

5

Operate

Monitor cost per conversation (tokens), latency, error rate, evaluation score drift and index freshness. Version the agent, canary new versions, and keep a rollback. Alert on cost anomalies the same way you alert on job failures (§23).

31. Data Architecture: Principles & Patterns

Data architecture is the undercurrent that decides whether today's design can absorb tomorrow's requirement. Good architecture is not the fanciest diagram; it is the set of decisions that fit the business need, cost what they are worth, and can be reversed when they turn out wrong. This section gives you the principles, the major patterns, the technology-choice framework and the back-of-envelope habits that a system-design interview probes, applied to Databricks. The concrete blueprints are in §32.

2. Plan for failureDesign for availability, reliability, durability, and explicit recovery targets (RTO, RPO).Idempotent jobs, replay from bronze, RESTORE, multi-zone compute, regional DR (§32).
3. Architect for scalabilityScale up and down; scale to zero when idle.Serverless and autoscaling compute; separated storage and compute; liquid clustering.

7. Make reversible decisionsPrefer choices you can undo cheaply ("two-way doors").Open formats (Delta, Parquet, Iceberg), open protocols (Delta Sharing), IaC.

9. Embrace FinOpsCost is an architectural dimension, managed continuously.Job compute and serverless choices, tags, cost queries (§25).

Concepts Every Architecture Answer Uses

  • Loose vs. tight coupling. Tightly coupled pipelines (one giant job) fail together and change together. Loosely coupled ones (independent tasks that communicate through tables or streams) can be scaled, tested and replaced separately, at the cost of more moving parts.
  • Event-driven architecture. Producers publish events; consumers react. It decouples teams and gives replay, at the cost of eventual consistency and harder debugging.
  • Distributed-systems realities. Networks fail, machines die, messages arrive twice or out of order. This is why idempotency and replay are design requirements, not refinements.
  • Single-tenant vs. multi-tenant. Shared infrastructure with logical isolation (row filters, catalogs per tenant) is cheaper; physical isolation is safer and simpler to reason about. Decide by compliance and noisy-neighbor risk.
  • Brownfield vs. greenfield. Most real work is brownfield: migrate incrementally (the strangler pattern: route one domain at a time to the new platform) rather than a big-bang rewrite.
  • OLTP vs. OLAP. Row-oriented transactional stores serve applications; columnar analytical stores serve aggregation. The lakehouse is the OLAP side, and Lakebase is the OLTP companion.

Lambda vs. Kappa on Databricks. Because Delta tables serve both batch and streaming reads and writes, and declarative pipelines run the same logic incrementally, you can get most of the Kappa benefit (one code path) without giving up the ability to reprocess in batch. Choose lambda-style separation only when the fast path has a genuinely different definition of correctness (for example an approximate real-time count that a nightly job later corrects).

Data mesh on Databricks. Domains map to catalogs or schemas; data products are governed Unity Catalog objects with an owner, a contract and an SLO; the platform team supplies self-serve templates (bundles, cluster policies); governance is federated (central policies through ABAC and tags, domain-level stewardship); and Delta Sharing or catalog grants deliver products across domains.

Back-of-the-Envelope Sizing

Estimates show you understand scale, and they expose bad designs early. A worked example for a clickstream platform:

Requirement: 50 million users, 20 events per user per day, 1 KB per event, keep 13 months.

Events per day  = 50e6 * 20               = 1e9 events/day
Peak rate       = 1e9 / 86,400 * 5 (peak) = ~58,000 events/s     -> needs a partitioned streaming log, not one API
Raw volume      = 1e9 * 1 KB              = 1 TB/day raw
Columnar+compressed (about 5x)            = ~200 GB/day in Delta
13 months retention                       = 200 GB * 395 days = ~79 TB   -> object storage, tiering for cold months
Daily batch aggregation reads ~200 GB     -> a mid-size cluster in tens of minutes, not hours

Round aggressively, state assumptions, and check the result against a sanity limit (a single machine, a network link, a cost ceiling). Interviewers care about the method far more than the exact numbers.

Interview angle "Why this architecture and not another?" Answer with requirements first, then name the principle each choice serves (reversible, loosely coupled, plans for failure), the alternative you considered and why you rejected it, and the trigger that would make you revisit ("if latency needs fall below a minute, move ingestion to continuous streaming"). Showing how the design can change is what "always be architecting" means.

32. End-to-End Architectures & System Design

A system-design round asks you to combine everything above into one coherent platform and defend the trade-offs. This section gives you three complete reference blueprints (a metadata-driven bank pipeline, a modern Lakeflow retail platform and a real-time Kafka fraud-detection stream), a way to present a project in an interview, a repeatable framework for any design question, a short disaster-recovery primer, and six practice scenarios with model-answer outlines.

Blueprint A: Metadata-Driven Batch Platform (Neo Bank)

Problem. A bank's data is scattered: a core banking SQL Server database (branches, customers, accounts, transactions), plus files from external parties (credit-bureau scores, payment-gateway logs). Manual pipelines per table are slow, brittle and do not scale; business users have no self-service view. Solution. A reusable, metadata-driven framework on the medallion architecture, where adding a table means adding a row of metadata, not writing a pipeline.

The four metadata tables

TableHolds
tablesOne row per table to load: table_id, name, source system, source schema or file path, target layer (silver or gold), target schema, and load_order for dependencies.
table_parametersGeneric name/value pairs per table: load_strategy (full or incremental), merge_keys, watermark_column. New parameters need no schema change.
table_watermarksThe last successfully loaded watermark value per table, so an incremental run reads only newer rows.
audit_logOne row per table per run: run id, table id, layer, start and end time, status, record count, error message. Feeds the email summary and the operational dashboard.

The generic loader (the heart of the framework)

from datetime import datetime
from delta.tables import DeltaTable
from pyspark.sql import functions as F

def load_table(table_id: str, run_id: str):
    cfg    = spark.table("banking.metadata.tables").where(F.col("table_id") == table_id).first()
    params = {r.parameter_name: r.parameter_value
              for r in spark.table("banking.metadata.table_parameters").where(F.col("table_id") == table_id).collect()}
    started, status, n, err = datetime.utcnow(), "success", 0, None
    try:
        # 1) extract: only new rows for incremental loads
        if params["load_strategy"] == "incremental":
            wm = (spark.table("banking.metadata.table_watermarks")
                       .where(F.col("table_id") == table_id).select("last_watermark").first()[0])
            query = f"(SELECT * FROM {cfg.source_schema}.{cfg.table_name} WHERE {params['watermark_column']} > '{wm}') q"
        else:
            query = f"{cfg.source_schema}.{cfg.table_name}"
        df = (spark.read.format("jdbc").option("url", jdbc_url).option("dbtable", query)
                   .option("user", user).option("password", pwd).load())        # creds from a secret scope
        n = df.count()

        # 2) land raw (bronze), then upsert into silver on the configured keys
        df.write.mode("append").saveAsTable(f"banking.bronze.{cfg.table_name}")
        if params["load_strategy"] == "incremental":
            keys = " AND ".join(f"t.{k} = s.{k}" for k in params["merge_keys"].split(","))
            (DeltaTable.forName(spark, f"banking.silver.{cfg.table_name}").alias("t")
                .merge(df.alias("s"), keys).whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())
            new_wm = df.agg(F.max(params["watermark_column"])).first()[0]
            # 3) advance the watermark ONLY after the write succeeded
            if new_wm is not None:
                spark.sql(f"MERGE INTO banking.metadata.table_watermarks w USING (SELECT '{table_id}' id, '{new_wm}' wm) n "
                          f"ON w.table_id = n.id WHEN MATCHED THEN UPDATE SET last_watermark = n.wm "
                          f"WHEN NOT MATCHED THEN INSERT (table_id, last_watermark) VALUES (n.id, n.wm)")
        else:
            df.write.mode("overwrite").saveAsTable(f"banking.silver.{cfg.table_name}")
    except Exception as e:
        status, err = "failed", str(e)[:2000]
        raise
    finally:
        spark.createDataFrame([(run_id, table_id, cfg.target_layer, started, datetime.utcnow(), status, n, err)],
            "run_id string, table_id string, layer string, start_time timestamp, end_time timestamp, status string, records long, error string"
        ).write.mode("append").saveAsTable("banking.metadata.audit_log")

Look for the design decisions that interviewers care about: the watermark is advanced after success (so a crash re-reads rather than skips); the silver write is a MERGE (idempotent, so a retry does not duplicate; the same retry re-appends those rows to bronze, which is acceptable for a raw layer and easy to trace if you stamp a run id on each batch); the audit row is written in finally (so failures are recorded too); credentials come from a secret scope; and the function is parameterized by table_id, so a For Each task can fan out over the tables of a given load_order in parallel (§19).

How the framework is wired: the job graph

The loader function above is the idea; in the actual build it is split into small, reusable notebooks stitched together by jobs. Knowing this wiring lets you draw it on a whiteboard, which is what an interviewer asks for.

Design trade-offs to be ready to defend

  • Where to keep metadata: Delta tables are simplest when everything is on Databricks and get lineage and governance for free; an external transactional database is better when non-Databricks systems must edit or read the config, or when you need row-level transactional updates at high frequency.
  • Watermarks miss things: a timestamp watermark cannot see deletes, and rows committed late with an older timestamp are skipped. Mitigate with a small overlap window plus the MERGE (dedupes the overlap), periodic full reconciliation, or move to real CDC (§11).
  • Concurrency on metadata tables: parallel loads all write the audit table. Appends do not conflict; concurrent MERGEs to the watermark table can (§13), so keep each table's update to its own row and enable deletion vectors / row-level concurrency, or retry on conflict.
  • Notebooks vs. pipelines: this framework predates or sidesteps Lakeflow Declarative Pipelines; a pipeline gives you expectations and lineage for free but is less flexible for arbitrary source-specific logic.

Blueprint B: Lakeflow Platform with Semantic Layer (Retail)

Problem. A retailer's CRM (Salesforce), product and inventory data (Postgres) and transaction files are disconnected. Solution. Managed ingestion, declarative transformation, a star schema, a semantic layer and natural-language access, all governed by Unity Catalog.

  • Ingestion. Lakeflow Connect ingestion pipelines pull Salesforce and Postgres with managed incremental logic. Per table you choose history tracking: off = SCD Type 1 (a current-state mirror; deleted source rows are deleted), on = SCD Type 2 (start/end validity columns; a deleted source row is closed out rather than removed). Files land through Auto Loader (§10).
  • Transformation. A declarative pipeline defines bronze, silver and gold as streaming tables and materialized views, with expectations to quarantine the deliberately dirty records (negative quantities, null keys). The gold layer is a star schema: one sales fact and three dimensions (§17).
  • Semantics and consumption. A metric view over the star schema defines revenue, units and average order value once; an AI/BI dashboard and a Genie space both read it (§27, §28).
  • Orchestration. One job: ingestion pipeline(s) then the transformation pipeline then dashboard refresh, on a daily schedule with failure notifications.

Blueprint C: Real-Time Fraud Detection with Kafka and Structured Streaming (FinGuard)

Problem. A card issuer wants to react within a minute to suspicious card activity: alert a customer when a single transaction exceeds their personal limit, alert when a card that is on a fraud watchlist is used, and show operations a near-real-time dashboard of volumes and alerts. Solution. A streaming lakehouse: transactions flow from Kafka into bronze, silver and gold streaming tables; customer attributes (a slowly changing table) and a watchlist (files) enrich them; alerts are written as gold tables and delivered by email; windows produce live volume metrics; a dashboard and jobs finish the loop.

The event, and the simulator that produces it

Each Kafka record is a JSON card transaction: transaction id, customer id, card number, merchant id, name and category, amount, currency, transaction type, payment channel, device id, city, country, event timestamp, an international flag and a status. The producer is a small Python service using the Confluent client with reliability settings worth memorizing: acks=all, enable.idempotence=true, retries with backoff, message key = transaction id, graceful shutdown on signals. Its rate (transactions per second) and fraud percentage are configurable, and separate producers emit "normal" traffic and deliberately fraudulent traffic for one specific test card, so you can trigger a watchlist alert on demand.

The simulator also runs a rule-based fraud engine that scores each transaction (high value 40, impossible travel 50, new device 20, high-risk merchant 25, blacklisted merchant 60, international 25, velocity 45, card testing 30; capped at 100) but removes the score and reason before publishing. That is a good pattern: you keep ground-truth labels aside for evaluating the detector, and the pipeline has to detect fraud from the raw event, as in production.

Reliability and Disaster Recovery in Brief

  • Idempotency first. Any step can be re-run after a failure without duplicating or corrupting data: MERGE instead of append for keyed data, deterministic overwrites by partition/date, checkpoints for streams. Idempotent pipelines make retries, repairs and backfills safe.
  • Replay from bronze. Because bronze is a lossless raw copy, you can rebuild silver and gold after a logic bug. Time travel (RESTORE) undoes a bad write within the retention window.
  • Regional DR. Define RPO (acceptable data loss) and RTO (acceptable downtime) first. Data: cross-region replication of the storage, or incremental DEEP CLONE of critical Delta tables to a second region. Metadata and code: Unity Catalog objects, jobs and dashboards recreated from infrastructure-as-code (bundles and Terraform), which is the strongest argument for never clicking production into existence. Run a secondary workspace warm or cold, and rehearse the failover, because an untested DR plan is a hope.
  • Streaming caveat. Checkpoints are tied to a specific table location and are not trivially portable, so plan the streaming restart procedure (reprocess from a known offset or from bronze) explicitly.

Platform and Architecture

What is the control plane, and what runs where?

The control plane is the Databricks-managed part: the web app, the storage of notebooks, queries and job definitions, the compute orchestration that starts and stops clusters, and the Unity Catalog service. The compute plane is where your code runs: classic compute in the customer's cloud account (VMs the control plane manages on your behalf), serverless compute in Databricks' own account. Your table data always lives in your object storage. (§02)

Account vs. workspace vs. metastore?

Account: the organization; holds identity, billing, and the list of workspaces and metastores. Workspace: a collaboration environment for running code and jobs. Metastore: the Unity Catalog governance container, one per region, attached to many workspaces. Users and groups are managed once at the account level and shared by all workspaces. (§02)

How is billing split between Databricks and the cloud on classic vs. serverless?

Classic: two bills, DBUs to Databricks and VMs/storage/network to the cloud provider. Serverless: one all-in usage bill from Databricks because the infrastructure is Databricks-managed. (§03)

Unity Catalog and Governance

What is Unity Catalog and what problem did it solve?

A centralized governance layer providing access control, auditing, lineage, data discovery and quality monitoring across workspaces. Before it, each workspace had its own users, metastore and permissions, so governance was duplicated and inconsistent. Now you define users, one metastore and grants once. (§05)

Explain the object hierarchy and the three-level namespace.

Metastore (one per region) contains catalogs; a catalog contains schemas; a schema contains tables, views, volumes, functions and models. You address objects as catalog.schema.object; the metastore is implicit. Typical use: a catalog per environment or domain, schemas per layer (bronze, silver, gold).

How do you connect Databricks to an ADLS or S3 location the governed way?

An admin creates a storage credential (the managed identity or IAM role that can reach the storage), then an external location binding a storage path to that credential, then tables or volumes on top of it. Developers use the volume path /Volumes/catalog/schema/volume/... and never touch keys.

Managed vs. external tables?

Managed: Unity Catalog owns the storage, files are deleted with the table (with a retention period), and you get automatic optimizations. External: you own the path; dropping the table leaves the files. Default to managed unless the data must live in a specific place or be shared with other writers.

What is Delta Sharing? What is Lakehouse Federation?

Delta Sharing is an open protocol for sharing live data with other Databricks or non-Databricks consumers (Spark, pandas, Power BI, Tableau) without copying it; the recipient does not need to be in your workspace. Lakehouse Federation lets you query an external database (Snowflake, Oracle, SQL Server, Synapse and others) as a foreign catalog in Unity Catalog without ingesting the data. Share out with Delta Sharing; read in place with Federation.

What are system tables and what do you use them for?

Built-in, queryable Delta tables under the system catalog: audit logs, lineage, billing usage and prices, compute and warehouse events, job and task runs, query history, data-classification results. Uses: cost attribution, failed-job dashboards, who-accessed-what audits, right-sizing. (§23)

Row filters, column masks, ABAC: when do you use which?

Row filter: a boolean function attached to a table that hides rows per user. Column mask: a function that redacts a column per user. Both are per-table. ABAC uses governed tags and policies to apply masks and filters to every matching column or table at once, so it scales to hundreds of tables and covers newly tagged columns automatically. (§06)

Compute

All-purpose vs. job cluster vs. SQL warehouse?

All-purpose: interactive development, multi-user, higher rate, idle time. Job cluster: created for a run and destroyed after, lower rate, for production. SQL warehouse: SQL only, fast start, concurrency scaling, for BI and dashboards. The same workload costs less on a job cluster because of the lower per-DBU rate and no idle time. (§03)

Serverless vs. classic: when would you not choose serverless?

When you need custom libraries, init scripts or Spark configs, strict network placement or full visibility into where data is processed, or when a large steady workload is cheaper on tuned classic clusters. Serverless wins on zero management, fast start and spiky workloads.

Single-user vs. shared cluster (access modes)?

Dedicated (single user) binds the cluster to one user or group and allows low-level APIs and ML libraries. Standard (shared) isolates multiple users on one cluster with full Unity Catalog enforcement but restricts some low-level features. Standard is the default for teams; dedicated for ML or special libraries.

Should Photon always be on?

No. It roughly doubles the DBU rate of a node, so it pays off only when the job speeds up by more than that (scan, join and aggregation-heavy workloads). Measure total cost, not just runtime.

Notebooks and DBUtils

What are magic commands? Name the common ones.

A keyword on a cell's first line that changes its behavior: %python, %sql, %scala, %r (language), %md (documentation, never executed), %sh (shell on the driver), %fs (file system), %pip (install packages), %run (run another notebook), %skip (skip the cell). (§04)

How do you run one notebook from another, and how do you choose?

%run executes the child inline in the same session, so its functions and variables are available; it must be alone in its cell and cannot return a value or handle errors. dbutils.notebook.run(path, timeout, args) launches a separate ephemeral run, returns a string from dbutils.notebook.exit, and lets you catch failures. Use %run to import shared code, notebook.run when you need isolation, parameters, output or error handling; prefer separate Job tasks when you need visibility and repair.

How do you parameterize a notebook, and pass values out of it?

Widgets (dbutils.widgets.text/dropdown/combobox/multiselect and .get) receive job or caller parameters. Out: dbutils.notebook.exit(json) to a calling notebook, or dbutils.jobs.taskValues.set to downstream job tasks. Big data goes through tables.

How do you store and read credentials securely?

Secret scopes (Databricks-backed, or Key Vault-backed on Azure) holding key/value secrets, read with dbutils.secrets.get(scope, key). Values print as [REDACTED]. Scope ACLs (READ/WRITE/MANAGE) control who can read; only admins put secrets. Prefer UC storage credentials and service principals over embedded keys. Caveat: redaction is display-only and can be bypassed by a user who can run code, so scope access is the real control.

How do you list, copy, move and delete files, and what is a volume?

A volume is a Unity Catalog folder for files, addressed as /Volumes/catalog/schema/volume/path, managed or mapped to external storage. dbutils.fs.ls lists, cp copies (with recurse=True for directories; overwrites the target), mv moves, rm deletes (recurse for directories), mkdirs creates the path, head peeks at the first bytes, put writes a string to a file. Copies across two volumes work across storage accounts.

How do you debug a failing notebook?

Set a breakpoint in the gutter and use Debug cell: step in, next line, step out, continue, with the debug console and variable inspector (you can even assign values to test a fix). For Spark issues use explain(), the Spark UI, and bisect with limit().display(); remember lazy evaluation means the failing line may not be the guilty one. Genie Code's "Diagnose error" is the fast path. Difference between step in and step out: step in enters the called function; step out finishes the current function and returns to the caller.

Jobs and Orchestration

How do you orchestrate notebooks, pipelines and dashboards?

A Databricks Job: a DAG of tasks (notebook, pipeline, SQL, dashboard refresh, dbt, run-job, condition, for-each), each with its own compute, retries and notifications, triggered by schedule, file arrival or continuously. (§19)

How do you pass parameters into a For Each loop and between tasks?

A first task computes the list and publishes it with dbutils.jobs.taskValues.set(key="tables", value=json_array). The For Each task takes {{tasks.fetch.values.tables}} as its inputs; the inner task receives each element as {{input}} and maps it to a parameter. Set concurrency to run iterations in parallel.

What failure-handling tools does a job give you?

Per-task retries (count, interval, retry on timeout), timeouts, run-if conditions (all succeeded, at least one failed, all done and so on) so a cleanup task can run on failure, notifications on start/success/failure/duration, and repair run, which reruns only failed tasks and their dependents, including only the failed iterations of a For Each, without re-running what already succeeded. Do not blindly retry logic bugs.

How would you send an email with a run summary after a pipeline?

Built-in job notifications cover start/success/failure. For a custom summary, a final notebook task reads the audit table for this run id, builds an HTML table of tables loaded, statuses and counts, and sends it via an SMTP/API secret held in a scope. Dashboard subscribers get their own snapshot email on refresh.

Auto Loader and Ingestion

What is Auto Loader and which sources and formats does it support?

An incremental file-ingestion source (cloudFiles) that processes new files as they arrive in cloud storage and remembers which it has done, with no infrastructure to write. Sources: S3, ADLS/Blob, GCS, and volumes. Formats: JSON, CSV, XML, Parquet, Avro, ORC, text, and binaryFile for unstructured files. (§10)

How does it discover new files?

Directory listing mode (default, incremental listing, simple, gets slower with huge directories) or file notification mode (cloud events into a queue, more efficient at scale, needs cloud setup permissions). Progress is tracked in the checkpoint.

Which triggers exist and when do you use each?

availableNow: process everything available, then stop; the usual scheduled incremental batch. processingTime: run micro-batches on an interval continuously for near-real-time. once: single batch, legacy in favor of availableNow.

What are schemaLocation, checkpointLocation and the rescued data column?

cloudFiles.schemaLocation stores the inferred and evolved schema so it persists across runs. The checkpoint stores stream progress (which files were processed) for exactly-once. _rescued_data captures fields that do not match the schema or are malformed, so bad data is kept, not lost or crashing the stream. With no schema provided, columns default to string unless cloudFiles.inferColumnTypes is true; production loads should declare a schema.

Lakeflow Connect vs. a custom JDBC/Auto Loader framework?

Lakeflow Connect: managed connectors for supported sources; you pick tables and load type, and Databricks handles incremental logic, schema drift and CDC with no code. A custom, metadata-driven framework wins when you have hundreds or thousands of tables to onboard by adding metadata rows, unsupported sources, or bespoke logic. (§11)

Lakeflow Declarative Pipelines vs. hand-written Structured Streaming?

Declarative pipelines: you declare tables and queries; the engine handles dependency order, incremental processing, retries, expectations and lineage, plus deployment through bundles. Structured Streaming: full control, but you write and maintain the orchestration, error handling and auditing yourself. Pipelines sit between "managed SQL transformation" and "custom streaming code." (§16)

CI/CD

What are Declarative Automation Bundles (formerly Asset Bundles)?

Infrastructure-as-code for Databricks projects: YAML describing jobs, pipelines, dashboards, notebooks, models and their settings per target environment, deployed with the CLI. They bring source control, review, testing and CI/CD to data and AI assets. Renamed in March 2026; the CLI and configuration are unchanged. (§20)

Walk me through your CI/CD process end to end.

Feature branch from dev; test in a personal development target; pull request reviewed; merge to dev; deploy the bundle to the dev workspace (manually or by GitHub Actions) and run tests; pull request dev to main with required reviewers; merge triggers a GitHub Action that runs the bundle deploy to prod as a service principal. Environments differ by target variables (catalog, cluster sizes, schedules). Hotfix: branch from main, fix, test, merge straight back to main, then back-merge to dev.

Cost and Operations

How do you calculate the exact cost of a job run with SQL?

Join system.billing.usage (filter usage_metadata.job_run_id; rows are per hour with usage_quantity DBUs and sku_name) to system.billing.list_prices on SKU and time, multiply DBUs by pricing.effective_list.default, and sum. Group by job and date for a cost dashboard. Use it before and after an optimization to report time and dollars saved. (§23)

What data-quality features does Databricks provide out of the box?

Pipeline expectations (row-level rules that warn, drop or fail); Lakehouse Monitoring (profile and drift metrics on a table over time); data-quality anomaly detection on schemas (freshness: was the table updated when expected; completeness: did the expected volume arrive in the last 24 hours); data profiling statistics. Layered with job alerts for operational failures.

PII and Semantics

How do you handle PII in the platform?

Lifecycle: minimize, classify (tags and automatic classification), protect per column (salted hash, tokenization, generalization, encryption), control (RBAC, masks, row filters, ABAC), monitor (audit and lineage), delete (DELETE, PURGE, VACUUM and downstream copies). (§06)

Hashing vs. tokenization vs. encryption?

Hashing: irreversible fingerprint, joinable, needs a secret salt for low-entropy values. Tokenization: replace with a random token and keep the mapping in a locked-down vault table, so it is reversible only for authorized users. Encryption: reversible with a key; protects stored values; key management is the hard part.

What is a metric view and why not just use a view?

A Unity Catalog object defining dimensions and measures in YAML, aggregated at query time with MEASURE(). A view fixes the grain and needs one per aggregation; a metric view defines the KPI once and lets every consumer (dashboards, Genie, SQL) slice it any way. (§27)

AI and Consumption

What is Genie, and how do you make a Genie space accurate?

Genie turns natural-language questions into SQL, results and charts over the tables you choose. Accuracy comes from a small curated set of tables with good comments, general instructions, explicit join conditions, SQL expressions (measures/filters/dimensions with synonyms), example queries, and benchmarks with ground-truth SQL to measure accuracy. (§28)

What is Databricks One?

A simplified UI for business users showing only dashboards, Genie spaces and apps, plus a natural-language box, so they need no exposure to the developer workspace. Same Unity Catalog permissions apply.

How do you use AI in development? What are the modes?

Genie Code has chat mode (answers, no execution) and agent mode (plans multi-step work, edits and runs notebooks, builds pipelines, dashboards and jobs, fixes its own errors), with inline edits, slash commands and @ mentions. Customize with workspace and user instructions, skills and MCP servers; review everything and keep destructive statements gated. (§29)

Explain RAG and where the data engineering work is.

Retrieve relevant chunks from a knowledge base, augment the prompt with them, generate a grounded answer. The data-engineering work: parsing and chunking documents, embeddings and a Vector Search index, keeping it in sync (CDF, jobs), exposing tables as narrow UC-function tools, access control and PII, evaluation, tracing and cost. (§30)

Lifecycle, Undercurrents and System Design

What is the data engineering lifecycle, and what are the six undercurrents?

The lifecycle is the path data takes: generation (source systems), ingestion, transformation and serving, with storage underlying all of them. The six undercurrents cut across every stage: security, data management, DataOps, data architecture, orchestration and software engineering. A design is only complete when both the flow and the undercurrents are addressed. (§01)

How do you structure an answer to "design a data platform for X"?

Clarify requirements (consumers, freshness, volume, retention, compliance); walk the lifecycle with a concrete component and reason per stage; sweep the six undercurrents (security, governance and quality, monitoring and deployment, architecture trade-offs, orchestration, engineering practice); then name failure modes and what would make you revisit the design. (§01, §32)

What questions do you ask about a source system before ingesting from it?

Who owns it and how are changes announced; whether data is append-only or mutable; whether there is a reliable change signal or a log; volume and velocity; delivery guarantees (duplicates, ordering); event vs. ingestion time and time zones; how much load it tolerates and whether a replica exists; whether history can be replayed; PII; and schema stability. (§09)

What are the ways to do CDC, and which do you prefer?

Log-based (reads the database log: low impact, captures deletes, preferred), query-based on a timestamp or version column (simple, misses deletes and can miss late commits), trigger-based (adds load to the source) and snapshot diffs (heavy). Prefer log-based, via Lakeflow Connect or Debezium; fall back to watermark pulls from a replica for simple cases. (§09)

How do you get effectively-once results when sources deliver at least once?

Make writes idempotent: MERGE on a business key with a sequence column, replaceWhere for partition overwrites, or dedupe on an event id within a watermark. At-least-once delivery plus an idempotent sink behaves as exactly-once from the consumer's view.

What is a data contract and how do you enforce it?

A versioned agreement between producer and consumers on schema, semantics, quality, freshness, ownership and change policy. Enforce it at ingestion (schema enforcement, rescued data), at write time (expectations), in CI (contract tests when the producer changes) and in production (monitoring), and back it with a named owner and a deprecation process. (§07)

What are data SLIs and SLOs? Give an example.

An SLI is a measurement (freshness, completeness, validity, pipeline success rate, query latency); an SLO is the target agreed with consumers, for example "gold sales is under 6 hours old 99% of the time." The error budget (1% here) governs whether the team ships features or spends time on reliability. Measure freshness from table history or last-altered metadata and alert on breach. (§24)

A pipeline failed at 3 a.m. and a dashboard is wrong. What do you do?

Contain (pause downstream refreshes, flag the table), triage with lineage to the first bad table, fix the cause, recover with repair run, RESTORE or an idempotent backfill from bronze, verify against a control total, communicate to consumers, and hold a blameless postmortem that adds the missing test or alert. (§24)

What does good software engineering look like in a data team?

Logic in modules with pure, unit-tested transformation functions and thin I/O shells; Git with pull requests and review; lint, type checks and tests as CI gates; bundles for project resources and Terraform for platform infrastructure; config instead of hard-coded values; idempotent writes; structured logging with a run id. Notebooks for exploration, not as the unit of production. (§22)

Name principles of good data architecture.

Choose common components wisely; plan for failure; architect for scalability; architecture is leadership; always be architecting; build loosely coupled systems; make reversible decisions; prioritize security; embrace FinOps. Tie each to a concrete choice, such as open formats for reversibility. (§31)

Lambda vs. Kappa: which would you use on Databricks?

Delta tables serve batch and streaming, and declarative pipelines run the same logic incrementally, so a Kappa-like single code path with replay from bronze covers most needs. Use a separate speed layer only when real-time and batch have genuinely different definitions of correctness. (§31)

What is a data mesh and how would you build one on Databricks?

Domain teams own data as products on a self-serve platform, with federated governance. On Databricks: domains as catalogs or schemas, data products as governed tables with owner, contract and SLO, platform templates as bundles and cluster policies, central policies via ABAC and tags, and cross-domain delivery through grants or Delta Sharing. It needs organizational maturity; do not adopt it just for the name. (§31)

What are the pitfalls of reverse ETL?

Non-idempotent writes after partial failure, flooding the target with unchanged records, API rate limits, missing audit trail, sending more personal data than the destination needs, and unclear ownership of the field's meaning. Use keyed upserts, diff against a sync-state table, throttle and resume, log what was sent. (§26)

Airflow or Databricks Jobs?

Jobs when the workflow lives mostly in Databricks (managed, native repair, For Each, lineage). Airflow when you orchestrate many systems or the company already runs it. A common split: Airflow owns the cross-system schedule and calls a Databricks job as a task; Jobs owns the multi-task logic inside the platform. Either way tasks must be idempotent and backfills routine. (§19)

How do you decide between batch and streaming?

Ask what decision depends on the freshness. If minutes-old data changes no decision, run micro-batch or hourly batch, which is cheaper and simpler to operate. Choose continuous streaming only when a latency requirement justifies always-on compute and stateful complexity. Streaming and batch are a continuum on Delta, so start slow and tighten the cadence if the business proves it needs to.

Streaming and Project Deep Dives

Explain Kafka to someone who has only used databases.

A durable, append-only log split into partitions and replicated across brokers. Producers append records; consumers read at their own pace using offsets and can rewind within the retention period. Ordering is guaranteed only within a partition; the record key decides the partition. It decouples producers from consumers and gives replay. (§12)

How does Spark Structured Streaming know where it stopped in Kafka after a restart?

It stores the consumed offsets per partition, plus a write-ahead log of committed batches, in the checkpoint location, not in Kafka consumer-group commits. startingOffsets only applies when there is no checkpoint; a new checkpoint location with earliest reprocesses the entire topic.

Why keep the raw Kafka value in bronze and parse in silver?

Bronze stays lossless and never fails on a schema surprise, so nothing is lost and you can reparse when logic changes. Silver applies an explicit schema, expectations and quarantine. Parsing in bronze couples ingestion to the producer's schema and turns a producer change into a lost-data incident.

Stream-static vs. stream-stream joins: when do you use each?

Stream-static when one side is reference data in a table (customer limits, an active watchlist): stateless, cheap, and the static side is re-read each micro-batch, though earlier records are not corrected retroactively. Stream-stream when two event streams must be correlated in time: it keeps state for both sides, so it needs watermarks on both and an event-time range condition so state can expire. A watchlist is usually reference data, so a stream-stream join is often the wrong tool.

What is a watermark and what does it cost you?

The maximum lateness tolerated for event-time operations, computed from the maximum event time seen minus the delay. It bounds state and lets windows close. The costs: events later than the watermark are dropped from those aggregations, and in append mode a window's result appears only after the window ends plus the watermark, so dashboards lag by that amount. It is a business decision about acceptable lateness versus freshness.

Tumbling vs. sliding vs. session windows?

Tumbling: fixed, non-overlapping (each event in one window). Sliding: fixed size that advances by a smaller slide, so events land in several windows (a 5-minute window sliding every minute counts each event five times). Session: dynamic, closes after an inactivity gap.

Stateless vs. stateful streaming, and why does it matter?

Stateless operations (select, filter, parse, stream-static join) need no memory of past batches and restart trivially. Stateful ones (aggregations, deduplication, stream-stream joins) keep state in a store persisted in the checkpoint, grow with keys unless bounded by watermarks, and can force a new checkpoint when their logic changes. Keep ingestion stateless and confine state to a few monitored gold streams.

How do you avoid sending duplicate alert emails when a micro-batch is retried?

Delivery to the outside world is at-least-once. Give each alert a deterministic id, write alerts to an outbox table, have a notifier record what it sent (or anti-join against a sent table) before or immediately after sending, and suppress repeats per entity per window. For Delta writes from a batch sink use txnVersion and txnAppId so retried writes are skipped.

Availablenow vs. processingTime vs. continuous: how do you choose?

Choose by the freshness requirement. availableNow processes what is there and stops (scheduled incremental loads, tests): cheapest. processingTime runs micro-batches on an interval on an always-on cluster for near-real-time. Continuous mode is experimental sub-second. If minutes are acceptable, scheduled availableNow gives the same code at much lower cost.

How do you monitor a streaming job?

Input rate versus processing rate, offset lag (avgOffsetsBehindLatest), batch duration trend, state rows and memory, and the query status. Run it as a job with restart and alerts, and treat consumer lag as the freshness SLI.

In the metadata-driven framework, why does a For Each need an inner job?

A For Each task can contain only one task. If the per-table work is a sequence (read parameters, load bronze, merge silver), that sequence is a separate job, and the loop's single task is a Run Job task called once per item with the item passed as a parameter. (§19)

Why pass the master job's run id to every child?

So all audit rows, across sources and layers, share one id: one query shows a whole run, the summary email is built from one id, and a retried task can upsert its own audit row on (run id, table id) instead of duplicating it.

Retail project: what is wrong with joining transactions to opportunities on name?

Names are not unique or stable, so repeats fan out into duplicate fact rows and inflate revenue, and typos lose links. Carry the source key through the feed or build a governed mapping table with a uniqueness test, and assert that the fact's row count equals the transaction count. Also design the fact's dimension keys before building gold. (§32)

Walk me through a project you built.

State the problem and stakes in one sentence, the constraints, the architecture by lifecycle stage (with the undercurrents you handled), two or three decisions with alternatives, the hardest problem and its fix, the numbers you measured, and what you would change for production. Say clearly what you extended beyond a tutorial. (§32, "How to Present a Project in an Interview")

35. Glossary

Unity Catalog (UC)
Databricks' governance layer: one namespace, one grant model, lineage, and audit across every workspace attached to a metastore.
Metastore
The top-level UC container, one per region, attached to one or more workspaces.
Managed vs. external table/volume
Managed: Databricks owns the storage path, deleted with the object. External: you own the path, UC only governs access via a storage credential + external location.
Row filter / column mask
A function attached directly to a table that transparently filters rows or redacts a column for every query, based on the querying user.
Auto Loader (cloudFiles)
Databricks' incremental file-ingestion source, built on Structured Streaming, with schema inference/evolution and a rescued-data column for malformed records.
Rescued data column
A JSON string column (_rescued_data) Auto Loader routes unexpected/mistyped fields into instead of failing or silently dropping them.
COPY INTO
A simpler, idempotent, SQL-native bulk load statement that tracks already-loaded files; best for occasional loads rather than continuous high-volume ingestion.
Lakeflow Connect
Databricks' managed connector service for databases (via CDC) and SaaS applications.
Micro-batch
One cycle of Structured Streaming's execution: read new data, process it, write results, checkpoint progress.
Trigger (availableNow / processingTime / continuous)
Controls a streaming query's cadence: process everything available then stop; fire on a fixed interval; or an experimental low-latency continuous mode.
Checkpoint (streaming)
The offsets + write-ahead log a streaming query uses to resume exactly where it left off after a failure, enabling exactly-once processing.
Watermark
The maximum lateness a streaming aggregation tolerates before dropping late data and freeing the associated state.
foreachBatch
A streaming sink that hands each micro-batch to you as a static DataFrame - the standard way to run a streaming MERGE.
_delta_log
The folder of ordered JSON commit files (plus periodic Parquet checkpoints) that is the actual source of truth for a Delta table's state and history.
Optimistic concurrency control
Delta's approach to concurrent writes: attempt the next version number, detect and retry/fail on genuine conflicts, rather than locking.
Deletion vector
A side file marking specific rows as deleted without rewriting their Parquet file - makes row-level DELETE/UPDATE/MERGE far cheaper.
OPTIMIZE
Compacts small files into larger, right-sized ones. Combined with ZORDER BY, also co-locates data for better data skipping.
Z-Ordering
A one-time, OPTIMIZE-triggered physical co-location of rows by column values, to narrow file-level min/max stats for data skipping.
Liquid Clustering
The current-generation replacement for Z-Ordering and much of Hive-style partitioning: declared once, maintained incrementally on every write.
Data skipping
Skipping entire Parquet files at query time because their tracked min/max stats can't match the query's filter.
VACUUM
Permanently deletes data files no longer referenced within the retention window - breaks time travel to versions older than that window.
MERGE INTO
The atomic upsert/delete statement that's the backbone of incremental Delta pipelines; fails if the source has duplicate keys per matched row.
Change Data Feed (CDF)
A per-row change stream (insert/update_preimage/update_postimage/delete) a Delta table can expose so downstream consumers process only what changed.
SCD Type 1 / Type 2
Type 1 overwrites old values (no history). Type 2 keeps every historical version as its own row with validity date ranges.
Lakeflow Declarative Pipelines (DLT)
Declarative ETL: define what each table contains, Databricks handles dependency ordering, incremental processing, and data quality enforcement.
Streaming table / Materialized view / View
The three DLT table types: incremental exactly-once processing; recomputed-on-change aggregation; not persisted at all.
Expectation
A DLT data-quality constraint with a configurable violation action: keep-and-count, drop the row, or fail the whole pipeline update.
APPLY CHANGES INTO / AUTO CDC
DLT's native CDC-to-table mechanism, including out-of-order event handling and SCD Type 1/2, replacing a hand-written MERGE.
Adaptive Query Execution (AQE)
Runtime query re-optimization using real statistics: coalescing shuffle partitions, switching join strategy, splitting skewed partitions.
Broadcast join
Ships the smaller side of a join to every executor, avoiding a shuffle of the larger side entirely.
Data skew / salting
One key holding disproportionately more rows than others, slowing a whole stage; salting spreads a skewed key across synthetic sub-keys to parallelize it.
Spill
Data written to disk mid-shuffle/aggregation because it didn't fit in executor memory - a strong signal of undersized executors or too few partitions.
Photon
Databricks' vectorized native execution engine; a drop-in speedup for eligible operators with no code changes.
Job / Workflow
A DAG of tasks (notebooks, pipelines, SQL, dbt, other jobs) with its own compute, retries, and triggers.
Task values
Small pieces of metadata passed between job tasks (dbutils.jobs.taskValues) - not a substitute for writing real data between tasks.
Declarative Automation Bundles (DABs)
Formerly Databricks Asset Bundles. YAML-defined infrastructure-as-code for jobs, pipelines and more, deployed identically across dev/staging/prod via the CLI - the current standard for Databricks CI/CD.
Service principal
A non-human identity for automation; every production job and CI/CD deploy should run as one, not as a personal account.
System tables
Built-in, queryable Delta tables under the system catalog covering audit, lineage, billing, job runs, and compute utilization.
Lakehouse Monitoring
Automatic statistical profiling and drift detection for a table over time, surfacing silent data-quality regressions.
DBU (Databricks Unit)
Databricks' per-second usage billing metric, layered on top of the underlying cloud VM cost and varying by compute type/tier.

Account / workspace / metastore

Cursor column
The source column (such as an update timestamp) a managed connector uses to find changed rows incrementally.
Run job task / For Each task
A job task that triggers another job, and a task that runs one inner task per list element; combine them to loop over a multi-step sequence.
Run if condition
The rule for when a task runs relative to upstream outcomes: all success, all done, none failed, at least one failed, and so on.
Bus matrix
A grid of business processes (facts) against the dimensions each needs, used to design keys and conformed dimensions before building gold.
