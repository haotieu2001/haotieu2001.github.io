01. What Data Modeling Actually Means

Strip away the jargon and data modeling is one skill: turning a business process into a set of tables that are fast and easy to query for the questions that process raises. Everything else in this guide — star schemas, complex types, SCDs, graphs — is a technique for doing that well at a specific scale or shape of data.

A useful way to picture the raw material you're modeling is a chain of four layers, each answering a different question about the same underlying data:

1. Transactional

Normalized OLTP tables an application writes to directly — one row per real-world event, optimized for fast single-record reads/writes, not analysis.

2. Master data

A consolidated, non-destructive merge of many transactional sources into one trustworthy table per business entity — the layer this guide spends the most time on.

3. OLAP cube

Denormalized, population-level tables shaped for grouping and aggregation — the classic fact/dimension star schema.

4. Metrics

A single number (or a small time series of them) rolled up from the cube — what actually lands on an executive dashboard.

OLTP vs. OLAP: Two Different Jobs

These two live at opposite ends of the chain above, and confusing them is the single most common data-modeling mistake:

OLTP (transactional)OLAP (analytical)
ShapeNormalized (3NF) — minimal redundancyDenormalized — redundancy traded for read speed
Typical query"Fetch this one customer's order""Total revenue by region, last quarter"
Optimized forFast, safe single-row reads/writes; referential integrityScanning and aggregating millions of rows
Who owns itSoftware/backend engineers, application constraintsData engineers, analysts

The master data layer exists precisely because jumping straight from a dozen normalized OLTP tables to an OLAP cube forces every analyst to re-derive the same joins, and re-litigate the same business logic, over and over. A well-built master table (say, a single consolidated view of "everything about a customer" merged from the accounts, billing, and support systems that each hold a piece of it) is what a data engineer builds once so downstream cubes and metrics can be derived from one clean source instead of five raw ones.

Definition Data modeling is the practice of deciding what tables exist, what a row in each one represents (its grain), and how those tables relate to each other — done in service of specific queries, not as an abstract exercise.

02. Dimensions & Knowing Your Data Consumer

Before touching fact tables, it's worth building a precise vocabulary for the "context" columns that describe an entity — and for who's actually going to query the table you're about to build.

Identifier vs. Attribute

Every dimension is made of two kinds of column. An identifier uniquely names an entity (a customer ID, a device ID, a VIN) and never changes. An attribute describes that entity, and attributes split further into two kinds that matter a great deal once you reach slowly changing dimensions:

Fixed attributes

Genuinely immutable facts about an entity — a person's date of birth, the model year a car was manufactured. No history to track; store one value.

Slowly changing attributes

Can legitimately change over the entity's lifetime — a customer's address, a product's price tier, an employee's job title. Whether and how to keep history for these is the entire subject of §07.

Know Your Data Consumer

The "right" shape for a table isn't universal — it depends entirely on who queries it next. Four consumer types show up again and again, and each wants something different:

ConsumerWantsImplication for modeling
Analysts / data scientistsFlat, simple, one-value-per-column tablesFavor exploded, denormalized OLAP-shaped tables; avoid nested types here
Other data engineersComplete, compact, reusable master dataNested types (struct/array/map, §05) are welcome — they know how to unnest them
ML modelsAn identifier plus flat numeric/categorical feature columnsSimilar to analysts, but every feature must already be numeric or encoded
Executives / end customersA chart or a number, never a raw tableThe table itself is invisible to them; it only has to correctly feed a metric or dashboard
Why this matters A table that's "wrong" for analysts (say, one packed with nested arrays) can be exactly right one layer upstream, feeding other engineers who build the flattened version analysts actually query. Ask "who reads this table next, and how" before optimizing its shape.

03. Fact Tables & Dimension Tables

Dimensional modeling (Ralph Kimball's framework, still the industry default) splits a business process into exactly two kinds of table.

Fact table

Records something that happened: an event or transaction. Rows are numeric/measurable and grow constantly — an order, a page view, a payment, a ride.

Dimension table

Describes the context around a fact: who, what, when, where. Rows are relatively stable and much smaller in number — a customer, a product, a date, a store.

Grain: the Single Most Important Decision

The grain of a fact table is a precise statement of what one row represents — "one row per completed order," not "one row per order," which is ambiguous about whether cancelled or in-progress orders appear. Every downstream query, every join, and every aggregation bug traces back to whether the grain was stated precisely and held consistently. Decide the grain first, before adding a single column.

-- Grain: one row per completed order line item
CREATE TABLE fact_order_items (
  order_item_id   BIGINT PRIMARY KEY,
  order_id        BIGINT NOT NULL,
  customer_id     BIGINT NOT NULL,   -- FK to dim_customer
  product_id      BIGINT NOT NULL,   -- FK to dim_product
  store_id        INT NOT NULL,      -- FK to dim_store
  order_date_key  INT NOT NULL,      -- FK to dim_date
  quantity        INT NOT NULL,
  unit_price      DECIMAL(10,2) NOT NULL,
  line_total      DECIMAL(10,2) NOT NULL
);

Four Fact Table Shapes

TypeGrainExample
Transaction factOne row per discrete event, at the moment it happensOne row per order placed
Periodic snapshotOne row per entity per fixed time interval, regardless of activityOne row per account per day, showing its end-of-day balance
Accumulating snapshotOne row per entity, updated in place as it moves through a multi-step processOne row per order, with columns for ordered_at/shipped_at/delivered_at filled in as each milestone happens
Factless factOne row per event with no numeric measure at all — the row's existence is the factOne row per (student, class, date) marking attendance — there's nothing to sum, only rows to count
Interview-relevant detail: factless facts These trip people up because there's no obvious "measure" column. The value is in what you can count or join against: "how many students attended class X" is COUNT(*), and "which students never showed up to a required class" is a join against the roster looking for missing rows — a coverage question a measure-bearing fact table can't easily answer.

Table Relationships

A fact table's foreign keys form the same three relationship types you'd recognize from any relational schema, just with fixed roles: a fact almost always sits on the "many" side.

  • Many-to-one (the common case): many fact_order_items rows reference one dim_customer row.
  • One-to-one: rare between fact and dimension; more common between two dimensions extending each other (a dim_employee row extended by a one-to-one dim_employee_payroll_details).
  • Many-to-many: needs a bridge (associative) table — e.g. students and classes, resolved through an enrollment table that itself often is the factless fact above.

04. Star Schema, Snowflake & One Big Table

Once you have facts and dimensions, three ways to physically arrange them cover almost every real system.

Star schema

One fact table, surrounded directly by denormalized dimension tables. The default choice — fewer joins, easy to reason about, what most BI tools expect.

Snowflake schema

Dimensions are further normalized into sub-dimensions (dim_product splits into dim_product + dim_product_category). Saves storage and centralizes updates, at the cost of extra joins.

One Big Table (OBT)

Facts and dimension attributes are pre-joined and flattened into a single wide table. Fastest to query (zero joins), at the cost of storage, write amplification, and update complexity when a dimension attribute changes.

StarSnowflakeOBT
Query joins neededFewMoreNone
StorageModerateLowest (normalized)Highest (fully denormalized)
Updating a shared attributeOne row in one dimension tableOne row in one sub-dimension tableEvery fact row carrying that attribute
Best fitGeneral-purpose BI/analyticsVery large, slowly-changing reference dimensions shared across many factsA single, well-known, latency-sensitive query pattern (a serving layer, an ML feature table)
Interview angle "Why not just always use OBT?" is a favorite follow-up. The honest answer: OBT trades flexibility for speed on one specific query shape. It duplicates every dimension attribute onto every fact row, so a change to a shared attribute (a product's category, say) means rewriting every historical fact row that referenced it — expensive, and dangerous if that rewrite isn't done atomically. A star schema keeps that as a one-row update in the dimension table. Pick OBT deliberately, for a known serving pattern, not as a default.

05. Complex Data Types: Struct, Array & Map

Modern lakehouse engines (Spark, Snowflake, BigQuery) support nested columns, which opens a middle ground between "fully flat" and "fully compact" that's worth understanding deliberately rather than reaching for by accident.

The Compactness vs. Usability Spectrum

Picture a spectrum with two ends. At the maximally usable end sits a fully flat table — every value in its own plain column, trivial to filter and group on, but verbose and sometimes duplicative. At the maximally compact end sits a single encoded blob column — smallest on disk, but unreadable without decoding logic that only the system that wrote it understands. Struct, array, and map sit in the middle: more compact than fully flat, still queryable with plain SQL.

The Three Nested Types

Struct

A fixed set of named, independently-typed fields — effectively "a table inside a table." Use it to group attributes that always travel together and are known ahead of time.

Array

An ordered list of values (which can themselves be structs). Use it for a variable-length, ordered collection tied to one parent row — a history, a set of tags, a sequence of events.

Map

Homogeneously-typed key/value pairs where the keys aren't known in advance. Most engines cap practical key counts in the tens of thousands per row before performance degrades — it's for genuinely dynamic attributes, not a substitute for a proper schema.

-- A product catalog row using all three nested types deliberately
CREATE TABLE dim_product (
  product_id     BIGINT,
  name           STRING,
  dimensions     STRUCT<length_cm: DOUBLE, width_cm: DOUBLE, height_cm: DOUBLE>,  -- fixed, known fields
  image_urls     ARRAY<STRING>,                                                   -- variable-length, ordered
  custom_attrs   MAP<STRING, STRING>                                              -- seller-defined, unpredictable keys
);
Tie this back to §02 Nested types are usually the wrong shape for analysts (who want flat columns to GROUP BY) and the right shape for a master-data table read by other data engineers, who can explode/unnest what they need. Choosing to nest a column is a statement about who reads the table next.

A Gotcha: Nested Arrays, Joins, and Compression

Columnar formats like Parquet compress a sorted, repetitive column extremely well using run-length encoding — a column of mostly-identical adjacent values collapses to almost nothing on disk. This matters for a specific, easy-to-miss failure mode: imagine a "one row per entity per day" table, sorted by entity, so each entity's rows sit together and compress beautifully. The moment that table goes through a Spark shuffle — any join, any repartition — rows get physically reordered, that sort locality is destroyed, and file size can balloon even though the logical data didn't change.

The practical fix: keep the repeating, per-day values inside an array on one row per entity instead of exploded across many rows. An array survives a join untouched (the join key is still one row per entity), and only gets exploded back into row-per-day form as the very last step, right before whichever downstream consumer needs the flat shape — keeping the expensive, reorder-prone operation as late in the pipeline as possible.

06. Cumulative Table Design

A pattern for building one table that holds the complete history of every entity you've ever seen — active or not — that grows by one day's worth of work each day, forever.

The Pattern

Each day, take yesterday's version of the cumulative table and FULL OUTER JOIN it against today's new activity, keyed on the entity ID. A full outer join is essential, not a stylistic choice: it's the only join type that correctly keeps an entity present in yesterday's table but absent today (inactive, but still part of history) and an entity present today but absent from yesterday's table (brand new).

-- dim_users_cumulated: one row per user, growing by one day each run
INSERT OVERWRITE TABLE dim_users_cumulated
SELECT
  COALESCE(y.user_id, t.user_id)                         AS user_id,
  COALESCE(y.signup_date, t.signup_date)                 AS signup_date,   -- fixed attribute, never re-derived
  CASE
    WHEN y.dates_active IS NULL THEN ARRAY(t.activity_date)                 -- brand new user, seen for the first time
    WHEN t.activity_date IS NOT NULL THEN ARRAY_UNION(y.dates_active, ARRAY(t.activity_date))  -- active today, extend history
    ELSE y.dates_active                                                     -- inactive today, carry history forward unchanged
  END                                                     AS dates_active,
  t.activity_date IS NOT NULL                             AS is_active_today
FROM dim_users_cumulated y
FULL OUTER JOIN daily_user_activity t
  ON y.user_id = t.user_id
WHERE t.activity_date = CURRENT_DATE() OR t.activity_date IS NULL;

Every fixed attribute (§02) is carried forward with a simple COALESCE; every accumulating attribute (the activity-dates array here) gets its own three-way CASE: start it, extend it, or leave it untouched. Once the array exists, expensive historical questions collapse into index lookups instead of scans:

-- "Was this user active at any point in the last 90 days?" - no scan, no GROUP BY
SELECT user_id, EXISTS(dates_active, d -> d >= CURRENT_DATE() - INTERVAL 90 DAYS) AS active_last_90d
FROM dim_users_cumulated;

Why Bother: State-Transition Analysis

Because each row already knows "active today" and carries forward "active yesterday" implicitly (it's just whether the array's second-to-last entry is yesterday's date), classifying every user into new / retained / churned / resurrected for a given day becomes a single self-comparison against the table's own state, instead of a join across two separately-computed daily snapshots.

The Trade-Offs

Pro: cheap historical lookups

"Active in the last N days" and growth-accounting metrics become array operations on one row, not aggregations over N rows.

Pro: nothing is ever lost

An entity that goes inactive still has a row — useful for lifecycle and reactivation analysis that a table only containing "currently active" rows can't support.

Con: inherently sequential

Day N's output depends on day N-1's output. You cannot backfill multiple days in parallel — each day must run after the previous one finishes. This directly threatens idempotency if the chain runs out of order.

Con: deletion is a separate problem

An entity that should be forgotten (a deleted account, a privacy request) doesn't just disappear — it keeps getting carried forward by the COALESCE/CASE logic. Deletion needs its own explicit pruning step run against this table.

07. Slowly Changing Dimensions

A slowly changing dimension (SCD) is any dimension attribute from §02 that can legitimately change value over an entity's lifetime. The question an SCD strategy answers is simple to state and easy to get wrong: when it changes, what happens to the old value?

TypeStrategyKeeps history?Notes
Type 0Never changes; store it onceN/AOnly valid for genuinely fixed attributes (§02) — using Type 0 on something that actually changes silently corrupts data.
Type 1Overwrite in place with the latest valueNoSimplest option, but dangerous for analytics: reprocessing (a backfill) pulls today's value into every historical row, quietly rewriting the past. Reasonable inside OLTP systems; risky as a source for historical reporting.
Type 2 — the default choiceInsert a new row per change, with validity datesFull historyAny historical date maps deterministically to exactly one row, which is what makes it safe to backfill. The current row's end_date is either a far-future sentinel (e.g. 9999-12-31) or NULL — both conventions are common; pick one and apply it consistently.
Type 3Add an "original value" and a "current value" columnOnly 2 valuesOne row, no extra joins — but silently breaks (loses everything before the second change) the moment a value changes a third time. Only safe when a maximum of one change is a guaranteed business rule.
Types 4–7Various hybrids (a separate mini-dimension, a history table alongside a current-state table, combinations of the above)VariesExist for specific high-cardinality or very-high-change-frequency edge cases; worth knowing the names exist, rarely worth implementing from scratch.
A genuine debate worth knowing Not everyone agrees SCDs should exist at all. An alternative school of thought argues for simply taking a full snapshot of every dimension every single day — guaranteed idempotent, trivially simple, at the cost of storing far more rows. SCD Type 2 is the storage-efficient middle ground; daily full snapshots are the simplicity-maximizing alternative. Knowing both positions, and being able to argue the storage/complexity trade-off either way, is a strong interview signal.

In practice, Type 0 and Type 2 cover the overwhelming majority of real analytics needs: Type 0 for what truly never changes, Type 2 for everything that does and where history matters. Reach for Type 1 or Type 3 only when you have a specific, well-understood reason to accept their limitations.

08. Implementing SCD Type 2 in SQL

Two genuinely different strategies exist for building an SCD Type 2 table, and interviewers like probing which one you'd pick and why.

Strategy A: Recompute From Full History

Reprocess every historical row every run, using window functions to detect where a value changed and collapse consecutive unchanged rows into one validity range. Simple to reason about, and the whole table is always internally consistent because it's derived fresh each time.

-- Example: tracking an employee's job_title and department over time
WITH with_previous AS (
  SELECT
    employee_id, effective_date, job_title, department,
    LAG(job_title)   OVER (PARTITION BY employee_id ORDER BY effective_date) AS prev_job_title,
    LAG(department)  OVER (PARTITION BY employee_id ORDER BY effective_date) AS prev_department
  FROM employee_history_snapshots
),
with_change_flag AS (
  SELECT *,
    CASE WHEN job_title  IS DISTINCT FROM prev_job_title
       OR department IS DISTINCT FROM prev_department
    THEN 1 ELSE 0 END AS is_change
  FROM with_previous
),
with_streak AS (
  SELECT *,
    SUM(is_change) OVER (PARTITION BY employee_id ORDER BY effective_date) AS streak_id
  FROM with_change_flag
)
SELECT
  employee_id, job_title, department,
  MIN(effective_date) AS start_date,
  MAX(effective_date) AS end_date
FROM with_streak
GROUP BY employee_id, streak_id, job_title, department;

The streak_id (a running total of the change flag) is the trick: it stays constant across consecutive rows where nothing changed, and increments the moment something does — giving the final GROUP BY exactly the buckets you want to collapse into validity ranges. Note the deliberate use of IS DISTINCT FROM instead of !=: plain inequality comparisons against NULL evaluate to NULL rather than TRUE, which silently fails to flag a change when a value goes from populated to NULL or vice versa. This is the single most common bug in hand-written SCD logic.

Strategy B: Incremental (Yesterday's State + Today's Delta)

Split the table into rows that are already closed (never change again), the one still-open row per entity from the prior run, and today's new data — then only touch entities that appear in today's data, unioning everything else through unchanged.

WITH closed_rows AS (
  SELECT * FROM employee_scd WHERE end_date IS NOT NULL
),
open_rows AS (
  SELECT * FROM employee_scd WHERE end_date IS NULL
),
classified AS (
  SELECT
    o.employee_id, o.job_title AS old_job_title, o.department AS old_department,
    t.job_title AS new_job_title, t.department AS new_department, t.effective_date
  FROM open_rows o
  LEFT JOIN today_snapshot t ON o.employee_id = t.employee_id
)
-- unchanged rows pass through untouched; changed rows emit a closed old row + a new open row;
-- entities with no open row at all are brand new and simply get inserted
SELECT * FROM closed_rows
UNION ALL
SELECT * FROM classified WHERE new_job_title IS NULL  -- no update today: keep the open row as-is
-- ... plus the close-old-row / open-new-row logic for changed entities, and a plain INSERT for new ones

This scans a fraction of the data Strategy A does — only the previously-open row plus today's delta, never the full closed history. The cost: it reintroduces the same "depends on yesterday's output" sequential dependency as cumulative table design, so backfilling multiple days out of order isn't safe.

Which one to pick Strategy A (full recompute) is the right default for dimension-sized data — it's simpler, easier to reason about, and a full rescan is genuinely cheap for anything short of enormous entity counts. Reach for Strategy B (incremental) only once profiling shows the full recompute is actually too slow — a deliberate trade of simplicity for scan cost, not a default.

09. Idempotent Pipeline Design

A pipeline is idempotent if running it twice (or ten times) against the same inputs produces exactly the same output as running it once. This single property is what makes backfills, retries, and reruns safe — and every SCD or cumulative table design choice above should be evaluated against whether it preserves it.

Four Ways Idempotency Breaks

1. Blind append

A plain INSERT INTO with no truncate, overwrite, or merge duplicates every row on a rerun. Prefer MERGE or a partition-scoped INSERT OVERWRITE, which are safe to run any number of times.

2. An unbounded date filter

WHERE event_date > '2026-01-01' with no upper bound returns a different row set depending on when you run it, not just what date you're processing. Always bound both ends of the window explicitly.

3. Missing partition sensors

Starting a job before every upstream partition it depends on has actually landed means an early, incomplete run and a later, complete backfill silently disagree. Gate the job on an explicit check that all required upstream partitions exist.

4. A "depends on yesterday" chain

Cumulative tables (§06) and incremental SCDs (§08) are inherently sequential. Running days out of order, or skipping a day, corrupts every day after it. If you need parallel backfills, this is the price you're paying for the cheaper incremental design.

A cautionary pattern worth internalizing A common, well-documented failure mode at companies running large growth-analytics pipelines: a job reads "whatever the latest partition happens to be" from an upstream table instead of a fixed, dated partition. In production this is a bug waiting to happen — two runs on two different days silently see two different inputs, state-transition metrics stop reconciling, and by the time anyone notices, the root cause is buried under weeks of already-corrupted downstream history. The fix is structural, not a one-off patch: pipelines should be pure functions of an explicit, fixed set of dated input partitions. (The one defensible exception: intentionally reading the latest state of a properly-modeled SCD table during a backfill, where "latest" is itself the correct, well-defined input.)

Why Unit Tests Don't Catch This

Idempotency bugs are almost invisible to conventional unit tests, because a unit test runs a pipeline exactly once against a fixed fixture and checks the output — which is precisely the case where a non-idempotent pipeline still produces a correct-looking result. The bug only appears on the second run, or on a run at a different wall-clock time, or during a backfill — none of which a typical single-execution test exercises. Treat "does this produce the same output if I run it twice, and if I run it out of calendar order" as its own explicit test, separate from correctness tests.

10. Additive vs. Non-Additive Dimensions

A subtle but very commonly tested modeling bug: pre-aggregating a count by dimension, then summing those sub-counts, silently produces the wrong grand total whenever an entity can hold more than one value of that dimension at once.

The Rule

A dimension is additive (for counting purposes, over some window) exactly when an entity can only ever hold one value of it at a time. If it can hold two or more simultaneously, sub-counts by that dimension will double-count any entity that has more than one value, and summing them overstates the true total.

Worked counter-example Suppose you want "total number of customers, broken down by which support channel they've used: email, chat, or phone." Count customers who used email, count customers who used chat, count customers who used phone, and add the three sub-totals together — the sum will be larger than the true number of distinct customers, because any customer who contacted support through two different channels gets counted once in each bucket. Channel-used is not additive: a customer can hold more than one value of it at once.

Compare that to counting support tickets by channel instead of customers: a single ticket can only ever be associated with exactly one channel, so ticket counts by channel do sum correctly to the total ticket count. The dimension didn't change — what you're counting did. This is the practical test to apply before trusting any pre-aggregated sub-total: "can one entity hold two of these values at the same time?" If yes, don't sum pre-aggregated counts — compute COUNT(DISTINCT entity_id) at the ungrouped grain instead, or design the aggregation to dedupe entities across groups before summing.

SUM-based metrics are usually safe This entire problem is specific to counting entities. A metric like "total revenue by channel" doesn't have it — a single dollar of revenue is attributable to exactly one transaction and one channel, so revenue sub-totals by channel always sum correctly to total revenue. Watch specifically for COUNT and count-based ratios (rates, percentages) built on a dimension where multi-membership is possible.

11. Enums as a Modeling Tool

An enumerated type — a column constrained to a fixed, named set of values — is one of the cheapest, most underused tools in a data engineer's modeling toolkit.

What an Enum Buys You

Free data-quality enforcement

A value outside the allowed set fails to load at all, instead of silently landing as an unrecognized string an analyst has to notice later.

A place to hang metadata

Static, per-value metadata (is this order status a "terminal" state? is this transaction type revenue or cost?) can be attached to the type definition itself — cheaper and more reliable than a broadcast join against a tiny lookup table every query.

Free documentation

The type declaration itself lists every valid value — a form of documentation that can't drift out of sync with the actual data the way a wiki page can.

CREATE TYPE order_status AS ENUM ('placed', 'paid', 'shipped', 'delivered', 'cancelled', 'refunded');

CREATE TABLE fact_orders (
  order_id BIGINT,
  status   order_status,   -- any other value fails to insert
  ...
);

When to Reach for One

A practical rule of thumb: a column is a good enum candidate when its cardinality is small and stable — roughly 50 distinct values or fewer, and not growing on its own. A country column is the standard counter-example: it looks enum-shaped, but new countries/territories occasionally form or rename, and 190+ values is already past where the "documentation" benefit holds up well. Order status, transaction type, and subscription tier are typical good fits.

Enums also make excellent sub-partition columns: partitioning a notification-processing pipeline by channel (sms / email / push), for instance, lets a downstream job enumerate the known, finite set of expected partitions and confirm they've all landed before proceeding — directly supporting the partition-sensor idempotency practice from §09.

12. Modeling Heterogeneous Sources

A recurring integration problem: you need one clean output table fed by dozens of upstream sources that each look slightly different — marketing platforms, payment processors, third-party data feeds. Bolting on a new JOIN and a new set of columns for every new source doesn't scale past a handful.

The Source-Registry Pattern

Centralize the list of known sources as an enum (§11), and pair each enum value with its own small, isolated mapping function that translates that source's raw shape into the shared output schema, plus its own source-specific data-quality checks. Adding source #41 means adding one enum value and one mapping function — the core pipeline logic never changes.

CREATE TYPE marketing_source AS ENUM ('google_ads', 'meta_ads', 'linkedin_ads', 'tiktok_ads', ...);

-- One mapping function per source, isolated and independently testable
CREATE FUNCTION map_google_ads(raw JSON) RETURNS fact_ad_spend_row AS ...;
CREATE FUNCTION map_meta_ads(raw JSON)   RETURNS fact_ad_spend_row AS ...;

-- The pipeline itself just dispatches by source and unions the results
INSERT INTO fact_ad_spend
SELECT map_google_ads(raw) FROM raw_google_ads WHERE load_date = CURRENT_DATE()
UNION ALL
SELECT map_meta_ads(raw)   FROM raw_meta_ads   WHERE load_date = CURRENT_DATE();

This pattern is common wherever a single reporting or unit-economics table has to reconcile many structurally different upstreams — ad platforms, payment processors, expense categories, infrastructure inventories drawn from many internal tools. The value is organizational as much as technical: the enum is a living, enforced list of "every source we currently support," and the pipeline stays self-documenting as it grows.

Flexible Schema via MAP

Sometimes even the shared output schema can't be fully fixed in advance — different sources genuinely carry different optional attributes. A catch-all MAP<STRING, STRING> column (or a raw JSON "other_properties" column) avoids a wide, mostly-NULL, constantly-ALTER TABLE-d table.

The real cost Maps and JSON compress noticeably worse than typed columns, because the "column name" becomes per-row data instead of schema-level metadata that a columnar format can encode once. A table full of maps is often one of the worst-compressing shapes you can choose. Use a catch-all map only for attributes that are genuinely optional and unpredictable — promote anything that turns out to be common across most rows into a proper typed column.

13. Graph Data Modeling

Every technique so far has modeled entities first and relationships as a side effect (a foreign key). Graph modeling flips that: relationships are the point, and the schema is deliberately generic so it can represent almost any kind of connection without a schema change.

When to Reach for a Graph Shape

Reach for graph modeling when the questions you need to answer are fundamentally about connections rather than individual entities: "who is connected to whom, how, and how strongly," "what's the shortest path between these two things," "which entities cluster together." A star schema can technically represent relationships too, but graph modeling makes traversal and relationship-centric queries far more natural, at the cost of being a worse fit for straightforward aggregation.

A Universal Two-Table Schema

Almost any graph can be represented with exactly two tables, deliberately schema-light so new entity and relationship types never require a migration:

-- One row per entity, of any type
CREATE TABLE vertices (
  identifier  STRING,
  vertex_type STRING,   -- an enum (§11): 'person', 'team', 'project', ...
  properties  MAP<STRING, STRING>
);

-- One row per relationship, of any type, in one direction
CREATE TABLE edges (
  subject_identifier STRING,
  subject_type        STRING,
  object_identifier   STRING,
  object_type         STRING,
  edge_type           STRING,   -- an enum: 'works_with', 'manages', 'reports_to', ...
  properties           MAP<STRING, STRING>
);

The mental shift: stop asking "what table does this entity belong in" and start asking "what is this entity connected to, and by what kind of relationship." A person, a team, and a project can all be vertices; "works on," "manages," and "belongs to" can all be edges — the same two tables hold all of it, and a new relationship type is just a new edge_type value, not a new table or column.

Interview angle A strong signal in an interview is naming why you'd reach for this shape over a normal fact/dimension design: it's specifically the queries ("find everyone within two hops of this person," "find all projects two teams have both contributed to") that a relational join chain handles awkwardly and a graph traversal handles naturally. Don't reach for a graph model just because relationships exist — every schema has relationships. Reach for it when traversal, not aggregation, is the dominant access pattern.

14. Worked Example: An Employee Collaboration Graph

Pulling §11–§13 together: given a raw table of project staffing (project_id, employee_id, role, hours_logged), build a graph that answers "who has worked with whom, and how much."

1

Load the vertices

One row per employee, with career-level aggregates computed once and stored as properties rather than recomputed by every downstream query.

INSERT INTO vertices
SELECT
  employee_id AS identifier,
  'employee'  AS vertex_type,
  MAP('total_projects', CAST(COUNT(DISTINCT project_id) AS STRING),
      'total_hours',    CAST(SUM(hours_logged) AS STRING)) AS properties
FROM project_staffing
GROUP BY employee_id;
2

Build the "worked with" edges via a self-join

Two employees are connected whenever they share a project_id. A self-join on the staffing table, excluding an employee pairing with themselves, produces every co-staffing pair — aggregated once per pair rather than once per shared project, so the edge table stays small.

INSERT INTO edges
SELECT
  a.employee_id AS subject_identifier, 'employee' AS subject_type,
  b.employee_id AS object_identifier,  'employee' AS object_type,
  'worked_with' AS edge_type,
  MAP('shared_projects', CAST(COUNT(DISTINCT a.project_id) AS STRING)) AS properties
FROM project_staffing a
JOIN project_staffing b
  ON a.project_id = b.project_id
 AND a.employee_id > b.employee_id   -- keeps one direction only, avoids duplicate mirrored edges
GROUP BY a.employee_id, b.employee_id;
Why >, not != a.employee_id != b.employee_id alone still produces both (A, B) and (B, A) as separate rows — a symmetric relationship stored twice. Requiring one side to be strictly greater than the other keeps exactly one direction per pair, the same trick used to de-duplicate any symmetric self-join.
3

Query the graph

"Who has this person worked with the most, and on how many shared projects?" — a single join against the pre-aggregated edge table, with no need to touch the much larger raw staffing table again.

SELECT
  object_identifier AS coworker_id,
  CAST(properties['shared_projects'] AS INT) AS shared_projects
FROM edges
WHERE edge_type = 'worked_with' AND subject_identifier = 'employee_123'
ORDER BY shared_projects DESC
LIMIT 5;

Note the explicit cast pulling the value back out of the properties map — values stored in a map or JSON column compare and sort as strings unless cast back to their real type, an easy detail to forget.

15. Common Data Modeling Anti-Patterns

A recap, framed as things to actively watch for rather than as new concepts.

16. A Repeatable Interview Framework

Data modeling interview prompts ("design a data model for a ride-hailing app," "design a data model for a video streaming service") look open-ended, but the same four-step approach applies to nearly all of them.

1

Scope the business process

Decide, out loud, how much of the business you're actually modeling. "Ride-hailing" could mean just the ride lifecycle, or it could include payments, driver onboarding, promotions, and support tickets. Naming the boundary first prevents you from either over-scoping (running out of time) or under-scoping (missing what the interviewer actually wants to probe).

2

Ask clarifying questions

The answers materially change the model, so ask before designing: Does a ride support multiple stops or pooled riders? Can a booking be made in advance, or only on-demand? Can a driver operate multiple vehicles? Each answer can flip a relationship from one-to-many to many-to-many, or add a dimension you'd otherwise miss. Treat this step as part of what's being graded, not throat-clearing before the "real" answer.

3

Identify events (facts) and entities (dimensions)

Walk through the business process and sort every noun/verb into one of the two buckets from §03. For ride-hailing: rides, payments, and ratings are events (facts); riders, drivers, and vehicles are entities (dimensions). Say each classification out loud and justify it — this is where interviewers probe whether your dimensional-modeling fundamentals are solid.

4

Enumerate attributes, then stress-test with change

List the columns each table needs, then explicitly ask "what happens to this model if X changes?" — a driver switches vehicles, a rider's phone number updates, a promo code's terms change mid-campaign. Naming which attributes need an SCD strategy (§07) and which are safely fixed is exactly what separates a surface-level answer from one showing real judgment.

What's actually being evaluated Not whether you land on "the" correct schema — there usually isn't one. Interviewers are watching whether you gather requirements before designing, whether your fact/dimension split is sound, whether you handle change (SCDs) correctly, and whether the queries your model would need to answer are actually simple to write against it. Narrate your reasoning, not just your final tables.

Prompts Worth Practicing

The same framework applies whether the prompt is a ride-hailing app, a food-delivery platform, a video-streaming service, cloud file storage, or a social network — practicing across a variety of these builds pattern recognition for which facts/dimensions/SCDs each domain tends to need.

17. Interview Questions & Model Answers

Five representative questions, spanning the breadth of this guide, each with a model answer structured the way you'd actually want to deliver it out loud.

Q1

Design a data model for a ride-hailing app. Walk me through your approach.

Model answer: Start by scoping — "I'll model the core ride lifecycle: requesting, matching, completing, and paying for a ride; I'll leave promotions and support tickets out unless you want them in scope." Then ask clarifying questions: does the platform support pooled rides, scheduled/advance bookings, and can a driver operate more than one vehicle? Assume single-rider, on-demand rides with one vehicle per driver unless told otherwise.

Identify the events and entities: fact_rides (one row per completed ride — a transaction fact) and fact_payments (one row per payment, potentially split from rides to support tips or refunds as separate events) are the facts; dim_rider, dim_driver, dim_vehicle, and dim_date are the dimensions. State the grain explicitly: "one row in fact_rides per completed ride, not per ride request" — rejected or cancelled requests either get their own factless fact table or a status column, depending on whether you need to analyze the funnel.

fact_rides(ride_id, rider_id, driver_id, vehicle_id, pickup_date_key,
           pickup_location, dropoff_location, distance_km, fare_amount, status)
dim_driver(driver_id, name, rating, signup_date, current_vehicle_id)  -- current_vehicle_id: SCD Type 2 if drivers switch vehicles

Close by naming the SCD decision explicitly: a driver's assigned vehicle and a driver's rating both change over time, so dim_driver needs Type 2 history if you ever need to ask "what was this driver's rating at the time of this specific ride" — a detail many candidates miss until prompted.

Q2

What's the difference between a fact table and a dimension table? Give an example of a factless fact table and explain why it's useful.

Model answer: A fact table records something that happened — an event, usually with a numeric measure, growing continuously. A dimension table describes context around that event — who, what, when, where — and is comparatively small and stable. Most fact tables have an obvious measure (an order's dollar amount, a ride's distance), but a factless fact table has none: the row's existence itself is the fact.

Example: an attendance table with grain "one row per (student_id, class_id, date) if and only if that student attended that class that day," with no measure column at all. It answers questions a measure-bearing table can't cleanly express: "how many students attended class X" is a COUNT(*), but "which enrolled students never attended a single session" requires a join against the enrollment dimension looking for students with no matching row — a coverage/absence question that only makes sense because the fact table's grain is "did this happen," not "how much."

Q3

How would you model a customer's shipping address so historical orders always show the address that was correct at the time? Which SCD type, and why?

Model answer: This is a Type 2 slowly changing dimension, not Type 1. If dim_customer simply overwrote the address column in place (Type 1), every past order would silently start showing the customer's current address the moment they moved — which is factually wrong for historical reporting and non-idempotent under a backfill.

CREATE TABLE dim_customer_scd (
  customer_id BIGINT,
  address     STRING,
  start_date  DATE,
  end_date    DATE,      -- NULL, or a far-future sentinel, for the current row
  is_current  BOOLEAN
);

-- fact_orders joins on the address that was valid on the order's own date,
-- not on customer_id alone:
SELECT o.order_id, o.order_date, c.address
FROM fact_orders o
JOIN dim_customer_scd c
  ON o.customer_id = c.customer_id
 AND o.order_date BETWEEN c.start_date AND COALESCE(c.end_date, '9999-12-31');

The join condition is the detail interviewers listen for: joining on customer_id alone would match every historical order to whichever SCD row happens to satisfy the join first, or fail outright with duplicate rows — the date-range join is what makes each historical order deterministically resolve to the one address that was actually correct on that date.

Q4

Why can summing counts across a "breakdown by category" query give the wrong total? Give a concrete example.

Model answer: It happens whenever the category being broken down by isn't additive — that is, whenever a single entity can belong to more than one category at once. Summing pre-aggregated counts then double-counts any entity that belongs to multiple categories.

Concrete example: counting customers by support channel used (email/chat/phone) and adding the three counts together overstates the real number of distinct customers, because a customer who contacted support through two channels gets counted in both buckets. The fix is either COUNT(DISTINCT customer_id) computed once across all channels for the true total, or being explicit that the per-channel counts are "channel touches," not "unique customers," if that's genuinely what's being reported. The general test to apply before trusting any such sub-total: can one entity hold two of these values simultaneously? If yes, the breakdown isn't additive and summing it is unsafe.

Q5

When would you model something as a graph instead of a normal fact/dimension schema? Sketch a schema for "who follows whom" on a social platform.

Model answer: Reach for a graph shape when the dominant access pattern is traversal and relationship structure — "who's connected to whom," "how many hops apart are these two users," "which users form a tight cluster" — rather than aggregation. A follows-relationship is a textbook case: the relationship itself, not any single user's attributes, is what's being queried.

-- vertices: one row per user
vertices(identifier, vertex_type, properties)   -- vertex_type = 'user'

-- edges: one row per follows relationship, directional
edges(subject_identifier, subject_type, object_identifier, object_type, edge_type, properties)
-- edge_type = 'follows'; subject = the follower, object = the user being followed

-- "who does user_42 follow"
SELECT object_identifier FROM edges WHERE edge_type = 'follows' AND subject_identifier = 'user_42';

-- "who follows user_42 back" (mutual follows)
SELECT a.object_identifier
FROM edges a
JOIN edges b ON a.subject_identifier = b.object_identifier AND a.object_identifier = b.subject_identifier
WHERE a.edge_type = 'follows' AND b.edge_type = 'follows' AND a.subject_identifier = 'user_42';

Worth naming explicitly: unlike a follows-relationship modeled as a plain bridge table (which works fine too, for simple one-hop queries), the vertex/edge shape stays uniform as more relationship and entity types are added later — a "blocked," "liked a post from," or "shares a group with" edge is just a new edge_type value, not a schema change.

18. Glossary

Grain
A precise statement of what one row in a table represents. The first decision in any modeling exercise, and the root cause of most downstream bugs when left ambiguous.
OLTP
Online transaction processing — normalized, application-facing tables optimized for fast single-record reads and writes.
OLAP
Online analytical processing — denormalized, population-facing tables optimized for grouping and aggregation across many rows.
Master data
A consolidated, non-destructive merge of many transactional sources into one trustworthy table per business entity, sitting between OLTP and OLAP.
Fact table
Records an event or transaction; numeric/measurable, grows continuously.
Dimension table
Describes context (who/what/when/where) around a fact; comparatively small and stable.
Identifier vs. attribute
An identifier uniquely and permanently names an entity; an attribute describes it and may be fixed or slowly changing.
Transaction / periodic snapshot / accumulating snapshot / factless fact
The four fact table shapes: one row per event; one row per entity per fixed interval; one row per entity updated across a multi-step process; one row per event with no numeric measure.
Star / snowflake schema
A fact table surrounded by denormalized dimensions (star), or by further-normalized sub-dimensions (snowflake).
One Big Table (OBT)
Facts and dimension attributes pre-joined into one flat, wide table — fastest to query, most expensive to update.
Struct / array / map
Nested column types: a fixed heterogeneous bundle of fields; an ordered variable-length list; homogeneous key/value pairs with unpredictable keys.
Cumulative table design
Building a table via a daily full outer join of yesterday's state against today's new data, carrying every entity's complete history forward indefinitely.
Idempotency
The property that running a pipeline any number of times against the same inputs produces identical output — the property every SCD, backfill, and rerun strategy must preserve.
Slowly changing dimension (SCD)
A dimension attribute that can legitimately change over an entity's lifetime, and the strategy chosen for what happens to the old value when it does (Types 0–7).
SCD Type 1 / Type 2 / Type 3
Overwrite in place (no history); insert a new row with validity dates (full history); add an original-value and current-value column (exactly two values, breaks on a third change).
Additive dimension
A dimension where an entity can only ever hold one value at a time, making sub-counts by that dimension safe to sum to a correct grand total.
Enum
A column constrained to a fixed, named set of values — enforces data quality, documents valid values, and can carry static per-value metadata.
Source-registry pattern
Centralizing an enum of known upstream sources paired with one isolated mapping function per source, so integrating a new heterogeneous source doesn't require touching shared pipeline logic.
Vertex / edge
Graph modeling's two universal tables: one row per entity of any type (vertex), and one row per directional relationship of any type between two entities (edge).
