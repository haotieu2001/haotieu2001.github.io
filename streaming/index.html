Real-Time Data & Stream Processing

What a data engineer actually needs to use Apache Kafka and Spark Structured Streaming together: basic-to-intermediate Kafka concepts, the Structured Streaming engine end to end, and how the two wire into one production pipeline feeding a lakehouse. A diagram for almost every idea, and no assumed background.

~45 min read · updated 2026 · scoped for the Data Engineer role, not Kafka platform work

Imagine a bank's mobile app. Every time a customer taps "transfer," something has to record that event immediately, check it for fraud in under a second, update a balance, and eventually land in a report - all while millions of other customers do the same thing at the same time. A normal database that only answers "what is true right now" cannot do this well. You need something built for a constant, never-ending flow of events. That is stream processing.

Two tools show up in almost every real-time data system built today: Apache Kafka, which moves and durably stores the flow of events, and Spark Structured Streaming, which reads that flow and computes answers from it (counts, joins, alerts, aggregates) as the data arrives. This guide covers the parts a data engineer uses day to day - enough Kafka to be dangerous, all of Structured Streaming, and the seam where they meet - and deliberately skips the Kafka platform-engineering material you do not need yet (section 19 lists exactly what and why).

01. The Big Picture: Kafka vs Spark

Two different jobs - a durable buffer, and a processing engine

For decades most data systems worked in batch: data piled up all day, and once a night a job read the whole pile and produced a report for the next morning. Stream processing flips that around - you process each new piece of data the moment it arrives, or within a few seconds of it. It is a spectrum, not a hard line: batch jobs run occasionally and take hours; micro-batch systems (Spark Structured Streaming) collect a small slice of new data every few seconds and process that slice like a tiny batch; true streaming systems process one event at a time, often within milliseconds.

Bounded data vs. unbounded data

Bounded data has a fixed size - a CSV file, a table as it looks right now, last month's sales. You can count its rows exactly. Unbounded data - a stream - never finishes. New events keep arriving for as long as the system producing them runs: every card swipe, every sensor reading, every click. You can never say "that's all of it."

Example: a spreadsheet of last year's transactions is bounded. The live feed of transactions happening right now, forever, is unbounded.

Kafka and Spark Structured Streaming are not competitors - they do two different jobs, and a real pipeline uses both.

The division of labour

Kafka = event streaming platform / durable buffer. It accepts events from many producers, keeps them in order, replicates them so nothing is lost, and lets many independent consumers read (and re-read) them for days or weeks. Kafka does not transform your data; it moves and stores it reliably.

Spark Structured Streaming = distributed stream-processing engine. It reads events out of Kafka (or files), applies DataFrame / SQL logic - filter, parse, join, aggregate, deduplicate - and writes results to a lakehouse table or back to Kafka. It does not store the raw event history; it computes answers from it.

Zoom out and the full picture a data engineer builds looks like this: applications write to Kafka topics; Spark reads those topics and lands raw events in a bronze table; more Spark logic cleans, deduplicates and enriches into silver; aggregates roll up into gold tables that BI and ML read. That end-to-end shape is section 17; everything between here and there is the pieces you need to build it.

❯ Short version

Kafka is the durable, replayable buffer that captures every event in order and never loses it. Spark Structured Streaming is the engine that reads that buffer and turns it into continuously updated answers. You need both, and you need to understand the seam between them.

02. Kafka Fundamentals

Topics, partitions, offsets, retention - the words you actually need

Everything else in Kafka is built from a handful of ideas. Get these right and the rest of the guide follows.

A Kafka record

Every piece of data written to Kafka is a record with four parts: a key (optional - used to decide which partition it lands in and to group related records), a value (the payload - the data you care about), a timestamp, and optional headers (small metadata tags such as a trace ID, kept outside the value).

Example: key = "customer-482", value = { amount: 250000, currency: "VND" } - keeps every event for that customer in one partition, in order.

A topic is a named stream of records - think of it as a named folder events get dropped into, for example a topic called transactions. A topic is split into one or more partitions, and each partition is its own ordered, append-only sequence of records. Kafka only guarantees ordering within a single partition - it makes no promise about order across partitions of the same topic. Each record's position inside its partition is its offset: a simple number starting at 0 that only ever increases.

Partitions are the unit of parallelism and scalability. More partitions means more consumers can read the topic at once (section 03) and more brokers can share the storage. The trade-off: you can always increase a topic's partition count later but never decrease it, and adding partitions changes which partition a given key hashes to, so new records for an existing key can start landing in a different partition than its older records.

A broker is one Kafka server; a group of brokers is a cluster. For safety, each partition is copied to several brokers - the number of copies is the replication factor. One copy is the leader (it handles all reads and writes for that partition); the rest are followers that copy the leader and can take over if its broker fails. A durable default is replication factor 3. You mostly do not run this yourself - a platform team or a managed service (Confluent Cloud, MSK) does - but you should know the words when they come up.

Retention and compaction

Kafka does not keep data forever by default. Retention deletes records from a partition after a fixed time (7 days, say) or once it passes a size limit. While records are retained, any consumer can replay them - re-read from an old offset - which is what makes Kafka a buffer and not just a queue. A second mode, log compaction, keeps only the latest record per key forever, quietly dropping older ones; it suits a "current state" topic (latest address per customer) rather than a full event history.

# create a topic with 3 partitions and replication factor 3
kafka-topics.sh --create --topic orders \
  --partitions 3 --replication-factor 3 \
  --bootstrap-server localhost:9092

# describe it - partition count, leaders, replicas
kafka-topics.sh --describe --topic orders \
  --bootstrap-server localhost:9092

❯ Short version

A topic is a named stream, split into ordered partitions. Order holds only within a partition. Every record has an offset. Partitions set your parallelism ceiling. Retention keeps records around long enough to replay; compaction keeps only the newest per key.

03. Producing & Consuming

Keys and partitions on the write side; consumer groups, offsets and lag on the read side

Producers

A producer is any code that sends records into Kafka. You give it a topic, an optional key, and a value; the client handles serialization, choosing a partition, batching and retries. The one decision that matters most is the key, because it decides the partition: Kafka computes roughly partition = hash(key) % number_of_partitions, so records with the same key always land in the same partition and stay in order relative to each other. No key means Kafka spreads records across partitions to balance load, and you get no cross-record ordering.

producer = KafkaProducer(
    bootstrap_servers="broker1:9092",
    value_serializer=lambda v: json.dumps(v).encode(),
    acks="all",              # wait for leader + in-sync replicas
    enable_idempotence=True, # a retried send is never written twice
)

producer.send(
    "transactions",
    key=b"customer-482",     # same key -> same partition -> stays in order
    value={"amount": 250000, "currency": "VND"},
)
producer.flush()
acksWhat must happen before "sent" comes backTrade-off
acks=0Nothing - fire and forget.Fastest; a record can be silently lost.
acks=1Only the partition leader wrote it.Balanced; lost if the leader dies before followers copy it.
acks=allLeader + enough in-sync replicas (min.insync.replicas) confirmed.Slowest; safe as long as enough replicas got it.

If a send times out the producer retries - which risks a duplicate if the first attempt actually succeeded and only the acknowledgment was lost. Setting enable.idempotence=true fixes this: the broker tags each record with a producer ID and a per-partition sequence number and drops any it has already seen. It costs nothing extra and should always be on. Making a write across multiple partitions atomic needs Kafka transactions, which most data-engineering pipelines can leave to the source system or handle at the Spark sink instead (section 16).

Consumers and consumer groups

A consumer reads records by repeatedly polling for whatever is new. Consumers almost always run in a consumer group: a named set of consumers that split a topic's partitions between them, so within one group each partition is read by exactly one consumer at a time. That is what makes reads parallel and safe at once - and it caps useful parallelism at the partition count (8 partitions keep at most 8 consumers in a group busy). Different consumer groups read the same topic completely independently, each with its own position.

Kafka remembers how far each group has read in each partition as the committed offset, stored in an internal topic. You can auto-commit periodically or commit manually after processing - and the timing decides your delivery guarantee:

Commit timingIf the consumer crashes right after processing but before committingLeans toward
Commit before processingOffset already saved, so on restart the record is skipped - even though it never finished.At-most-once
Commit after processingOffset not saved yet, so on restart the same record is read and processed again.At-least-once

Consumer lag

Lag = (latest offset written to a partition) − (offset the consumer group has committed). It is a count of records already in Kafka that this consumer has not processed yet - the single most useful health number in a streaming pipeline.

Example: partition written up to offset 1000, group's committed offset 940 → lag = 60 records behind.

When a consumer joins or leaves a group, Kafka reassigns partitions - a rebalance - which briefly pauses processing for that group. Modern Kafka rebalances are fast and mostly incremental, so as a data engineer you just need to know they happen (on deploys, crashes, scaling) and that they show up as a short lag spike, not a reason to redesign anything.

❯ Short version

On the write side, the key picks the partition and buys you ordering; turn on idempotence. On the read side, a consumer group splits partitions among its members, tracks a committed offset per partition, and its lag (trend, not value) tells you whether the pipeline is keeping up.

04. Delivery Semantics

At-most-once, at-least-once, exactly-once - and what each really costs

Every streaming system makes some promise about how many times a record can be processed. There are three, and they come straight out of the acks setting and the commit timing from the last section:

GuaranteeWhat can go wrongHow you get it
At-most-onceA record can be silently skipped after a crash - possible data loss.Commit offsets before processing; acks=0 or 1.
At-least-onceA record can be processed more than once (duplicates), but never lost.Commit offsets after processing; acks=all; retries on.
Exactly-onceNothing - if it is configured correctly at every hop. The hard part is making producer, Kafka and the consumer/sink all agree.Idempotent producer + Kafka transactions + read_committed consumers, or an idempotent sink downstream.

In practice a data engineer almost always builds on at-least-once from Kafka and then makes the sink idempotent or transactional, so re-processing the same record produces the same end state instead of a duplicate row. Spark Structured Streaming does the offset bookkeeping for you through checkpoints, so "exactly-once end to end" becomes a property of the whole pipeline rather than a single Kafka setting. That full chain is section 16.

"Exactly-once" is not a checkbox. Turning on idempotence or transactions in one place does not give you exactly-once everywhere. It only holds if the source can replay, the processing is deterministic, and the sink de-duplicates. Drop any one and the pipeline quietly degrades to at-least-once.

05. Reading Kafka from Spark

One readStream, six columns of bytes, and a from_json to turn them into real data

This is the seam the whole guide is about. Spark's Kafka source hands you every record as a fixed set of columns, and the value column is raw bytes - Kafka has no idea whether they are JSON, Avro, or anything else. So the first thing your query does, almost always, is cast those bytes to a string and parse them into typed columns you can filter and aggregate.

Column from the Kafka sourceTypeWhat it is
keybinaryThe record key (the thing that chose the partition). Cast to string if you need it.
valuebinaryThe payload. This is what you parse - the actual event.
topicstringWhich topic the record came from (useful when you subscribe to several).
partitionintWhich partition it came from.
offsetlongIts position in that partition.
timestamptimestampKafka's record timestamp - often not the same as your business event time (section 09).
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# 1. describe the shape of the JSON in the value bytes
schema = StructType([
    StructField("order_id",    StringType()),
    StructField("customer_id", StringType()),
    StructField("amount",      DoubleType()),
    StructField("event_time",  TimestampType()),
])

# 2. read the topic as an unbounded stream
raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker1:9092")
    .option("subscribe", "orders")
    .option("startingOffsets", "latest")   # or "earliest" to backfill
    .load())

# 3. turn value bytes -> string -> typed columns
orders = (raw
    .select(from_json(col("value").cast("string"), schema).alias("o"))
    .select("o.*")
    .filter("amount > 100"))

After step 3, orders is an ordinary streaming DataFrame with order_id, customer_id, amount and event_time columns - every transformation in the rest of this guide operates on something like it. If your team publishes Avro with a Schema Registry instead of JSON, you swap from_json for from_avro and point it at the registry; the shape of the pipeline is identical.

Plan for schema drift. If a producer team renames a field or changes a type, from_json quietly returns nulls rather than failing loudly. Pin an explicit schema (never infer it on a stream), keep the raw value string in your bronze table so you can re-parse later, and alert on a sudden rise in null rates.

06. Structured Streaming & the Micro-Batch Model

Treat the stream as a table that never stops growing - everything else follows from that.

Before any more code, there is exactly one idea to internalize, because every other feature - output modes, watermarks, joins, dedup - is a consequence of it.

The unbounded table

Structured Streaming asks you to picture the incoming stream not as "events flying past" but as a table - ordinary rows and columns, like something you'd query with SQL - except new rows keep getting appended to the bottom of it, forever. It never finishes loading. That is what "unbounded" means.

Example: a Kafka topic of payment events becomes, from Spark's point of view, a table where each new payment is one more row appended at the bottom.

Why does this matter? Because once the stream is a table, you reuse the exact same DataFrame API Spark already uses for batch jobs - filter, groupBy, join, select. A streaming query and a batch query over the same data share almost identical code. The only difference is the two ends: spark.read becomes spark.readStream, and df.write becomes df.writeStream. Everything in between stays the same.

How does Spark turn "an ever-growing table" into something that runs on real machines with finite memory? By default, through micro-batch execution: instead of processing one record the instant it arrives, Spark waits a short moment, grabs whatever new data showed up since the last check, and processes that whole chunk as one small batch job - reusing the exact same query engine that powers regular Spark SQL. Then it repeats. A micro-batch might take 100 milliseconds or 10 seconds; from the outside it looks continuous, but underneath it is a tight loop of small batch jobs.

There is also a continuous mode. Spark ships an experimental continuous processing mode that skips micro-batching and processes records one at a time for true millisecond latency - but it supports a much smaller set of operations (no aggregations, most joins unsupported) and has seen little production use. Over 95% of real Structured Streaming jobs run on micro-batches; treat continuous mode as "the other mode" and move on.

❯ Short version

Think of the stream as a table that keeps growing, write ordinary DataFrame code against it, and let Spark run that code repeatedly as small batch jobs (micro-batches), checkpointing its progress after each one.

A streaming query is just a batch query that Spark happens to run over and over, forever.

One place the pandas comparison breaks down: a Spark DataFrame is not a pandas DataFrame. A pandas DataFrame lives in one machine's memory and every operation runs immediately. A Spark DataFrame describes work that is lazy (nothing runs until you ask for output) and distributed (the real data is split across many machines). The code looks similar; what happens underneath is completely different.

07. Checkpointing

The small folder that turns a fragile query into a recoverable one.

State that lives only in an executor's memory dies when that executor dies. A checkpoint is how Structured Streaming survives that. After every micro-batch, Spark writes a little bookkeeping to a durable location you configure - normally cloud object storage (S3, ADLS, GCS) or HDFS - and two things go in it:

• Offsets - exactly which records from the source (which Kafka offsets, per partition) have already been processed.

• State - a durable copy of any running aggregation / dedup / join state the query is keeping.

If the query crashes - a bug, a cluster failure, a planned redeploy - it reads both from the checkpoint and resumes from exactly that point. It does not reprocess from the beginning, and it does not silently skip data, as long as the source can replay (Kafka can, via offsets).

(orders.writeStream
   .format("delta")
   .option("checkpointLocation", "abfss://lake/_checkpoints/orders-bronze-v1")
   .toTable("bronze.orders"))

Do not reuse or hand-edit a checkpoint across structural changes. The checkpoint's saved state is tied to the exact query shape that wrote it. If you restart with a different aggregation, a new join, or a changed watermark column but point at the same checkpoint folder, recovery can break or produce corrupted results. Version the path (…/orders-bronze-v2) whenever you change the query structurally. Deleting a checkpoint to "start clean" also means re-reading from startingOffsets - fine for a fresh backfill, a data-loss event for a live pipeline.

❯ Short version

Every streaming query needs its own durable checkpointLocation. It stores processed offsets + running state, and it is the entire reason a crashed query can resume correctly. Treat the folder as part of the query's identity: one per query, versioned on structural change, never shared.

08. Output Modes & Triggers

Output mode decides WHAT gets written each micro-batch. Trigger decides WHEN a micro-batch happens.

Two independent knobs on every writeStream, easy to confuse because both affect "when do I see data." Output mode controls which rows of the result table are written to the sink on a given micro-batch. Trigger controls how often a micro-batch happens at all.

Picture a tiny aggregation - SELECT key, COUNT(*) FROM stream GROUP BY key - with keys A, B, C in the result table. On this micro-batch, B's count went 3 → 4, and C appeared for the first time:

• Append - only rows that are brand-new and final get written. The default, and required for plain non-aggregated streams (a filter or map with no groupBy). For windowed aggregations it also works, but only once a watermark (section 09) guarantees a window's result is final.

• Update - only rows whose value changed since the last micro-batch. The natural fit for a continuously updated aggregate - a running count or total per key - where you want the sink to reflect the latest number without resending unchanged rows.

• Complete - the entire result table is rewritten every micro-batch. Only realistic when the result is small (a handful of aggregate groups, a dashboard summary), because its cost scales with the whole table, not just what changed.

Append and unfinished aggregates do not mix. A windowed aggregation in Append mode with no watermark: Spark refuses to start the query. Append can only emit a row once it is sure that row is final, and without a watermark it has no way to know. Fix it in the next section.

Now triggers - how often a micro-batch fires, independent of what gets written:

• Default (unspecified) - the next micro-batch starts the instant the previous one finishes. Lowest latency, but the query is always busy - wasteful if the source is only a trickle most of the time.

• Fixed interval - trigger(processingTime="30 seconds") fires a micro-batch every 30 seconds on the clock, even if the last one finished in 2. Smooths load and cost at the price of a little latency.

• Trigger.AvailableNow - processes everything currently in the source, across as many micro-batches as needed, then stops. The standard way to run a "streaming" job on a schedule (hourly, nightly cron) with incremental, checkpoint-tracked processing and no 24/7 cluster. It replaced the older Trigger.Once, which forced everything into one giant batch that could blow past executor memory.

counts = orders.groupBy("customer_id").count()

(counts.writeStream
   .outputMode("update")                 # only changed rows, per micro-batch
   .trigger(processingTime="30 seconds") # fire on a schedule, not ASAP
   .option("checkpointLocation", "/chk/customer-counts")
   .toTable("gold.customer_counts"))

# same query, run as an incremental "batch" job on a schedule:
(counts.writeStream
   .outputMode("complete")
   .trigger(availableNow=True)           # process the backlog, then stop
   .option("checkpointLocation", "/chk/customer-counts")
   .toTable("gold.customer_counts"))
Output modeWrites each micro-batchTypical use
AppendNew, final rows onlyFilters, maps, watermarked windows
UpdateRows changed this batchRunning counts / totals per key
CompleteThe entire result tableSmall dashboards, few aggregate groups

❯ Short version

Output mode = what rows get written (Append = new only, Update = changed only, Complete = everything). Trigger = when a micro-batch fires (default = ASAP, fixed interval = on a schedule, AvailableNow = catch up then stop).

09. Event-Time & Watermarks

Real data does not arrive in order - a watermark is how Spark decides when to stop waiting for stragglers.

Event-time vs. processing-time

Event-time is when something actually happened in the real world - the moment a customer tapped "pay." Processing-time is when Spark received and started processing that record. In a perfect world they are identical; in real systems they almost never are, and the gap is called skew.

Example: a customer taps "pay" at 10:00:00 (event-time), but their phone is offline and only sends it at 10:04:30 (processing-time) - 4m30s of skew.

Why so often? A phone loses signal, buffers taps locally, and dumps a burst when it reconnects. A network retry delays delivery by seconds. A slow upstream service forwards an event minutes late. None of these are exotic - they are just how distributed systems behave, which is why Structured Streaming handles them first-class. For any time-based logic you should aggregate by the event's own timestamp column, not by current_timestamp().

So if events show up late and out of order, how does Spark ever decide an aggregation window is "done"? That is what a watermark solves.

Watermark

A moving line on the event-time axis: the latest event-time Spark has seen so far, minus a delay threshold you configure. It is tracked once per streaming query - not per key, not per window. Any record whose event-time is older than the current watermark counts as "too late," and for stateful operations Spark may drop it, having already closed that window.

Example: df.withWatermark("event_time", "10 minutes") - "I'll wait up to 10 minutes past the latest event-time I've seen for stragglers. After that, that period is closed."

counts = (orders
    .withWatermark("event_time", "10 minutes")   # allow up to 10 min of lateness
    .groupBy("customer_id")
    .count())

# a record with event_time older than (max event_time seen - 10 min)
# is considered too late and dropped from this aggregation

Bigger threshold (e.g. 24 hours). Catches almost all legitimately late data - good if clients buffer for a long time offline. Cost: results finalize much later, and Spark holds a lot more aggregation state while it waits, since every open window stays open until the watermark passes it.

Smaller threshold (e.g. 2 minutes). Finalizes fast and keeps far less state - cheaper and simpler. Cost: any record more than 2 minutes late gets dropped from aggregations, even a legitimate one.

Look at your data's real lateness distribution before picking a number, and lean slightly generous at first - you can tighten later, but data dropped by too small a watermark is gone for good.

A watermark is not a guarantee no data is late - it is a deadline you set for how long you will wait before moving on.

10. Windowing

Turning an endless stream into time-bounded buckets you can actually aggregate.

In batch, "count orders per customer" is a plain GROUP BY. In streaming the stream never ends, so that count would update forever and never be final. Windowing adds a second grouping key: time. Instead of "count per customer," you compute "count per customer, per 10-minute slice." Each slice is a window, and once the watermark has passed it, Spark treats its result as done.

Two window types cover almost everything a data engineer builds: tumbling and sliding. Both are created inside a normal groupBy; the aggregation (count, sum, avg) inside them is unchanged.

Tumbling window

Fixed-size, non-overlapping. Every event belongs to exactly one window - the timeline sliced into equal back-to-back pieces, no gaps, no overlap.

Example: groupBy(window("event_time", "10 minutes")).count() - one row per 10-minute slice: 10:00-10:10, 10:10-10:20, …

Sliding window

Also fixed-size, but a new window starts more often than the window's own length - the slide is shorter than the size, so windows overlap and one event can fall in several. Useful for smoothed, rolling metrics like "average price over the last 10 minutes, refreshed every 5."

Example: groupBy(window("event_time", "10 minutes", "5 minutes")).avg("price") - the second string is the slide.

Session window - the third kind, briefly

A session window has no fixed size. You configure a gap of allowed quiet time; the session stays open while events for that key keep arriving within the gap, and closes once the gap passes with nothing new. Good for grouping a user's activity into "visits." You will meet it less often than tumbling and sliding; the syntax is session_window("event_time", "30 minutes") inside the groupBy.

# tumbling: one window per event, no overlap
tumbling = (orders.withWatermark("event_time", "5 minutes")
    .groupBy(window("event_time", "10 minutes"))
    .count())

# sliding: windows overlap because slide (5 min) < window size (10 min)
sliding = (orders.withWatermark("event_time", "5 minutes")
    .groupBy(window("event_time", "10 minutes", "5 minutes"))
    .avg("price"))

Windows and watermarks are joined at the hip. A windowed number for, say, 10:00-10:10 is only final once the watermark has passed 10:10. Read it from the sink before then and you may be reading a value that will still change on a later micro-batch (unless you use complete output mode, which recomputes everything).

❯ Short version

Tumbling = fixed, no overlap, one window per event. Sliding = fixed, overlapping, one event can hit several windows. Session = no fixed size, driven by an inactivity gap. All three only become final once the watermark passes the window's end.

~/streaming ❯ spark: remembering things

11. Stateful Processing & State

Which operations need memory, where that memory lives, and why it can grow forever if you let it.

A select or filter processes each row independently and forgets it. A running count, a dedup check, a windowed aggregation, a stream-stream join - these cannot. They need to remember something from earlier micro-batches. That remembered information is state, and any query that keeps it is stateful.

State store

Where that memory physically lives while the query runs. Spark ships two implementations, chosen by config:

• Default (in-memory) - state kept as objects in the executor's memory. Fast, but only practical when total state fits comfortably in RAM.

• RocksDB state store (Spark 3.2+) - state kept in an embedded key-value database on each task's local disk, with a working set in memory. Lets state grow far larger than RAM, at a little extra latency per key. This is the default choice for any non-trivial stateful job.

State in memory or on local disk is not durable by itself - if an executor dies, that copy dies with it. That is why checkpointing (section 07) writes a durable snapshot of the state store after every micro-batch, alongside the offsets. On restart, the query rebuilds its state from that snapshot and resumes.

The other thing to watch is state cleanup. A stateful aggregation with no watermark never knows it is safe to forget an old key, so the state store grows forever and eventually exhausts memory or disk. A watermark gives Spark permission to evict state for windows and keys older than the line. Always set one on a streaming aggregation, even a generous 24-hour one - "generous" beats "none," and "none" means "grow forever."

Fully custom per-key logic exists too. When your rule does not fit a built-in aggregate, Structured Streaming offers arbitrary stateful processing - mapGroupsWithState / flatMapGroupsWithState (and the newer transformWithState), where you write the per-key "read old state, compute new state, emit rows" function yourself and set a timeout so idle keys get cleaned up. It is powerful and rarely needed early; reach for it only after windows and simple aggregations genuinely cannot express what you need.

End-to-end exactly-once needs all three legs of the stool. It is a query-wide property, not a switch: (a) a replayable source like Kafka, so you can re-read from an offset after a failure; (b) deterministic processing, so re-running the same input gives the same output; (c) an idempotent or transactional sink, so writing the same result twice does not create duplicates. Drop any one and the pipeline degrades to at-least-once - see section 16.

~/streaming ❯ spark: the same event twice

12. Deduplication

At-least-once sources mean duplicates are normal - here is how to drop them without your state growing forever.

Because Kafka is at-least-once by default (a producer resend after a lost ack, a consumer reprocessing after a crash), the same logical event can show up in your stream more than once - usually with the same business ID:

Structured Streaming has a built-in operator for this:

• dropDuplicates(["event_id"]) - remembers every ID it has ever seen, forever. Correct, but the state store grows without bound - fine only for a bounded backfill, dangerous on a long-running stream.

• withWatermark("event_time", "1 hour").dropDuplicates(["event_id"]) - only remembers IDs within the watermark window, so state stays bounded. The catch: two copies of an event more than an hour apart are not caught.

• dropDuplicatesWithinWatermark(["event_id"]) (Spark 3.5+) - the cleaner form of the same idea: dedups within the watermark's lateness window without needing the duplicates to share an exact event_time.

deduped = (orders
    .withWatermark("event_time", "1 hour")
    .dropDuplicatesWithinWatermark(["order_id"]))   # Spark 3.5+

Streaming dedup is a bounded best-effort, not a guarantee. It only removes duplicates that fall inside the watermark window. A duplicate that arrives days later slips through. For true correctness, pair it with an idempotent sink - a Delta MERGE keyed on order_id inside foreachBatch (section 14) - so even a late duplicate updates the existing row instead of inserting a second one. Dedup in the stream keeps volume down; the sink makes it correct.

❯ Short version

Duplicates are normal with an at-least-once source. Dedup on a business key with dropDuplicatesWithinWatermark so the "seen" state stays bounded by the watermark. Treat it as volume reduction; rely on an idempotent sink for the correctness guarantee.

~/streaming ❯ spark: combining streams

13. Streaming Joins

Joining a stream with a lookup table is the one you will use constantly. Joining two streams is a scheduling problem in disguise.

Structured Streaming supports two very different kinds of join, and the difference decides how you configure the query. The first - stream-static - is the everyday enrichment pattern; learn it well. The second - stream-stream - is rarer and needs more care.

Stream-static join Both / Integration

One side is a streaming DataFrame (unbounded, always growing); the other is an ordinary static/batch DataFrame (bounded, finite). The classic example: enriching a stream of raw transactions with a slow-changing customers or products lookup table. Spark re-reads the static side as needed each micro-batch, but since it is bounded, Spark never buffers it waiting for more data - no watermark is required on either side.

Example: transactionsStream.join(customersStaticDF, "customer_id").

customers = spark.read.format("delta").table("customers")   # bounded, re-read per batch

enriched = orders_stream.join(customers, "customer_id")      # no watermark needed

Stream-stream join

Here both sides are live, unbounded streams - for example matching "order placed" with "payment confirmed." Spark cannot wait forever for a match, or it would buffer unmatched rows forever. So it requires a watermark on both streams plus a time-range condition - "the payment must arrive within 15 minutes of the order" - which tells Spark exactly how long to keep an unmatched row before giving up on it.

Example: orders.join(payments, expr("payments.order_id = orders.order_id AND payment_time BETWEEN order_time AND order_time + interval 15 minutes")).

orders   = orders_stream.withWatermark("order_time", "20 minutes")
payments = payments_stream.withWatermark("payment_time", "20 minutes")

matched = orders.join(
    payments,
    expr("""
        payments.order_id = orders.order_id AND
        payment_time BETWEEN order_time AND order_time + interval 15 minutes
    """),
    "leftOuter"   # unmatched orders still emitted (null payment) once watermark clears them
)

The join type decides what happens to a row that never matches inside that window:

• Inner - an unmatched row is simply never emitted.

• Outer (left / right / full) - an unmatched row is eventually emitted with nulls for the missing side, but only once the watermark has advanced far enough that no late match can still arrive.

No watermark, no stream-stream join. Without watermarks on both sides and a time-range condition, Spark refuses to run the query (or, in looser configs, buffers state without bound until you run out of disk). The time-range condition is the mechanism that tells Spark when it is safe to stop waiting - it is not optional.

14. foreachBatch

When you need batch-style operations on every micro-batch, this is how.

foreachBatch

The sink you reach for when the built-in sinks (Kafka, files, console) cannot do what you need. Instead of writing rows for you, Spark hands you a plain batch DataFrame for each micro-batch, plus its batch_id. Inside that function you can do anything a regular batch Spark job can: write to a relational database over JDBC, run a Delta / Iceberg MERGE (upsert), write to two or three destinations at once, or call an external API.

from delta.tables import DeltaTable

def upsert_batch(batch_df, batch_id):
    # dedup within the batch, then MERGE on the business key
    latest = batch_df.dropDuplicates(["order_id"])
    (DeltaTable.forName(spark, "silver.orders").alias("t")
        .merge(latest.alias("s"), "t.order_id = s.order_id")
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute())

(orders.writeStream
    .foreachBatch(upsert_batch)
    .option("checkpointLocation", "/chk/silver-orders")
    .trigger(processingTime="1 minute")
    .start())

Why it matters: a MERGE keyed on order_id is the standard way to get an idempotent sink. Re-running the exact same micro-batch after a crash produces the same end state instead of double-counting rows - which is the "idempotent sink" leg of end-to-end exactly-once (section 16). It is also how you land silver tables that are deduplicated and updated in place rather than append-only.

Your function can run more than once for the same batch_id. After a failure Spark may re-invoke foreachBatch for a batch it already partly wrote. Make the body idempotent: MERGE on a key, or check whether batch_id was already applied. Also, if you use batch_df more than once in the function, batch_df.persist() first (and unpersist() after) so Spark does not recompute it.

❯ Short version

foreachBatch(fn) hands you each micro-batch as a normal batch DataFrame. Use it for JDBC writes, multi-sink fan-out, and above all a Delta/Iceberg MERGE - the everyday way to build an idempotent, upsert-style silver table. Make the function safe to run twice.

15. Performance & Scaling

If Kafka produces faster than Spark consumes, the backlog grows forever. Here is the chain of levers that fixes it.

Say Kafka receives 100,000 events/sec and your Spark job processes 50,000/sec. The gap does not disappear - it piles up as consumer lag, and the pipeline falls further behind every second. Scaling a streaming pipeline means walking one chain: Kafka partitions set how much parallelism is even possible; Spark's executors and cores set how much of it you actually use; per-batch limits keep each micro-batch a sane size; and the trigger interval has to be longer than the time a batch takes to process.

LeverWhat it doesWhen to reach for it
Kafka partition countHard ceiling on read parallelism - Spark reads at least one task per partition.Sustained lag with executors under-utilised. Increase partitions (you cannot decrease), or set minPartitions on the Kafka source to split partitions across more tasks.
Executors / coresHow many read+process tasks actually run at once.Lag with partitions available but batch duration high and CPU maxed. Add executors, or enable autoscaling.
maxOffsetsPerTriggerCaps how many records one micro-batch pulls from Kafka.After a big backlog: without a cap, the first catch-up batch is enormous and can OOM. Set it so each batch is a size the cluster handles comfortably.
Trigger intervalTime between micro-batches.Must be > the batch's actual processing time. If a batch takes 8s but the trigger is 5s, batches queue up and lag only grows.
State store = RocksDBMoves large aggregation/join/dedup state off-heap to local disk.Stateful jobs where the default in-memory store causes GC pressure or OOM.
 
(spark.readStream.format("kafka")
   .option("subscribe", "orders")
   .option("maxOffsetsPerTrigger", 500_000)   # bound each micro-batch after a backlog
   .option("minPartitions", 64)               # more read tasks than Kafka partitions
   .load())
# and: trigger(processingTime="30 seconds")  with  batch duration comfortably under 30s

What to watch. Two numbers tell you almost everything: consumer lag trend (flat or falling = healthy; steadily rising = under-provisioned), and batch duration vs trigger interval (batch time should sit well under the interval, with headroom for spikes). Both are on the Spark Structured Streaming UI and in the StreamingQueryListener metrics.

16. Exactly-Once & Fault Tolerance

Not a Spark setting - a chain of guarantees that all have to hold at once.

When people say a Kafka → Spark → Delta pipeline is "exactly-once," they mean four separate guarantees, each covered earlier, holding at the same time. Break it into the hops and it stops being mysterious:

• Hop 1 - the producer is idempotent (a retried send never double-writes) or wrapped in a Kafka transaction.

• Hop 2 - the Kafka log is durable and replicated: once enough in-sync replicas acknowledge a write, it survives a broker crash.

• Hop 3 - the Spark checkpoint records the exact offsets processed in every micro-batch, so a restarted query resumes from precisely where it stopped - never re-reading or skipping.

• Hop 4 - the sink is itself idempotent or transactional. The common pattern is a Delta MERGE inside foreachBatch, keyed so re-running the same micro-batch produces the same end state instead of double-counting.

So why does the pipeline recover from a failure? A crash (bad node, OOM, redeploy) stops the query mid-batch. On restart Spark reads its checkpoint: the offsets say "you got through Kafka offset 8,340 on partition 2," and the state snapshot restores the running aggregations. Spark re-requests from offset 8,341 onward - Kafka still has those records because retention has not expired - and re-runs the last, possibly-incomplete micro-batch. That re-run can write some rows a second time, which is at-least-once - and the idempotent sink (the MERGE) absorbs the repeat so the final table is correct. That is how duplicates are handled: not by preventing every re-process, but by making a re-process harmless.

Exactly-once is a chain, and a chain is only as strong as its weakest link - one hop that is merely at-least-once turns the whole pipeline into at-least-once.

❯ Short version

Recovery works because the checkpoint stores exact offsets + state, Kafka can replay from those offsets, and the sink is idempotent. Between restarts you get at-least-once; the idempotent sink (typically a keyed Delta MERGE) turns that into effectively exactly-once. If any hop is not safe, the whole pipeline is at-least-once.

17. Putting It Together: the Reference Architecture

Everything so far, wired into one real pipeline you could actually design and explain.

In production, Kafka and Spark Structured Streaming are almost always used together, with a lakehouse table format (Delta Lake or Apache Iceberg) on the far end. Here is the shape of a typical real-time pipeline as five steps:

• 1. Produce - apps and services (a checkout service, a mobile event tracker, a sensor gateway) write events into Kafka topics as they happen, keyed so related events stay ordered.

• 2. Read - a Spark Structured Streaming job opens a readStream on those topics and deserializes the value bytes into typed columns.

• 3. Transform - it cleans, filters, deduplicates and enriches each micro-batch. A common enrichment is a stream-static join against a small, slow-changing reference table.

• 4. Write - it lands results somewhere durable via writeStream / foreachBatch: a Delta/Iceberg table, or back into another Kafka topic for downstream consumers.

• 5. Serve - BI dashboards, ad-hoc SQL and ML models read the lakehouse tables, seconds to hours behind the original event depending on tuning.

Bronze tables hold events almost exactly as Kafka delivered them (just enough parsing to make them queryable, plus the raw value string for re-parsing). Silver tables hold cleaned, deduplicated, enriched versions - this is where a foreachBatch MERGE and a stream-static join earn their keep. Gold tables hold business-level aggregates that are cheap for a dashboard to query. Not every pipeline needs all three, but it is a useful default shape. Exactly-once across all these hops is section 16.

One more pattern: fan-out. A single Kafka topic can be read independently by any number of consumer groups, each for a different purpose, none affecting the others. The same orders topic might feed a fraud-scoring Spark job and, separately, a plain archival job copying raw events into bronze - two independent consumer groups, two independent jobs, one topic.

Worked example: the card-swipe fraud check from the intro

Roughly how the concepts combine to build "score a card swipe in under a second": (1) a payments service produces one event per swipe to a card-swipes topic, keyed by account_id (§03) so every swipe for an account lands in order in one partition; (2) Spark reads and parses that topic (§05); (3) a stream-static join (§13) checks each swipe against a slow-changing blocklist of known-bad merchants; (4) in parallel, a windowed aggregation (§10) with a short watermark (§09) keeps a rolling count of swipes per account over the last few minutes, to catch "10 swipes in 2 minutes"; (5) both signals feed a rule inside foreachBatch (§14) that writes any flagged swipe to an alerts topic and a Delta table; (6) a downstream service consumes alerts and blocks the transaction. Nothing new - just §03, §05, §09, §10, §13 and §14 combined.

swipes = (spark.readStream.format("kafka")
    .option("subscribe", "card-swipes").load()
    .select(from_json(col("value").cast("string"), swipe_schema).alias("s")).select("s.*")
    .withWatermark("event_time", "2 minutes"))

blocklist = spark.read.format("delta").table("known_bad_merchants")   # static, §13
flagged_by_merchant = swipes.join(blocklist, "merchant_id")           # stream-static join

rolling_counts = (swipes.groupBy("account_id", window("event_time", "2 minutes"))
    .count())                                                         # windowed aggregation, §10

def write_alerts(batch_df, batch_id):
    risky = batch_df.filter("count >= 10")
    (risky.write.format("delta").mode("append").saveAsTable("alerts"))

(rolling_counts.writeStream
    .foreachBatch(write_alerts)
    .option("checkpointLocation", "/chk/fraud-alerts")
    .start())

❯ Short version

A real pipeline is: producers → Kafka topics → Spark readStream/transform/writeStream → bronze/silver/gold lakehouse tables → BI/ML. One Kafka topic can safely feed many independent consumers doing different jobs at once. Exactly-once holds only if every hop is individually safe.

18. Common Pitfalls & Best Practices

The mistakes almost everyone makes at least once - so you do not have to.

Most streaming incidents are not exotic bugs - they are a handful of well-known mistakes, easy to avoid once you know they exist. Kafka-side first, then Spark-side, then the habits that prevent most of them.

Kafka Pitfalls

Wrong number of partitions. Too few caps parallelism - 4 partitions means at most 4 consumers in a group ever work at once. Too many adds overhead (file handles, replication traffic, slower leader elections) with no benefit if you never have enough consumers. And you can only increase partition count later, never decrease - so under-provisioning is the easier mistake to fix.

A hot partition from a bad key. Key by a low-cardinality field like country with 80% of traffic from one country, and that one partition (and its one consumer) is overloaded while the rest idle. Key by something high-cardinality and evenly distributed - user_id, order_id.

Ignoring consumer lag until it is an incident. Lag creeps up quietly for hours before anyone notices a stale dashboard - and by then there can be millions of records to catch up on.

Forgetting min.insync.replicas. Without it, acks=all can still land a write on only one replica if the others are briefly down - silently trading away the durability you thought you had.

Unbounded topic retention. No retention limit (or one far too generous) keeps every message forever, and broker disks fill quietly until one day there is no room for anything new.

Spark Pitfalls

Unbounded state from a missing watermark. A stateful aggregation with no watermark never knows it is safe to forget old keys, so its state store grows forever until memory or disk runs out.

Changing what the checkpoint means. Restart a query with a structurally different set of transformations (new aggregation columns, a different join, a changed watermark column) but point it at the same checkpoint folder, and recovery can silently break or produce corrupted results.

A trigger interval that is too aggressive. A 5-second trigger where each micro-batch actually takes 8 seconds means batches queue up faster than they clear and lag only grows.

No plan for schema drift. A producer team renames a field or changes a type without warning; from_json silently returns nulls instead of failing loudly, and garbage flows downstream.

Treating late data as an afterthought. The watermark threshold is a real design decision with real trade-offs, not a default to skip and fix later - skipping it usually means silently dropping or double-processing data.

Best Practices

Default to idempotent producers. There is almost never a reason to leave it off; it prevents duplicate writes from retries at essentially no cost.

Monitor consumer lag from day one. A first-class metric with alerts, not something you look at only after something else broke.

Always set an explicit watermark on streaming aggregations. Even a generous 24 hours beats none, because "none" means "grow forever."

Test the failure/recovery path before production. Kill the job mid-run, restart it, confirm it resumes from checkpoint with no duplicated or missing results. Prove it, do not assume it.

Version your checkpoint location on structural changes. checkpoints/orders-agg-v2/ instead of reusing v1's folder avoids the silent-corruption pitfall entirely.

# a sane default recipe that avoids most of the pitfalls above

# producer config
acks=all
enable.idempotence=true
min.insync.replicas=2          # paired with replication.factor=3 on the topic

# streaming query
(orders.withWatermark("event_time", "24 hours")   # generous default beats "none"
   .writeStream
   .option("checkpointLocation", "checkpoints/orders-agg-v2")   # bump vN on structural change
   .toTable("silver.orders"))

21. Learning Path & Resources

A concrete, hands-on order to actually learn this by doing it.

The concepts click into place much faster once you have seen them on your own laptop. A practical, ordered path - each step builds on the last, and none needs more than a laptop and some free disk space.

• 1. Run a single-node Kafka broker locally in KRaft mode. Create a topic, use the command-line producer and consumer to send and read a few messages, and watch offsets and partitions change.

KAFKA_CLUSTER_ID="$(kafka-storage.sh random-uuid)"
kafka-storage.sh format -t "$KAFKA_CLUSTER_ID" -c config/kraft/server.properties
kafka-server-start.sh config/kraft/server.properties

# in another terminal: create a topic, then produce and consume
kafka-topics.sh --create --topic practice --bootstrap-server localhost:9092
kafka-console-producer.sh --topic practice --bootstrap-server localhost:9092
kafka-console-consumer.sh --topic practice --from-beginning --bootstrap-server localhost:9092

• 2. Write a tiny producer and consumer in whatever language you like, against that broker.

• 3. Start a small Spark Structured Streaming job that reads the same topic and counts records per key, writing to the console sink so you can watch it update.

• 4. Add a tumbling window and a watermark and watch how the results and their timing change.

• 5. Add a stream-static join against a tiny lookup table, then land a silver table with foreachBatch + a Delta MERGE so you see idempotent upserts in action.

• 6. Break it on purpose. Kill the job mid-run, restart it against the same checkpoint, and confirm it resumes with no duplicated or missing rows. This is the single most convincing way to understand checkpoints.

• 7. Once you run one of these in production, go deep on that engine's official docs. Defaults and config names shift with almost every release; no guide can track that faster than the source.

Reference sources. This guide draws on two O'Reilly books - Kafka: The Definitive Guide, 2nd Edition and Learning Spark, 2nd Edition - plus the official docs, which are the place to check exact current syntax and defaults:

• kafka.apache.org - official Kafka documentation and configuration reference.

• spark.apache.org/docs/latest/structured-streaming-programming-guide.html - the official Structured Streaming programming guide, updated every release.

❯ Short version

Run Kafka locally → producer/consumer → simple Spark job → add windowing/watermarks → add a join and a foreachBatch MERGE → kill it and watch it recover → then go deep on the docs for whatever you actually ship.

∎ The takeaway

Kafka and Spark Structured Streaming solve two halves of one problem. Kafka makes sure every event is captured, kept in order, and never lost - the durable, replayable buffer. Spark Structured Streaming turns that endless flow into continuously updated answers - counts, joins, alerts, tables - by treating the stream as a table that never stops growing. Section 17 shows the two combined into one real pipeline, not just how each works alone.

You do not need to memorize everything here. Come back when you hit a real problem: a consumer that keeps rebalancing, a Spark job whose state keeps growing, a watermark dropping data you did not expect. Re-read the section, look at the diagram, and it clicks faster the second time. And when someone hands you a Kafka internals or cluster-ops question, section 19 is your permission slip to say "that is the platform team's job."
