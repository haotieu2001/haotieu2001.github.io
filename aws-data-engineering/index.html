01. Why AWS for Data Engineering

One cloud, a dozen-plus services, and one question that decides which ones you need

AWS never designed one "data engineering product." It grew a family of separate services — storage, compute, warehousing, streaming, orchestration — that compose well together because most were built to read and write the same underlying storage layer: Amazon S3. That one fact makes the rest learnable instead of overwhelming: almost every service in this guide writes data into S3, reads it out of S3, or helps you query, govern, or move data sitting in S3.

The one question that decides your service list

Before reaching for any AWS service, ask: is this data moving (streaming) or sitting still (batch), and does it need to be queried with SQL, transformed with code, or just stored? Batch storage and transformation points toward S3 + Glue. SQL analytics points toward Athena or Redshift. Continuously arriving data points toward Kinesis or MSK. Tying steps together on a schedule or an event points toward Step Functions, Lambda, and EventBridge. Real architecture decisions get made in that order, which is why this guide follows it.

❯ Short version

AWS data engineering isn't one product — it's a family of services composing around a shared storage layer, Amazon S3. Nearly everything else here writes to S3, reads from S3, or helps you query, govern, or move data that lives there. Picking services starts with one question: is the data moving or sitting still, and what do you need to do with it once it lands?

02. AWS Fundamentals for Data Engineers

The baseline every other section in this guide quietly assumes you already have

"The cloud" is not a technology, it's a billing and provisioning model: instead of buying servers and racking them, you rent compute, storage, and managed services by the second or by the gigabyte, and you can request more — or release what you have — in minutes instead of months. That shift, from owned fixed capacity to rented elastic capacity, is why almost everything in this guide is "provision nothing, pay for what runs."

Regions and Availability Zones — and why "regional" vs "global" matters

An AWS Region is an independent geographic area (us-east-1, ap-southeast-1) built from multiple isolated data centers called Availability Zones (AZs) — physically separate enough that one failing doesn't take the others with it, but linked with low enough latency to replicate across them. For a data engineer this is concrete, not academic: an S3 bucket, a Redshift cluster, and a Glue job each live in exactly one Region, data-residency rules (keeping customer data inside a specific country) are enforced at the Region level, and moving data between Regions costs money and adds latency. IAM is the deliberate exception — no Region at all, one set of users, roles, and policies everywhere the account operates.

# The Region segment in an ARN shows which resources are Region-scoped -- and which aren't
arn:aws:redshift:us-east-1:111122223333:cluster:sales-cluster   # regional resource
arn:aws:s3:::yt-pipeline-silver                                # S3: no Region segment
arn:aws:iam::111122223333:role/GlueETLRole                      # IAM: no Region -- it's global

The Shared Responsibility Model: "of the cloud" vs "in the cloud"

AWS secures everything of the cloud — the data centers, the hardware, the hypervisor, and the underlying durability of a service like S3 (the standard claim: 11 nines, from replicating objects across many devices and AZs). You are responsible for everything in the cloud: how you configure it. Concretely — if S3 loses an object to an AWS-side hardware failure, that's AWS's problem, and it essentially never happens. If a bucket is publicly readable because someone left Block Public Access disabled, that's yours. AWS built the switch; flipping it was your decision.

EC2 underneath: why a data engineer should still recognize instance types

Amazon EC2 rents virtual machines by family, sized to a workload shape: general purpose (m, balanced CPU/memory), compute-optimized (c, CPU-heavy transforms), memory-optimized (r, large in-memory joins and aggregations). Glue, Lambda, and Athena hide this completely — you never pick an instance type. Amazon EMR does not: an EMR cluster is a managed fleet of EC2 instances running Spark/Hadoop, so choosing an EMR node type is choosing an EC2 instance type under a different label.

One AWS account rarely means one AWS account

Every AWS account has one all-powerful root user — created with the account, should have MFA, almost never used day-to-day — plus any number of IAM identities for everything else. Real organizations never run everything in one account: AWS Organizations manages many accounts (separate dev, staging and prod, or one per team) under a single consolidated bill and one set of guardrails, so a mistake or a leaked credential in dev can't reach production data.

Picking the wrong Region costs money you won't notice until the bill arrives. Data crossing Regions — an EC2 instance in us-east-1 reading a bucket in ap-southeast-1 — is billed as inter-Region transfer on top of the added latency. Easy to do when a team defaults to whichever Region held their first bucket, without checking where the rest of the pipeline runs.

Almost every service in this guide — S3, Glue, Athena, Lambda — bills on consumption: per GB stored, per DPU-hour, per GB scanned, per millisecond executed. No fixed server sits underneath most of a pipeline racking up cost while idle. That's why AWS's default recommendation for new data workloads is serverless-first: you pay when a pipeline runs, and nights, weekends, and quiet periods cost nothing.

❯ Short version

The cloud is rented, on-demand infrastructure billed by consumption rather than owned. S3 and Redshift are Regional (with AZs inside for resilience); IAM is global. AWS secures the infrastructure "of the cloud"; you secure how you configure it "in the cloud." EC2 quietly underlies EMR, and the six Well-Architected pillars are worth naming even in a pure-data context.

03. AWS Networking for Data Engineers

VPCs, endpoints, and the difference between a free path to S3 and a NAT-Gateway-billed one

Every other section here describes a service that looks "serverless," which tempts you into assuming there's no network to think about. There is: a Glue job with a VPC connection, a Lambda attached to a VPC, an EMR cluster and an Amazon Redshift cluster all run inside a private network you wire yourself. Get it wrong and the job either fails outright or quietly routes traffic — and cost — through the public internet when it didn't need to.

Amazon VPC: your own private slice of the AWS network

A VPC (Virtual Private Cloud) is an isolated network inside one Region, defined by a CIDR block (e.g. 10.0.0.0/16) that sets its total address range. It divides into subnets, each pinned to one AZ and either public (has a route to an Internet Gateway, so resources in it can hold a public IP) or private (no such route). Pipeline compute — a Glue job's VPC connection, an EMR cluster, a VPC-attached Lambda, a Redshift cluster — goes in private subnets almost by default: none of it needs inbound connections from the public internet, and in most environments keeping it unreachable is a security requirement before it's ever a "nice to have."

Internet Gateway vs NAT Gateway — inbound-capable vs outbound-only

An Internet Gateway (IGW) is what makes a subnet "public" — a two-way door: resources with a public IP can be reached from the internet and can reach out to it. A NAT Gateway sits in a public subnet and gives private-subnet resources a one-way door out: a private Lambda calling an external weather API exits through the NAT Gateway, which translates its private IP to the gateway's public one — but nothing on the internet can open a connection back in. Reachable outward, unreachable inward.

A Gateway Endpoint only helps the subnets whose route table you added it to. Adding an S3 Gateway Endpoint doesn't cover every subnet in the VPC automatically — forgetting to associate it with a private subnet's route table is a common reason a Glue job "can't reach S3" while the endpoint exists elsewhere in the same VPC.

Route 53 and CloudFront — light-touch for most data pipelines

Amazon Route 53 is AWS's DNS service; for a data platform the relevant piece is the private hosted zone, which resolves internal names (metastore.internal) only inside a VPC — service discovery between pipeline components without hardcoded IPs. Amazon CloudFront is a CDN caching content at edge locations close to users; a data engineer meets it mainly when caching an embedded Amazon QuickSight dashboard or an API Gateway-fronted data API, so repeat requests don't hit the underlying compute every time.

Connecting many VPCs, and connecting to on-premises

AWS Transit Gateway is a hub-and-spoke router for many VPCs and accounts that would otherwise need a tangle of point-to-point peering — attach each VPC once instead of pairing every VPC with every other directly. AWS Direct Connect is a dedicated private link from an on-premises data center straight into AWS, bypassing the public internet; it's the connection of choice when migrating a large on-premises database or warehouse via AWS DMS, where stable, high bandwidth off the internet matters more than the extra setup cost.

❯ Short version

Pipeline compute (Glue VPC connections, EMR, Lambda-in-VPC, Redshift) lives in private subnets. A NAT Gateway gives it one-way outbound internet; a free Gateway VPC Endpoint gives it a private, no-cost path to S3/DynamoDB that never touches the internet or the NAT Gateway. Security Groups are stateful and resource-level; NACLs are stateless and subnet-level, mostly for explicit deny rules. Transit Gateway connects many VPCs; Direct Connect connects on-premises to AWS over a dedicated line.

04. Amazon S3: The Foundation of Every AWS Data Platform

Object storage, storage classes, and the partitioning scheme that decides how everything downstream performs

Amazon S3 (Simple Storage Service) stores objects — blobs from a 1KB JSON file to a multi-terabyte export — inside buckets, addressed by a key (the full "path" string; S3 has no real folders, the slashes are just characters tools render as a folder tree). Every object also carries a storage class, which is a cost/retrieval-speed dial rather than a different product.

Storage classRetrievalTypical use in a data pipeline
S3 StandardMillisecondsBronze/silver/gold data actively being read by ETL jobs and queries
S3 Intelligent-TieringMilliseconds (auto-moves objects)Default choice when access patterns are unpredictable — no lifecycle rules to hand-tune
S3 Standard-IA / One Zone-IAMilliseconds, cheaper storage, pricier retrievalOlder partitions still queried occasionally (last quarter's data, not last year's)
S3 Glacier Instant/Flexible/Deep ArchiveMilliseconds (Instant); Flexible Retrieval spans minutes (Expedited) to ~12 hours (Bulk); Deep Archive's Bulk tier can take up to 48 hoursCompliance retention, rarely-touched historical archives

Partitioning — the single biggest lever on query cost and speed

A partition is a folder-like grouping baked into the S3 key itself, almost always by date and sometimes one other moderate-cardinality dimension: s3://bucket/table/region=US/date=2026-04-01/hour=12/file.parquet. Athena, Redshift Spectrum, and Glue all use partition values in a query's WHERE clause to skip entire folders of irrelevant data — one day's query against a partitioned table might read a 200MB folder instead of a 2TB table. Get partitioning wrong (too fine, too coarse, or missing) and every downstream query pays for it, every single time it runs.

The classic mistake: partitioning by a column nobody filters on. Partitioning by customer_id when every real query filters by date gives thousands of tiny partitions and zero speedup — the planner still checks every partition's date range. Partition by what your WHERE clauses actually use, almost always date first, and don't add a second column unless a real query pattern needs it.

❯ Short version

S3 stores objects in buckets, addressed by a key; storage classes trade cost against retrieval speed. Partitioning — encoding columns like date or region into the key path — lets engines skip entire folders instead of scanning everything, and is the biggest single lever on query cost and speed. Partition by what your queries actually filter on, not by whatever column feels most "unique."

05. IAM for Data Engineers

The permission model every other service in this guide sits on top of

IAM (Identity and Access Management) isn't a data service, but every other service in this guide checks with it before doing anything — a Glue job can't read from S3, and a Lambda can't write to a Glue table, without an IAM identity that explicitly allows it. Two building blocks up front save hours of "access denied" debugging later.

IAM roles vs. IAM users, and why data pipelines almost never use a "user"

An IAM user represents a person, with long-lived credentials. An IAM role has no long-lived credentials at all: a service (Lambda, Glue, Step Functions) assumes it temporarily, gets short-lived credentials scoped to exactly that role's permissions, and they expire automatically. Every service-to-service permission in a real pipeline should be a role, not a user with an access key hardcoded somewhere — least privilege, with no long-lived secrets lying around.

// A trust policy: WHO is allowed to assume this role (attached to the role itself)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "glue.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}

// A permissions policy: WHAT the role can do once assumed (attached separately)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::yt-data-pipeline-silver-*/*"
  }]
}

Two policies, two different jobs — a common source of confusion. The trust policy answers "who can become this role" (above: the Glue service itself). The permissions policy answers "what can it do once assumed" (read/write specific S3 paths). A role with a perfect permissions policy but the wrong trust policy simply can't be assumed by the service that needs it — and that error ("not authorized to perform sts:AssumeRole") looks nothing like a normal permissions error, which is exactly why it trips people up.

❯ Short version

Service-to-service access should always be an IAM role, assumed temporarily, never a user with a long-lived key. A role has two separate policies: a trust policy (who can assume it) and a permissions policy (what it can do once assumed). Mixing the two up is the most common source of confusing IAM errors.

06. AWS Security & Encryption for Data Platforms: KMS, Secrets Manager & Macie

Encryption at rest and in transit, credential management, and finding PII nobody knew was there

IAM answers "who can call which API." Lake Formation answers "which columns and rows within a table." This section covers a third, easily-skipped layer: how data is protected once it's on disk or moving over a wire, how a job gets credentials without anyone typing a password into a script, and how you'd ever find out the lake already contains raw PII nobody reviewed.

Customer managed vs. AWS managed vs. AWS owned keys — who's actually in control

An AWS owned key is the default, invisible encryption many services apply automatically (plain SSE-S3 on an S3 object): you never see the key, there's no key policy to manage, and no per-object entry in CloudTrail. An AWS managed key (aws/s3, aws/redshift) is created and rotated by AWS inside your account when you turn on default SSE-KMS without naming your own — visible in the console, its usage logged, but its key policy isn't editable. A customer managed key (CMK) is one you create: you own the key policy, choose whether to enable annual rotation, and can grant or deny kms:Decrypt per principal. The trigger for reaching for a CMK is simple — the moment who can decrypt this has to be a decision separate from who has S3 permissions, or compliance requires you to disable or schedule deletion of a key, owned and managed keys can't do it.

 SSE-S3SSE-KMS
Who manages the keyAWS, entirely — invisible to youYou (customer managed key) or AWS (aws/s3 managed key)
Audit trailNone — no per-object decrypt event anywhereEvery Encrypt/Decrypt/GenerateDataKey call logged to CloudTrail, including caller identity
CostFreeSmall per-request charge per KMS API call, plus ~$1/month per customer managed key
When to chooseDefault for most objects — no regulatory need to prove who decrypted whatAn audit trail is required, decrypt access must be controlled separately from S3 permissions, or a key (not the data itself) needs to be revocable

A third option, SSE-C, has AWS encrypt and decrypt with a key you supply on every request and never store — rarely usable in a pipeline, since Athena, Glue, and Redshift Spectrum have no way to attach your key to calls they make on your behalf. In transit, S3 and every AWS API endpoint enforce TLS by default; the pipeline-relevant control is a bucket policy that denies any request where aws:SecureTransport is false, closing off plain HTTP entirely rather than discouraging it.

Secrets Manager — the anti-pattern it exists to eliminate

AWS Secrets Manager stores credentials — database passwords, API keys, OAuth tokens — as versioned values, retrievable at runtime by any principal with secretsmanager:GetSecretValue on that secret, and rotates natively-integrated secrets (RDS, Redshift, DocumentDB) on a schedule via a managed Lambda. The anti-pattern it replaces: a database password typed into a Glue job script argument or a Lambda environment variable. That password now lives in version-control history, in the Glue console's job parameters, and in CloudTrail's StartJobRun request parameters — and it never rotates, so one leak stays valid until someone notices by accident.

# Anti-pattern: password embedded directly in the job -- visible in the script,
# in git history, and to anyone with read access to the job definition
DB_PASSWORD = "Sup3rSecret!"   # never do this

# Fix: fetch the secret at runtime; access is controlled purely by the job's IAM role
import boto3
import json

def get_db_credentials(secret_id):
    client = boto3.client("secretsmanager", region_name="ap-southeast-1")
    resp = client.get_secret_value(SecretId=secret_id)
    return json.loads(resp["SecretString"])   # {"username": "...", "password": "..."}

creds = get_db_credentials("prod/redshift/etl-user")
conn = psycopg2.connect(host=DB_HOST, user=creds["username"], password=creds["password"])

Secrets Manager vs. Systems Manager Parameter Store — a real "which one" distinction

Parameter Store (standard tier) is free and holds arbitrary configuration strings — a table name, a feature flag, an S3 prefix, even a KMS-encrypted SecureString — but has no built-in rotation. Secrets Manager charges per secret per month plus per API call, and exists for native automatic rotation of things that must periodically change. Rule of thumb: a credential that should rotate goes in Secrets Manager; a config value that doesn't need rotation goes in Parameter Store, which is cheaper and simpler.

Amazon Macie — finding PII nobody knew was there

Amazon Macie runs ML-based and pattern-based detection (its "managed data identifiers") over S3 objects to flag sensitive data — national ID numbers, card numbers, financial account numbers, credentials embedded in a file — without anyone opening every file that ever landed in the lake. That matters because a lake ingests from many upstream sources and nobody reviews every column by hand before it arrives. A Macie job produces severity-rated findings, per bucket or per object, which typically feed an EventBridge rule for alerting or a concrete governance action — for example a Lake Formation column-level policy hiding the column Macie just flagged from everyone except a compliance role.

Macie finds; it doesn't fix. It scans only the buckets and accounts you scope a job to, must be re-run or scheduled to catch newly arrived objects, and a finding is a starting point: nothing about it encrypts, masks, restricts, or deletes anything. Someone — or a workflow triggered off the finding — still has to act on it.

❯ Short version

KMS has three key tiers — AWS owned (invisible), AWS managed (visible, not editable), customer managed (full control). An object encrypted with SSE-KMS under a customer managed key needs its role granted kms:Decrypt in the key policy, separately from S3 permissions; missing that grant is a very common real "access denied" bug. Secrets Manager retrieves rotating credentials at runtime instead of hardcoding them; Parameter Store is cheaper for non-rotating config. Macie discovers PII sitting in S3 that nobody reviewed, feeding findings into alerting or a Lake Formation policy fix.

07. AWS Lambda for Data Engineering

The right tool for short, event-driven work — and the wrong one for heavy transforms

AWS Lambda runs a function in response to a trigger — an S3 upload, an API call, a Step Functions task, a schedule — with no server for you to provision or manage. You pay per invocation and per millisecond, and it scales from zero to thousands of concurrent invocations by itself. In a data pipeline Lambda is almost always doing one of three jobs: pulling data from an external API, a small fast transformation, or a quick validation check.

Lambda's real limits — and why they matter for data work specifically

A single invocation has a hard 15-minute maximum runtime and up to 10GB of memory. Deployment package size has two limits depending on packaging: a zip-based deployment caps at roughly 250MB unzipped (code plus layers), dropping to 50MB if you upload the zip through the console rather than via S3; a container image can go to 10GB. None of that troubles "call an API and write JSON to S3" — all of it troubles "run a multi-gigabyte Spark join," which is exactly why heavy transforms belong in Glue or EMR (sections 09, 11), not Lambda. Reaching for Lambda for genuinely large-data transforms is one of the most common early-career AWS data engineering mistakes.

# A minimal ingestion Lambda -- the shape almost every "pull from an API, land in S3" job takes
import json, boto3, urllib.request
from datetime import datetime

s3 = boto3.client("s3")

def lambda_handler(event, context):
    response = urllib.request.urlopen("https://api.example.com/trending?region=US")
    data = json.loads(response.read())

    now = datetime.utcnow()
    key = f"raw_statistics/region=US/date={now:%Y-%m-%d}/hour={now:%H}/data.json"
    s3.put_object(
        Bucket="yt-data-pipeline-bronze-ap-south-1-dev",
        Key=key,
        Body=json.dumps(data),
    )
    return {"status": "success", "records": len(data), "s3_key": key}

Cold starts, briefly. A function that hasn't run recently needs a few hundred milliseconds to a couple of seconds to initialize before your code even starts — a cold start. A pipeline running every few hours doesn't care about a 1-second cold start; it matters for latency-sensitive, user-facing APIs, a different use case from most of what this guide covers.

❯ Short version

Lambda runs short, event-triggered code with no server to manage — ideal for API ingestion, small transforms, and validation checks. Its real limits (15-minute max runtime, 10GB memory cap) mean genuinely heavy data transforms belong in Glue or EMR instead. Triggers (S3 events, EventBridge schedules, Step Functions, SQS) are what actually start a Lambda function in a real pipeline.

08. AWS Glue Data Catalog & Crawlers

S3 has no schema of its own — the Catalog is what gives your files a table structure SQL engines can use

S3 stores files; it has no idea those files are "a table." The Glue Data Catalog is a persistent, central metadata store — for every table, it holds the schema (column names/types), the S3 location, the file format, and the partition scheme. It is not a AWS-Glue-only detail: Athena, Redshift Spectrum, EMR, and Glue ETL jobs all read the same Catalog, which is exactly why defining a table's metadata once, in one place, makes it usable everywhere.

Crawlers — the lazy way to populate the Catalog

A Crawler connects to a data source (an S3 prefix, a JDBC database), inspects a sample of files, infers the schema and partition structure, and writes or updates a table definition in the Catalog — no CREATE TABLE required. Crawlers are convenient for getting started and for sources whose schema genuinely drifts, but they cost real money per run and can infer a schema you wouldn't have chosen by hand: a column that's usually an integer but holds one string value in a rare file becomes a string column for the whole table. Many production teams define Catalog tables explicitly as infrastructure-as-code instead, reserving Crawlers for genuinely evolving or exploratory sources.

❯ Short version

The Glue Data Catalog is the shared metadata store — schema, S3 location, format, partitions — that Athena, Redshift Spectrum, EMR, and Glue ETL all read from: define a table once, use it everywhere. Crawlers auto-populate it by inspecting files, which is convenient but neither free nor always the schema you'd choose by hand; many production tables are defined explicitly as code instead.

09. AWS Glue ETL Jobs

Managed Spark, without managing a cluster

A Glue ETL job is a managed Apache Spark (or plain Python) script AWS runs on infrastructure you never provision or patch — you write the transformation logic, pick how much compute to give it, and Glue handles cluster startup, scaling within the job, and teardown. This is the workhorse for medallion-style bronze→silver→gold transforms in an AWS-native data lake.

DynamicFrame vs. DataFrame — Glue's one real API quirk

Glue's Spark jobs can use a normal Spark DataFrame, but Glue also offers its own DynamicFrame: the same idea, more forgiving about schema inconsistencies across files (a column that's sometimes missing, sometimes a different type) and with helpers for reading straight from a Catalog table. Most real jobs read as a DynamicFrame, convert to a DataFrame immediately for the transformation logic — where the far larger Spark ecosystem is available — and convert back only to write through a Glue-specific sink.

# glue_jobs/bronze_to_silver_statistics.py -- the real shape of a medallion transform
import sys
from awsglue.transforms import *
from awsglue.utils import getResolvedOptions
from awsglue.context import GlueContext
from pyspark.context import SparkContext
from pyspark.sql import functions as F

12. Amazon Athena

Serverless SQL over the Glue Catalog — no cluster, no loading, pay per query

Amazon Athena runs standard SQL (built on Trino/Presto) directly against files sitting in S3, using the Glue Data Catalog for schema and location — nothing to provision, nothing to load, no cluster idling between queries. You pay per query, priced by data actually scanned, which is why storage format and partitioning (section 04) control your Athena bill, not just your query latency.

Two levers that change an Athena bill by 10-100x on the same data

Columnar formats (Parquet, ORC) let Athena read only the columns a query selects instead of every column in every row — SELECT views FROM table against Parquet reads a fraction of what the same query reads against row-oriented CSV/JSON. Partition pruning (section 04) lets Athena skip entire S3 prefixes the WHERE clause can't match. Together they are why the same logical query costs cents against a well-organized table and dollars against a poorly organized one holding identical data.

-- Athena reads the Glue Catalog for schema + partition locations -- no data movement
CREATE EXTERNAL TABLE trending_gold (
  video_id string, title string, views bigint, likes bigint, region string
)
PARTITIONED BY (trending_date string)
STORED AS PARQUET
LOCATION 's3://yt-data-pipeline-gold-ap-south-1-prod/trending_analytics/';

-- Only the matching partition + selected columns are scanned and billed
SELECT video_id, views FROM trending_gold
WHERE trending_date = '2026-04-01' AND region = 'US';

Athena vs. a data warehouse — not a replacement, a different entry point. Athena doesn't load or store data; it queries files you already have in S3. That makes it excellent for ad hoc analysis, one-off investigations, and BI tools pointed straight at S3. A warehouse like Redshift (section 13) still wins for heavy, repeated joins and aggregations at scale, because its storage engine is built and tuned for exactly that, while Athena is bounded by whatever format and layout the underlying S3 files happen to have.

❯ Short version

Athena runs serverless SQL directly against S3 via the Glue Catalog, billed by data scanned. Columnar formats (Parquet/ORC) and partition pruning are the two levers that most directly control cost. It's the natural first tool for ad hoc SQL and BI-over-S3 — reach for Redshift instead once workloads need heavy, repeated, large-scale joins a warehouse engine is built for.

14. AWS Lake Formation

Fine-grained governance on top of the Glue Catalog — column, row, and cell-level access control

IAM (section 05) controls access at the level of an S3 bucket, a Glue table, or an API call. It has no concept of "this analyst can see 8 of a table's 12 columns" or "this role can only see rows where region='US'." AWS Lake Formation sits on top of the Glue Catalog to add exactly that grain: column-level, row-level and — via data filters — cell-level permissions, defined once centrally and enforced consistently across Athena, Redshift Spectrum, EMR, and QuickSight, instead of every consuming service needing its own access-control mechanism.

Why this matters specifically for a regulated data platform

A common real requirement: an analytics team should see aggregated customer metrics but never raw PII columns like national ID or account number, though both live in the same underlying table. With IAM alone you either duplicate the table — a masked copy for analysts, a full copy for compliance, at the cost of extra storage, extra pipelines and drift risk — or write custom application-layer masking everywhere the data gets queried. Lake Formation's column-level permissions and data filters solve it once, centrally, at the Catalog layer: every engine reading the table through Lake Formation sees the same enforced view.

❯ Short version

Lake Formation adds column-, row-, and cell-level access control on top of the Glue Catalog — permissions IAM alone can't express — enforced consistently across Athena, Redshift Spectrum, EMR, and QuickSight. It's the practical answer to "this role should see this table, but not these PII columns," without duplicating data or hand-rolling masking in every consumer.

15. Amazon Kinesis Data Streams

A durable, ordered, replayable buffer for continuously arriving records

Everything so far assumes data already sitting still, in a file. Kinesis Data Streams is for data that isn't: clickstreams, IoT telemetry, application logs, change events — records arriving continuously for one or more consumers to process, often in near-real-time. A stream splits into shards, each an ordered, independently-scalable sequence of records; a partition key on each record decides which shard it lands on, and records sharing a key always land on the same shard, preserving order for that key.

Why "durable and replayable" is the actual point

Records stay available for a configurable retention window — 24 hours by default, up to 365 days — and can be re-read from any point in it by any number of independent consumers, each tracking its own read position. That's the core difference from a simple pub/sub queue: a stream isn't consumed-and-gone, so a second consumer can be added later, or a failed one can rewind and reprocess, without losing or duplicating what already happened upstream.

Firehose is managed, no-code delivery of streaming records into S3, Redshift, or OpenSearch — batching, compressing, and retrying automatically, with an optional Lambda for light in-flight transforms. It complements Kinesis Data Streams rather than replacing it: Streams for custom processing and multiple consumers, Firehose for "just land it reliably."

18. Amazon Managed Service for Apache Flink

Continuous, stateful computation over a stream — the piece Kinesis Data Streams and Firehose don't do

Apache Flink is an open-source stateful stream-processing engine. It doesn't just move records (Kinesis Data Streams) or land them somewhere (Firehose) — it runs a continuous computation that keeps state across many events: a running count, a session window, a join between two streams. Amazon Managed Service for Apache Flink (renamed from Kinesis Data Analytics) runs Flink applications without handing you a cluster to size or patch: AWS runs the compute, checkpoints application state to a durable store so a failed task resumes where it left off instead of from zero, and scales the application's parallelism with load.

Why a Lambda function sitting on a Kinesis stream can't do this

Take "the rolling 5-minute average of views per video," or a fraud check correlating several events across a time window. A single Lambda invocation is stateless and short-lived: it processes one batch and exits, carrying nothing forward except what you manually write out and reload — typically to DynamoDB — on every invocation, which is slow and easy to get subtly wrong (missed windows, double counts on retries). Flink keeps the aggregation state in memory, checkpointed for durability, for the entire life of the window, as a first-class part of how you write the application rather than something you bolt on.

Processing modelPer-record/per-batch, stateless between invocationsContinuous, stateful, windowed computation built into the engine
Good fitSimple transform, filter, or per-record enrichment before landing elsewhereRolling aggregations, session windows, joins across streams, event-pattern detection

Windowed state isn't free or automatically bounded. A window keyed on a high-cardinality field (e.g. a raw user_id with millions of distinct values, kept "forever") grows the checkpointed state size and cost right along with it. Bounding window length and key cardinality deliberately is part of designing the Flink application, not something the managed service does for you.

❯ Short version

Apache Flink is a stateful stream-processing engine: it computes continuously over events rather than just moving or delivering them. Managed Service for Apache Flink removes the cluster, checkpoints state to a durable store, and auto-scales the application. Reach for it over a Kinesis-plus-Lambda consumer when the problem needs a rolling window, a running aggregate, or state correlated across events — something a stateless, short-lived Lambda invocation structurally cannot hold onto.

19. Amazon SQS & SNS

A queue for one consumer to work through at its own pace, and a topic for fanning out to many

Amazon SQS is a message queue: a producer sends a message, exactly one consumer out of however many are polling picks it up and processes it, deleting it when done — a natural fit for "a backlog of work items to get through," decoupling how fast producers send from how fast consumers can process. Amazon SNS is a pub/sub topic: a message published to it is delivered to every subscriber (an SQS queue, a Lambda function, an email address) — a natural fit for "several independent systems all need to react to this same event."

The "SNS fan-out to SQS" pattern. Publish once to an SNS topic, and give each independent consumer its own SQS queue subscribed to that topic. SQS is a queue — one message goes to one consumer, good for work backlogs. 20. Amazon EventBridge

Scheduling a pipeline, and routing events between services, without hand-wiring either

Amazon EventBridge does two related jobs. As a scheduler, a cron or rate expression triggers a target (a Lambda, a Step Functions execution) on a fixed cadence — the most common way a batch pipeline actually starts, replacing a literal cron job on a server nobody wants to maintain. As an event bus, it routes events from AWS services (an S3 upload, a Glue job state change) or custom applications to one or more targets, using rules that match on the event's content — more flexible than wiring services directly together.

Where EventBridge sits relative to the "one Lambda triggers the next" instinct

It's tempting to have a Lambda directly invoke the next Lambda when it finishes. EventBridge — or Step Functions, next section — decouples that: a producer emits an event or runs on a schedule without knowing who consumes it, and rules and targets can be added, removed or changed later without touching the producer's code. For anything beyond a single trigger → single action, that decoupling is what keeps a pipeline's services from becoming invisibly wired together.

❯ Short version

EventBridge schedules pipelines on a cron/rate cadence and routes events between AWS services or custom applications based on rules — the decoupled alternative to hard-wiring one service to directly call the next. It's almost always the first thing in a batch pipeline, and the mechanism behind most "this AWS event triggered that action" behavior.

~/aws-data-eng ❯ the conductor

21. AWS Step Functions

A visual state machine for stitching many services into one reliable, observable pipeline

AWS Step Functions defines a pipeline as a state machine: a sequence and branching structure of states, each usually a Task that invokes another AWS service (a Lambda, a Glue job, an ECS task), with declarative handling for retries, error branching, parallel execution and waiting — instead of hand-coding every one of those concerns inside a monolithic script. It's the piece that turns "several separate AWS services" into "one pipeline with one execution history you can look at."

The state types that show up in almost every real pipeline

Task invokes a service and waits for its result. Wait pauses for a fixed time or until a timestamp — used to pace a step that depends on an upstream async process, like a Glue Crawler or Catalog update, finishing first. Parallel runs branches concurrently and waits for all of them. Choice branches on a prior state's output, commonly right after a data-quality check to route to "continue" or "fail loudly." Retry and Catch attach to any state: Retry re-attempts a failed state automatically with backoff, and Catch routes a failure to a specific error-handling state instead of failing the whole execution silently.

Step Functions vs. orchestrating from inside a Lambda. One Lambda can call several others in sequence, and you can call that "orchestration." What matters in production: Step Functions gives a visual execution history for every run (which state failed, with what input, at what time), declarative retry and catch without try/except sprawl, and the 15-minute Lambda timeout stops applying to the pipeline as a whole — a Step Functions execution can run for up to a year. Any pipeline with more than two or three steps, or one step that can plausibly fail, benefits almost immediately.

❯ Short version

Step Functions defines a pipeline as a visual state machine — Task, Wait, Parallel, Choice, with declarative Retry/Catch — giving every execution a full, inspectable history. It's the standard way to stitch Lambda, Glue, and other AWS services into one reliable, observable pipeline instead of hand-coding orchestration logic inside a single script.

22. Amazon MWAA (Managed Workflows for Apache Airflow)

Orchestration as version-controlled Python DAGs — the choice for teams who already think that way

Amazon MWAA (Managed Workflows for Apache Airflow) is a managed Apache Airflow environment: AWS runs the webserver, scheduler and worker infrastructure, and handles patching and version upgrades on a schedule you control. You author pipelines as DAGs (Directed Acyclic Graphs) — plain Python files — in an S3 bucket MWAA continuously watches; drop a new or changed DAG file in and the scheduler picks it up, with no redeploy step.

The real mental-model difference from Step Functions: code vs. configuration

A Step Functions state machine is a declarative JSON/ASL document: you describe states, and Step Functions calls each AWS service through its own SDK integration. An Airflow DAG is imperative Python: you instantiate Operators — an S3KeySensor that waits for a file, a GlueJobOperator that starts a Glue job, a PythonOperator that runs any callable — as task objects, then wire dependencies with >>. Retries, branching and what runs in parallel live in a file that goes through the same code review and version control as any other application code, rather than in a separate state-machine artifact.

~/aws-data-eng ❯ getting data out of a live database

23. AWS Database Migration Service (DMS)

One-time migration, and ongoing CDC replication, out of operational databases

AWS DMS replicates data from a source database (on-premises, RDS, or another cloud) to a target — often S3, for landing operational data into a data lake. It supports a one-time full load of existing data, and, separately, ongoing CDC (change data capture) replication that reads a database's transaction log and streams every subsequent insert/update/delete to the target continuously, without querying or impacting the source database with repeated polling queries.

Why log-based CDC beats "just run a SELECT on a schedule"

A naive alternative — periodically querying a source table for rows changed since last time — needs a reliable updated_at column (not every table has one), misses deletes entirely (a deleted row simply isn't there to select), and adds repeated read load to a live operational database. DMS's log-based CDC reads the database's own transaction log (binlog/WAL/redo log depending on engine), which captures every change, including deletes, with minimal load on the source — the same fundamental technique this guide's dbt-focused sibling covers in depth (collapsing a change log to current state via ROW_NUMBER() ordered by log sequence number).

❯ Short version

DMS moves data out of operational databases into a target like S3 — a one-time full load, plus ongoing CDC replication read from the source's transaction log, which captures deletes and adds minimal load compared to polling with SELECT. It's the standard bridge from "data trapped in a live application database" to "data available in the lake."

~/aws-data-eng ❯ the databases everything else reads from

24. Amazon RDS & Aurora

The operational relational stores a pipeline pulls from via DMS

Amazon RDS and Amazon Aurora are the two managed relational database services you'll actually find running production workloads, and — with Amazon DynamoDB (see that section) — the databases a real pipeline most often gets data out of rather than building analytics on top of. Everything else in this guide (S3, Glue, Athena, Redshift) assumes data has already arrived from somewhere; RDS and Aurora, reached via AWS DMS (see the DMS section), are frequently that somewhere.

Amazon RDS — a managed engine, not a managed schema-less black box

Amazon RDS runs PostgreSQL, MySQL, MariaDB, SQL Server, or Oracle as a managed service: AWS handles patching, automated backups, and — in a Multi-AZ deployment — synchronous replication to a standby in a second Availability Zone that's promoted automatically if the primary fails. What AWS does not take off your plate: you still pick a specific engine and version, and you still schedule and test its upgrades. In a data pipeline, RDS is almost always cast as the source — the classic operational database an application writes to, that a pipeline reads from later, not a place data gets loaded into for analytics.

Amazon Aurora — same SQL, different storage underneath

Amazon Aurora is AWS's own MySQL- and PostgreSQL-compatible engine: wire-compatible with the open-source engines, but built on a distributed, log-structured storage layer that's decoupled from compute and replicated across 3 Availability Zones by default, instead of one synchronously-mirrored standby. That architecture is why AWS's own published guidance claims significantly higher throughput than standard MySQL/PostgreSQL, and faster failover than a typical Multi-AZ RDS deployment — because a newly-promoted Aurora primary picks up the same shared storage instantly, with no standby storage state that needs rebuilding or catching up first. Treat both of those as AWS-reported figures, not independently reproduced benchmarks — the same caution this guide applies to other AWS-published performance claims. Aurora Serverless v2 is the variant that scales compute capacity up and down automatically instead of running on a fixed instance size, useful for spiky or hard-to-size workloads.

# Aurora exposes two different endpoints for one cluster -- they're not interchangeable
mycluster.cluster-xxxxxx.us-east-1.rds.amazonaws.com      # writer endpoint: app traffic goes here
mycluster.cluster-ro-xxxxxx.us-east-1.rds.amazonaws.com    # reader endpoint: point BI/reporting here

The anti-pattern this guide keeps warning about, applied to RDS/Aurora specifically. Pointing a BI tool or a scheduled batch job straight at a live RDS/Aurora primary for repeated analytical queries competes for the exact compute and I/O the production application needs — a slow analytical scan can visibly slow down the app it's supposed to be a harmless bystander to. An Aurora read replica offloads that read traffic to a separate instance; better still, replicate into the lake/warehouse via DMS's log-based CDC (see the DMS section) — which reads RDS/Aurora's own binlog rather than querying live tables at all — and run analytics there instead of against the OLTP database.

❯ Short version

Amazon RDS is the classic managed relational operational database — pick an engine (PostgreSQL, MySQL, MariaDB, SQL Server, Oracle), get patching, backups and Multi-AZ failover handled, but still manage the engine version yourself. Aurora is AWS's own MySQL/PostgreSQL-compatible engine on different, distributed storage, with AWS claiming higher throughput and faster failover as a result. Both are usually the source a pipeline reads from via DMS's log-based CDC, never a target for repeated live analytical queries — that's what read replicas and the lake/warehouse are for.

25. Amazon CloudWatch

Logs, metrics, and alarms — the observability layer underneath every service in this guide

Amazon CloudWatch collects logs and metrics from nearly every AWS service automatically — a Lambda's print statements, a Glue job's Spark logs, a Step Functions execution's state transitions — and lets you build alarms that fire when a metric crosses a threshold (error count, duration, a custom business metric a pipeline emits itself). For a data pipeline specifically, CloudWatch is usually where you'd notice a job silently stopped running, started taking much longer than usual, or started failing at a higher rate — none of which a pipeline's own success/failure return value necessarily surfaces on its own.

Logs vs. metrics vs. alarms — three layers, not three names for the same thing

Logs are the detailed, textual record of what happened — what you read after something's already gone wrong, to find out why. Metrics are numeric time series (invocation count, duration, error rate) — what you'd graph to see a trend. Alarms watch a metric and act (notify via SNS, trigger a Lambda) when it crosses a threshold — what actually gets a human's attention without them having to go look. A pipeline with only logs, and nobody reading them proactively, is a pipeline that fails silently; alarms are what close that gap.

❯ Short version

CloudWatch is the observability layer under every AWS service — logs for post-incident detail, metrics for trends, alarms for getting notified automatically when something crosses a threshold. A pipeline without alarms wired to at least its failure states and its freshness/latency will fail silently far more often than one with them.

CloudTrail vs. Config — an audit log is not the same thing as a compliance check

AWS CloudTrail records that role X called s3:PutBucketAcl at 2:14am from IP Y — a discrete event log, useful for reconstructing a sequence of actions after the fact. AWS Config instead asks, continuously: is this resource compliant with a rule right now, regardless of which specific API call (or console click) got it there? A managed rule like s3-bucket-public-read-prohibited or encrypted-volumes re-evaluates on every configuration change and can trigger automated remediation via Systems Manager Automation — catching configuration drift that happened by hand in the console, which CloudTrail would technically have a record of but nothing would ever proactively flag.

AWS Systems Manager — Parameter Store and Session Manager

Parameter Store (see the Security & Encryption section) holds cheap, non-rotating configuration values. Session Manager opens a shell into an EC2 instance or EMR cluster node purely through IAM permissions — no SSH key pair, no bastion host, no open inbound port 22 — with every session logged for later review.

Amazon Managed Grafana

Amazon Managed Grafana is a managed Grafana service for dashboarding metrics, often pointed at CloudWatch metrics or a Prometheus-compatible source. It's a lighter-weight complement (or competitor) to QuickSight for ops-style dashboards — cluster health, job latency, queue depth — rather than the business-facing reporting QuickSight (see the QuickSight section) is built for.

AWS Well-Architected Tool

The AWS Well-Architected Tool walks a specific, named workload through a structured review against the six pillars introduced in the Fundamentals section, producing a list of identified risks and improvement items tied to that workload. It's a formal, repeatable review process, not a monitoring service — it doesn't touch running infrastructure, it organizes the review conversation and tracks whether previously flagged risks actually got addressed.

Cost Explorer & Budgets — catching the bill before it arrives

Cost Explorer visualizes and forecasts spend by service, tag, or cost category; AWS Budgets sets a threshold against that spend and alerts proactively (before the bill closes out, not after). The classic data-engineering cost surprise is a runaway Athena query scanning far more data than intended — a missing partition filter turning a few-cent query into one that scans an entire dataset — or an always-on EMR cluster nobody remembered to terminate after a one-off job. A concrete guardrail against the first: cap an Athena workgroup's per-query scan limit, so a bad query fails fast instead of quietly billing for terabytes.

# Cap how much data a single Athena query is allowed to scan before it's stopped --
# catches a missing WHERE clause or a missing partition filter before it becomes a bill
aws athena create-work-group \
  --name "analytics-guarded" \
  --configuration '{
    "BytesScannedCutoffPerQuery": 10737418240,
    "EnforceWorkGroupConfiguration": true
  }'

AWS Data Exchange — buying data instead of building a pipeline to get it

AWS Data Exchange lets you subscribe to third-party datasets directly from AWS Marketplace, with many providers delivering updates straight into an S3 bucket in your own account rather than requiring you to build and maintain an ingestion pipeline against an external API. For data that's genuinely commodity (market reference data, demographic datasets, weather history), this is often a faster and cheaper path than acquiring and maintaining the equivalent pipeline yourself.

AWS Backup — one policy instead of a backup script per service

AWS Backup centralizes backup scheduling, retention, and restore across services that would otherwise each need their own backup mechanism — Amazon EBS volumes (the block storage attached to EC2 and EMR nodes), RDS/Aurora databases, DynamoDB tables, EFS file systems, and more, all governed by one reusable backup plan instead of a different script or console setting per service. For a data platform, this matters most for the stateful pieces that aren't just files sitting in S3 (which already has its own versioning/replication story) — an RDS instance behind DMS, or an EBS-backed EMR cluster's local storage, are the kinds of resources a real backup plan actually needs to cover.

Two pitfalls worth calling out directly. CloudTrail records API activity against AWS — it has no idea what happened inside a running Glue job or what it printed; that's still CloudWatch Logs' job (see the CloudWatch section). And AWS Config is enabled per-region — turning it on in ap-southeast-1 says nothing about resources sitting in us-east-1; a genuinely account-wide compliance view needs Config enabled in every region actually in use, or aggregated across an AWS Organization.

❯ Short version

CloudTrail answers who called which API and when; AWS Config answers whether a resource's configuration is compliant right now, continuously; CloudWatch answers what a running service or job actually did. Session Manager gives keyless shell access; Managed Grafana covers ops dashboards; the Well-Architected Tool formalizes a workload review. Cost Explorer and Budgets exist specifically to catch a runaway Athena scan or a forgotten EMR cluster before the bill does, and Data Exchange is the option to buy a dataset instead of building a pipeline to acquire it.

27. Amazon DynamoDB

Not a data-lake service itself — but the operational database most CDC pipelines pull from

Amazon DynamoDB is a fully managed, serverless NoSQL key-value/document database, built for single-digit-millisecond lookups by a known key at massive scale. It shows up in this guide not as an analytics engine — it isn't one — but because a huge share of real-world data pipelines exist specifically to move data out of an operational store like DynamoDB (an application's live order table, a user-profile table) and into the analytics stack this guide otherwise covers.

DynamoDB Streams — the CDC mechanism that's actually built in

DynamoDB Streams captures a time-ordered log of every item-level change (insert/update/delete) in a table, which a Lambda function can subscribe to directly — no separate CDC tool needed, unlike the log-parsing DMS does for relational databases (section 23). This is the standard way a DynamoDB-backed application's data ends up landing in S3 continuously rather than through periodic full-table exports, and it's also the mechanism behind the DynamoDB-to-S3-Tables zero-ETL integration AWS added in 2025 (section 30).

❯ Short version

DynamoDB is a managed NoSQL database for operational, key-based access at scale — not an analytics engine. It matters to a data engineer chiefly through DynamoDB Streams, its built-in item-level change log, which is the standard way DynamoDB-backed application data flows into a data lake via CDC without a separate replication tool.

28. Amazon QuickSight

Where the pipeline's output finally becomes a chart someone in the business actually looks at

Amazon QuickSight is AWS's managed BI tool — dashboards, visuals, and (via its SPICE in-memory engine) fast interactive exploration over data pulled from Athena, Redshift, S3, or a growing set of other sources. Everything else in this guide exists to get data clean, modeled, and queryable; QuickSight is usually the last hop, the layer a non-engineer in the business actually opens.

SPICE — why QuickSight dashboards feel instant even over large tables

SPICE (Super-fast, Parallel, In-memory Calculation Engine) is QuickSight's option to import and cache a dataset in memory rather than re-querying the source engine on every single interaction. A dashboard built on SPICE stays fast even as users filter and drill in repeatedly; the tradeoff is that SPICE data is a snapshot as of its last refresh, not live, so a dashboard needing up-to-the-second data should query the source directly instead — a small, deliberate choice that decides whether "fast" or "fresh" wins for a given dashboard.

❯ Short version

QuickSight is the managed BI layer where a pipeline's gold-layer output finally becomes a dashboard. Its SPICE in-memory engine trades freshness for speed by caching data instead of re-querying the source on every interaction — the right default for most dashboards, with direct-query as the alternative when true real-time numbers matter more than snappy interactivity.

29. Infrastructure as Code & CI/CD for Data Pipelines

Why production pipeline infrastructure gets defined in code instead of clicked together by hand

Hand-clicking through the AWS console to create an S3 bucket, a Glue job, an IAM role, and a Step Functions state machine works fine for a first prototype. It falls apart the moment there's a second environment: nothing guarantees staging matches prod, there's no code review for an infrastructure change the way there is for application code, and recreating an environment from scratch after deleting it means remembering — and re-clicking — every setting by hand. Infrastructure as Code (IaC) fixes this by defining infrastructure as a versioned, reviewable artifact that gets deployed the same way every time.

AWS CloudFormation — AWS's native, declarative IaC

AWS CloudFormation takes a YAML or JSON template describing the desired resources — an S3 bucket, a Glue job, an IAM role, whatever — and deploys or updates them together as a single unit called a stack. It's declarative: you describe the end state, and CloudFormation figures out the create/update/delete calls needed to get there, including rolling back automatically if a deployment fails partway through.

AWS CDK — the same stack, written in a real programming language

Writing every resource by hand in YAML gets repetitive fast — ten pipelines with a similar S3-bucket-plus-Glue-job shape mean ten near-identical, copy-pasted template blocks. The AWS CDK (Cloud Development Kit) lets you define that same infrastructure in Python, TypeScript, or another supported language, using loops, functions, and reusable constructs instead — then cdk synth compiles it down to an ordinary CloudFormation template, and cdk deploy deploys it exactly like any other stack. Teams choose CDK over raw CloudFormation for the same reason they choose code over a spreadsheet: type-checking catches a typo'd property name before deployment, and one function can define twenty near-identical pipelines instead of twenty pasted YAML blocks.

# CDK (Python) -- defines the same CloudFormation stack, in code
bucket = s3.Bucket(self, "GoldBucket",
    versioned=True,
    removal_policy=RemovalPolicy.RETAIN)

glue_job = glue.CfnJob(self, "SilverToGoldJob",
    role=glue_role.role_arn,
    command={"name": "glueetl",
             "scriptLocation": f"s3://{bucket.bucket_name}/scripts/gold.py"})

AWS SAM (Serverless Application Model) is a CloudFormation extension purpose-built for serverless resources specifically — Lambda functions, API Gateway APIs, DynamoDB tables — with a shorthand syntax that needs far fewer lines than the equivalent raw CloudFormation, plus a local-testing CLI (sam local invoke) that runs a Lambda function on a laptop before it's ever deployed. It's narrower in scope than CDK or CloudFormation by design: reach for SAM specifically for serverless application resources, not as a general-purpose IaC replacement for a whole data platform.

The AWS CLI scripts one-off or repeated operations against any AWS service straight from a terminal — aws s3 cp, aws glue start-job-run, aws cloudformation deploy — and it's the tool that actually runs inside most CI/CD deploy scripts, gluing together whatever a pipeline stage needs to do: package a template, kick off a job, check a status.

CI/CD for pipeline code — the same pattern software engineering already uses

A data pipeline's Glue scripts, Lambda functions, and CloudFormation/CDK templates benefit from the same source-control-triggered release process application code does, just aimed at infrastructure and transformation logic instead of a web app. AWS CodePipeline orchestrates the overall release — source, build, test, deploy stages, triggered by a commit. AWS CodeBuild runs the actual build/test commands inside that pipeline, such as linting a Glue script or running unit tests against transformation logic. AWS CodeDeploy handles the deployment step itself onto compute targets like EC2, ECS, or Lambda.

Amazon Q Developer is AWS's generative-AI assistant for writing and explaining code and infrastructure templates inside supported IDEs and the AWS console — useful for drafting a CDK construct or understanding an unfamiliar CloudFormation template faster, but it's a productivity tool sitting alongside this workflow, not a pipeline component itself.

Manual console edits cause state drift. If CloudFormation (directly or via CDK) created an IAM policy, and someone later tweaks that policy by hand in the console — adding a permission, say — the stack's recorded template no longer matches the deployed resource. The next stack update can silently revert that manual change, or fail outright on a conflicting property, because CloudFormation only knows about the state it last wrote, not any state changed outside it.

❯ Short version

CloudFormation deploys declarative YAML/JSON templates as a stack; CDK writes that same infrastructure in a real language and synthesizes it down to CloudFormation, trading copy-paste for loops and reusable constructs; SAM is a narrower, serverless-specific extension with a local-test CLI. CodePipeline/CodeBuild/CodeDeploy apply ordinary CI/CD to infrastructure and Glue/Lambda code changes. Never hand-edit a resource that IaC also manages — it causes drift that the next deploy can silently undo.

36. AWS Lakehouse vs. Databricks Lakehouse: A Head-to-Head Comparison

Building the same lakehouse a second way — and a fair look at where each platform genuinely wins

The lakehouse architecture sections you just read solve one problem: keep one physical copy of the data, wrapped in a table format that gives every engine ACID transactions, schema evolution, and time travel over that same copy, instead of syncing separate copies into a lake and a warehouse. Databricks solves the exact same problem, with the same underlying ideas — but it draws the platform boundary in a different place. AWS composes many separate, best-of-breed services (S3, Glue Catalog, Lake Formation, Glue/EMR, Athena, Redshift) around a shared storage-and-catalog foundation, each independently priced and independently swappable. Databricks is one unified product — notebooks, job scheduling, a metastore, SQL warehouses, and ML tooling all under one roof — that itself runs on top of a cloud (AWS, Azure, or GCP) rather than being one. Neither is "the lakehouse" — they're two different ways of assembling the same idea, and the AWS-Native vs. Cross-Cloud Alternatives section already flagged Databricks briefly as one such alternative; this section is the dedicated deep-dive on exactly that question.

Delta Lake vs. Apache Iceberg — genuinely both good, genuinely not identical

Delta Lake and Apache Iceberg are both open table formats that add ACID transactions, schema evolution, and time travel on top of plain Parquet files — neither is "the real one" and the other a knockoff. Delta Lake originated at Databricks and, despite being open-sourced years ago, is still the format most deeply and natively integrated into the Databricks product itself. Iceberg has broader multi-engine, multi-vendor adoption, and it's what AWS has invested in natively — S3 Tables, Athena, Redshift, and EMR are all built to read and write Iceberg directly, with no translation layer. The gap is narrowing: Delta's UniForm feature can expose a Delta table's metadata as Iceberg (and vice versa), and Databricks itself now supports Unity Catalog acting as an Iceberg REST catalog, so tables built in one ecosystem are increasingly readable from the other without a full rewrite. That said, picking one on day one still meaningfully shapes which tools integrate cleanly out of the box — treat the formats as converging, not yet interchangeable.

Where AWS-native wins. Granular, pay-per-service pricing — you pay AWS for exactly the Glue, Athena, or Redshift compute a job actually consumes, with no platform license layered on top. The deepest possible integration with every other AWS service a team is already running — IAM, VPC, KMS, CloudWatch, and EventBridge are all first-class citizens, not bolted-on connectors. One vendor to manage and negotiate with, not two. And it's proven at genuinely enormous scale: see this guide's Enterprise Validation section's LSEG example.

Where Databricks wins. A meaningfully more unified, polished developer experience — one notebook environment spans ETL, SQL, and ML, instead of context-switching between Glue Studio, Athena's query editor, and SageMaker separately. Unity Catalog's governance model covers data and ML assets — models, features, the works — in one place, where Lake Formation's scope stops at data. Genuine multi-cloud portability: the same Databricks workspace concept runs on AWS, Azure, or GCP, which matters for a company avoiding single-cloud lock-in or already operating across clouds for unrelated reasons. And often a faster path to production for teams without deep AWS-specific expertise already on staff, since Databricks abstracts away more of the cloud plumbing (VPC networking, IAM role wiring) that a fully AWS-native build requires getting right explicitly.

The cost model is structurally different, not just a different price tag

AWS-native is "pay AWS for the compute and storage you use — there's no other bill." Databricks is "pay Databricks (in DBUs) on top of the underlying cloud infrastructure cost it runs on" — a real, structural extra layer, not a rounding error. That said, sticker price per hour isn't the whole picture: a unified platform can lower total cost of ownership for some teams by needing fewer specialized engineers and less glue-code integration work between separately-billed services. Whether that trade nets out in Databricks' favor depends entirely on team size, in-house AWS depth, and how many of those "separate services" a given team would actually need to wire together by hand anyway.

The trap: assuming Databricks means "no AWS bill." Running Databricks on AWS still means paying AWS for the underlying EC2 compute, EBS/S3 storage, and networking Databricks provisions — the DBU charge is layered on top of that infrastructure cost, not a replacement for it. Teams that only budget for the DBU line item are routinely surprised by the infrastructure bill sitting underneath it.

A pragmatic decision rule, not a universal answer. If the team is AWS-only already, has real in-house AWS expertise, and wants to minimize per-service cost with full control over every layer, AWS-native tends to win. If the team is multi-cloud, wants one unified environment spanning data engineering and data science/ML without needing deep cloud-plumbing knowledge on staff, or is already standardized on Databricks elsewhere in the org, Databricks tends to win. This mirrors the honest framing of the AWS-Native vs. Cross-Cloud Alternatives section: the right call depends on the team's actual constraints, not on inertia toward whichever platform is more familiar.

❯ Short version

Both platforms solve the same problem — one copy of data, ACID transactions, multi-engine access — but AWS composes many separately-priced, deeply-integrated services around S3 + Iceberg + Glue Catalog, while Databricks is one unified product (Unity Catalog, notebooks, SQL warehouses, ML) that itself runs on top of AWS, Azure, or GCP. Iceberg and Delta Lake are converging but not yet interchangeable. AWS-native wins on granular pricing, AWS-service integration, and single-vendor simplicity; Databricks wins on developer-experience unification, ML-plus-data governance, and multi-cloud portability — and its DBU cost sits on top of, not instead of, the underlying cloud bill.

Separately, Netflix describes its Real-Time Distributed Graph ingestion pipeline: individual Kafka topics running at roughly a million messages per second, with topic records also persisted into Apache Iceberg tables specifically so data aging out of Kafka's retention window can still be backfilled from Iceberg later. Netflix's public AWS case study also states it uses Amazon EMR for large-scale data workloads behind its recommendation and personalization systems.

London Stock Exchange Group — a fully serverless architecture at genuinely large scale

An AWS-published account describes the London Stock Exchange Group migrating 75 petabytes of historical data to Amazon S3, processing 274 billion daily market updates across 575+ exchanges through a serverless architecture combining S3, AWS Glue, and Amazon Athena (with Amazon Bedrock added for anomaly detection) — reporting a 5x cost reduction and a shift from multi-day to multi-minute processing times. It's a useful data point against the instinct that "serverless" implies "small-scale only": the pattern this guide covers in sections 04, 08, 09, and 13 (S3 + Glue Catalog + Glue ETL + Athena) is the same one running at genuinely enormous, regulated-financial-market scale here.

❯ Short version

Yelp's Kafka/MSK+Flink streamhouse, Airbnb's HDFS→S3+Iceberg warehouse migration, Netflix's Kafka-backed data mesh and EMR-driven personalization workloads, and LSEG's 75-petabyte serverless S3+Glue+Athena platform are four real, company-documented architectures — confirming that the services and patterns in sections 01-28 are exactly what large-scale production systems on AWS actually look like, not simplified teaching examples.

38. AWS-Native vs. Cross-Cloud Alternatives

Where an AWS-native choice is the obvious default, and where it's a genuine trade-off

Every service in this guide has at least one popular alternative — some AWS-native competitors, some genuinely cross-cloud. Knowing where AWS-native is simply the path of least resistance, versus where teams make a deliberate trade-off, is part of using these services well rather than by default.

AWS serviceCommon alternativeWhy a team might choose the alternative
Glue ETLDatabricks (on AWS or elsewhere)A more mature notebook/collaboration experience, Delta Lake instead of (or alongside) Iceberg, and a single platform spanning ETL, ML, and BI
RedshiftSnowflake, Databricks SQLCross-cloud portability, or a team already standardized on that platform's ecosystem for reasons beyond just data warehousing
MSKConfluent CloudA fully managed Kafka experience with less operational surface than even MSK exposes, plus Confluent-specific tooling (Schema Registry UI, ksqlDB)
Step FunctionsApache Airflow (self-hosted or MWAA), DagsterPipeline logic expressed as Python code and DAGs rather than JSON state machines — often preferred when data engineers, not just infra engineers, own the orchestration layer

The pattern underneath most of these choices. AWS-native services win on integration — the Glue Catalog behind Athena, Redshift Spectrum, and EMR simultaneously is a real, hard-to-replicate advantage. Alternatives tend to win on either genuine multi-cloud portability, a more mature standalone product experience, or fitting a team's existing skill set and tooling. Neither is a universal right answer — but a team should be able to say which of those reasons is driving their choice, rather than defaulting to AWS-native purely because it's what's already there.

❯ Short version

AWS-native services generally win through tight integration (one Glue Catalog serving many engines); alternatives like Databricks, Snowflake, Confluent, or Airflow win through portability, product maturity, or fit with a team's existing skills. The right call depends on which of those actually matters for a given team — not on inertia.

39. Common Pitfalls

The recurring early mistakes this guide's sections have each flagged, collected in one place

Each section flagged one specific pitfall as it came up. Collected together, they form a pattern: almost every one of these is a case of reaching for the wrong tool's default behavior, not a deep technical error.

PitfallWhy it happensFix
Partitioning by a column nobody filters onPartitioning by whatever feels "unique" (customer_id) instead of what queries actually filter byPartition by the column(s) real WHERE clauses use — almost always date first (section 04)
Using Lambda for a heavy Spark-scale transformLambda is the easiest service to start with, so it's tempting to stretch it past its 15-minute/10GB limitsMove genuinely large transforms to Glue or EMR once data volume justifies distributed processing (sections 07, 09, 11)
Confusing a trust policy with a permissions policyBoth are JSON IAM documents attached to a role, but they answer different questionsTrust policy = who can assume the role; permissions policy = what it can do once assumed (section 05)
Polling a source table with SELECT ... WHERE updated_at > ? instead of real CDCIt's the first idea that comes to mind, and doesn't need a new serviceUse log-based CDC (DMS, or DynamoDB Streams) — it captures deletes and doesn't add repeated load to a live database (sections 23, 27)
One generic "pipeline failed" alert for every failure typeIt's less code to write one Catch/notify path than severalGive each failure category (ingestion, transform, DQ, aggregation) its own notification with its own context
Treating a Crawler-inferred schema as ground truthCrawlers are the path of least resistance to get a table into the CatalogReview (or define explicitly, as code) the schema for tables where correctness matters, especially ones with any type ambiguity in the source files (section 08)

❯ Short version

Nearly every recurring AWS data-engineering mistake is a case of a convenient default (Lambda, polling for changes, a Crawler-inferred schema, one generic alert) being stretched past where it actually fits. Each has a well-established, not-much-harder fix — the pattern is worth recognizing once so it's easy to spot the next time.

40. Glossary

Every term this guide used, defined once, for later reference

TermDefinition
Bronze / Silver / GoldThe medallion architecture's three data-quality tiers: raw, cleansed, business-ready.
CDC (Change Data Capture)Capturing every insert/update/delete on a source, usually by reading a transaction log, rather than periodically re-querying.
Choice stateA Step Functions state type that branches to different next states based on a prior state's output.
Cold startThe brief initialization delay before a Lambda function that hasn't run recently starts executing.
Columnar formatA file layout (Parquet, ORC) storing data column-by-column, letting a query read only the columns it needs.
CrawlerA Glue feature that inspects a data source and automatically writes/updates its schema in the Glue Data Catalog.
DynamoDB StreamsDynamoDB's built-in, time-ordered log of item-level changes, consumable by Lambda for CDC.
DynamicFrameGlue's schema-flexible wrapper around a Spark DataFrame, more forgiving of inconsistent source schemas.
Firehose (Amazon Data Firehose)Managed, no-code delivery of streaming records into S3, Redshift, or OpenSearch.
Glue Data CatalogThe shared metadata store (schema, location, partitions, format) read by Athena, Redshift Spectrum, EMR, and Glue jobs.
IAM role vs. userA role has no long-lived credentials and is temporarily assumed by a service; a user represents a person with long-lived credentials.
Kinesis Data StreamsA durable, ordered, replayable buffer for continuously arriving records, split into shards.
Lake FormationColumn-, row-, and cell-level access control layered on top of the Glue Catalog.
Medallion architectureThe bronze/silver/gold layered pattern for progressively cleaning and aggregating data.
MSK (Amazon Managed Streaming for Kafka)Managed, real Apache Kafka brokers — same protocol and ecosystem compatibility as self-hosted Kafka.

Parallel stateA Step Functions state type running multiple branches concurrently and waiting for all to finish.
Permissions policyThe IAM policy defining what an identity or role can do once it has access.
Retry / CatchStep Functions constructs for automatically re-attempting a failed state, or routing its failure to an error-handling state.
ShardAn ordered sub-stream within a Kinesis Data Stream, with its own throughput limit.
SPICEQuickSight's in-memory caching engine, trading data freshness for interactive query speed.
Storage class (S3)A cost/retrieval-speed tier for an S3 object (Standard, Intelligent-Tiering, Glacier, etc.).
Trust policyThe IAM policy defining who or what is allowed to assume a role.
Wait stateA Step Functions state type that pauses execution for a fixed duration or until a timestamp.
Zero-ETL integrationA fully managed AWS replication path (e.g. DynamoDB or a SaaS app into Redshift/S3 Tables) requiring no custom pipeline code.

41. Learning Path: What to Build Next

This guide is the map — the services only become real once you've built something with them

Reading this guide gives the vocabulary and the mental model; it doesn't yet give the muscle memory. The fastest way to close that gap is to build a small, complete pipeline — end to end, not one service in isolation — and hit the real friction points (an IAM permission that's subtly wrong, a Glue job that's slow because of a partitioning mistake, a Step Functions execution that fails in a way the console's visual debugger makes obvious in seconds) firsthand.

A concrete first project, sized to be finishable

Pick any public API or dataset producing at least daily-changing data. Land raw pulls in S3 (Bronze) via a scheduled Lambda (sections 07, 20). Transform to cleaned, typed, deduplicated Parquet (Silver) with a Glue job (section 09). Add one automated data-quality check before promoting to a Gold aggregate table (section 10). Orchestrate the whole thing with Step Functions, including at least one retry policy and one SNS failure notification (section 21). Query the Gold table from Athena (section 12), and, if there's appetite, put a QuickSight dashboard on top (section 28).

❯ Short version

This guide's value compounds once it's paired with actually building something: a small, real, end-to-end pipeline — ingest, medallion transform, a DQ gate, Step Functions orchestration, a queryable Gold table — with your own source data. That's where the AWS console's error messages, IAM's rough edges, and Step Functions' execution history actually teach the parts a document can't.
