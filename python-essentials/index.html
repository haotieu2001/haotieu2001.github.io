01. Why these fundamentals matter

Python is easy to write badly and easy to write well, and the gap between the two comes down to a fairly short list of ideas. This page is a practical tour of those ideas, plus the slice of data structures and algorithms that shows up constantly in coding interviews.

Start with a fact that surprises a lot of newcomers: Python is not a fast language for raw computation. There are three reasons for this:

  • Python is interpreted. The CPython virtual machine runs each line of code one at a time, instead of compiling the whole program to machine code ahead of time the way C or Rust do.
  • A lock called the Global Interpreter Lock (GIL) means a single Python process can only use one CPU core at a time for heavy computation. Section 13 covers this in detail.
  • Everything a Python program touches lives in the RAM of one machine.

Put those three together and here is what happens in practice: try to sort a dataset bigger than your computer's memory using a plain Python list, and the operating system runs out of memory and kills the process before it finishes.

None of this makes Python a bad language. It makes Python a language where knowing what a tool costs matters as much as knowing what it does. That is the real subject of this page, split into two halves. The first half, sections 02 through 13, covers the Python features that separate a quick script from code you would actually want to maintain: picking the right container for the job, comprehensions and generators, decorators, context managers, classes and dataclasses, type hints, and concurrency. The second half, sections 14 through 25, covers the data structures and algorithms that come up again and again in coding interviews: arrays and two pointers, strings, hashmaps and sets, sorting and binary search, stacks and queues, linked lists, trees and graphs, sliding windows, heaps, and a little dynamic programming. None of it requires competitive-programming depth. It is exactly enough to handle Easy and Medium problems calmly. The last two sections wrap it up: a priority map for where to spend your study time, and a dense cheat sheet to scan right before an interview.

The habit worth building

Write code that is boring to read. The moment you find yourself proud of a clever one-liner, stop and ask whether the next person to read it (often you, in six months) will understand it in one pass. Clear, well-named, correctly-costed code beats a clever trick almost every time, whether you are shipping a feature or solving problem two of four in an interview.

02. The four structures: list, dict, set, tuple

Pick the right container for the job and half your performance problems disappear before they start. Pick the wrong one, and a task that should take n steps can end up taking n² steps instead.

Four built-in types carry nearly every data pipeline: list, dict, set and tuple. Knowing what each one does is not enough — you also need to know how expensive each operation on it is. That is what separates a job that finishes in seconds from one that hangs.

list — the dynamic array

A list is a growable array of references. Appending an item and reading by index are both O(1) (append is O(1) on average — the technical term is "amortised"). But checking membership with x in mylist is O(n): Python scans the list one element at a time until it finds a match or reaches the end. A list is great for an ordered batch of records you iterate over once. It is a poor choice as a lookup table.

dict — the hash map you'll use constantly

A dict is a hash table. Insert, lookup and delete are all O(1) on average. Since Python 3.7, a dict also remembers the order you inserted its keys. This is one of the most important structures you'll use: it is how you build in-memory lookups, join keys, and grouping accumulators without needing a database or an engine.

set — dedup, membership, set algebra

A set is like a dict that only stores keys, with no values. Checking membership is O(1), and adding the same value twice has no effect, so duplicates disappear automatically. A set also supports real set algebra: | for union, & for intersection, - for difference. That makes it the right tool for diffing two datasets: which IDs are new, and which ones disappeared.

tuple — immutable and hashable

A tuple is a fixed sequence that cannot be changed after it is created — it is immutable. Because it is immutable, it is also hashable, which means a tuple can be used as a dict key or a set member. This is the standard trick for building a composite key, such as (region, product). Tuples are also how Python returns multiple values from a function, and how unpacking works.

python
# list: an ordered batch of records you scan once
events = [{"user": 1, "amt": 10}, {"user": 2, "amt": 7}]

# dict: an O(1) lookup table (the join-side of a small dimension)
user_region = {1: "APAC", 2: "EMEA"}
for e in events:
    e["region"] = user_region.get(e["user"], "UNKNOWN")   # enrich = dict lookup

# set: diff yesterday vs today to find new / churned ids
yesterday = {1, 2, 3}
today     = {2, 3, 4}
new_ids    = today - yesterday      # {4}
churned    = yesterday - today      # {1}

# tuple: a composite key for a set / dict
seen = set()
key = ("APAC", "widget")     # hashable because it's a tuple
seen.add(key)
print(key in seen)          # True, O(1)

The collections toolkit

collections gives you specialised structures that remove boilerplate and speed up common patterns:

  • defaultdict — auto-creates a default value, so grouping needs no "if key not in dict" dance.
  • Counter — frequency counting and top-N in one line.
  • deque — a double-ended queue with O(1) appends/pops at both ends; ideal for a rolling window or a bounded buffer.
  • namedtuple — a lightweight, immutable record with named fields (readability without a class).
python
from collections import defaultdict, Counter, deque, namedtuple

# group amounts by region WITHOUT checking membership first
by_region = defaultdict(list)
for e in events:
    by_region[e["region"]].append(e["amt"])

# frequency + top-N in one shot
paths = ["/a", "/b", "/a", "/a", "/c"]
print(Counter(paths).most_common(2))   # [('/a', 3), ('/b', 1)]

# rolling buffer of the last 3 latencies (auto-drops the oldest)
window = deque(maxlen=3)
for ms in (12, 18, 9, 30):
    window.append(ms)
print(list(window))                # [18, 9, 30]

Row = namedtuple("Row", ["region", "amt"])
r = Row("APAC", 10)
print(r.region, r.amt)          # named fields, immutable

Two traps that bite everyone

1. x in a_list is O(n). Filtering a million rows against a list of allowed IDs is O(n·m) — potentially billions of comparisons. Convert the lookup side to a set first and it becomes O(n). This single change routinely turns a 20-minute job into a 2-second one.
2. The mutable default argument. def f(x, acc=[]) creates acc once and shares it across every call — state leaks between runs. Use acc=None then acc = acc or [] inside (covered in Section 05).

03. Comprehensions & generator expressions

A comprehension writes a filter-and-transform in one short, readable line. Its lazy sibling, the generator expression, does the same job without ever building a list in memory.

A comprehension builds a collection from an iterable in a single expression. It reads top-to-bottom like the sentence "give me X for each item where condition". It also runs faster than the equivalent for-loop, because the looping happens inside Python's C code instead of being interpreted step by step. There is a comprehension for each of the core containers: list, dict and set.

python
records = [{"id": 1, "amt": 10, "ok": True},
           {"id": 2, "amt": 0,  "ok": False},
           {"id": 3, "amt": 7,  "ok": True}]

# list comprehension: map + filter
amounts = [r["amt"] for r in records if r["ok"]]        # [10, 7]

# dict comprehension: build a lookup in one line
by_id = {r["id"]: r for r in records}

# set comprehension: distinct valid ids
valid_ids = {r["id"] for r in records if r["ok"]}

# conditional EXPRESSION inside a comprehension (ternary, not a filter)
labels = ["hi" if r["amt"] > 5 else "lo" for r in records]

# nested: flatten a list of batches into rows
batches = [[1, 2], [3, 4]]
flat = [x for batch in batches for x in batch]   # [1,2,3,4]

Note the two ways if appears. As a filter it goes after the loop (... for r in records if r["ok"]). As a ternary expression it goes before the loop ("hi" if x > 5 else "lo" for x in ...) — that form must have an else.

Generator expressions: same syntax, lazy execution

Swap the square brackets for parentheses and you get a generator expression. It looks almost identical, but it builds nothing up front. It yields items one at a time, only as they are consumed. This is the difference between allocating a list of a million integers all at once and streaming through them one by one. When the generator is the only argument to a function, you can even drop the extra parentheses.

python
# LIST comp: builds the whole list in RAM, then sums it
total_eager = sum([len(line) for line in open("huge.log")])

# GENERATOR expr: streams line by line, holds one line at a time
total_lazy = sum(len(line) for line in open("huge.log"))

# chain lazy steps: parse -> filter -> count, nothing materialised
lines   = (l.rstrip() for l in open("events.jsonl"))
errors  = (l for l in lines if '"level":"ERROR"' in l)
n_errors = sum(1 for _ in errors)

List-comp vs. gen-exp: the memory tradeoff

A list comprehension [...] materialises every element in RAM at once — use it when you need the collection again (index it, len it, iterate twice). A generator expression (...) is lazy and O(1) in memory — use it when you consume the result once, especially over a file or API stream. Rule of thumb: if the source could be large, reach for the parentheses. If you only ever call sum(), any(), max() or a single loop on it, a generator is strictly better.

Know when to stop

A comprehension with three nested loops and two conditionals becomes impossible to read at a glance. When it no longer reads like a plain sentence, use a for-loop instead — clarity beats cleverness in code your on-call teammate has to debug at 3am. Also remember a generator is single-use: once consumed it is exhausted, and iterating it again yields nothing.

04. Generators & iterators: streaming without OOM

Generators let you process a file bigger than your computer's RAM, one record at a time. This is one of the most important Python techniques you can know. It is what stops a program from crashing with an out-of-memory error.

A generator function is any function that contains the word yield. Calling it does not run the function's body right away. Instead, it returns a generator object: a lazy iterator that has not done any work yet. Each time you ask it for the next value, the function runs until it hits the next yield, hands back that one value, and then pauses. It remembers exactly where it stopped — its local variables and its position in the code — until you ask for the next value. Because of this, you can iterate over a 50 GB log file while only ever holding a single line in memory.

python
def read_lines(path: str):
    # opening a file is ALREADY lazy — iterating yields one line at a time
    with open(path) as f:
        for line in f:
            yield line.rstrip("\n")

gen = read_lines("huge.log")   # nothing read yet
first = next(gen)               # now ONE line is read

Chaining generators into a streaming pipeline

Because each stage is lazy, you can chain generators together into a pipeline: parse, then filter, then transform. Data flows through one record at a time, and memory use stays flat no matter how large the file is. The yield from keyword hands control to another generator underneath it — useful for combining many files into a single stream.

python
import json

def parse(lines):
    for line in lines:
        yield json.loads(line)

def only_paid(records):
    for r in records:
        if r["status"] == "paid":
            yield r

def all_files(paths):
    for p in paths:
        yield from read_lines(p)   # delegate: fan many files into one stream

# the pipeline: memory is O(1), file size can be terabytes
pipeline = only_paid(parse(all_files(["a.jsonl", "b.jsonl"])))
for rec in pipeline:
    ...   # write to warehouse, one record at a time

Batching a stream with itertools

In practice you rarely insert one row at a time into a database — you batch rows together first. The itertools module is the standard library's toolkit for working with iterators: islice takes or skips items without building a list, chain concatenates iterables, groupby groups a sorted stream, and (on 3.12+) batched splits a stream into fixed-size chunks. Here is the streaming-plus-batching pattern that most data loaders are built on:

python
from itertools import islice

def batched(iterable, n: int):
    # backport for < 3.12; on 3.12+ use itertools.batched
    it = iter(iterable)
    while chunk := tuple(islice(it, n)):
        yield chunk

# stream a huge file, load 1000 rows per round-trip to the DB
rows = parse(read_lines("huge.jsonl"))
for chunk in batched(rows, 1000):
    bulk_insert(chunk)      # only 1000 records in RAM at any moment

Generator gotchas

A generator can only be used once. You cannot loop over it twice, and you cannot call len() on it. If you need the data again, convert it to a list with list(gen) — but that gives up the memory savings. itertools.groupby only groups keys that sit next to each other, so sort the data first or the same key will get split into several separate groups. Also open the file inside the generator using with — that guarantees the file closes once the generator has been fully consumed.

05. Functions as first-class citizens

In Python, a function is just another object. You can pass it around, return it, and store it like any other value. This is exactly what lets you build reusable transforms instead of copy-pasting the same logic everywhere.

Functions in Python are first-class objects. You can assign one to a variable, put it in a list or dict, pass it as an argument, or return it from another function. A function that takes another function as input, or returns one as output, is called a higher-order function. This is what makes a pluggable pipeline possible: one generic runner that accepts whichever transform you hand it.

python
# functions are objects: store them, dispatch on them
def to_upper(s): return s.upper()
def strip_ws(s): return s.strip()

CLEANERS = {"upper": to_upper, "strip": strip_ws}   # a registry

def clean(value: str, steps: list[str]) -> str:
    for name in steps:
        value = CLEANERS[name](value)   # look up a fn and call it
    return value

print(clean("  hi ", ["strip", "upper"]))   # "HI"

Flexible signatures: *args, **kwargs, keyword-only

*args collects any extra positional arguments into a tuple. **kwargs collects any extra keyword arguments into a dict. Putting a bare * in the function signature forces everything after it to be passed by name, not by position, which is very useful for functions with many config options where positional arguments would be hard to read. The same */** operators also work in reverse: they unpack a sequence or a dict back into arguments when you call the function.

python
def connect(host: str, *, port: int = 5432, timeout: int = 30, **opts):
    # port & timeout are keyword-only (after the bare *)
    return {"host": host, "port": port, "timeout": timeout, **opts}

cfg = {"port": 6543, "sslmode": "require"}
conn = connect("warehouse", **cfg)     # unpack a dict into kwargs
# connect("warehouse", 6543)  ->  TypeError: port is keyword-only

lambda, map/filter, and why comprehensions usually win

A lambda is a small function with no name, useful as a quick, one-off key= for sorting. map and filter apply a function lazily across an iterable, but in idiomatic Python a comprehension is usually clearer and just as fast. Save map/filter for when you already have a named function to apply.

python
rows = [{"id": 3, "amt": 10}, {"id": 1, "amt": 50}]
rows.sort(key=lambda r: r["amt"], reverse=True)   # sort by amount desc

# map/filter (lazy) ...
ids = map(lambda r: r["id"], rows)
# ... but a comprehension reads better and is preferred:
ids = [r["id"] for r in rows]

from functools import partial
# closures & partial: bake in config to build a reusable transform
def rounder(digits):
    def _round(x): return round(x, digits)   # closes over `digits`
    return _round

round2 = rounder(2)
to_cents = partial(round, ndigits=2)   # same idea, stdlib style
print(round2(3.14159), to_cents(3.14159))   # 3.14 3.14

The mutable default argument trap

Default arguments are evaluated once, when the function is defined, not once per call. So def f(x, acc=[]) creates a single list and shares it across every call to f. Data left over from one call leaks into the next. In a long-running worker, this turns into a bug that grows silently over time. The fix is the sentinel pattern:
def f(x, acc=None): then acc = acc if acc is not None else [] inside the function. The same problem, and the same fix, applies to {} and any other mutable default value.

06. Decorators: retry, timing, logging

A decorator wraps a function to add extra behaviour, such as retries, timing, or logging, without touching the function's own body. That is exactly the kind of glue a pipeline needs everywhere.

A decorator is a callable that takes a function and returns a new function. Usually the new function calls the original one, with some extra behaviour added around it. The @name syntax written above a def is just shorthand for fn = name(fn). Always wrap the inner function with functools.wraps, so the wrapper keeps the original function's name, docstring and signature. Without it, every decorated function shows up as wrapper in tracebacks and logs, which makes debugging harder.

python
import functools, time

def timing(fn):
    @functools.wraps(fn)                # preserve name/docstring
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            dt = time.perf_counter() - t0
            print(f"{fn.__name__} took {dt:.3f}s")
    return wrapper

@timing
def extract():
    time.sleep(0.1)
    return "done"

Decorators with arguments: a factory returning a decorator

To give a decorator its own arguments (for example, "retry up to 5 times") you add one more layer: an outer function that takes those arguments and returns a decorator. That gives you three nested levels — configuration, function, and call — but the pattern is always the same. Here is one everyone ends up writing eventually: @retry, with exponential backoff, for a flaky API or database call.

python
import functools, time

def retry(max_attempts: int = 3, backoff: float = 0.5, exc=Exception):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return fn(*args, **kwargs)
                except exc as e:
                    if attempt == max_attempts:
                        raise                       # give up, re-raise
                    sleep = backoff * 2 ** (attempt - 1)   # exponential
                    print(f"attempt {attempt} failed: {e!r}; retry in {sleep}s")
                    time.sleep(sleep)
        return wrapper
    return decorator

@retry(max_attempts=5, backoff=0.5)
def fetch(url: str):
    import requests
    r = requests.get(url, timeout=10)
    r.raise_for_status()
    return r.json()

Stacking decorators

Decorators stack bottom-up: the one nearest the def wraps first, the topmost wraps last and therefore runs its "before" code first. Read them from the inside out, one layer at a time.

python
def log(fn):
    @functools.wraps(fn)
    def wrapper(*a, **k):
        print(f"→ {fn.__name__}")
        return fn(*a, **k)
    return wrapper

@timing          # outermost: runs last around the call
@retry(max_attempts=3)
@log             # innermost: closest to the function
def pull(url): ...
# equivalent to: pull = timing(retry(3)(log(pull)))

Decorator gotchas

Forgetting @functools.wraps quietly breaks introspection, logging, and any framework that reads fn.__name__. A careless @retry that catches a bare Exception will happily retry a ValueError caused by bad data, which is not what you want. Only retry errors that are actually temporary and safe to repeat, such as timeouts, 5xx server errors, or connection resets, and never blindly retry a write that is not idempotent (one that would cause harm if run twice). Finally, exponential backoff with no cap and no randomness ("jitter") can overwhelm a service that is already struggling to recover. In production, add a maximum delay and a little randomness.

07. Classes & OOP, properly

You won't write classes to model cats and dogs. You'll write them to model the moving parts of a pipeline: a connector to a source, a config object, a reusable transformation step. That keeps the code testable, and keeps it from rotting over time.

Object-oriented programming has one core idea: bundle state (data) together with the behaviour (functions) that acts on that data, behind a clean interface. A function that takes inputs and returns outputs, with nothing to remember in between, should stay a plain function. But the moment something needs to hold on to state between calls, a class starts to earn its place. That kind of state might be an open database connection, a running row count, a set of credentials, or a buffer of rows waiting to be flushed. This is exactly why the standard example everyone reaches for is a connector: it holds a live connection, and exposes read() and write() methods that use that connection.

The honest rule: don't reach for a class too early

A stateless transform, such as "take this DataFrame, return a cleaned one," is just a function. Wrapping it in a class with a single method and no state is over-engineering. Ask yourself: is there state to keep, or a contract that several different implementations must share? If the answer to both is no, write a function instead (or a dataclass, §08, if all you need is to hold data).

Anatomy: class, __init__, and self

A class is a blueprint. An instance is one object built from that blueprint. __init__ is the initialiser: it runs right after the instance is created, and sets up its starting state. self is the instance itself — Python hands it to every method automatically, as the first argument. When you write conn.read(), Python actually calls read(conn) behind the scenes: self is conn. That is the whole trick. Once self stops feeling mysterious, classes get much easier to read.

python
class SQLConnector:
    """Holds a connection and knows how to run queries against it."""

    def __init__(self, dsn: str, timeout: int = 30):
        self.dsn = dsn              # instance attribute: unique to THIS object
        self.timeout = timeout
        self.conn = None          # not connected yet — lazy
        self._rows_read = 0       # leading _ = "internal, don't touch from outside"

    def connect(self) -> None:
        # imagine a real driver here (psycopg, etc.)
        self.conn = open_connection(self.dsn, timeout=self.timeout)

    def read(self, sql: str) -> list[dict]:
        if self.conn is None:
            raise RuntimeError("call connect() first")
        rows = self.conn.execute(sql).fetchall()
        self._rows_read += len(rows)   # state that persists across calls
        return rows

db = SQLConnector("postgres://…")   # __init__ runs now
db.connect()
rows = db.read("SELECT * FROM orders LIMIT 10")

Notice what the class gives you: db remembers its dsn, its live conn, and a running _rows_read — the read method uses and updates that state. A bare function could not, without you passing everything in and out every single call.

Instance attributes vs class attributes

An instance attribute (set on self) belongs to one object. A class attribute (set directly in the class body) is shared by every instance of that class. Class attributes are great for constants: a default value, a registry, a schema version. But they become a classic source of bugs when they hold something mutable, like a list, because every instance ends up mutating the same shared object.

python
class Loader:
    source_type = "postgres"     # class attribute: shared, fine because it's immutable
    seen_files = []             # DANGER: shared mutable list

    def __init__(self, name):
        self.name = name        # instance attribute: per-object

a, b = Loader("a"), Loader("b")
a.seen_files.append("f1.csv")
print(b.seen_files)             # ['f1.csv'] — b sees a's file! same list

The shared-mutable-class-attribute trap

If each instance needs its own list/dict/set, initialise it in __init__ (self.seen_files = []), never in the class body. It's the same bug as the mutable default argument (§05), and it bites hardest when one long-lived object leaks state into the next run.

The three method flavours: instance, @classmethod, @staticmethod

A regular method takes self and works on one instance. A @classmethod takes the class itself (cls) instead of an instance. Its most useful job in everyday code is the alternate constructor: a clean from_config() or from_uri() method that builds and returns an instance. A @staticmethod takes neither self nor cls. It is just a plain function that logically belongs on the class — a helper you don't want floating loose in the module.

python
class SQLConnector:
    def __init__(self, host, port, user):
        self.host, self.port, self.user = host, port, user

    @classmethod
    def from_uri(cls, uri: str) -> "SQLConnector":
        # parse "host:port/user" then build an instance via cls(...)
        host, rest = uri.split(":")
        port, user = rest.split("/")
        return cls(host, int(port), user)   # cls, not SQLConnector → subclasses work too

    @staticmethod
    def mask(secret: str) -> str:
        return secret[:2] + "***"       # pure helper, no self/cls needed

db = SQLConnector.from_uri("db.internal:5432/etl")   # reads much better than SQLConnector(...)

@property: a computed attribute with a method behind it

@property lets a method be accessed like a plain attribute, with no parentheses needed. Use it for values that are computed from other state, or to control access, without forcing the caller to remember which things are fields and which are methods. Add a setter only when you want to allow assignment, and validate the new value there.

python
class Batch:
    def __init__(self, rows):
        self._rows = rows

    @property
    def size(self) -> int:
        return len(self._rows)      # computed on access, always correct

    @property
    def is_empty(self) -> bool:
        return self.size == 0

b = Batch([{...}, {...}])
print(b.size)      # 2  — no () , it looks like a plain attribute
print(b.is_empty)  # False

        self.rows = rows

    def __repr__(self) -> str:               # debuggable, not <object at 0x…>
        return f"RowBatch(n={len(self.rows)})"

    def __len__(self) -> int:
        return len(self.rows)

    def __iter__(self):                        # now: for row in batch: ...
        return iter(self.rows)

    def __enter__(self):                       # now usable as: with RowBatch(...) as b:
        return self

    def __exit__(self, exc_type, exc, tb):      # cleanup runs even on error
        self.rows = []                        # release the buffer
        return False                         # don't swallow exceptions

batch = RowBatch([{"id": 1}, {"id": 2}])
print(batch)          # RowBatch(n=2)
print(len(batch))     # 2
for row in batch:     # works because of __iter__
    ...

The __eq__ / __hash__ pact

If you define __eq__, Python automatically sets __hash__ to None. That makes the object unhashable: it can no longer go into a set, or be used as a dict key. Two objects that are equal must also hash equal, so define __eq__ and __hash__ together (or make the type frozen with a dataclass, §08, which does this for you automatically). The rule is simple: equal objects must have equal hashes, never one without the other.

Inheritance and super()

Inheritance models an is-a relationship: a PostgresConnector is a Connector. The subclass inherits all of the parent's methods, and can add new ones or override existing ones. super() calls back up to the parent's version of a method (most often super().__init__(...), so the parent class still gets to set up its part of the state). When you look up an attribute on an object, Python searches the child class first, then each parent in turn, and uses the first match it finds. This search order is called the MRO, or method resolution order.

python
class Connector:
    def __init__(self, name: str):
        self.name = name
        self.reads = 0

    def read(self, query):
        raise NotImplementedError       # subclasses must define this

class PostgresConnector(Connector):     # PostgresConnector is-a Connector
    def __init__(self, name, dsn):
        super().__init__(name)          # let the parent set name + reads
        self.dsn = dsn                  # then add our own state

    def read(self, query):              # override with the real behaviour
        self.reads += 1
        return run_pg(self.dsn, query)

Abstract base classes: writing a contract

Raising NotImplementedError only causes a failure when the method is actually called. An abstract base class (from the abc module) fails earlier, at the moment you try to create an instance, if a required method is missing — you cannot even build an incomplete connector. This is a standard pattern: define one Connector interface where every source (Postgres, S3, Mongo, an API) must implement read and write. The rest of your pipeline can then treat all of them the same way.

python
from abc import ABC, abstractmethod

class Connector(ABC):
    @abstractmethod
    def read(self, query: str) -> list[dict]: ...
    @abstractmethod
    def write(self, rows: list[dict]) -> None: ...

class S3Connector(Connector):
    def read(self, query):  return read_from_s3(query)
    def write(self, rows): write_to_s3(rows)

# Connector()          → TypeError: can't instantiate abstract class
# a half-built subclass missing write() → TypeError at construction, not in prod
src: Connector = S3Connector()      # the pipeline just needs "a Connector"
def run(src: Connector, dst: Connector):   # works for ANY connector — polymorphism
    dst.write(src.read("…"))

Composition over inheritance

Inheritance is the right tool for a genuine is-a relationship with shared behaviour. For almost everything else, prefer composition instead: a has-a relationship. A Pipeline is not a special kind of Connector — it has a source, a destination, and a list of steps. Composition keeps the pieces swappable and easy to test, and it avoids the deep, fragile class hierarchies that inheritance tempts you into building.

python
class Pipeline:
    def __init__(self, source: Connector, sink: Connector, steps: list):
        self.source = source     # has-a source
        self.sink = sink         # has-a sink
        self.steps = steps       # has-a list of transform callables

    def run(self, query: str):
        rows = self.source.read(query)
        for step in self.steps:   # each step is just a function/callable
            rows = step(rows)
        self.sink.write(rows)

Class, function, or dataclass? A quick decision

Function — stateless input→output (most transforms). Dataclass (§08) — you only need to hold structured data (a config, a record, a schema). Class — you have state and behaviour (a connector, a buffered writer), or a contract multiple implementations must share (an ABC). When in doubt, start with a function and let a real need for state pull you toward a class.

08. Dataclasses & Pydantic

Stop passing bare dicts around your pipeline. Give every record and config a typed shape instead, and decide up front whether you need cheap structure (a dataclass) or real runtime validation (Pydantic).

Anyone who moves data around for a living knows the worst bugs come from records that look right but are not: a missing key, a string where a number should be, a config typo that only causes a failure at 3am. @dataclass and Pydantic both replace the "just use a dict" habit with explicit, self-documenting types. What they differ on is when the shape gets checked.

Dataclasses: structure without boilerplate

The @dataclass decorator inspects the class annotations and auto-generates __init__, __repr__ and __eq__ for you. You write the fields once, and you get a constructor, a readable repr for logs, and value equality — all for free.

python
from dataclasses import dataclass, field

@dataclass
class Record:
    id: int
    name: str
    tags: list[str] = field(default_factory=list)  # NOT tags=[]

r = Record(1, "orders")
print(r)               # Record(id=1, name='orders', tags=[]) — free __repr__
print(r == Record(1, "orders"))  # True — free value __eq__

The mutable-default trap

Never write tags: list = [] — that single list is shared across every instance, so appending to one record mutates them all. Use field(default_factory=list) so each instance gets a fresh list. This is the same shared-mutable-state bug as a mutable default argument.

The flags worth knowing

  • frozen=True — makes instances immutable and hashable. Perfect for a PipelineConfig you never want mutated mid-run, and it can be a dict key or set member.
  • order=True — generates __lt__/__gt__ etc. so instances sort by field order (handy for sorting records or watermarks).
  • slots=True (3.10+) — stores fields in __slots__ instead of a per-instance __dict__: less memory and faster attribute access, which adds up when you materialise millions of records.
  • __post_init__ — runs right after the generated __init__; use it for validation or derived fields.
python
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class PipelineConfig:
    source_bucket: str
    batch_size: int = 1000
    retries: int = 3

    def __post_init__(self):
        if self.batch_size <= 0:
            raise ValueError("batch_size must be positive")

cfg = PipelineConfig(source_bucket="s3://raw", batch_size=500)
# cfg.batch_size = 10   -> FrozenInstanceError: can't reassign a frozen field
seen = {cfg}              # hashable because frozen -> usable in a set / dict key
print(cfg.retries)        # 3

Dataclass vs namedtuple vs plain class vs dict

A namedtuple is immutable, indexable, and very lightweight, but you cannot add methods to it cleanly, and every field is positional. A plain class gives you full control, but you have to hand-write all the dunder methods yourself. A raw dict has no schema at all: any key, any type, and typos fail silently. The dataclass is the best balance for internal records: typed fields, real methods, and very little boilerplate.

Pydantic: validation at the boundary

Dataclasses trust you: they do not check anything. The moment data crosses a boundary you do not control, such as an HTTP payload, a Kafka message, or a CSV file from a partner, you want real runtime checks instead. Pydantic's BaseModel validates and converts types as soon as an object is built, and raises a ValidationError with a precise, machine-readable list of everything that failed. It is the standard choice for validating external input (FastAPI is built on it).

09. Type hints and why teams enforce them

Type hints do nothing while your code is running. Their entire value comes from static analysis, editor autocomplete, and pipelines that document themselves.

This is the single most misunderstood feature for newcomers: writing path: str does not make Python reject a value that is not a string. The interpreter just records the hint in __annotations__ and otherwise ignores it completely. The real value comes from tools that read those hints before your code ever runs, like mypy and pyright, plus IDE autocomplete and the plain readability of a signature that tells the next engineer exactly what flows through it.

Modern syntax (3.11+)

  • Built-in generics: list[int], dict[str, int], tuple[str, ...] (3.9+ — no more typing.List).
  • Union with |: str | None instead of Optional[str], int | str instead of Union[int, str] (3.10+).
  • Callable[[int], str] for functions, TypedDict for dict-shaped records, Literal["append", "overwrite"] for fixed choices, Final for constants.
  • TypeVar/Generic for reusable generic containers, and Protocol for structural (duck) typing that a checker can still verify.
python
from typing import Protocol, TypedDict, Literal, Final

MAX_ROWS: Final = 1_000_000

class Row(TypedDict):        # a dict with a known shape
    id: int
    name: str

class Sink(Protocol):        # structural: anything with write() fits
    def write(self, rows: list[Row]) -> int: ...

def flush(rows: list[Row],
          sink: Sink,
          mode: Literal["append", "overwrite"] = "append") -> int | None:
    if not rows:
        return None
    return sink.write(rows)   # mypy knows write() takes list[Row]

Why teams gate CI on mypy

A pipeline that quietly converts or drops the wrong type does not crash. It just writes bad data, and you find out days later from a broken dashboard. Running mypy --strict as a required CI check catches whole classes of bugs before code ever reaches production: passing None where a value is required, arguments in the wrong order, a function that forgets to return on some path. It also turns every function signature into living documentation. A new engineer reads def extract(cfg: PipelineConfig) -> Iterator[Row] and instantly knows the contract, without running anything.

Type hints lie at runtime

A str hint will not stop you from passing an int. def f(x: str): return x + "!" called as f(5) raises a TypeError from the + operator, not from the annotation itself. If you need real enforcement at a boundary, validate with Pydantic (section 08) instead — hints alone are only checked by whatever tools you choose to run.

10. Errors, retries & logging

Production pipelines do not fail gracefully by accident. You have to design that in: specific exceptions, chained error context, retries with backoff, and structured logs instead of print.

Handle the exceptions you expect, and only those

The try/except/else/finally structure gives you four slots. try holds the risky call. except handles specific failures. else runs only when there was no exception, for the success path. finally runs no matter what, for cleanup. Always catch specific exception types — a bare except: also catches things like KeyboardInterrupt, and it hides the real cause of the failure.

Never bare-except, never silently swallow

except: pass is how a pipeline "succeeds" while writing zero rows. Catch the narrowest exception you can name, log it, and either re-raise or route the record to a dead-letter store. Silence is the enemy of debuggability.

Custom exceptions and chaining

Define your own exception types, such as class ExtractError(Exception), so callers can catch your failures separately from a stray KeyError. When you translate a low-level error into a higher-level one specific to your domain, use raise NewError(...) from e. This keeps the chain of exceptions intact, so you can still see the original traceback and the root cause. Python's idiomatic style prefers EAFP over LBYL. EAFP stands for "easier to ask forgiveness than permission": just try the operation, and catch the exception if it fails. LBYL stands for "look before you leap": check first, then act. Python prefers EAFP because checking and then acting as two separate steps can race against other code and miss edge cases.

python
import logging, time, json

log = logging.getLogger("extract")

class ExtractError(Exception):
    """Raised when a source record cannot be pulled."""

def fetch(record_id: int) -> dict:
    if record_id == 13:
        raise ConnectionError("socket reset")
    return {"id": record_id}

def extract(record_id: int, retries: int = 3) -> dict:
    err: Exception | None = None       # hold the cause; `as e` is cleared per-loop
    for attempt in range(1, retries + 1):
        try:
            return fetch(record_id)          # EAFP: just try it
        except ConnectionError as e:      # specific, not bare
            err = e                          # keep it — `e` is out of scope after the block
            wait = 2 ** attempt              # exponential backoff
            log.warning("fetch failed",
                        extra={"record_id": record_id,
                               "attempt": attempt, "retry_in": wait})
            time.sleep(wait)
    # out of retries -> translate to a domain error, keep the cause
    raise ExtractError(f"gave up on {record_id}") from err

Logging, not print

print sends text to standard output with no severity level, no timestamp, and no structure. That makes it nearly useless once your job runs on a scheduler instead of your terminal. The logging module gives you severity levels (DEBUG/INFO/WARNING/ERROR/CRITICAL), a configurable handler, and, for pipelines, structured/JSON logs that your log platform can index and alert on. Emit fields a machine can parse, such as record id, attempt number, and latency, rather than a plain string.

python
import logging, json

class JsonFormatter(logging.Formatter):
    def format(self, r: logging.LogRecord) -> str:
        payload = {"level": r.levelname, "msg": r.getMessage(),
                   "logger": r.name}
        if r.exc_info:
            payload["error"] = self.formatException(r.exc_info)
        return json.dumps(payload)

h = logging.StreamHandler()
h.setFormatter(JsonFormatter())
logging.basicConfig(level=logging.INFO, handlers=[h])

try:
    extract(13)
except ExtractError:
    logging.getLogger("extract").exception("dead-letter")  # logs full chain

Put those two ideas together and you get a robust extract step: retry transient failures with backoff, log every attempt as structured JSON, and after the last retry, push the record to a dead-letter queue instead of crashing the whole run. Also make the operation idempotent, meaning safe to run more than once (for example, upsert by key instead of a blind insert), so a retry never writes the same record twice.

11. Context managers & files

A context manager guarantees that cleanup code runs, even when the code inside it raises an error. That is exactly what you want for file handles, database transactions, and temporary credentials.

The with protocol

Any object with __enter__ and __exit__ methods is a context manager. with obj as x: calls __enter__ first (whatever it returns becomes x), runs the code block, and then calls __exit__ on the way out, whether the block finished normally or raised an exception. __exit__ receives information about the exception, if there was one, so it can commit on success and roll back on failure. This "cleanup always happens" guarantee is why with open(...) is better than calling open() and close() manually: if the code between them raises an error, a manual close() never runs, and the file handle leaks.

Why with open(...) wins

It closes the file on normal exit and on exception, flushing buffered writes so you don't end up with a half-written, corrupt output file. Manual close() only runs if you reach it — one early raise or return and the handle leaks.

A DB transaction manager

The generator style, using @contextmanager, lets you write setup, yield, and teardown as a single function. Everything before the yield acts as __enter__. Everything after it, inside a finally block, acts as __exit__. This is the cleanest way to express "commit on success, roll back on exception".

python
from contextlib import contextmanager

@contextmanager
def transaction(conn):
    cur = conn.cursor()
    try:
        yield cur                 # hand the cursor to the with-block
        conn.commit()             # reached only if no exception
    except Exception:
        conn.rollback()           # body raised -> undo everything
        raise                     # re-raise so the caller still sees it
    finally:
        cur.close()              # always release the cursor

with transaction(conn) as cur:
    cur.execute("insert into staging values (%s)", (1,))
    # if this line raises, the insert above is rolled back

To manage several resources at once, with a() as x, b() as y: nests them, and closes them in reverse order. When the number of resources is not known ahead of time, for example when opening one file per partition, use contextlib.ExitStack to enter them all in a loop while still guaranteeing every one gets closed.

Files the modern way: pathlib

Skip building file paths by concatenating strings. pathlib.Path gives you the / operator to join path parts, .glob() to search a directory tree, and convenient reader/writer methods. It works the same way across operating systems, and is far harder to get wrong than joining paths yourself with os.path.join.

python
from pathlib import Path

root = Path("/data/landing")
for f in sorted(root.glob("orders/*.csv")):   # walk matching files
    if not f.exists():
        continue
    text = f.read_text(encoding="utf-8")     # open+read+close in one call
    print(f.name, len(text.splitlines()), "lines")

out = root / "processed" / "orders.done"       # / joins path parts
out.parent.mkdir(parents=True, exist_ok=True)
out.write_text("ok", encoding="utf-8")

12. JSON, CSV, datetime

Serialization is where quiet data corruption tends to hide: broken unicode, quoted commas split in half, and timestamps with no timezone that drift your whole warehouse by hours.

JSON and the streaming standard: JSON Lines

json.loads and json.dumps convert between text and Python objects. Pass ensure_ascii=False to keep unicode readable (otherwise "Hà Nội" turns into \u... escape codes), and pass a default= function to serialize types that json does not know how to handle, such as datetime or Decimal. For pipelines, prefer JSON Lines, also called NDJSON: one JSON object per line. That format lets you stream and process a huge file one record at a time, without loading it all into memory, and lets you append new records cheaply. A single giant JSON array, by contrast, forces you to parse the whole thing at once.

python
import json
from datetime import datetime, timezone
from decimal import Decimal

def encode(o):
    if isinstance(o, datetime): return o.isoformat()
    if isinstance(o, Decimal):  return str(o)   # keep precision as text
    raise TypeError(type(o))

rows = [{"city": "Hà Nội", "ts": datetime.now(timezone.utc),
         "amount": Decimal("19.99")}]

# write NDJSON: one object per line, stream-friendly
with open("out.ndjson", "w", encoding="utf-8") as fh:
    for r in rows:
        fh.write(json.dumps(r, default=encode, ensure_ascii=False) + "\n")

CSV: use the module, never split(',')

The csv module handles the messy parts of the format for you: quoted fields, commas and newlines embedded inside a field, and configurable delimiters and quoting rules. DictReader reads each row as a dict keyed by the header row. DictWriter writes rows back out the same way. A naive line.split(',') breaks a value like "Hanoi, Vietnam" into two separate columns — a classic pipeline bug that only shows up on the one row that happens to contain a comma.

python
import csv, io

raw = 'id,city\n1,"Hanoi, Vietnam"\n'       # note the comma inside quotes

print(raw.splitlines()[1].split(","))       # ['1', '"Hanoi', ' Vietnam"']  WRONG

for row in csv.DictReader(io.StringIO(raw)):
    print(row)                            # {'id': '1', 'city': 'Hanoi, Vietnam'}  right

datetime: store UTC, always

A naive datetime has no timezone attached to it. Comparing or storing it is ambiguous, and it is a frequent source of bugs that are off by a few hours. Make every datetime in your pipeline timezone-aware, and store everything in UTC. Convert to local time only when displaying it to a person. Parse text into a datetime with strptime, format a datetime back into text with strftime, prefer the ISO-8601 format when sending dates between systems, and convert to or from epoch seconds when a system needs a plain number instead.

python
from datetime import datetime, timezone

naive = datetime.now()               # no tz -> ambiguous, avoid
now = datetime.now(timezone.utc)     # aware, in UTC -> correct

iso = now.isoformat()               # '2026-07-16T03:00:00+00:00'
parsed = datetime.strptime("2026-07-16 03:00:00+0000",
                          "%Y-%m-%d %H:%M:%S%z")   # aware
epoch = int(now.timestamp())      # -> UTC epoch seconds
back = datetime.fromtimestamp(epoch, timezone.utc)

The naive-datetime trap & JSON float precision

Mixing naive and aware datetimes raises a TypeError. Worse, a naive value silently assumes the server's local timezone, so running the same job in two different regions can produce disagreeing data. The rule: everything should be UTC and timezone-aware, from ingest all the way to storage. Separately, JSON has no decimal type, so json.loads("0.1") gives you a binary float that has lost precision. For money, use Decimal, and serialize it as a string.

13. Concurrency & the GIL

Python can wait on thousands of things at once, but it can only compute one thing at a time. Understanding that split is the key to correctly picking between threads, processes, and asyncio.

CPython has a Global Interpreter Lock (GIL): only one thread can execute Python bytecode at any given instant. This leads to the single most misunderstood fact in Python performance: threads do not give you parallel CPU computation. But the GIL is released while a thread is waiting on the operating system, for example on the network or on disk, so threads do help with I/O-bound work. While one thread is blocked waiting on a socket, another thread can run.

The three tools:

  • threading — shared memory, cheap, great for I/O-bound fan-out; no CPU parallelism.
  • multiprocessing — separate interpreters, each with its own GIL, so real CPU parallelism; you pay a serialization cost to move data between processes.
  • asyncio — one thread, one event loop, async/await cooperative scheduling; best when you have huge numbers of concurrent I/O operations and want to avoid thread overhead.

In practice you rarely use these tools directly. The concurrent.futures module gives you ThreadPoolExecutor and ProcessPoolExecutor: one clean, high-level API where changing a single word switches you between an I/O strategy and a CPU strategy.

Parallel downloads with ThreadPoolExecutor

This is a classic I/O-bound task: call an API for many keys, or download many files. It is I/O-bound, so threads are the right tool. map preserves the input order. as_completed lets you handle each result as soon as it arrives.

python
from concurrent.futures import ThreadPoolExecutor, as_completed
import urllib.request

urls = [f"https://api.example.com/v1/items/{i}" for i in range(50)]

def fetch(url: str) -> bytes:
    with urllib.request.urlopen(url, timeout=10) as r:
        return r.read()

results = {}
with ThreadPoolExecutor(max_workers=8) as pool:
    futures = {pool.submit(fetch, u): u for u in urls}
    for fut in as_completed(futures):
        url = futures[fut]
        try:
            results[url] = fut.result()
        except Exception as e:
            print(f"failed {url}: {e}")   # one bad call won't sink the batch

print(f"got {len(results)} of {len(urls)}")

To convert this into CPU-bound work, for example parsing each downloaded blob, you would change ThreadPoolExecutor to ProcessPoolExecutor and nothing else. Each separate process gets its own GIL, so they can run on separate CPU cores at the same time.

The "threads make Python faster" myth

Adding threads to a CPU-bound, pure-Python loop makes it the same speed or slower. The GIL still forces the bytecode to run one instruction at a time, and you have only added the overhead of switching between threads. Threads help only when the work spends most of its time waiting. For heavy computation, use separate processes, native or NumPy code that releases the GIL, or, if the workload has genuinely outgrown one machine, move it to a distributed system instead of trying to work around the GIL on a single box.

14. Big-O intuition

You do not need formal proofs. You need to look at a solution and instantly know its order of growth, because that is the number the interviewer is really checking against the size of the input.

Big-O answers one question: as the input n gets big, how does the work grow? Ignore the constants, and keep only the dominant term. A senior engineer reads a loop the way you read a road sign: no arithmetic, just pattern recognition. Here are the five patterns you must recognise on sight.

The five orders, with everyday analogies

O(1) — constant. The work never changes with n. Looking a word up in a Python dict is O(1): the hash points straight at the slot. Grabbing nums[i] from a list is O(1). It's like knowing someone's phone number by heart — the size of the phone book doesn't matter.

O(log n) — logarithmic. Each step throws away half the remaining work. Binary search in a sorted array is the classic case: 1 million items, ~20 comparisons. Like finding a name in a physical phone book by repeatedly splitting it in half.

O(n) — linear. One pass, touch each element a constant number of times. Summing a list, or scanning a log file line by line. Reading every page of a book once.

O(n log n) — linearithmic. The cost of a good sort (Python's Timsort), and of most "sort then sweep" solutions. Think: split the deck, sort halves, merge. If a Medium problem feels like it needs order, this is usually the target.

O(n²) — quadratic. A loop inside a loop over the same data. Comparing every pair of records. Fine for n = 100, a disaster for n = 100000 — that's 10 billion operations. This is the pattern you learn to watch for.

python
# Same problem, two orders. The interviewer wants the second one.
def has_pair_slow(nums, target):        # O(n^2) — nested loop
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return True
    return False

def has_pair_fast(nums, target):        # O(n) — one pass + a set
    seen = set()
    for x in nums:
        if target - x in seen:        # membership is O(1)
            return True
        seen.add(x)
    return False

Space complexity, briefly

The same idea applies to memory: how much extra space does your solution use as n grows? A hashmap holding every element is O(n) space. Two pointers walking an array in place is O(1) space. Recursion adds one stack frame per call, so its space cost is O(depth). In practical terms, this is the difference between streaming a file line by line (O(1) space) and loading the whole thing into a list (O(n) space) — interviewers often care about space precisely because production data does not fit in RAM.

The practical rule

If n is large and you just wrote a loop nested inside another loop over the same data, stop. There is almost always a dict/set that turns it into one pass, or a sort that lets you sweep once. Nested-loop-over-big-n is the #1 reason a working solution still fails the round.

15. Arrays & two pointers

The Python list is a dynamic array. The two-pointer technique is how you take an O(n²) array problem and squeeze it down to O(n) time using only O(1) extra space.

A list stores its elements next to each other in memory, and allocates a bit of extra room ahead of time so that append is O(1) on average. Reading by index is O(1). Inserting or deleting at the front is O(n), because every other element has to shift over by one. Slicing with a[i:j] copies the elements into a new list — that is safe, but it costs O(k) in both time and space, so avoid slicing inside a tight loop when a plain index would do the job.

python
a = [10, 20, 30, 40]
b = a[1:3]              # COPY -> [20, 30]; a is untouched
a[1:3] = [99]         # in-place splice -> [10, 99, 40]
a.reverse()             # in-place, O(n), returns None
c = a[::-1]             # reversed COPY

The two-pointer technique

Two indices walk the array instead of one, so a job that looks like "check every pair" becomes a single sweep. Two flavours dominate interviews:

The opposite-ends pattern starts one pointer at the beginning and one at the end, and moves them toward each other. It requires the array to be sorted, or at least that you are matching from both sides. It shows up in sorted two-sum, container-with-most-water, and valid palindrome. The fast/slow pattern moves two pointers at different speeds through the same array. It is used for in-place rewriting, such as moving zeros or removing duplicates, and for cycle detection.

Worked: Two Sum II — sorted input

Problem: given a sorted array and a target, return the 1-based indices of the two numbers that add up to it.

python
def two_sum_sorted(nums: list[int], target: int) -> list[int]:
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        s = nums[lo] + nums[hi]
        if s == target:
            return [lo + 1, hi + 1]
        if s < target:
            lo += 1          # need a bigger sum
        else:
            hi -= 1          # need a smaller sum
    return []

assert two_sum_sorted([2, 7, 11, 15], 9) == [1, 2]

Time O(n), space O(1). The sortedness is what lets a single number tell you which pointer to move.

Worked: Container With Most Water

Problem: heights h[i] are vertical lines; pick two to hold the most water (width × min height).

python
def max_area(h: list[int]) -> int:
    lo, hi = 0, len(h) - 1
    best = 0
    while lo < hi:
        area = (hi - lo) * min(h[lo], h[hi])
        best = max(best, area)
        if h[lo] < h[hi]:      # the short wall caps us; move it in
            lo += 1
        else:
            hi -= 1
    return best

assert max_area([1, 8, 6, 2, 5, 4, 8, 3, 7]) == 49

Time O(n), space O(1). The insight: moving the taller wall can never help (width shrinks, height still capped by the shorter wall), so always move the shorter one — which is why one pass suffices.

In-place trio worth memorising

Reverse: swap a[lo], a[hi] and step both inward. Move zeros: a slow pointer marks the next non-zero slot while a fast pointer scans. Dedup sorted array: slow pointer writes, fast pointer reads; write only when a[fast] != a[slow]. All O(n) time, O(1) space.

16. Strings & parsing

Strings are immutable in Python. That single fact matters more than anything else for both correctness and performance in a coding interview.

Because a str cannot be changed in place, every s += piece inside a loop allocates a brand-new string and copies everything you have built so far into it. Doing this N times costs O(n²). Instead, build up a list and call ''.join() on it once, which costs O(n). This exact mistake shows up constantly when people assemble a CSV row, or a log line, piece by piece.

python
# WRONG: O(n^2), a new string every iteration
out = ""
for tok in tokens:
    out += tok + ","          # quadratic blow-up on big input

# RIGHT: O(n)
out = ",".join(tokens)

Everyday ops and slicing

python
s = "  Software Engineer  "
s.strip()                # 'Software Engineer'
s.lower().split()         # ['software', 'engineer']
"pipe" in "pipeline"      # True — substring test, O(n)
"abc"[::-1]              # 'cba' — reversed copy

Parsing logs with re

Real-world code involves a huge amount of semi-structured text. A compiled regular expression with capture groups is the fastest way to turn a raw access-log line into typed fields.

python
import re

LINE = '127.0.0.1 - - [16/Jul/2026:10:22:01] "GET /api/v1/users HTTP/1.1" 200 1534'
# ip ... "METHOD PATH PROTO" status bytes
pat = re.compile(r'(\S+) .* "(\S+) (\S+) [^"]+" (\d+) (\d+)')

m = pat.match(LINE)
if m:
    ip, method, path, status, size = m.groups()
    print(ip, method, path, int(status), int(size))
    # 127.0.0.1 GET /api/v1/users 200 1534

Compile the pattern once, outside the loop, when you parse millions of lines — recompiling it on every line quietly slows everything down.

17. Hashmaps & sets

If there is one family of tools that wins Easy and Medium interviews, it is the hashmap. O(1) lookup is the key that solves nearly every "make this faster" problem.

Four patterns cover the vast majority of what you'll be asked. Know them from memory and you'll recognise the solution before the interviewer finishes the prompt.

1. Count frequency with collections.Counter. 2. Check membership or remove duplicates with set. 3. Group rows by a key with defaultdict(list). 4. The complement trick: remember what you have already seen in a dict, so a second nested loop turns into a single lookup.

python

Worked: Two Sum (the complement trick)

Problem: return indices of the two numbers that sum to target (unsorted input).

python
def two_sum(nums: list[int], target: int) -> list[int]:
    seen = {}                        # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:       # have we seen the complement?
            return [seen[target - x], i]
        seen[x] = i
    return []

assert two_sum([3, 2, 4], 6) == [1, 2]

Time O(n), space O(n). One pass; the dict replaces the inner loop of the O(n²) brute force. This is the template — the same "remember what you've seen" idea powers dozens of variants.

Worked: Group Anagrams

Problem: group words that are anagrams of one another.

python
from collections import defaultdict

def group_anagrams(words: list[str]) -> list[list[str]]:
    groups = defaultdict(list)
    for w in words:
        key = tuple(sorted(w))    # consistent form for every anagram; tuple is hashable
        groups[key].append(w)
    return list(groups.values())

group_anagrams(["eat", "tea", "tan", "ate", "nat"])
# [['eat','tea','ate'], ['tan','nat']]

Time O(n · k log k) (k = word length, from sorting each word), space O(n · k). The trick is choosing a consistent key that every anagram maps to.

Worked: Subarray Sum Equals K

Problem: count contiguous subarrays whose elements sum to k.

python
from collections import defaultdict

def subarray_sum(nums: list[int], k: int) -> int:
    count = 0
    prefix = 0
    seen = defaultdict(int)         # prefix-sum -> how many times seen
    seen[0] = 1                    # empty prefix
    for x in nums:
        prefix += x
        count += seen[prefix - k]    # subarrays ending here that sum to k
        seen[prefix] += 1
    return count

assert subarray_sum([1, 1, 1], 2) == 2

Time O(n), space O(n). This uses a running prefix sum together with a count-map. If prefix - k was seen before, every one of those earlier occurrences closes off a valid subarray ending here. This "prefix sum plus hashmap" combination is a genuine step up in difficulty, and a favourite for the harder Medium-level questions.

Keys must be hashable

A list cannot be a dict/set key, because it is mutable — trying to use one raises TypeError: unhashable type: 'list'. Convert it to a tuple first (that is why Group Anagrams uses tuple(sorted(w))). str, int, frozenset, and tuples made only of hashable items are all fine.

18. Sorting, searching & binary search

Sorting is O(n log n), and it is often the cheapest way to put your data in order so that a single linear sweep becomes possible. Binary search is O(log n), and it is the interviewer's favourite way to check whether you can write a loop without an off-by-one error.

Sorting in Python

sorted(x) returns a new list. x.sort() sorts the list in place and returns None. Both use Timsort, which is O(n log n) and stable — elements that compare equal keep their original relative order. That stability is what lets you sort by multiple keys in separate passes. Use key= to sort by a computed field, and reverse=True to sort in descending order.

python
rows = [("b", 2), ("a", 2), ("c", 1)]
sorted(rows, key=lambda r: r[1])          # by 2nd field asc
sorted(rows, key=lambda r: (-r[1], r[0]))   # count desc, then name asc

# Top-K by sorting — fine, but a heap (see §23) is better at O(n log k)
top3 = sorted(counts.items(), key=lambda kv: -kv[1])[:3]

Worked: the binary-search template

Problem: find target in a sorted array, return its index or -1. Memorise this exact skeleton — the <= and the mid ± 1 updates are what keep it from looping forever or missing the last element.

python
def binary_search(nums: list[int], target: int) -> int:
    lo, hi = 0, len(nums) - 1      # inclusive bounds
    while lo <= hi:                     # note: <=
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

Time O(log n), space O(1). For most real code, reach for the standard library instead:

python
from bisect import bisect_left, bisect_right

a = [1, 3, 3, 5, 8]
bisect_left(a, 3)    # 1  -> first index where 3 fits (leftmost)
bisect_right(a, 3)   # 3  -> just past the last 3
# count of 3s = bisect_right - bisect_left = 2

The deeper skill interviewers are really probing for is binary search on the answer: when the answer is some number in a range, and the question "is X feasible?" is monotonic (false, false, …, true, true), you can binary-search the space of possible answers instead of an array. It is the same template — the "array" is just the range of candidate answers.

Worked: Search in Rotated Sorted Array

Problem: a sorted array was rotated at an unknown pivot; find target in O(log n).

python
def search_rotated(nums: list[int], target: int) -> int:
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[lo] <= nums[mid]:                # left half is sorted
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:                                   # right half is sorted
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1
            else:
                hi = mid - 1
    return -1

assert search_rotated([4, 5, 6, 7, 0, 1, 2], 0) == 4

Time O(log n), space O(1). At each step, one half of the array is guaranteed to be sorted. Decide whether the target lies inside that sorted half, and discard the other half. This is the model "modified binary search" that the interview round is testing for.

Worked: Merge Intervals (sort then sweep)

Problem: merge all overlapping intervals.

python
def merge(intervals: list[list[int]]) -> list[list[int]]:
    intervals.sort(key=lambda iv: iv[0])   # sort by start
    out = [intervals[0]]
    for start, end in intervals[1:]:
        if start <= out[-1][1]:            # overlaps the last kept interval
            out[-1][1] = max(out[-1][1], end)
        else:
            out.append([start, end])
    return out

merge([[1, 3], [2, 6], [8, 10], [15, 18]])
# [[1, 6], [8, 10], [15, 18]]

Time O(n log n), dominated by the sort, and space O(n) for the output. Sorting first is what turns "compare every pair of intervals" into a single linear sweep — this "sort first, then walk once" move comes up again and again.

19. Stacks & queues

A stack is last-in-first-out, like an undo history. A queue is first-in-first-out, like a task backlog. Picking the right container for the job is the difference between O(1) and O(n) per operation.

A stack is just a Python list: append pushes a value on, and pop removes one from the end. Both are O(1). A queue needs efficient removal from the front, so use collections.deque instead: append adds to the right, and popleft removes from the left, both O(1) at either end.

python
from collections import deque

stack = []
stack.append(1); stack.append(2)   # push
stack.pop()                          # 2  (LIFO), O(1)

q = deque()
q.append("job1")                   # enqueue at right, O(1)
q.popleft()                       # 'job1' (FIFO), O(1)

Never use list.pop(0) for a queue

list.pop(0) and list.insert(0, x) both shift every remaining element over by one, which is O(n) each. That means a "queue" built on a plain list is secretly O(n²) overall. This is the classic performance bug in BFS solutions. Use deque instead and it becomes O(1) — the same reason BFS over a graph, or a level-order tree traversal, always reaches for deque.

Worked: Valid Parentheses

Problem: is a string of brackets ()[]{} balanced and correctly nested?

python
def is_valid(s: str) -> bool:
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in s:
        if ch in pairs:                      # a closing bracket
            if not stack or stack.pop() != pairs[ch]:
                return False
        else:                                # an opening bracket
            stack.append(ch)
    return not stack                       # must be empty at the end

assert is_valid("()[]{}") is True
assert is_valid("(]") is False

Time O(n), space O(n). The stack remembers the most recent unmatched opener — exactly what LIFO is for.

The monotonic-stack pattern

A monotonic stack keeps its contents sorted, either increasing or decreasing, by popping off anything that would break the order before pushing a new value. It answers "next greater" or "next smaller element" questions in O(n) instead of O(n²), because each element is touched at most twice: once when it is pushed, and once when it is popped.

Worked: Daily Temperatures (next greater element)

Problem: for each day, how many days until a warmer temperature? (0 if none.)

python
def daily_temperatures(temps: list[int]) -> list[int]:
    ans = [0] * len(temps)
    stack = []                          # indices, temps decreasing
    for i, t in enumerate(temps):
        while stack and temps[stack[-1]] < t:   # t is warmer than stack top
            j = stack.pop()
            ans[j] = i - j              # days waited for day j
        stack.append(i)
    return ans

daily_temperatures([73, 74, 75, 71, 69, 72, 76, 73])
# [1, 1, 4, 2, 1, 1, 0, 0]

Time O(n), space O(n). The stack holds the days that are still waiting for a warmer one. When a warmer day arrives, it resolves all of the waiting days at once. The same skeleton solves "Next Greater Element" — just store values instead of the number of days waited.

Recognising a monotonic-stack problem

Phrases like "next greater", "next warmer", "nearest smaller to the left", "largest rectangle in histogram", or "how far until…" are the signal to look for. If you're about to write a nested loop scanning forward for the next bigger thing, a monotonic stack collapses it to O(n).

20. Linked lists

You will almost never touch a linked list in production data code. Interviewers love them anyway, because they force you to reason carefully about pointers. Learn the three tricks below and you can solve about 90% of the questions.

A linked list is a chain of nodes where each node holds a value and a reference to the next node. There is no contiguous block of memory and no index: to reach the 5th element you follow four pointers. The whole model is one tiny class.

python
# The one data structure the whole section is built on.
class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next          # singly linked: one pointer forward

A singly linked list has one pointer per node, called next. A doubly linked list adds a second pointer, prev, pointing backward. That gives O(1) deletion when you already have a reference to the node, which is exactly why Python's own collections.OrderedDict and LRU caches use a doubly linked list internally. In most real-world data, linked lists are rare: columnar files, Arrow buffers and DataFrames are all contiguous arrays, because scanning contiguous memory is far faster than following pointers. Linked lists show up in interviews, not in your Parquet files.

The dummy-head trick

Half of all linked-list bugs come from special-casing the head node. Allocate a temporary dummy node in front of the real list, build everything off dummy.next, and return dummy.next at the end. Now "insert at the head" and "insert in the middle" become the same code path.

Reverse a linked list — iterative and recursive

Problem: given the head of a singly linked list, return the head of the reversed list. Walk the list carrying three pointers — prev, cur, and a saved nxt — and flip each link as you pass it.

python
def reverse_list(head: ListNode | None) -> ListNode | None:
    prev = None
    cur = head
    while cur:
        nxt = cur.next        # 1. save the rest of the list
        cur.next = prev       # 2. flip this node's pointer backward
        prev = cur            # 3. advance prev
        cur = nxt             # 4. advance cur
    return prev              # prev is the new head

# Recursive version: reverse the tail, then hook head onto the end.
def reverse_rec(head: ListNode | None) -> ListNode | None:
    if head is None or head.next is None:
        return head                 # base case: empty or single node
    new_head = reverse_rec(head.next)
    head.next.next = head          # make the next node point back to us
    head.next = None              # and drop our old forward link
    return new_head

Merge two sorted lists — the dummy head in action

Problem: given the heads of two sorted linked lists, splice them into one sorted list. This is the linked-list version of the merge step in merge sort, and it mirrors merging sorted runs of data when a sort spills to disk.

python
def merge_two(a: ListNode | None, b: ListNode | None) -> ListNode | None:
    dummy = ListNode()      # temporary head — no special case for the first node
    tail = dummy
    while a and b:
        if a.val <= b.val:
            tail.next = a
            a = a.next
        else:
            tail.next = b
            b = b.next
        tail = tail.next
    tail.next = a or b       # attach whatever list still has nodes
    return dummy.next

Fast/slow pointers — cycle detection & the middle

Two pointers, one moving twice as fast as the other, is called Floyd's tortoise-and-hare algorithm. If the list has a cycle, the fast pointer eventually catches up to the slow one and they collide. If the list ends cleanly instead, the fast pointer simply runs off the end. The same trick, stopped when the fast pointer reaches the end, finds the middle node in a single pass, with no need to count the length first.

Problem: return True if the linked list contains a cycle.

python
def has_cycle(head: ListNode | None) -> bool:
    slow = fast = head
    while fast and fast.next:
        slow = slow.next          # one step
        fast = fast.next.next     # two steps
        if slow is fast:          # they met → there is a loop
            return True
    return False                 # fast reached the end → no loop

def middle(head: ListNode | None) -> ListNode | None:
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
    return slow                  # when fast hits the end, slow sits at the middle

Interview tip

If you can reverse a list, merge two lists, and detect a cycle from memory, you can improvise almost every Medium linked-list question. Reach for the dummy head whenever the answer's head might change, and fast/slow whenever the question mentions "middle", "cycle", or "nth from the end".

21. Recursion, trees & BFS/DFS

Trees are recursion made visible. Almost every tree question follows the same shape: "do something at this node, then recurse into its children." The two ways to walk a tree, DFS and BFS, are the traversals interviewers expect you to write from memory.

Recursion works because each call gets its own frame on the call stack, holding its own local variables and its own return address. A recursive function needs a base case, which tells it when to stop, and a recursive case, a smaller version of the same problem. Miss the base case, and you overflow the stack.

python
import sys
# CPython caps recursion around 1000 frames to protect the C stack.
sys.setrecursionlimit(10_000)   # raise it — but see the warning below

Deep recursion is easy to get wrong

Raising the limit lets you recurse deeper, but each frame still costs real C-stack memory and you can crash the interpreter with a segmentation fault ("segfault"). For a linked list or a skewed tree of a million nodes, convert the recursion to iteration with an explicit stack. Python has no tail-call optimisation, so recursion depth is a hard ceiling, not a suggestion.

A binary tree node mirrors the list node, with two child pointers instead of one:

python
class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

DFS — go deep first

Depth-first search dives all the way to the bottom of one branch before backing up. The three orders differ only in when you visit the node relative to its children: pre-order visits node, then left, then right. In-order visits left, then node, then right, which gives sorted output for a BST. Post-order visits left, then right, then node. Recursion is the natural way to write DFS. An explicit stack is the iterative form interviewers sometimes ask for instead.

python
# Recursive in-order (gives sorted values for a BST).
def inorder(root: TreeNode | None) -> list[int]:
    if root is None:
        return []
    return inorder(root.left) + [root.val] + inorder(root.right)

# Iterative pre-order with an explicit stack — no recursion limit to hit.
def preorder(root: TreeNode | None) -> list[int]:
    if root is None:
        return []
    out, stack = [], [root]
    while stack:
        node = stack.pop()
        out.append(node.val)
        if node.right:            # push right first so left pops first
            stack.append(node.right)
        if node.left:
            stack.append(node.left)
    return out

Problem: return the maximum depth (root-to-deepest-leaf node count) of a binary tree. This is DFS distilled to one line of recurrence.

python
def max_depth(root: TreeNode | None) -> int:
    if root is None:
        return 0                                  # base case: empty subtree has depth 0
    return 1 + max(max_depth(root.left), max_depth(root.right))

BFS — level by level with a deque

Breadth-first search visits every node at depth d before it visits any node at depth d+1. You need a FIFO queue for this, so use collections.deque, whose popleft() is O(1) (a plain list's pop(0) is O(n)). The trick for "give me each level as its own list" is to record len(q) at the top of each loop, before processing anything — that count is exactly the size of one level.

Problem: return the node values grouped level by level, top to bottom.

python
from collections import deque

def level_order(root: TreeNode | None) -> list[list[int]]:
    if root is None:
        return []
    out, q = [], deque([root])
    while q:
        level = []
        for _ in range(len(q)):     # snapshot: exactly one level's worth
            node = q.popleft()
            level.append(node.val)
            if node.left:
                q.append(node.left)
            if node.right:
                q.append(node.right)
        out.append(level)
    return out

Validate a BST — DFS carrying bounds

Problem: decide whether a binary tree is a valid binary search tree. The classic trap is comparing a node only to its immediate children, which misses violations further down the tree. The fix is to pass down an open interval, (low, high), that each node's value must fall strictly inside, tightening that interval as you descend.

python
def is_valid_bst(root: TreeNode | None) -> bool:
    def check(node, low, high):
        if node is None:
            return True                      # empty subtree is valid
        if not (low < node.val < high):    # must sit strictly inside the interval
            return False
        return (check(node.left,  low, node.val) and
                check(node.right, node.val, high))
    return check(root, float('-inf'), float('inf'))

Every one of these traversals is O(n) time, since each node is visited exactly once. Space is O(h) for DFS, where h is the tree's height, because that is how deep the recursion or stack goes. Space is O(w) for BFS, where w is the widest level of the tree. These are the easy-to-medium tree problems interviewers actually reach for. Know max-depth, level-order, and validate-BST from memory, and you have covered the bulk of them.

22. Sliding window & prefix sums

Tier 2 · good to know, not required

When a problem asks for the best contiguous run, whether that is the longest, the shortest, or the max-sum subarray or substring, a sliding window turns the naive O(n²) scan of every possible subarray into one clean O(n) pass.

A window is a pair of indices, left and right, that bound a contiguous slice of the data. There are two flavours. A fixed-size window has a given length k, and you slide it one step at a time. A variable-size window grows its right edge greedily, and only shrinks its left edge when some constraint is broken.

Fixed window — max sum of size K

Problem: find the maximum sum of any contiguous subarray of length k. Compute the first window's sum once, then slide: add the entering element, subtract the leaving one. No re-summing.

python
def max_sum_k(nums: list[int], k: int) -> int:
    window = sum(nums[:k])          # first window, O(k)
    best = window
    for i in range(k, len(nums)):
        window += nums[i] - nums[i - k]   # slide: +entering, -leaving
        best = max(best, window)
    return best

Variable window — the expand/contract template

This is the pattern worth memorising. Move right across the array to expand the window. Whenever the window breaks the constraint, advance left to shrink it until it becomes valid again. Each index enters and leaves the window at most once, so the whole thing is O(n), even though it looks like a nested loop.

Problem: length of the longest substring without repeating characters. A "last seen index" dict lets left jump straight past the previous occurrence instead of crawling.

python
def length_of_longest(s: str) -> int:
    last: dict[str, int] = {}
    left = best = 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:
            left = last[ch] + 1          # jump past the duplicate
        last[ch] = right
        best = max(best, right - left + 1)
    return best

Prefix sums — O(1) range queries after an O(n) build

A prefix-sum array pre, where pre[i] is the sum of the first i elements, lets you answer "what is the sum of the slice [i, j)?" as pre[j] - pre[i], in constant time. The same idea powers cumulative aggregates in SQL window functions and in pandas' cumsum.

Problem: count the number of contiguous subarrays whose elements sum to exactly k. Combine a running prefix sum with a hashmap of how many times each prefix value has been seen — a single pass, no window needed.

python
from collections import defaultdict

def subarray_sum(nums: list[int], k: int) -> int:
    seen = defaultdict(int)
    seen[0] = 1                 # empty prefix sums to 0, seen once
    running = count = 0
    for x in nums:
        running += x
        count += seen[running - k]   # a prior prefix that makes the gap == k
        seen[running] += 1
    return count

Good to know for stronger interview loops

Sliding window and prefix sums are not tools you reach for daily, but they show you can think in one-pass streaming terms — exactly the mindset for processing an unbounded event stream where you cannot re-scan. Worth knowing well for the stronger interview loops.

23. Heaps & priority queues

Tier 2 · good to know, not required

When the question is "the top K", "the k closest", or "merge k sorted streams", a heap gives you the smallest or largest element in O(log n), without needing to keep everything fully sorted. Python ships one in its standard library.

A binary heap keeps the smallest (or largest) element instantly reachable while everything else stays only loosely ordered. Python's heapq operates on a plain list and is always a min-heap: the smallest element sits at index 0.

There is no max-heap in Python

heapq is min-only. For max-heap behaviour, push the negated value (heappush(h, -x)) and negate on the way out, or push a tuple with a negated key like (-count, item) so the largest count pops first. Tuples compare lexicographically, so put your sort key first.

Kth largest — a bounded min-heap of size k

Problem: return the k-th largest element in an array. Keep a min-heap that holds only the k biggest values seen so far. Its root is the smallest of those k values, which is exactly the k-th largest overall. Popping whenever the heap grows past size k caps memory at O(k) — a streaming-friendly move for when the array does not fit in memory.

python
import heapq

def find_kth_largest(nums: list[int], k: int) -> int:
    heap: list[int] = []
    for x in nums:
        heapq.heappush(heap, x)
        if len(heap) > k:          # keep only the k largest
            heapq.heappop(heap)     # drop the smallest of them
    return heap[0]                # root = smallest of the top k = kth largest

Top K frequent — Counter + heap

Problem: return the k most frequent elements. Count with Counter, then let nlargest pull the k highest counts — it runs a size-k heap internally, so it is O(n log k), cheaper than a full sort when k is small.

python
import heapq
from collections import Counter

def top_k_frequent(nums: list[int], k: int) -> list[int]:
    counts = Counter(nums)
    # nlargest by count; each item is a (value, count) pair
    top = heapq.nlargest(k, counts.items(), key=lambda kv: kv[1])
    return [value for value, _count in top]

The other heap classics follow the same shape. K closest points: push (-dist, point) onto a size-k heap. Merge k sorted lists: push the head of each list, pop the smallest, then push its successor. A streaming running median: keep a max-heap for the lower half of the values and a min-heap for the upper half, rebalancing them on every insert, so the median is always one or two lookups away. That two-heap trick is the standard tool for "latest N events" and online percentile dashboards.

Good to know for stronger / infra roles

Heaps underpin real infrastructure: priority scheduling, k-way merges when a sort spills to disk, rate limiters, and expiry timers. If you are aiming at platform or infrastructure-flavoured roles, being comfortable with heapq tuples and the two-heap median pays off.

24. Basic 1D dynamic programming

You do not need to be a DP expert — you need enough not to freeze when a simple one shows up, and to recognise the signs of a DP problem fast enough to reach for a recurrence instead of brute force.

Dynamic programming applies when a problem has two properties. The first is overlapping subproblems: the same smaller computation comes up again and again. The second is optimal substructure: the best answer is built from the best answers to smaller versions of the same problem. The method is to write the recurrence first, meaning "the answer at step n, in terms of earlier steps," and then either memoise the recursion or fill a table bottom-up.

Climbing Stairs — the Fibonacci in disguise

Problem: you can climb 1 or 2 steps at a time; how many distinct ways to reach step n? The number of ways to reach step n equals the ways to reach step n-1, then taking one more step, plus the ways to reach step n-2, then taking two more steps. That recurrence is exactly Fibonacci, so two rolling variables are enough — O(n) time, O(1) space.

python
def climb_stairs(n: int) -> int:
    a, b = 1, 1              # ways to reach step 0 and step 1
    for _ in range(n):
        a, b = b, a + b        # roll forward one step
    return a

House Robber — max over a choice with reuse

Problem: maximum money robbable from houses in a row, without robbing two adjacent houses. At each house you choose: skip it (keep the previous best) or rob it (its value plus the best up to two houses back). Take the max.

python
def rob(nums: list[int]) -> int:
    prev, cur = 0, 0          # best up to i-2 and i-1
    for x in nums:
        prev, cur = cur, max(cur, prev + x)   # skip vs rob-this-house
    return cur

Coin Change — memoization and tabulation side by side

Problem: fewest coins that sum to a target amount, or -1 if impossible. The recurrence: best(a) = 1 + min(best(a - c)) over every coin c. Here is the top-down memoised form and the bottom-up 1D table: the same recurrence, written two different ways.

python
from functools import lru_cache

# Top-down: recursion + automatic cache.
def coin_change_memo(coins: list[int], amount: int) -> int:
    @lru_cache(maxsize=None)
    def best(a: int) -> float:
        if a == 0:
            return 0
        if a < 0:
            return float('inf')
        return min((1 + best(a - c) for c in coins), default=float('inf'))
    ans = best(amount)
    return ans if ans != float('inf') else -1

# Bottom-up: fill a 1D table, dp[a] = fewest coins for amount a.
def coin_change_tab(coins: list[int], amount: int) -> int:
    INF = amount + 1                 # sentinel bigger than any real answer
    dp = [0] + [INF] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)
    return dp[amount] if dp[amount] != INF else -1

@lru_cache is the fastest way to turn any recursive solution into a memoised one: just add the decorator, and repeated calls with the same arguments return instantly. Tabulation trades away that convenience in exchange for tighter control and no recursion-depth limit to worry about. Both approaches run in O(amount × len(coins)) time.

Signs of a DP problem

Reach for DP when a problem says count the number of ways, or asks for a min/max over a sequence of choices, and those choices reuse overlapping subresults. "How many ways to…", "fewest/most … to reach…", "longest/shortest subsequence…" are the signal. If a greedy pick can be undone by a later choice, greedy fails and DP is your tool.

25. Graphs & topological sort

Tier 2 · good to know, not required

Graphs are the one DSA topic that maps directly onto real software you already use. Build systems, task schedulers, package managers: every dependency graph is a graph, and the order things run in is a topological sort, cycle detection included.

Represent a graph as an adjacency list: a dict that maps each node to the list of nodes it points to. This is compact for sparse graphs, and it gives O(1) access to a node's neighbours.

python
# A tiny directed graph as dict[node, list[node]].
graph: dict[str, list[str]] = {
    "extract":  ["clean", "join"],
    "clean":    ["join"],
    "join":     ["load"],
    "load":     [],
}

You traverse a graph almost exactly like a tree: BFS with a queue, DFS with a stack or recursion. There is one addition, though: a seen set. Unlike a tree, a graph can revisit the same node, and without a seen set your traversal could loop forever.

BFS shortest path on an unweighted graph

Problem: fewest edges (hops) from a start node to a goal node. On an unweighted graph BFS is the shortest-path algorithm: because it expands by distance, the first time you reach the goal you are on a shortest route. (For weighted edges you would reach for Dijkstra, which swaps the plain queue for a min-heap keyed by cumulative distance.)

python
from collections import deque

def shortest_path(graph: dict[str, list[str]], start: str, goal: str) -> int:
    q = deque([(start, 0)])       # (node, hops so far)
    seen = {start}
    while q:
        node, dist = q.popleft()
        if node == goal:
            return dist               # first arrival = shortest
        for nb in graph[node]:
            if nb not in seen:
                seen.add(nb)
                q.append((nb, dist + 1))
    return -1                        # goal unreachable

Topological sort — exactly how an orchestrator orders a DAG

A topological sort produces a linear order in which every task appears before everything that depends on it. This is exactly what Airflow and Dagster do to schedule a pipeline: they topologically sort the task DAG, and run each task only once everything it depends on has finished. Kahn's algorithm makes this concrete. Count each node's in-degree, meaning its number of dependencies, start with the nodes that have zero dependencies, and remove them one at a time.

Problem: given a pipeline DAG, return a valid task order — and detect a dependency cycle.

python
from collections import deque

def topo_sort(graph: dict[str, list[str]]) -> list[str]:
    indeg = {u: 0 for u in graph}
    for u in graph:                # count dependencies per node
        for v in graph[u]:
            indeg[v] += 1

    q = deque(u for u in graph if indeg[u] == 0)   # no upstreams → ready
    order = []
    while q:
        u = q.popleft()
        order.append(u)
        for v in graph[u]:          # u is done → relax its downstreams
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)

    if len(order) != len(graph):   # some node never hit in-degree 0
        raise ValueError("cycle detected — this is not a valid DAG")
    return order

# >>> topo_sort(graph)  ->  ['extract', 'clean', 'join', 'load']

A cycle means there is no valid order

If Kahn's algorithm finishes having emitted fewer nodes than the graph actually has, some nodes never reached an in-degree of zero — they depend on each other in a loop. That loop is a cycle, and a graph with a cycle is not a DAG: there is no order in which every task can run after everything it depends on. This is exactly the error an orchestrator throws when you accidentally wire task A → B → A.

Retry decorator skeleton

python
import time, functools

def retry(tries=3, delay=1.0):
    def deco(fn):
        @functools.wraps(fn)
        def wrap(*a, **kw):
            for i in range(tries):
                try:
                    return fn(*a, **kw)
                except Exception:
                    if i == tries - 1: raise
                    time.sleep(delay * 2 ** i)   # exponential backoff
        return wrap
    return deco

＊. Glossary

The core vocabulary of this guide, defined clearly. Skim it to check that you can explain each term in a sentence.

GIL (Global Interpreter Lock)
A CPython lock that lets only one thread execute Python bytecode at a time, so threads help I/O-bound work but not CPU-bound work — for parallel compute use processes or push down to an engine.
Generator
A function using yield that produces values lazily, one at a time, in constant memory — the backbone of streaming a file too big for RAM.
Iterator
Any object with __next__ that yields items until StopIteration; a for loop is shorthand for calling next() on one.
Lazy evaluation
Computing a value only when it is actually needed rather than up front — how generators and itertools avoid materialising whole collections in memory.
Comprehension
Concise syntax to build a list, set, or dict from an iterable, e.g. [x*2 for x in xs if x]; a generator expression uses parentheses and stays lazy.
Decorator
A callable that wraps a function to add behaviour (retry, timing, caching) without editing it, applied with @name above the def.
Closure
An inner function that captures variables from the enclosing scope and keeps them alive after the outer function returns — the mechanism decorators are built on.
Context manager
An object usable in a with block that guarantees setup and teardown (open/close, commit/rollback) even when an exception fires; built via __enter__/__exit__ or @contextmanager.
Dataclass
A class decorated with @dataclass that auto-generates __init__, __repr__, and equality from typed fields — ideal for config and records.
Type hint
An annotation such as x: int or -> list[str] that documents intent and lets tools like mypy catch bugs; not enforced at runtime.
Protocol
A typing construct for structural (duck) typing: any object with the right methods satisfies it, no inheritance required.
Hashmap
A key-value structure with average O(1) lookup, insert, and delete; Python's dict is one. Underlies counting, grouping, and joins.
Hashable
An object with a stable __hash__ (typically immutable — str, int, tuple) so it can be a dict key or set member; a list is not.
Set
An unordered collection of unique hashable items with O(1) membership and fast union/intersection — the go-to for dedup and "have I seen this?".
Deque
A double-ended queue (collections.deque) with O(1) append and pop at both ends — the right FIFO queue and BFS frontier.
Two pointers
An array technique using two indices moving toward or with each other to solve pair/partition problems in one O(n) pass instead of nested loops.
Sliding window
A moving sub-range over a sequence whose bounds expand/contract to maintain a property — how you compute rolling metrics in O(n).
Prefix sum
A precomputed array of cumulative totals so any range sum is answered in O(1) as pre[j] - pre[i].
BFS (breadth-first search)
Level-by-level graph/tree traversal driven by a queue; finds shortest paths in unweighted graphs.
DFS (depth-first search)
Traversal that goes as deep as possible before backtracking, driven by recursion or a stack; used for cycle detection and topological order.
Topological sort
A linear ordering of a DAG's nodes where every edge points forward — the ordering that runs task dependencies, e.g. an Airflow DAG.
DAG (directed acyclic graph)
A directed graph with no cycles; the model for build graphs, task schedulers and dependency graphs, and what topological sort operates on.
Memoization
Caching a function's result per input so repeated calls are instant; in Python often just @functools.lru_cache.
Dynamic programming
Solving a problem by combining answers to overlapping subproblems, stored to avoid recomputation; 1D DP carries a running best across one array.
Big-O
Notation for how runtime or memory grows with input size n — the order (constant, log, linear, n²) matters far more than the exact formula.
Vectorisation
Expressing an operation over a whole array/column at once so it runs in fast native code, instead of a Python-level loop — the pandas/NumPy performance mindset.
DB-API
Python's standard database interface (PEP 249): connect, cursor, execute, fetch*, commit — the shape every SQL driver follows.
Idempotency
A property where running an operation again yields the same result — critical for safe pipeline retries and backfills (e.g. upsert, not blind insert).
