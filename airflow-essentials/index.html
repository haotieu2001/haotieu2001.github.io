How Airflow actually works — the DAG model, the scheduler/executor/triggerer architecture, and the authoring habits that keep it fast in production — then the same ground for Amazon MWAA, where AWS runs that architecture for you.

A batch job that runs once, by hand, from a laptop is not a data pipeline — it is a demo. 01. What Is Apache Airflow?

Workflows as code: an orchestrator that schedules, sequences, and watches over the jobs that do the real work.

Apache Airflow is an open-source platform for programmatically authoring, scheduling, and monitoring workflows. It started in 2014 inside Airbnb, where engineers needed a way to manage a growing pile of interdependent batch jobs, and it later became a top-level project of the Apache Software Foundation. The defining idea behind it is "workflows as code": instead of describing a pipeline through a drag-and-drop UI or a pile of shell scripts glued together with cron, you describe it as ordinary Python. That code defines a graph of tasks, their dependencies, and the rules under which they should run — and Airflow takes care of executing that graph reliably, retrying what fails, and recording what happened.

Two things make it different from what it usually replaces. Cron has no concept of "wait until job A succeeds" — only "run at this time." Scripts that call each other directly do handle ordering, but leave no history to consult when someone asks what ran and why it failed. Airflow treats dependencies, retries, scheduling windows, and execution history as first-class citizens instead.

Orchestration

Coordinating a set of separate, otherwise-unaware tasks so they run in the correct order, at the correct time, with visibility into success or failure — without hard-coding that coordination logic inside the tasks themselves.

Plain example — a restaurant expediter never cooks a dish; they track which stations have finished, call out what's ready to plate, and flag anything running late. Airflow plays that same role for a fleet of computer programs.

What Airflow Is Not

Airflow is not a data-processing engine. It does not move rows, transform records, or hold data in memory — it triggers and tracks the systems that do: a Spark cluster, a warehouse query engine, an S3 copy, a training container. The practical consequence: when a task is slow, the fix is almost never "give Airflow more resources," it's giving the underlying compute more. Airflow's own footprint stays lightweight — scheduling metadata, task state, and thin calls out to other systems.

That division of labor explains its typical uses: ETL/ELT orchestration, ML pipelines (feature generation → training → evaluation → deployment, in strict order), infrastructure automation, and cross-system workflows stitching together APIs and cloud services that share no scheduler.

02. DAGs, Tasks & Operators — Core Concepts

The three nouns you need before anything else in Airflow makes sense.

Three nouns describe every Airflow workflow: the DAG (the workflow's shape), the task (one node in it), and the operator (the template that gives a task its behavior). A fourth distinction — task versus task instance — trips up more newcomers than the other three combined.

DAG (Directed Acyclic Graph)

A collection of tasks connected by directional dependencies, with no cycles — there is never a path that loops back to a task already completed. In Airflow, a DAG is defined as Python code and represents one workflow: what to run, in what order, and under what scheduling conditions.

Plain example — extract must finish before transform, which must finish before load; nothing leads back from load to extract.

Task vs. Task Instance

A task is a definition — a node declared once in your Python file, describing one unit of work. A task instance is one concrete execution of it, tied to a specific DAG run and logical date. The task is the recipe; the task instance is one specific time someone cooked it, with its own state (queued, running, success, failed, up_for_retry) and its own log file. One task definition therefore produces a new instance for every run — today's schedule, yesterday's, last week's backfill.

An operator is the class you instantiate to create a task. Airflow and its providers ship three families of them — action, transfer, and sensor — summarised below; most production DAGs mix all three. Sensors get their own treatment in Section 11.

from datetime import datetime
from airflow import DAG
from airflow.operators.bash import BashOperator
from airflow.operators.python import PythonOperator

# A minimal DAG built from classic operators
with DAG(
    dag_id="daily_report",
    start_date=datetime(2026, 1, 1),
    schedule="0 6 * * *",   # recent Airflow versions use `schedule`; older ones use `schedule_interval`
    catchup=False,
    tags=["etl", "reporting"],
) as dag:

    def _build_report(**context):
        # business logic lives in plain Python
        print(f"Building report for logical date {context['ds']}")

    extract = BashOperator(
        task_id="extract_raw",
        # {{ ds }} is Jinja templating -- Airflow fills it in with this run's
        # logical date (e.g. "2026-07-13") at execution time; see Section 07
        bash_command="extract_raw.sh {{ ds }}",
    )

    build_report = PythonOperator(
        task_id="build_report",
        python_callable=_build_report,
    )

    notify = BashOperator(
        task_id="notify_slack",
        bash_command="notify.sh 'daily report ready'",
    )

    # >> declares the dependency graph, not the order Python statements execute in
    extract >> build_report >> notify

A classic trap: "clear this task" almost always means clearing specific task instances — the failed runs for the past three days — not deleting the definition from the DAG file. Definitions live in your Python code; instances live in the metadata database and multiply with every run.

03. Airflow Architecture: Scheduler, Webserver, Metadata DB, Executor & Triggerer

A small set of cooperating processes built around one shared database — how the pieces actually talk to each other.

Airflow is not one program but a small set of cooperating processes revolving around a single relational database. The key detail is which of them talk to each other directly versus which only communicate by reading and writing shared state — almost all of it is the latter.

The Scheduler is the heart: it parses DAG files, evaluates each schedule and each task's dependencies, decides which task instances are eligible, and hands them to the executor. Since Airflow 2.0 you can run several schedulers concurrently against the same database for redundancy, with row-level locking preventing two of them from double-dispatching the same task instance.

The Metadata Database — Postgres or MySQL in any real deployment; SQLite only for local experimentation, since it can't handle concurrent writes — is the shared source of truth. Run state, task state, connections, variables, XComs and pool usage all live there.

The Webserver serves the UI and is read-mostly: it presents what the scheduler and executor already recorded, and schedules nothing itself. The Executor gets its own section (04). The Triggerer uses a single asyncio event loop to await many long-running conditions at once without holding a worker slot for each — covered with sensors in Section 11.

Executor

The pluggable component that determines how and where a ready task instance runs — as a local subprocess, a job queued to a remote worker pool, or a freshly launched Kubernetes pod. The scheduler decides what should run and when; the executor decides where the work actually happens. Section 04 compares the main executor types.

Example — with LocalExecutor, a retried task becomes a new subprocess on the scheduler's own machine; with KubernetesExecutor, that same retry spins up an entirely new pod.

The DAG File Processor

Parsing every .py file in the DAGs folder into DAG objects is separate work from making scheduling decisions. On small deployments it runs as a thread inside the scheduler; on larger ones, recent Airflow versions can split it into its own process so one slow or buggy DAG file can't stall scheduling for everything else.

ComponentPrimary responsibilityTalks to metadata DB?
DAG filesPython source defining DAGs, parsed on a scheduleNo — read from disk/object storage
SchedulerParses DAGs, decides what runs next, dispatches to the executorYes — heaviest reader/writer
Executor / workersActually runs task instancesYes — writes task state and logs metadata
WebserverServes the Airflow UIYes — mostly reads
TriggererAwaits deferred conditions asynchronouslyYes — reads/writes deferred task state

The practical consequence of that design: a healthy, appropriately-sized Postgres or MySQL instance matters as much to Airflow's reliability as the scheduler process. If the database is slow, nearly every component feels it.

04. Executors Compared: Sequential, Local, Celery & Kubernetes

One setting that decides whether your DAGs run one at a time on a laptop or across a fleet of machines.

The executor is one configuration value — core.executor — that shapes how a deployment scales, fails, and costs money. The table below compares all five; what follows is the reasoning the table can't hold.

SequentialExecutor is the out-of-the-box default, paired with SQLite. It exists only so a fresh install can run its first DAG with no setup. LocalExecutor is the smallest genuinely production-usable step up: parallel subprocesses on the scheduler's own machine, requiring a real database.

CeleryExecutor hands tasks to remote workers through a broker (Redis or RabbitMQ); workers report back through the metadata database, so you absorb load by adding workers. This is the model AWS MWAA runs under the hood, as a managed auto-scaling Fargate fleet — see Section 15. KubernetesExecutor trades startup latency for isolation: a brand-new pod per task instance, each with its own resource limits and no leftover state. CeleryKubernetesExecutor routes per task by queue name, for when most tasks are light but a few need real isolation.

ExecutorParallelism modelTypical infraBest fitMain trade-off
SequentialExecutorNone — one task at a timeSQLite, single processFirst-run tutorials onlyNo concurrency, no production safety
LocalExecutorParallel subprocesses, one machinePostgres/MySQL, single hostSmall/medium single-box deploymentsScales only as far as that one machine
CeleryExecutorDistributed queue to remote workersRedis/RabbitMQ + worker fleetHorizontal scale across many machinesBroker & worker fleet to operate
KubernetesExecutorOne ephemeral pod per taskKubernetes clusterMaximum isolation, per-task resourcesPod cold-start latency per task
CeleryKubernetesExecutorHybrid, routed by queue nameBroker + worker fleet + KubernetesMostly light tasks, a few heavy onesMost moving parts to maintain

Choosing an Executor

Two questions settle it: does the workload need capacity beyond one machine, and does task-to-task isolation matter? A modest number of DAGs on one well-sized server rarely needs more than LocalExecutor. Hundreds of DAGs across many teams, with wildly varying per-task resource needs, pushes you toward Kubernetes or the hybrid.

Staying on the SequentialExecutor + SQLite defaults by accident is worse than it sounds: the symptom is usually silent task-queuing delays or corrupted metadata, not a clear error message.

05. Writing DAGs: TaskFlow API, Classic Operators & Dependencies

Two syntaxes, one dependency graph underneath.

However a DAG is written, it produces the same thing: a graph of tasks connected by upstream/downstream dependencies. Only the Python surface differs. The classic style instantiates an operator class with a task_id and wires dependencies explicitly. The TaskFlow API (Airflow 2.0) is a decorator layer — @dag, @task — that turns plain functions into tasks and infers dependencies from how you pass one function's result into another.

Both compile to the same DAG and BaseOperator objects; TaskFlow is sugar over PythonOperator, not a separate engine. So you can mix the two styles freely in one DAG and wire them together with the same >> syntax either way.

Dependency (upstream / downstream)

A dependency declares that one task must reach a terminal state before another is eligible to run. a >> b makes a upstream of b (and b downstream of a); the equivalent explicit calls are a.set_downstream(b) / b.set_upstream(a).

extract >> transform >> load — load runs only after transform succeeds, which runs only after extract succeeds.

Classic operators

In the classic style you import an operator class, instantiate it with a unique task_id inside a with DAG(...) as dag: block, and chain the resulting objects with >>. Data moves between tasks only via explicit XCom calls (see Section 06) — there is no automatic wiring.

from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

def extract(**context):
    context["ti"].xcom_push(key="rows", value=1000)

def transform(**context):
    rows = context["ti"].xcom_pull(task_ids="extract", key="rows")
    context["ti"].xcom_push(key="rows", value=rows * 2)

def load(**context):
    rows = context["ti"].xcom_pull(task_ids="transform", key="rows")
    print(f"Loading {rows} rows")

with DAG(
    dag_id="etl_pipeline_classic",
    schedule="@daily",
    start_date=datetime(2026, 1, 1),
    catchup=False,
) as dag:
    extract_task = PythonOperator(task_id="extract", python_callable=extract)
    transform_task = PythonOperator(task_id="transform", python_callable=transform)
    load_task = PythonOperator(task_id="load", python_callable=load)

    extract_task >> transform_task >> load_task

TaskFlow API

The same pipeline in TaskFlow style: functions decorated with @task become tasks automatically when called inside a @dag-decorated function, and passing one function's return value directly to another wires both the dependency edge and the XCom push/pull for you — no manual xcom_push/xcom_pull required.

from airflow.decorators import dag, task
from datetime import datetime

@dag(
    dag_id="etl_pipeline_taskflow",
    schedule="@daily",
    start_date=datetime(2026, 1, 1),
    catchup=False,
)
def etl_pipeline():

    @task
    def extract() -> int:
        return 1000

    @task
    def transform(rows: int) -> int:
        return rows * 2

    @task
    def load(rows: int) -> None:
        print(f"Loading {rows} rows")

    load(transform(extract()))

etl_pipeline()

For new Python-centric DAGs, prefer TaskFlow — it removes boilerplate and eliminates a whole class of XCom key-mismatch bugs. Classic operators are not deprecated: anything backed by a provider package (S3, Redshift, Snowflake, dbt, Kubernetes pods) is still written that way.

More Ways to Define Dependencies

Beyond >>/<<, three patterns are worth knowing: a list on either side of >> fans out or in without a loop; chain() wires a long linear sequence more readably; and cross_downstream() does the one thing a list can't — connect every task in one group to every task in another, a true many-to-many rather than a shared fan-in point.

from airflow.models.baseoperator import chain, cross_downstream

# fan-in: both extracts must succeed before transform runs
[extract_a, extract_b] >> transform

# a long linear sequence, more readable than a >> b >> c >> d >> e
chain(extract, validate, transform, load, notify)

# every task in the first list becomes upstream of every task in the second --
# four edges created here, not just two
cross_downstream([extract_a, extract_b], [transform_a, transform_b])

Templating with Jinja & the Airflow Context

Most operator parameters — bash_command, sql, a file path, an S3 key — are templated fields: Airflow treats the string as a Jinja template and renders it at execution time, not parse time. That's why {{ ds }} works at all: not Python interpolation, but Jinja substitution from a dictionary of runtime values called the context (roughly three dozen keys; the common ones are tabulated below).

Templated fields receive the context automatically. Inside a plain Python callable you get it three ways: accept **kwargs and read keys off it, call get_current_context() from anywhere inside a running task, or — in TaskFlow only — name a parameter after a context key (ds: str) and let Airflow inject it.

Airflow context

The dictionary of runtime values — logical date, DAG run, task instance, params, and macros — that Airflow makes available to every task and every templated field, refilled fresh for each run.

Example: bash_command="load.sh {{ ds_nodash }}" renders to load.sh 20260713 for the run whose logical date is 2026-07-13 — the same template text produces a different command every single run, without the DAG author writing any date-formatting code.

Context keyWhat it holds
dsLogical date as YYYY-MM-DD, e.g. 2026-07-13
ds_nodashLogical date with no separators, e.g. 20260713
tsLogical date/time as a full ISO 8601 timestamp
prev_ds / next_dsThe previous / next scheduled logical date, as YYYY-MM-DD
ti / task_instanceThe running TaskInstance object — used for XCom push/pull, retry count, etc.
dag / dag_runThe current DAG and DagRun objects
paramsParameters merged from the DAG's own params and any triggering conf
var.value.xShortcut for reading Airflow Variable x directly inside a template
macrosA namespace of helpers — macros.datetime, macros.timedelta, and more, for date arithmetic inside a template
from airflow.decorators import task
from airflow.operators.python import get_current_context

@task
def summarize_run(ds: str):              # TaskFlow auto-injects `ds` by parameter name
    print(f"Summarizing logical date {ds}")

@task
def log_task_instance():
    context = get_current_context()      # works anywhere inside a running task
    ti = context["ti"]
    print(f"Running as {ti.task_id}, attempt {ti.try_number}")

Two knobs matter once the built-in keys aren't enough. user_defined_macros and user_defined_filters (both passed to the DAG constructor) add your own names and Jinja filters for formats your team reuses. And in a custom operator (Section 10), the class attribute template_fields = ("sql", "bucket_key") declares which __init__ parameters get rendered — omit it and {{ ds }} reaches your logs unrendered as a literal string.

When a templated field renders to something unexpected, use airflow tasks render <dag_id> <task_id> <logical_date> (or the "Rendered Template" tab in the UI, next to the Log tab covered in Section 13) to see exactly what Jinja produced for that specific run — far faster than guessing from the DAG source alone.

06. XComs: Passing Data Between Tasks

A message-passing shortcut through the metadata database — built for pointers, not payloads.

XCom ("cross-communication") lets one task hand a small piece of data to another. A task pushes a value — explicitly with ti.xcom_push(key, value), or implicitly by returning it, which Airflow stores under the key return_value — and a downstream task pulls it with ti.xcom_pull() or, in TaskFlow, just by receiving it as a function argument.

Every pushed value is serialized and stored as a row in the metadata database, which is the whole reason XComs have a size ceiling. A DataFrame or file contents pushed through XCom gets written into that database and rendered back in the webserver UI — bloating the database, slowing every query touching the xcom tables, and in bad cases making the Grid view crawl.

So for anything beyond small metadata: write the real data to durable storage in the producing task, and pass only a reference — the S3 key, the table name, a row count.

XCom

A small, serialized value stored in the metadata database that one task instance pushes and another pulls, scoped to a specific DAG run.

extract writes a CSV to s3://lake/raw/2026-07-13/report.csv and pushes that key; process pulls the key and reads the file from S3 — the file itself never touches XCom.

from airflow.operators.python import PythonOperator

def _extract(**context):
    file_path = "s3://lake/raw/2026-07-13/report.csv"
    context["ti"].xcom_push(key="file_path", value=file_path)   # explicit push

def _process(**context):
    file_path = context["ti"].xcom_pull(task_ids="extract", key="file_path")  # explicit pull
    print(f"Reading {file_path}")

extract_task = PythonOperator(task_id="extract", python_callable=_extract)
process_task = PythonOperator(task_id="process", python_callable=_process)
extract_task >> process_task

# --- equivalent, implicit, TaskFlow style ---
from airflow.decorators import task

@task
def extract() -> str:
    return "s3://lake/raw/2026-07-13/report.csv"   # auto-pushed as return_value

@task
def process(file_path: str) -> None:              # auto-pulled as an argument
    print(f"Reading {file_path}")

process(extract())

For payloads between "pointer" and "large data," configure a custom XCom backend — Airflow's backends are pluggable, and the common implementation transparently stores the serialized value in S3 while keeping only a reference in the database. It raises the ceiling for moderate metadata; it does not license passing datasets.

07. Scheduling: Timetables, start_date, Catchup & Backfill

The interval ends before the run begins — and that single fact explains most scheduling confusion.

start_date is not "when the DAG starts running" — it is the earliest logical date Airflow will schedule a run for. The scheduler compares it against the DAG's schedule: a cron string, a timedelta, a preset like @daily, or a custom Timetable object for schedules that aren't fixed intervals ("every weekday except public holidays").

The most confusing mechanic in Airflow is that a run for an interval fires after that interval fully elapses, not at its start. Older docs called the interval start execution_date, which many people misread as "when this executes." The current terms are clearer: every run has a data interval start and end, the logical date is conventionally the start, and the run is queued only once the end has passed.

Cron Expressions, Timedeltas & Presets

Cron expression

Five whitespace-separated fields in a fixed order: minute (0–59), hour (0–23), day of month (1–31), month (1–12), day of week (0–6, Sunday = 0). Within a field, * means "any," 1,15 means those specific values, 1-5 an inclusive range, and */15 every 15 units.

Reading order: 0 6 * * * is "minute 0, hour 6, any day, any month, any weekday" — 6:00 AM daily.

Cron expressionMeaning
0 6 * * *Every day at 06:00
*/15 * * * *Every 15 minutes, all day, every day
0 */4 * * *Every 4 hours, on the hour (00:00, 04:00, 08:00, ...)
0 9 * * 1-59:00 AM, Monday through Friday only
30 2 * * 02:30 AM every Sunday
0 0 1 * *Midnight on the 1st of every month
0 0 1 1 *Midnight on January 1st every year

Two alternatives cover most other cases. A plain timedelta (schedule=timedelta(hours=6)) suits intervals that needn't land on clean clock boundaries — every 6 hours from start_date, rather than at 00:00/06:00/12:00/18:00. And Airflow ships presets as shorthand for the most common crons.

PresetEquivalent toMeaning
@once—Schedule exactly one run, ever, then never again automatically
@hourly0 * * * *Once at the top of every hour
@daily0 0 * * *Once at midnight every day
@weekly0 0 * * 0Once at midnight every Sunday
@monthly0 0 1 * *Once at midnight on the 1st of every month
@yearly / @annually0 0 1 1 *Once at midnight on January 1st
@continuous—Start a new run immediately after the previous one finishes — for DAGs that should always be running
None—No automatic schedule at all; the DAG only runs when explicitly triggered (see below)

Swapping the day-of-month and day-of-week fields is a common typo from other cron dialects, and because both accept small integers it produces a valid-but-wrong schedule rather than an error. Test an unfamiliar cron string before trusting it in production.

Logical date / data interval

The date-time window a DAG run represents. The run's logical date is the interval's start, but the run is not scheduled until the interval's end has passed.

For a @daily DAG, the run labeled 2026-07-13 covers [2026-07-13 00:00, 2026-07-14 00:00) and is triggered at 2026-07-14 00:00.

Catchup vs. backfill

catchup controls what happens when a DAG is deployed or unpaused with a start_date in the past. With catchup=True — historically the default — the scheduler creates a run for every missed interval since start_date, as fast as slots allow. Deploy a daily DAG today with start_date=datetime(2024, 1, 1) and you get 900-plus runs queued instantly, which can overwhelm shared resources or hammer downstream APIs. catchup=False runs only from the most recent completed interval forward.

Backfill is the deliberate counterpart: running a chosen past range on purpose, via airflow dags backfill -s <start> -e <end> <dag_id> or by re-triggering past runs in the UI. The difference is intent — catchup is a side effect of scheduling logic, backfill is a decision, usually made after fixing a bug in transformation logic.

Triggering DAG Runs Outside the Schedule

Three mechanisms start a run on demand, all producing the same DAG run object the scheduler would, just with run_type=manual. Manual triggering — the UI's "Trigger DAG" button or airflow dags trigger <dag_id> — runs it now, optionally with a JSON conf payload the tasks can read from the context. The REST API (POST /dags/{dag_id}/dagRuns) does the same programmatically, which is how a webhook or CI pipeline kicks off a DAG. TriggerDagRunOperator is a task inside DAG A that starts DAG B, optionally blocking on it with wait_for_completion=True.

Don't confuse this with trigger_rule in Section 08: trigger_rule decides whether an already-scheduled task may start given its upstreams' states; triggering decides whether a DAG run exists at all.

from airflow.operators.trigger_dagrun import TriggerDagRunOperator

kick_off_report = TriggerDagRunOperator(
    task_id="kick_off_report",
    trigger_dag_id="summary_report",       # the DAG to start
    conf={"source": "manual_reprocess"},   # available in the triggered run's context
    wait_for_completion=True,              # block this task until summary_report finishes
    poke_interval=30,
)

TriggerDagRunOperator is heavier coupling than the Dataset-based scheduling in Section 12. Prefer a Dataset when you only care that data became available; reach for the operator when you specifically need to control and wait on another DAG's execution.

08. Task Execution Semantics: Retries, Timeouts, Trigger Rules & SLAs

Controlling not just whether a task runs, but how it fails, how long it waits, and what upstream state it demands.

Each task carries execution controls that decide its resilience. retries sets automatic re-attempts, paired with retry_delay and optionally retry_exponential_backoff=True. execution_timeout is a hard ceiling: exceed it and the task is killed and marked failed.

sla looks like a timeout and is not one. It defines an expected maximum duration from the DAG run's start, and a miss fires an event — logged, optionally sent to an sla_miss_callback — but it does not stop, kill, or fail anything. If you need a task actually stopped after a duration, that's execution_timeout. (The classic sla mechanism was removed from core in Airflow 3.0 pending a successor; check your version's release notes.)

trigger_rule decides eligibility from the status of upstream tasks, not merely whether they finished. The default all_success demands every upstream succeed; all_done, one_success, all_failed, none_failed and one_failed enable patterns like a cleanup step that runs however things land, or a notifier that fires only on breakage.

from airflow.operators.python import PythonOperator
from airflow.utils.trigger_rule import TriggerRule
from datetime import timedelta

def call_partner_api():
    ...  # may fail transiently or run long

fetch_task = PythonOperator(
    task_id="fetch_partner_data",
    python_callable=call_partner_api,
    retries=3,
    retry_delay=timedelta(minutes=5),
    retry_exponential_backoff=True,
    execution_timeout=timedelta(hours=1),
)

cleanup_task = PythonOperator(
    task_id="cleanup_task",
    python_callable=lambda: print("releasing temp resources"),
    trigger_rule=TriggerRule.ALL_DONE,   # runs whether upstream succeeded or failed
)

09. Dynamic Task Mapping & Task Groups

Grouping tasks for humans vs. multiplying tasks for data — two different problems that both look like "lots of boxes"

Two unrelated needs get conflated here. One is organizational: a 40-task DAG is unreadable in the graph view unless related tasks collapse into one node. The other is structural: you often don't know how many tasks you need until the DAG is running — the number of files in a directory, partitions in a table, rows from a query.

Task Groups solve the first problem. A TaskGroup is purely a UI and organizational construct — it changes how tasks are drawn in the Graph view (collapsible into one node with a group_id prefix on each contained task's ID) but has zero effect on scheduling, parallelism, or execution semantics. The tasks inside still run exactly as their own dependencies dictate.

Dynamic Task Mapping, introduced in Airflow 2.3, solves the second problem. Instead of writing process_file_1, process_file_2, process_file_3... by hand, you write one mapped task definition and call .expand() on it; Airflow creates one task instance per element in the collection at runtime, after the upstream data is known. Each mapped instance gets its own log, its own retry behavior, and its own entry in the UI (shown as process_file[0], process_file[1], and so on).

Expand, expand_kwargs, and partial

Three forms cover the variations. .expand(arg=upstream.output) maps one keyword argument over a list. .expand_kwargs() takes a list of dictionaries and maps one dictionary per instance — for when several parameters vary together. And .partial() binds the arguments that should stay fixed before you chain .expand() for the varying ones: process_file.partial(bucket="raw-data").expand(filename=files).

# dynamic_mapping_example.py
from airflow.decorators import dag, task
from datetime import datetime

@dag(schedule=None, start_date=datetime(2024, 1, 1), catchup=False)
def process_incoming_files():

    @task
    def list_files() -> list[str]:
        # in practice: os.listdir(), an S3 ListObjects call, etc.
        return ["a.csv", "b.csv", "c.csv"]

    @task
    def process_file(filename: str) -> dict:
        # runs once per mapped instance: process_file[0], [1], [2]...
        return {"filename": filename, "rows": 1000}

    @task
    def summarize(results: list[dict]):
        total = sum(r["rows"] for r in results)
        print(f"processed {len(results)} files, {total} rows total")

    files = list_files()
    processed = process_file.expand(filename=files)
    summarize(processed)

process_incoming_files()

Watch the map length. Nothing stops .expand() from producing thousands of task instances if the upstream list is that large — but each mapped instance is a real row in the metadata database and a real node the webserver has to render. Airflow enforces a configurable ceiling via core.max_map_length (default 1024) precisely because unbounded fan-out can bog down the scheduler and make the UI sluggish. If you're mapping over genuinely huge collections, consider chunking the input (map over batches of 500 rather than individual rows) instead of raising the limit.

10. Connections, Variables, Hooks & Providers

How Airflow talks to everything that isn't Airflow

Airflow's core distribution is deliberately thin — scheduler, webserver, and DAG-authoring primitives, but almost none of the integrations needed to reach S3, Snowflake, Postgres, or Slack. Four concepts bridge that gap: Connections hold credentials, Hooks wrap a system's client library using those credentials, Operators package a hook into a ready-made task, and Providers are the installable packages bundling all three — separately versioned, released on their own schedule rather than with Airflow core.

A Connection stores everything needed to reach an external system: host, schema, login, password, port, and an arbitrary extra JSON blob for anything system-specific (region, role ARN, SSL mode, and so on). Connections are created through the Airflow UI (Admin → Connections), the CLI (airflow connections add), environment variables (AIRFLOW_CONN_<CONN_ID>), or — in production — a secrets backend. Code never references the credentials directly; it references a conn_id string, and Airflow resolves that string to the actual secret at task-execution time.

A Variable is a simpler key-value store for configuration that isn't a credential: a bucket name, a feature flag, a list of tables. Read it with Variable.get("my_var") or {{ var.value.my_var }} in a template. Where you call it matters: at a DAG file's top level, every lookup becomes a database query on every parse cycle (see Section 14). Read variables inside task functions, or use the Jinja form, which defers to execution time.

A Hook is the lower-level client wrapper: PostgresHook, S3Hook, SlackHook, and dozens more. A hook takes a conn_id, resolves the Connection, authenticates, and exposes Pythonic methods (hook.run(sql), hook.check_for_key(key, bucket_name)) instead of making you construct a boto3 or psycopg2 client by hand. Most built-in operators are themselves thin wrappers around a hook — and when no existing operator fits your exact logic, you can call a hook directly from inside a PythonOperator or @task function.

Building Custom Operators, Hooks & Sensors

When nothing existing fits logic your team repeats, subclass the same base classes the built-ins use. A custom hook subclasses BaseHook and wraps a client library the way S3Hook wraps boto3. A custom operator subclasses BaseOperator, takes its parameters in __init__, and does the work in execute(self, context) — whose return value becomes the task's XCom return_value. A custom sensor subclasses BaseSensorOperator and implements poke(), inheriting poke/reschedule mode for free.

They earn their cost when the same logic must be reused, tested, and documented as one named building block across teams. For a one-off, a plain @task calling an existing hook is simpler and no worse — don't write an operator class to wrap a single call site. Package the ones you do build as a plugin (plugins.zip, per Section 16) or as an installable package if more than one environment needs it.

# custom_operators/reconciliation_operator.py
from airflow.models import BaseOperator
from airflow.providers.amazon.aws.hooks.s3 import S3Hook

class S3RowCountCheckOperator(BaseOperator):
    # custom operators are ordinary classes -- __init__ takes the parameters
    # this task needs, execute() does the work when the task actually runs
    def __init__(self, bucket_name, prefix, min_rows, aws_conn_id="aws_default", **kwargs):
        super().__init__(**kwargs)
        self.bucket_name = bucket_name
        self.prefix = prefix
        self.min_rows = min_rows
        self.aws_conn_id = aws_conn_id

    def execute(self, context):
        hook = S3Hook(aws_conn_id=self.aws_conn_id)
        keys = hook.list_keys(bucket_name=self.bucket_name, prefix=self.prefix) or []
        if len(keys) < self.min_rows:
            raise ValueError(f"Expected at least {self.min_rows} files, found {len(keys)}")
        return len(keys)   # becomes this task's XCom return_value

Add template_fields = ("prefix",) as a class attribute and that parameter runs through Jinja at execution time, exactly like a built-in operator's sql — so a DAG author can pass prefix="daily/{{ ds }}/" and have it resolve per run, without your operator knowing anything about dates.

Airflow discovers packaged components two ways. A plugins.zip in the plugins folder (or synced by MWAA, per Section 16) is picked up at the next restart — fine for one environment. An installable package registers itself via Python entry points, the same mechanism every provider uses, so it can be versioned and reused across deployments without copying files by hand.

11. Sensors & Deferrable Operators — the Triggerer

Waiting for something to happen without paying for a worker slot the whole time

A huge share of real pipelines start with "wait until X exists" — a file lands, an upstream DAG finishes, an S3 key appears. Airflow's answer is the Sensor, a special operator subclass whose poke() method returns true once its condition is satisfied. Common examples include FileSensor (waits for a file on disk), ExternalTaskSensor (waits for a task in another DAG to reach a given state), and S3KeySensor (waits for an object to exist in S3). Downstream tasks simply depend on the sensor like any other task.

The naive way to wait is expensive. In mode="poke" (the historical default) the sensor holds a full worker slot for its entire wait, checking on a poke_interval and idling in between — a six-hour wait on a 16-slot pool burns 1/16th of your execution capacity doing nothing. mode="reschedule" releases the slot between checks, holding one only for the moment it pokes, at the cost of a small gap between checks.

Deferrable operators (Airflow 2.2) go further: the task suspends entirely and hands its condition to the Triggerer, whose single asyncio event loop can watch thousands of conditions at once because each is an async poll rather than a blocking call. A worker is claimed only for the seconds needed to resume once the condition is met. Many provider sensors ship deferrable versions — either a class suffixed Async or a deferrable=True parameter.

Poke modeOccupied for the entire waitPoor — one slot per waiting sensormode="poke" (default)
Reschedule modeReleased between checksBetter, but still a fixed check intervalmode="reschedule"
Deferrable operatorNone — no worker claimed while waitingHigh — one Triggerer handles thousands of waitsdeferrable=True, e.g. TimeSensorAsync
# reschedule mode: releases the worker slot between checks
from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor

wait_for_export = S3KeySensor(
    task_id="wait_for_export",
    bucket_name="reporting-exports",
    bucket_key="daily/{{ ds }}/export.csv",
    mode="reschedule",
    poke_interval=300,
    timeout=60 * 60 * 6,
)

# deferrable: no worker slot held at all while waiting
wait_for_export_deferrable = S3KeySensor(
    task_id="wait_for_export_deferrable",
    bucket_name="reporting-exports",
    bucket_key="daily/{{ ds }}/export.csv",
    deferrable=True,
    timeout=60 * 60 * 6,
)

Poke-mode sensors are a classic way to silently exhaust a deployment. A handful of long poke-mode sensors scheduled together can consume every worker slot, after which no task in any DAG can start — and the deployment looks "stuck" with no error, because nothing failed. For long waits, default to reschedule or a deferrable equivalent.

12. Datasets & Data-Aware Scheduling

Triggering a DAG when data is actually ready, not when the clock says it probably is

Time-based scheduling assumes you can predict when upstream data will be ready and pick a safe cron time after it. That safety margin is a guess, and guesses fail two ways: run too early and you process incomplete data, or pad the buffer so generously that reports are needlessly hours late. Datasets (Airflow 2.4) trigger on the data actually being updated instead.

A Dataset is identified by a URI string — conventionally something like s3://bucket/cleaned_data/, though Airflow does not validate or resolve the URI itself; it's an opaque logical identifier. A producing task declares it updates a dataset via the outlets parameter. A consuming DAG sets its schedule (in place of a cron expression) to a list of one or more Dataset objects; Airflow triggers that DAG automatically once every listed dataset has been updated at least once since the consumer's last run. If a downstream DAG depends on three datasets produced by three different upstream DAGs, it waits for all three before running — no cron guessing required.

A dedicated Datasets view in the UI shows which DAGs produce and consume each one — cross-DAG lineage that would otherwise be invisible outside each DAG's code. Compared with polling via ExternalTaskSensor, this is far lighter: no sensor task, no worker slot, and neither DAG needs the other's task IDs — only the shared URI. Airflow 3.0 generalised the idea into "Assets"; the producer/consumer model here is its foundation.

    def build_report():
        ...

Because the coupling is only a URI, either DAG can be renamed, split, or restructured internally without breaking the other. Reach for ExternalTaskSensor only when you need to react to one specific task's state — including its failure — rather than "this data was updated."

13. Monitoring, Logging, Alerting & the Airflow UI

Reading the Grid and Graph views, finding logs when workers are ephemeral, and wiring failures to a pager.

The UI is built around two complementary views of the same data. The Grid view lays runs out as columns and tasks as rows, so each cell is one task instance's state — the fastest way to answer "has this task been flaky for two weeks." The Graph view shows one run's dependency structure with each node coloured by state, answering "where exactly did today's run stop." Airflow 3.0 reworked the look and navigation, but both concepts carry over.

Both lean on the same vocabulary of task instance states, below. You'll also find a Gantt view for timing, a Calendar view for missed runs, and a Code view showing what the scheduler actually parsed.

Task instance state

success — the task's callable ran to completion without raising.

running — a worker currently has the task checked out and is executing it right now.

failed — the task raised (or was killed) and has exhausted all configured retries.

upstream_failed — an upstream dependency failed or was skipped in a way that blocks this task, so it was never attempted.

skipped — a branch operator, trigger rule, or short-circuit decided this task should not run this time.

up_for_retry — the task failed but retries remain; it is waiting out retry_delay before trying again.

queued — the scheduler has handed the task to the executor, which hasn't yet started it on a worker.

Logging: local disk vs. remote logging

Every task attempt writes its own log — stdout/stderr plus Airflow's lifecycle lines — to a configured location, by default local disk on whichever machine ran the task. That breaks the moment workers are ephemeral: with autoscaled Celery workers or Kubernetes pods torn down after the task finishes, "local disk" is a filesystem that no longer exists by the time you go looking.

Production deployments configure remote logging: logs stream to durable blob storage — S3, GCS, Azure Blob — as the task runs, and the webserver fetches them from there regardless of which worker produced them.

The remote-logging trap. Nothing looks wrong while tasks succeed. The gap appears the first time one fails, the pod is already garbage-collected, and the one log you need is gone. Configure remote logging before adopting ephemeral workers, not after the first unexplained outage.

Alerting: callbacks and built-in email hooks

Callbacks attach arbitrary Python to lifecycle events: on_failure_callback, on_success_callback, on_retry_callback and sla_miss_callback, set per task or in a DAG's default_args so every task inherits them. Each receives the context dictionary — task instance, DAG, date, exception — which is enough to post to Slack, open a PagerDuty incident, or emit a metric. The simpler email_on_failure and email_on_retry parameters need no code but are far less flexible.

14. Security & Production Best Practices

RBAC, secrets backends, and the authoring habits that keep the scheduler fast and retries safe.

"Production-ready" is two separate problems that get lumped together: securing who can see and do what, and writing DAGs that don't quietly damage the system running them.

On access control, the webserver ships RBAC with default roles of increasing restriction — Admin, Op, User, Viewer, Public — plus custom roles scoped to specific DAGs, so a role can be limited to one team's namespace. Credentials shouldn't sit in the metadata database at all: a secrets backend (AWS Secrets Manager, Vault, GCP Secret Manager) resolves connection and variable values at runtime from an external vault. At the network layer, restrict who can reach the webserver, and keep the metadata database unreachable from anything but the Airflow components that need it.

Idempotency: the habit that makes retries safe

Airflow re-runs tasks — retries, manual clears, backfills — far more often than you plan for. Idempotency is what turns "just re-run it" from a risky guess into a boring operation.

Idempotency

A DAG run for a given logical date produces the same end result no matter how many times, or in what order, it is re-executed.

Not idempotent: INSERT INTO daily_metrics SELECT * FROM staging WHERE ds = '{{ ds }}' — rerunning it duplicates every row.

Idempotent: DELETE FROM daily_metrics WHERE ds = '{{ ds }}'; INSERT INTO daily_metrics SELECT * FROM staging WHERE ds = '{{ ds }}' — or a native MERGE / INSERT ... ON CONFLICT DO UPDATE — so a rerun overwrites rather than appends.

Keep DAG files cheap and dumb

Top-level code — anything not inside a task function — runs every time the file processor parses that file, on a short interval, for every DAG in the folder. An API call or slow computation at the top level doesn't just slow its own DAG; it slows every parse cycle, competing for the resources every other DAG needs to get scheduled.

So keep top-level code to cheap static definitions — operator instantiation, dependency wiring — and push real work into task functions. Then test the structure like any other code: unit-test task logic directly, use dag.test() to run a DAG locally without a scheduler, and add a CI check that simply imports every DAG file. Catching a broken DAG at review time is much cheaper than noticing the scheduler quietly stopped loading it.

15. AWS MWAA: Overview & Architecture

Same Airflow you've been reading about, minus the pager for the infrastructure underneath it.

MWAA — Amazon Managed Workflows for Apache Airflow — is a fully managed AWS service that runs Apache Airflow on your behalf. Instead of standing up and operating the scheduler, webserver, metadata database, and executor yourself, you point MWAA at an S3 bucket containing your DAGs, and AWS provisions, patches, scales, and monitors the Airflow components for you, inside a VPC you designate. The trade you're making is explicit: you give up direct control over — and direct access to — the underlying infrastructure, in exchange for not having to run it.

One environment is one complete deployment, tied to exactly one VPC, one S3 bucket, and one set of size and autoscaling settings. Scheduler, workers, webserver and metadata database all live inside it.

What runs where

Every Airflow component runs as a task on AWS Fargate — serverless containers, so there's no EC2 fleet to patch — inside private subnets of a VPC you provide. MWAA requires at least two private subnets across two Availability Zones, so an environment survives losing one AZ.

The metadata database is an Aurora (PostgreSQL-compatible) cluster MWAA creates and manages; you cannot connect to it, query it, or pick its engine version. The executor is a managed Celery executor — MWAA doesn't expose the choice that Section 04 compares — and worker capacity autoscales on queue depth within limits you set. Amazon SQS is the broker underneath, an implementation detail rather than a resource you provision or tune.

Your side of the contract is the S3 bucket: a dags/ prefix, an optional plugins.zip, and a requirements.txt, all synced into the running environment automatically. The webserver is either public (behind AWS-managed auth) or, in private access mode, reachable only from your VPC or a network connected to it.

What you explicitly give up: executor choice, and any direct access to the metadata database — so no ad-hoc SQL against task instance history, and no custom monitoring queries against Aurora. That's the deliberate trade for not operating a scheduler, a broker, and a database cluster yourself.

16. Setting Up & Operating an MWAA Environment

No servers to SSH into — just an S3 bucket, an IAM role, and a few dials AWS turns for you.

On MWAA, AWS owns the scheduler, webserver, database, executor and broker; what you configure is a much smaller declarative surface — an S3 bucket layout, an IAM role, a size tier, and a networking choice.

Every environment is anchored to one S3 bucket whose layout is not arbitrary: MWAA looks for specific prefixes and object names. Enable versioning on it — that's your rollback path when a bad DAG or broken requirements.txt lands. The DAG processor polls the bucket on a short interval, so deploying is just aws s3 cp: no server to push to, no container to rebuild, no restart for a plain DAG change.

Two objects in that bucket carry more weight than a DAG file. plugins.zip holds custom operators, hooks and UI plugins; requirements.txt pins the environment's Python packages. Because both change the interpreter the scheduler and workers run in, editing either triggers a rebuild and restart that briefly interrupts scheduling. AWS publishes a "local-runner" Docker image reproducing MWAA's install process, so validate requirements.txt locally first.

Execution role (MWAA)

The IAM role MWAA assumes on your behalf to read your S3 bucket, ship logs to CloudWatch, and reach any AWS service your DAG code touches. There is exactly one per environment, and every permission any task in any DAG needs must be attached to it.

Example: a task calling S3Hook.download_file() needs s3:GetObject on that bucket in the role's policy. Without it the DAG still parses and appears in the UI — the failure surfaces only at run time as an access-denied error in the task log, which is why it catches teams off guard.

An environment is sized by an environment class — a few predefined tiers setting baseline scheduler and webserver capacity — and separately by minimum and maximum worker counts, which bound MWAA's autoscaling as load rises and falls. You're tuning capacity, not choosing an executor.

The last major decision is the webserver's networking mode. Public mode puts the UI on the internet, still gated by IAM permissions and a generated token mapped to an Airflow RBAC role rather than a separate Airflow password database. Private mode restricts it to your VPC or a network connected to it via Direct Connect, VPN, or peering — the better default for sensitive data, since it removes an entire class of internet-facing exposure regardless of how strong Airflow's own auth is.

17. MWAA Integrations with the AWS Ecosystem

MWAA rarely moves data itself — it tells other AWS services when to move it.

MWAA is the conductor, not the orchestra. Almost nothing in a well-designed DAG processes data directly — tasks call operators and hooks from apache-airflow-providers-amazon that reach out to purpose-built services doing the actual work, while Airflow handles sequencing, retries, backfills and alerting around them. That keeps the scheduler light and lets each service scale independently. The table below maps the common ones to their operators; three are worth a note.

S3 appears twice over — as the DAG-deployment bucket from Section 16, and separately as a data lake source and sink. AWS Glue is the most common Airflow-on-AWS pattern and the clearest illustration of the division of labor: Airflow decides when, Glue's own Spark environment does the what. And CloudWatch is where MWAA ships all component logs and metrics — the first place to look when a DAG that used to appear has silently stopped being parsed, since the Airflow UI can't tell you about a file it never loaded.

"Why not just use Step Functions?" Step Functions is AWS-native, defined in JSON/ASL, billed per state transition — a good fit for a simpler AWS-only state machine. MWAA is Python-native, with a provider ecosystem well beyond AWS and a mature scheduling, retry and backfill model out of the box. Plenty of architectures use both: a Step Functions state machine handling one Glue-triggered piece, nested inside a larger pipeline Airflow runs end to end.

∎ The takeaway

Airflow's entire value proposition comes down to one idea: workflows as code, coordinated by a scheduler that knows the full dependency graph, executed by workers that can be scaled independently of the scheduler itself. Everything else in this guide — TaskFlow, dynamic task mapping, deferrable operators, datasets — is refinement on top of that one idea, built to make DAGs easier to write correctly and cheaper to run at scale.

MWAA doesn't change any of that. It takes the same scheduler, the same executor model, the same metadata database, and runs them as a managed service inside your VPC — trading the operational work of patching and scaling Airflow yourself for the constraints of a managed environment (fixed environment classes, an S3-based deployment model, AWS-specific networking and IAM). Whether that trade is worth it depends on the same question every technology choice in data engineering comes down to: what does your team gain by not operating this themselves, and what do they give up in flexibility to get it.
