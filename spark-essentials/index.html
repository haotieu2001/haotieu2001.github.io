Part I · Foundations

01. Architecture: Driver, Executors & the DAG

Apache Spark is a distributed compute engine: it splits work too big for one machine across a cluster and coordinates it. A running Spark application is a small distributed system of its own — one driver that plans and coordinates, a cluster manager that hands out machines, and many executors that do the actual work.

Why Spark, briefly Spark replaced Hadoop MapReduce because MapReduce wrote every intermediate result to disk before the next step could read it — fine for one pass, painful for the multi-step pipelines real ETL needs. Spark's founding insight (UC Berkeley AMPLab, 2010-2012): keep the working data in memory across steps, and plan the whole job as one graph (a DAG) instead of a rigid Map-then-Reduce. Fault tolerance still holds without constant disk writes because every dataset remembers its lineage — the exact transformations that built it — so a lost partition is recomputed, not restored from a copy.

Driver

Runs your program, builds the DAG, schedules stages & tasks, tracks everything.

→

Cluster manager

The resource landlord. Grants containers (CPU + memory) for executors to run in.

→

Executors

JVM processes on worker nodes that run tasks and cache data in memory.

The handshake, in order: you spark-submit (or run a notebook cell) → the driver starts and creates a SparkSession → it asks the cluster manager for resources → the manager launches executor JVMs and registers them back → the driver turns your code into a DAG, splits it into stages/tasks, and ships tasks to executors → executors run tasks, cache data, and report back until the app ends.

The driver & SparkSession

The driver is the single coordinator: it hosts your SparkSession, builds the logical plan and hands it to Catalyst (the query optimizer), runs the DAG and task schedulers, tracks status/retries, and collects results when you call collect() or show(). If the driver dies, the application dies.

from pyspark.sql import SparkSession
spark = (SparkSession.builder
    .appName("orders_etl")
    .config("spark.sql.shuffle.partitions", 200)
    .getOrCreate())

df = spark.read.parquet("s3://lake/orders/")   # DataFrame API
spark.sql("SELECT * FROM orders LIMIT 10")     # SQL API
sc = spark.sparkContext                        # low-level RDD access, rarely needed
Common mistakeA df.collect() on a large DataFrame streams every row into driver memory and can crash it. Use .show(), .take(n), or write the result instead.

Spark is agnostic to which one you use — the same application code runs unchanged; only the launch flags change.

Executors, cores & tasks

An executor is a JVM process that lives for the app's life, runs the tasks the driver sends it, and holds cached data. Each core is a task slot: total parallel tasks = executors × cores per executor. Ten executors with 4 cores each can run 40 tasks at once; a 200-partition stage runs in 5 waves.

spark = (SparkSession.builder
    .config("spark.executor.instances", 10)   # how many executor JVMs
    .config("spark.executor.cores", 4)        # slots = parallel tasks per executor
    .config("spark.executor.memory", "8g")    # JVM heap per executor
    .getOrCreate())

Deployment modes: client vs cluster

The only question that matters: where does the driver run?

ModeDriver runsUse for
ClientOn the machine that submitted the jobInteractive work, notebooks, shells — fragile if that machine disconnects
ClusterInside the cluster, on a worker nodeScheduled production jobs — resilient, the standard for pipelines

Vocabulary you'll use constantly

TermMeaning
TransformationA lazy instruction describing a new dataset (filter, select, groupBy). Nothing runs — it just extends the DAG.
ActionA command that needs a result (count, collect, write) — triggers execution.
JobAll the work triggered by one action. One action → one job.
StageA slice of a job that runs without a shuffle. Boundaries are drawn at every shuffle.
TaskThe smallest unit of execution: one stage's work applied to one partition, on one core.

02. Transformations, Actions & the DataFrame API

Spark is lazy: transformations don't run when you write them, they only add a node to the DAG. Nothing computes until you call an action — which lets Spark see the whole plan before optimizing it.

df = spark.read.parquet("s3://lake/orders/")        # lazy: nothing runs
df2 = df.filter(df.amount > 100)                     # lazy: DAG grows
df3 = df2.groupBy("country").count()                 # lazy: DAG grows
# ---- still nothing has executed on the cluster ----
df3.show()                                            # ACTION: now the whole DAG runs
The hidden cost of lazinessEvery action re-runs the DAG from the start (or from the last cached point). Three actions on the same expensive df3 recompute it three times — unless you df3.cache() it first (§10).

Narrow vs wide: the shuffle

This is the single most important performance distinction in Spark. A narrow transformation needs only one input partition to produce one output partition — no data movement. A wide transformation needs data from many partitions, which forces a shuffle: data written to disk, sent over the network, and re-read.

NarrowWide
Data movementNone — same executorShuffle — disk + network
Examplesselect, filter, withColumngroupBy, join, distinct, orderBy, repartition
Stage impactFused into the current stageEnds the stage; a new one starts after
CostCheapExpensive — usually the slowest part of a job

Tracing one query: read (8 files → 8 partitions) → filter (narrow) → groupBy (WIDE, shuffle) → orderBy (WIDE, shuffle) → write. One action (write) → one job. Two shuffles → three stages. Each stage runs one task per partition — stage 1 gets ~8 tasks from the files; the post-shuffle stages get up to spark.sql.shuffle.partitions (default 200) tasks, which AQE (§05) coalesces down if the data is small.

The core DataFrame operations

A DataFrame is a distributed, schema-aware table — the API you'll write 95% of the time in Python. The schema is exactly what lets Catalyst optimize your query, which is why DataFrame/SQL beats hand-written RDD/UDF code for almost all data-engineering work.

from pyspark.sql import functions as F

result = (df
    .select("order_id", "country", "amount")         # column pruning
    .filter(F.col("amount") > 100)                    # pushdown
    .withColumn("amount_usd", F.col("amount") * 1.0)
    .groupBy("country")                                # shuffle
    .agg(F.sum("amount_usd").alias("total"), F.count("*").alias("n"))
    .orderBy(F.desc("total")))                         # shuffle

(result.write
    .mode("overwrite")
    .partitionBy("country")
    .parquet("s3://lake/gold/country_totals/"))

Spark SQL is the same engine

Spark SQL is not a bolt-on — a SQL string and a DataFrame chain build the identical plan and take the identical path through Catalyst. Pick whichever reads better; there's no performance trade-off between them.

spark.sql("""
  SELECT country, SUM(amount) AS total FROM orders
  WHERE status = 'PAID' GROUP BY country ORDER BY total DESC
""").show()

df.createOrReplaceTempView("orders")               # session-scoped view
spark.sql("SELECT * FROM parquet.`s3://lake/orders/`")   # query files directly
Spark 4.0, in one paragraphANSI mode (spark.sql.ansi.enabled) is now the default — overflow and invalid casts raise errors instead of silently returning NULL. A new VARIANT type stores semi-structured JSON efficiently. Arrow-optimized Python UDFs (§03) are on by default, cutting serialization cost. Mesos is gone; Standalone, YARN and Kubernetes remain.

03. Window Functions & UDFs

A window function computes a value for each row from a group of related rows — without collapsing the group the way groupBy does. This is how you write running totals, "rank within category," and "keep only the latest record per key."

partitionBy → orderBy → over

from pyspark.sql import functions as F, Window

w = Window.partitionBy("country").orderBy(F.col("order_ts"))
df = (df
    .withColumn("row_num", F.row_number().over(w))      # 1,2,3,... no ties
    .withColumn("rnk", F.rank().over(w))                 # 1,2,2,4 (gaps after ties)
    .withColumn("prev_amt", F.lag("amount", 1).over(w))  # previous row's value
    .withColumn("run_total", F.sum("amount").over(w)))   # running sum

The two patterns you'll actually write

# Top-N per group: highest 3 orders per customer
w = Window.partitionBy("cust_id").orderBy(F.desc("amount"))
top3 = df.withColumn("rn", F.row_number().over(w)).filter("rn <= 3").drop("rn")

# Deduplicate, keeping the most recent row per key
w = Window.partitionBy("user_id").orderBy(F.desc("updated_at"))
latest = df.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")
Window.partitionBy() with no partition column = OOMA window with orderBy but no partitionBy puts the entire DataFrame into one partition on one executor to sort it. Fine on a demo table, fatal at scale — always partition by something.

A window always produces Exchange hashpartitioning → Sort → Window in the physical plan: it costs the same as a groupBy or a join.

UDFs: built-in first, pandas UDF second, plain UDF last

A plain Python UDF ships every row to a separate Python process and back, and Catalyst cannot see inside it — so a filter or projection that would normally push down into the scan is blocked. Before writing one, check pyspark.sql.functions (300+ built-ins) and F.expr("...").

# SLOW: row-at-a-time Python, opaque to Catalyst
@F.udf("string")
def domain(email):
    return email.split("@")[1].lower() if email and "@" in email else None
df.withColumn("domain", domain("email"))

# FAST: same logic in built-ins, stays in the JVM, fully optimisable
df.withColumn("domain", F.lower(F.split(F.col("email"), "@").getItem(1)))

When you must write custom Python, a pandas UDF hands Spark data in Arrow batches instead of one row at a time — typically 10-100× faster than a plain UDF:

from pyspark.sql.functions import pandas_udf
import pandas as pd

@pandas_udf("double")
def celsius_to_f(c: pd.Series) -> pd.Series:
    return c * 9 / 5 + 32
df.withColumn("temp_f", celsius_to_f("temp_c"))

Legitimate reasons for a UDF: a Python library with no SQL equivalent (a model's predict, a tokenizer). Filter with built-ins first so the scan still prunes before the expensive function runs, and declare the return type exactly — a wrong type silently yields nulls.

Part II · How Spark Runs Your Code

04. Reading Query Plans & the Spark UI

Spark never runs your code line by line — it compiles it. Catalyst turns a DataFrame chain or a SQL string into a query plan, rewrites it into a cheaper one, picks concrete algorithms, and only then runs it as stages and tasks. Every debugging and tuning skill rests on that one idea: the code you wrote is not the work Spark does.

1. Parsed

Your query as a tree. Names unresolved.

→

2. Analyzed

Names/types resolved from the catalog. Typos fail here.

→

3. Optimized

Filter/column pushdown, constant folding.

→

4. Physical

Real algorithms & Exchanges. What explain() prints.

Steps 1-4 all run on the driver. Step 5 — stages cut at every shuffle, run as parallel tasks — is what you watch in the Spark UI.

Reading a physical plan: bottom-up

A plan is read bottom-up: the leaves (scans) run first, data flows up to the root. Ask three questions of every plan:

  1. Where are the Exchange nodes? Each is a shuffle and a stage boundary — almost always the cost.
  2. Did filters and columns reach the scan? Look for PushedFilters and a trimmed ReadSchema on the leaf.
  3. Which join/aggregate operators did you get? The names tell you the strategy.
orders.join(customers, "cust_id").explain()
# == Physical Plan ==
# *(5) SortMergeJoin [cust_id#2], [cust_id#20], Inner
# :- *(2) Sort [cust_id#2 ASC NULLS FIRST], false, 0     <- LEFT branch (:-)
# :  +- Exchange hashpartitioning(cust_id#2, 200)         <- shuffle #1
# :     +- FileScan parquet orders[cust_id#2,...]
# +- *(4) Sort [cust_id#20 ASC NULLS FIRST], false, 0     <- RIGHT branch (+-)
#    +- Exchange hashpartitioning(cust_id#20, 200)        <- shuffle #2
#       +- FileScan parquet customers[cust_id#20,...]

A two-branch operator (join, union) marks its left child :- and right child +-. Operators sharing a *(n) prefix were fused into one compiled function (whole-stage codegen); a shuffle or a Python UDF always breaks the fusion.

explain() modes

ModeShowsReach for it when…
explain()Physical plan onlyQuick check: shuffles? which join?
explain(True)All four plans, in orderYou want to see Catalyst rewrite the query
explain("formatted")Numbered tree + details blockThe plan is long and needs to stay readable
explain("cost")Estimated rows/bytes"Why didn't Spark broadcast that?"
Pushdown fails silentlyA filter on a UDF result, a non-deterministic expression, or an aggregate/window output cannot be pushed to the source — the scan reads every row with no PushedFilters. Filter on base columns first, before UDFs and joins, so Catalyst has something to push down.

The operators you'll actually meet

OperatorWhat it tells you
FileScanThe leaf. Check PushedFilters and ReadSchema.

BroadcastExchangeShips a small side to every executor — not a shuffle, the fast join.

AdaptiveSparkPlanPlan is under AQE and may change at runtime (§05).

The Spark UI: the diagnosis loop

On a live app the UI is served from the driver on port 4040 (the History Server on 18080 replays a finished run, if spark.eventLog.enabled was on). Run this pass on any slow job:

  1. Jobs tab — find the slow job; count its stages (stages = shuffles + 1).
  2. SQL / DataFrame tab — open the operator DAG, confirm the shuffles and join strategy match the plan.
  3. Stages tab — open the slow stage, expand Summary Metrics. Compare Max vs Median duration, shuffle read, and spill.
MetricRed flag
Duration: max vs medianMax far above median — a straggler task — usually skew (§08)
Shuffle read/writeThe biggest number on the page is usually the bottleneck
Spill (memory/disk)Any spill above zero means a task ran out of memory (§09)
GC timeOver ~10% of task time means memory pressure
The ruleNever tune blind, and never change two things at once — you won't learn which one helped. Change one thing, re-run, compare the same numbers.

05. Adaptive Query Execution (AQE)

Catalyst optimizes before the query runs, using estimates that are often wrong. AQE re-optimizes the plan during execution using the real statistics Spark measures after each shuffle. It's been on by default since Spark 3.2, and it's the largest free performance win in modern Spark.

Coalesces shuffle partitions

Merges small post-shuffle partitions into right-sized ones (~64 MB), so you stop paying for hundreds of near-empty tasks.

Switches join strategy

Converts a planned sort-merge join into a broadcast hash join on the fly, once it sees a side is actually small.

Splits skewed partitions

Breaks an oversized partition into sub-partitions so one straggler can't hold up the whole stage (§08).

spark.conf.set("spark.sql.adaptive.enabled", True)                    # on by default since 3.2
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", True)
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", True)
explain() never shows you the real planWith AQE on, explain() always prints the pre-adaptive plan, wrapped as AdaptiveSparkPlan isFinalPlan=false. Use explain() to check the shape you asked for, and the Spark UI's SQL tab after the run (isFinalPlan=true) to see what Spark actually did — look for AQEShuffleRead coalesced or skewed.
The one trapAQE can only coalesce partitions down from the configured count — it never raises it. On big jobs, set the ceiling high (e.g. 2000) and let AQE shrink it, rather than leaving 200 and wondering why partitions are huge.

Also on by default: dynamic partition pruning, which prunes fact-table partitions at runtime from a dimension-table filter in a star-schema join — it needs the fact table partitioned on the join key and the dimension small enough to broadcast, or it silently does nothing.

Part III · Partitioning, Joins & Skew

06. Partitioning: Shuffle, Disk Layout & Bucketing

"Partition" means three different things in Spark, and mixing them up is the most common source of confusion. Keep them separate: input partitioning sets read parallelism, shuffle partitioning sets in-memory parallelism after a wide op, and disk partitioning (partitionBy) is a write-time directory layout for pruning.

Shuffle partitions: sizing spark.sql.shuffle.partitions

Every wide operation regroups data into spark.sql.shuffle.partitions pieces — default 200, a fixed constant with no knowledge of your data. Too few and each partition overflows execution memory and spills; too many and per-task overhead (scheduling, launch, fetch) swamps the real work.

Per-partition sizeVerdict
< ~10 MBToo small — overhead dominates
~128-200 MBSweet spot
> ~200 MBToo large — spill, GC pressure

The sizing formula: divide the Shuffle Write bytes (read off the Spark UI) by a ~128 MB target, then round to a multiple of your cluster's core count so no wave is lopsided.

# measured from the Spark UI: Shuffle Write = 12,288 MB, cluster = 32 cores
total_mb, target_mb, cores = 12288, 128, 32
partitions = round((total_mb / target_mb) / cores) * cores   # -> 96 (3 clean waves)
spark.conf.set("spark.sql.shuffle.partitions", 96)

Or let AQE do it for you: set a generous starting count and let coalescePartitions shrink it at runtime to advisoryPartitionSizeInBytes (default 64 MB) — the hands-off version of the same answer.

repartition(n)coalesce(n)
Shuffle?Yes — full shuffleNo — merges local partitions
DirectionIncrease or decreaseDecrease only
Use forFixing skew, raising parallelismFewer output files after a filter

Input partitions: read parallelism

On read, Spark packs file bytes into chunks capped at spark.sql.files.maxPartitionBytes (default 128 MB); each chunk becomes one input partition, and therefore one task. A per-file open cost (openCostInBytes, 4 MB) pads the split size, which is why a partition is rarely exactly 128 MB. Always confirm with df.rdd.getNumPartitions() rather than assuming.

Disk partitioning: partitionBy & pruning

df.write.partitionBy("order_date") splits rows by distinct value into order_date=<value>/ directories. When a query filters on that column, Spark skips every non-matching directory entirely — partition pruning. It is unrelated to shuffle partitions; same word, different concept.

(orders.repartition("order_date")          # ~1 file per directory
    .write.mode("overwrite")
    .partitionBy("order_date")
    .parquet("/warehouse/orders"))

# filter on the partition column -> pruning, visible in the plan
spark.read.parquet("/warehouse/orders").filter("order_date = '2026-07-15'").explain()
# FileScan ... PartitionFilters: [order_date = 2026-07-15]  -> reads 1 of N directories
Choose a low-cardinality columnPartition on something like order_date, region, or status — few distinct values, each holding a healthy chunk of data. Partitioning on a high-cardinality column like user_id creates millions of tiny directories: the small-files problem, which crushes the driver with metadata and spawns a task per micro-file.

Bucketing: for high-cardinality join/group keys

When a column is too high-cardinality to partition on but you still want co-location — typically a join key like user_id — bucketing hashes rows into a fixed number of files at write time. Two tables bucketed identically join with no shuffle at all, because matching buckets are already co-located.

(orders.write.mode("overwrite")
    .bucketBy(64, "cust_id").sortBy("cust_id")
    .saveAsTable("orders_bkt"))               # same key + count on BOTH tables
(customers.write.mode("overwrite")
    .bucketBy(64, "cust_id").sortBy("cust_id")
    .saveAsTable("customers_bkt"))

spark.table("orders_bkt").join(spark.table("customers_bkt"), "cust_id").explain()
# SortMergeJoin with NO Exchange below it -- the shuffle happened once, at write time

Rule of thumb: partition on low-cardinality columns you filter on; bucket on high-cardinality columns you repeatedly join or aggregate on. Bucketing only works via saveAsTable (a metastore table) — a plain .parquet(path) write silently ignores bucketBy. It's a one-time bet: skip it for one-off jobs or small tables (broadcast already solves those for free).

07. Joins: Types & Strategies

A distributed join has one hard problem: get every row with the same key onto the same executor. Every strategy is really just a different answer to that. Keep two axes separate: type (which rows come back — your business logic) and strategy (how Spark executes it — a performance decision the optimizer makes).

TypeReturns
innerOnly rows with a key in both sides
left / rightAll rows from one side + matches; missing side → NULL
fullAll rows from both; missing side → NULL (never broadcastable)
left_semiLeft rows with a match (left columns only) — a fast existence filter
left_antiLeft rows without a match — a fast non-existence filter
Use semi/anti joinsleft_semi / left_anti are usually faster than an inner join + distinct or a NOT IN subquery — reach for them instead of hand-rolled existence checks.

The three strategies that matter

StrategyWhen Spark picks itCost
Broadcast Hash JoinOne side ≤ autoBroadcastJoinThreshold (default 10 MB), or a broadcast() hintCheapest — big side never shuffles
Sort Merge JoinThe default for two large sidesBoth sides shuffled + sorted — can spill
Shuffle Hash JoinRare — needs a hint; build side must fit a local hash mapBoth sides shuffled, no sort
from pyspark.sql.functions import broadcast
orders.join(broadcast(customers), "cust_id").explain()
# BroadcastHashJoin [cust_id], [cust_id], Inner, BuildRight -- big side never moves

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 50 * 1024 * 1024)  # raise to 50 MB
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)                # disable auto-broadcast
No equality key? A very different costA non-equi join (a.x < b.y) or a missing/mistyped join condition falls back to BroadcastNestedLoopJoin or CartesianProduct — O(n×m). If a "normal" join is inexplicably slow or its output explodes, check the plan for these two names first.

Hints, and letting AQE fix bad estimates

Every strategy decision runs on the optimizer's estimated size — and for compressed Parquet or a post-filter DataFrame, that estimate is routinely wrong. A hint overrides it; AQE re-runs the choice at runtime on real post-shuffle statistics.

# SQL:  SELECT /*+ BROADCAST(s) */ * FROM big b JOIN small s ON b.id = s.id
big.join(broadcast(small), "id")            # force broadcast
big.hint("merge").join(other, "id")         # force sort-merge
big.join(small.hint("shuffle_hash"), "id")  # force shuffle-hash

With AQE on (default since 3.2), Spark can convert a planned Sort Merge Join into a Broadcast Hash Join mid-query once the shuffle reveals a side is actually small — the most common reason explain()'s static plan differs from what actually ran.

Join tuning, in five checks

  1. Read the plan — which strategy did you get?
  2. Small side? Make sure it's broadcasting — hint it if the estimate is wrong.
  3. Both large? Expect Sort Merge Join; right-size shuffle partitions, filter early.
  4. One slow task? That's skew — AQE or salt it (§08).
  5. Same join repeatedly? Bucket the tables to kill the shuffle for good (§06).

08. Data Skew: Detecting & Fixing It

Data skew is data spread unevenly across partitions. Spark's whole model assumes work divides roughly equally into tasks — but if one key is far more common than the rest, every one of its rows piles onto a single partition after a shuffle, and that one task runs long after every other task has finished. A stage's duration is max(task_time), never the average — so a skewed job on a big cluster can finish slower than a balanced job on a small one.

The usual culprits

SourceExample
Power-law dominanceOne country / customer / product accounts for most rows
NULL keysMillions of rows with a missing join key collapse into one group
SentinelsA default like -1, "unknown" behaves like a NULL Spark can't recognise
Low cardinalityGrouping by a boolean or a handful of statuses
Time hotspotsA launch day or sale spike concentrated on one date/hour

Detecting it in the Spark UI

Stages tab → the slow stage → Summary Metrics for Completed Tasks. Two thresholds turn "that looks lopsided" into a decision: if Max task duration is more than 50% above the 75th percentile, suspect skew; if Max is 10× or more above the median, it's severe.

# quantify the same gap straight from a DataFrame
(df.groupBy("join_key").count()
    .select(F.expr("percentile_approx(count, 0.5)").alias("median"), F.max("count").alias("max"))
    .show())
# max >> median -- the same fingerprint the Spark UI draws

The fix, in order

  1. Broadcast the small side. If the other table is small, this removes the shuffle entirely — no shuffle, no skew.
  2. Rely on AQE. On by default in 3.2+; it splits a partition that's both >5× the median and >256 MB into balanced sub-partitions, and replicates the matching side so the join stays correct. Zero code.
  3. Salt the hot key when AQE isn't enough (both sides genuinely large) or it's a skewed groupBy AQE can't touch at all.
  4. Handle NULLs / sentinels separately — they usually can't match in a join anyway.

Salting: the manual fallback

Append a random 0..N-1 to the hot key, spreading its rows across N tasks instead of one. A join needs the small side replicated across all N salts so every sub-key still finds its match; an aggregation needs no replication, just two stages (a balanced partial aggregate per (key, salt), then a cheap final aggregate per key).

N = 16
# JOIN: big side gets a random salt; small side is exploded across all N
big_s = big.withColumn("salt", (F.rand() * N).cast("int"))
small_s = small.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)])))
result = big_s.join(small_s, ["id", "salt"]).drop("salt")

# AGGREGATION: two stages, no replication needed
stage1 = (df.withColumn("salt", (F.rand() * N).cast("int"))
    .groupBy("country", "salt").agg(F.sum("amount").alias("partial")))
result = stage1.groupBy("country").agg(F.sum("partial").alias("total"))
countDistinct does not survive saltingCounting distinct values per (key, salt) and summing double-counts anything that landed in more than one bucket. Random salting is for additive measures (sum, count) only; for averages, carry the sum and count through both stages and divide once, at the end.

Scope salting to the hot keys only (F.when(isin(hot), rand, otherwise 0)) — salting every key inflates the replicated side for no benefit.

Part IV · Memory, Caching & Storage

09. Executor Memory & Cluster Sizing

When a job dies with OutOfMemoryError or crawls from spilling, the cause is almost never "not enough RAM" — it's that the executor's heap is carved into fixed regions with fixed rules, and your data landed in the wrong one.

The on-heap layout

spark.executor.memory (the JVM heap) is split in a fixed order: a 300 MB Reserved block is skimmed off first; the rest (usable) splits by spark.memory.fraction (default 0.6) into Unified Memory (Execution + Storage, managed by Spark) and User Memory (your own objects — unmanaged, a common hidden OOM source).

# the 4 GB executor, worked to the megabyte
heap_mb = 4096
usable_mb = heap_mb - 300                       # 3796 (Reserved is a fixed constant)
unified_mb = usable_mb * 0.6                     # 2277.6  (spark.memory.fraction)
storage_floor = unified_mb * 0.5                 # 1138.8  (spark.memory.storageFraction)
execution_mb = unified_mb - storage_floor        # 1138.8
user_mb = usable_mb * 0.4                        # 1518.4
overhead_mb = max(384, 0.10 * heap_mb)           # 409.6   (added ON TOP of the heap)
container_mb = heap_mb + overhead_mb             # ~4505.6 -- what the cluster manager actually reserves

Inside Unified Memory, Execution and Storage share one sliding boundary. Execution wins: it can evict cached Storage blocks down to the storage floor. Storage never evicts Execution — a new .cache() simply doesn't fit if Execution holds the pool. That asymmetry is why a cache can shrink mid-job.

Spill: the failure mode to know

When a shuffle/sort/aggregation buffer can't fit in Execution memory, Spark serializes it to local disk and reads it back — correct, but orders of magnitude slower. Diagnose it in the Stages tab: any nonzero Spill (Disk) means Execution ran short.

Lever (cheapest first)What it does
Raise spark.sql.shuffle.partitionsSmaller per-task working set — often the whole fix, no extra RAM
Lower spark.memory.storageFractionLets Execution borrow more of the unified pool
Raise spark.executor.memory, or enable off-heapReal added capacity
Container killed vs Java heap OOMKilled with no Java stack trace (YARN "exceeded physical memory," K8s OOMKilled) → the off-heap budget overflowed, raise spark.executor.memoryOverhead (PySpark worker processes live here). A logged java.lang.OutOfMemoryError: Java heap space → the heap itself is short, raise spark.executor.memory.

Sizing executors: the ~5-core rule

A fat executor (few executors, many cores each) suffers long GC pauses and HDFS I/O contention past ~5 concurrent threads per JVM. A thin executor (one core each) pays memoryOverhead and JVM startup cost dozens of times over, and can't share a broadcast/cache across cores. The optimum sits in the middle.

RuleFormula
1. Cores per executor~5 (the HDFS I/O sweet spot)
2. Reserve for OS, per node1 core, ~1 GB RAM
3. Executors per node(cores − 1) / 5
4. RAM per executor(nodeRAM − 1) / execPerNode
5. Executor heapRAM-per-executor − ~10% overhead
6. Total executorsexecPerNode × nodes − 1 (for the driver)
# 10 nodes x 16 cores x 64 GB, worked end to end
# usable/node: 15 cores, 63 GB  ->  15/5 = 3 executors/node @ 5 cores
# 63/3 = 21 GB/executor -> ~19 GB heap + ~2 GB overhead (fits 21 GB)
# 10*3 = 30 executors, minus 1 for the driver = 29 -> 29*5 = 145 task slots
spark-submit \
  --deploy-mode cluster --driver-cores 1 --driver-memory 4g \
  --num-executors 29 --executor-cores 5 --executor-memory 19g \
  --conf spark.executor.memoryOverhead=2g \
  --conf spark.sql.shuffle.partitions=290 \
  app.py

On shared/bursty clusters, prefer dynamic allocation (spark.dynamicAllocation.enabled=true with minExecutors/maxExecutors) over a pinned --num-executors — the standard on managed platforms (Databricks, EMR, Dataproc). Keep the per-executor shape (cores, memory) fixed by the rules above; only the count floats.

10. Caching: Why, How & When Not To

A DataFrame is not a table sitting in memory — it's a recipe, the chain of transformations (its lineage) needed to produce it. Every action re-cooks that recipe from scratch. Caching cooks it once and lets later actions eat from the fridge.

df = spark.read.parquet("/data/events").filter(F.col("amount") > 0)
df.count()   # action 1 -> scans + filters the WHOLE source
df.count()   # action 2 -> scans + filters it ALL OVER AGAIN, unless cached

df.cache()   # marks for caching -- still lazy, nothing cached yet
df.count()   # first action materialises it into memory
df.count()   # served from cache, no re-scan

Confirm it worked in the Spark UI's Storage tab — the only ground truth for what's actually cached. Watch Fraction Cached: below 100% means some partitions were evicted, and Spark quietly recomputes the missing slice on every action.

Storage levels

LevelNotes
MEMORY_ONLYFastest; a partition that doesn't fit is dropped and recomputed on demand
MEMORY_AND_DISKKeeps what fits in RAM, spills the rest to disk — the cache() default for a DataFrame, the safe everyday choice
DISK_ONLYNever uses RAM; slow reads, frees memory for execution — for very large, occasionally-reused data
MEMORY_AND_DISK_2Replicated on 2 nodes — survives an executor dying, at 2× storage cost
PySpark specificsCached objects are always Pickle-serialized in PySpark, so MEMORY_ONLY vs MEMORY_ONLY_SER makes little practical difference — the _SER distinction matters mainly on the JVM side.

When to cache, and when not to

Caching is not free — it occupies the same executor memory your computations need. Cache only data that's genuinely reused across multiple actions or iterated (ML training loops). A one-shot pipeline gains nothing from caching, and an over-eager cache starves execution into spilling.

report = report.cache()
report.count()                                              # materialise once
report.write.parquet("s3://lake/out/revenue/")               # reads cache
report.filter("revenue > 1e6").write.parquet("s3://lake/out/big/")  # reads cache
report.orderBy(F.desc("revenue")).show(20)                   # reads cache
report.unpersist()                                            # ALWAYS free it when done

Measured effect: three actions on an expensive join+aggregation went from ~28s total (recomputed each time) to ~9s to materialise once plus well under a second per reuse. spark.catalog.clearCache() wipes every cached table/DataFrame in the session — handy between pipeline stages.

11. Parquet & Delta Lake

For an analytics pipeline the answer is almost always Parquet (or a table format — Delta / Iceberg / Hudi — built on top of it). Every optimization here exists to do one thing: read less.

FormatLayoutPruning / pushdownUse for
ParquetColumnarYes (stats + dictionary)The default for lakes & warehouses
AvroRowNoStreaming sinks, Kafka, schema evolution
JSON / CSVRow, textNoRaw landing only — convert to Parquet on ingest

Parquet's anatomy: why it's fast

A file is a stack of row groups; each holds one column chunk per column; a footer carries the schema plus per-row-group min/max statistics. That layout is the whole reason two free wins exist: column pruning (a query touching 3 of 50 columns reads only those 3 chunks) and row-group skipping (the footer's min/max lets Spark skip groups that can't match a filter).

(spark.read.parquet("s3://lake/orders/")
    .select("amount", "country").where("amount > 100")
    .explain("formatted"))
# scan shows ReadSchema of 2 cols + PushedFilters -- fewer bytes read off disk
Data skipping needs clustered dataSkipping only helps when each file's value range is narrow. If a filter column's values are scattered across every file, nothing gets skipped — this is why Z-ordering / liquid clustering and sensible partitioning matter.

Delta Lake: Parquet plus a transaction log

A Delta table isn't a new file format — the data is plain Parquet files. What Delta adds is _delta_log/, a transaction log recording which files currently belong to the table plus their statistics. Spark reads that log first, so it knows exactly which files to open without listing the directory — a big win on a cloud object store, where directory listing is slow.

sales = spark.read.format("delta").load("s3://lake/sales/")
spark.sql("DESCRIBE HISTORY delta.`s3://lake/sales/`").show()          # commits / versions
old = spark.read.format("delta").option("versionAsOf", 3).load("s3://lake/sales/")  # time travel

12. The Tuning Playbook

Spark tuning is a loop, not a bag of magic configs: measure → find the bottleneck → remove it → measure again. Ninety percent of the wins come from three enemies, and reading the Spark UI is the only way to know which one is hurting you.

Shuffle

Data moved across the network to regroup by key. Expensive — minimise it (§06, §07).

Spill

A task ran out of execution memory and wrote to disk. Wastes I/O and GC (§09).

Skew

Uneven data means one straggler task defines the wall clock (§08).

Symptom → cause → fix

Symptom (Spark UI)CauseFix
One task's time/shuffle ≫ medianSkew on a join/group keyAQE skew join; salting; broadcast the small side
Large Spill (memory/disk)Partition too big for execution memoryMore shuffle partitions; more executor memory
Huge shuffle; a stage dominatesUnnecessary or oversized shuffleBroadcast; bucket repeated joins; filter early
Thousands of tiny tasks/filesToo many partitionscoalesce; let AQE coalesce
SortMergeJoin where one side is smallBad broadcast size estimateExplicit broadcast() hint
Full fact-table scan in a star joinNo partition pruningPartition the fact table on the join key

Worked example: 18m 40s → 2m 30s

A join + groupBy + write on a 500 GB fact table and a 40 MB dimension. The Spark UI showed a SortMergeJoin (the dimension was just over the 10 MB broadcast threshold, so both sides — including the 500 GB table — shuffled), a 40 GB disk spill on 200 shuffle partitions each holding ~750 MB, and one straggler task 17× the median.
