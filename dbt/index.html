~/dbt ❯ the backstory

01. Why dbt Exists

From "a folder of SQL scripts" to a real, tested, documented codebase

Before dbt, SQL transformation work looked the same everywhere: a pile of .sql scripts run by hand or by a fragile cron job, in whatever order someone remembered. Nobody could answer "what depends on this table?" or "did this number change because of a bug?" — because nothing wrote that dependency down anywhere except in someone's head. dbt (data build tool) turns your SQL transformations into a real, version-controlled project — with dependencies, tests and documentation — while leaving data movement and computation to tools that already do those jobs well.

That last point matters more than it sounds: dbt does not extract data from source systems, and it does not execute SQL itself. It compiles the SQL you write (with some templating help from Jinja, section 08) and hands it to your warehouse — Snowflake, BigQuery, Databricks, Redshift, Postgres — which does 100% of the actual computation. dbt's job is everything around the SQL: dependency ordering, testing, documentation, and environments.

ETL vs. ELT — why dbt showed up when it did

Older data platforms did ETL: Extract from a source, Transform in a separate processing tool before the data ever reached the warehouse, then Load the finished result. That made sense when warehouses were expensive and slow. Cloud warehouses changed the economics — storage and compute got cheap and fast enough that it became easier to Load raw data first and Transform it afterward, inside the warehouse, with the warehouse's own SQL engine: ELT. Fivetran and Airbyte handle the "EL"; dbt is built for the "T" — turning that raw data into clean, tested, analysis-ready tables using nothing but SQL the warehouse already understands.

The role dbt helped create: analytics engineer

dbt didn't just ship a tool — it popularized a job title. An analytics engineer sits between the data engineer who moves raw data into the warehouse and the analyst who answers business questions with it. They own the transformation layer: writing and testing the SQL that turns raw, messy source tables into clean, well-modeled, documented tables analysts can trust — applying version control, code review, tests and CI to SQL that used to live in nobody's repository at all.

❯ Short version

dbt is the "T" in ELT: it doesn't move data or execute anything itself — it compiles SQL and pushes it into your warehouse, which does all the real computation. It exists to bring version control, dependency tracking, tests, and documentation to the SQL transformation layer, and it's the tool most responsible for "analytics engineer" becoming a real job title.

02. Core Concepts: Models, ref(), and the DAG

The three ideas everything else in dbt is built on

A model is the basic unit of work in dbt: one .sql file containing a single SELECT statement. There's no CREATE TABLE, no INSERT, no DDL of any kind in the file you write — dbt wraps your SELECT in whatever DDL/DML is needed based on how you've configured it to be built (section 06). If a file is named fct_orders.sql, running it produces an object named fct_orders in your warehouse.

ref() — the single most important function in dbt

Instead of SELECT * FROM analytics.staging.stg_orders, you write SELECT * FROM {{ ref('stg_orders') }}. That substitution does two things: dbt resolves it to the right, fully-qualified table name for whichever environment you're running in — dev schema, staging, prod, never hardcoded again — and, because dbt now knows this model reads from that one, it computes the correct build order for every model in the project. Do it consistently and the DAG (directed acyclic graph) of your entire transformation layer falls out for free, without you ever writing it down by hand.

-- models/marts/fct_orders.sql
WITH orders AS (
    SELECT * FROM {{ ref('stg_orders') }}
),
customers AS (
    SELECT * FROM {{ ref('dim_customers') }}
)

SELECT
    o.order_id,
    o.customer_id,
    c.customer_segment,
    o.order_total
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id

The other half is source() (section 04): a pointer to a raw table dbt did not create — something a loader like Fivetran or a native pipe wrote. Using it instead of hardcoding the raw table name gives dbt the DAG's starting nodes, plus a place to declare freshness checks on data it doesn't own. Between ref() and source(), every table your project touches — built or merely read — is one connected graph.

Two commands make the compile/run distinction concrete. dbt compile resolves every model's Jinja-templated SQL down to plain SQL your warehouse could run directly, writing it to target/compiled/ without touching the warehouse. dbt run does the same compilation and then executes the result, writing what it ran to target/run/. To know exactly what SQL dbt is about to run, or to debug a model behaving unexpectedly, read its file in target/compiled/ — it's the literal SQL your warehouse receives, with every ref() and macro already expanded.

❯ Short version

A model is one .sql file with one SELECT. ref() points to another model by name instead of a hardcoded table path, which both makes your project environment-independent and lets dbt compute the DAG automatically. source() plays the same role for raw tables dbt didn't build. dbt compile resolves Jinja to plain SQL without running it; dbt run compiles and actually executes it.

03. Project Anatomy

dbt_project.yml, profiles.yml, and the standard folder layout

Every dbt project is a plain folder, almost always checked into git. Two YAML files control almost everything about how it behaves, and they intentionally hold very different kinds of information.

Installing dbt

dbt Core installs like any Python package: pip install dbt-core dbt-snowflake — swap the adapter for whichever warehouse you use (dbt-bigquery, dbt-databricks, dbt-postgres). The adapter is the piece that knows how to talk to that specific warehouse; dbt Core itself is warehouse-agnostic. dbt init <project_name> scaffolds the standard folder layout below and walks you through your first profiles.yml entry. Run dbt debug immediately after — it confirms dbt can reach your warehouse before you write a single model.

dbt_project.yml vs. profiles.yml

dbt_project.yml lives inside the project, is committed to git, and configures the project itself: its name, which folders hold models/seeds/macros/tests/snapshots, and default materializations per folder. profiles.yml lives outside the project (by default ~/.dbt/) and is never committed, because it holds warehouse connection details — account, user, and for local dev, credentials. dbt Cloud sidesteps the file entirely, managing connections and secrets through its own UI and environment variables.

# dbt_project.yml
name: 'analytics'
version: '1.0.0'
profile: 'analytics'          # which profile in profiles.yml to use

model-paths:    ["models"]
seed-paths:     ["seeds"]
macro-paths:    ["macros"]
test-paths:     ["tests"]
snapshot-paths: ["snapshots"]
clean-targets:  ["target", "dbt_packages"]

models:
  analytics:
    +materialized: view      # default for everything...
    marts:
      +materialized: table   # ...override per folder

One folder is easy to overlook: analyses/ holds .sql files dbt will compile — resolving every ref(), source() and Jinja block exactly like a model — but never run or materialize. It's the right home for a one-off analytical query you still want version-controlled and templated, say an investigation into a data-quality anomaly, without permanently cluttering your DAG with a model nobody downstream should depend on.

What actually goes in git. Everything in the project folder except target/ and dbt_packages/ (both regenerated by dbt deps/dbt run) belongs in version control — including dbt_project.yml and packages.yml. profiles.yml and anything holding a password, API key, or account identifier does not — those are secrets, and belong in environment variables or your orchestrator's secret store instead, exactly as they would for any other application code.

❯ Short version

dbt_project.yml is committed config for the project itself (folders, default materializations). profiles.yml holds warehouse connection secrets and is never committed — dbt Cloud replaces it with UI-managed connections entirely. The standard folder layout splits models into staging/intermediate/marts, alongside seeds, snapshots, macros, and tests; target/ is generated output and always gitignored.

04. Sources & Seeds

Declaring the raw tables you didn't build, and loading the small ones you did

Every dbt project starts by reading data it didn't create. Sources are how you tell dbt about it: a YAML declaration mapping a friendly name to a real, already-existing table (usually one a loader like Fivetran, Airbyte, or a native pipe populated). You reference a source in a model with {{ source('source_name', 'table_name') }} — the same "don't hardcode the path" idea as ref(), extended to raw data.

# models/staging/sources.yml
version: 2

sources:
  - name: shop_raw
    schema: raw
    tables:
      - name: orders
      - name: customers
        loaded_at_field: _fivetran_synced
        freshness:
          warn_after: {count: 12, period: hour}
          error_after: {count: 24, period: hour}

Source freshness — catching a broken loader before your dashboards do

dbt source freshness checks how long ago each source table was last updated (via its loaded_at_field) against the warn_after/error_after thresholds you set. If the upstream loader silently stops overnight, this tells you before a stakeholder notices a dashboard hasn't moved in three days — a cheap check most teams run at the very start of every production job, before wasting compute on models built from stale data.

Seeds solve a smaller problem: small, static, rarely-changing datasets that live comfortably as a CSV in your repo — country codes to region names, a curated list of holiday dates, an internal mapping nobody else owns. Put the CSV in seeds/, run dbt seed, and dbt loads it into the warehouse as a real table you can ref() like any model. Seeds are for reference data measured in kilobytes, not a substitute for real ingestion — if a dataset changes often or grows large, it belongs behind a source.

❯ Short version

A source declares a raw table a loader (Fivetran, Airbyte, etc.) already populated, referenced with source(); it's also where you configure freshness checks that catch a broken loader early. A seed is a small, static CSV committed to the repo and loaded with dbt seed, then referenced with ref() exactly like a model — meant for small reference data, not real ingestion.

05. The Layered Architecture

The folder convention almost every real dbt project converges on

Nothing forces you to organize models any particular way, but almost every production dbt project — including dbt Labs' own recommended structure — converges on the same three layers, because it maps cleanly onto how a DAG naturally grows.

Staging → Intermediate → Marts

Staging models sit directly on sources: one per source table, doing only light, mechanical cleanup — renaming columns to a consistent convention, casting types, standardizing casing — never joins, never business logic. Intermediate models sit between staging and marts, where joins, deduplication and business-logic building blocks live; they're often not meant to be queried from outside the project, and are frequently ephemeral (section 06) so they never appear in the warehouse at all. Marts are the consumption-ready layer — the dimension and fact tables, or wide denormalized tables, that BI tools, analysts and other teams actually query.

Naming convention most teams follow: stg_orders, stg_customers (staging) → int_orders_joined (intermediate) → dim_customers, fct_orders (marts, Kimball-style dimension/fact naming).

❯ Short version

Staging models do light, 1:1 cleanup on top of sources with zero business logic. Intermediate models hold joins and business-logic building blocks, often not meant for outside consumption. Marts are the final, wide, dimension/fact tables analysts and BI tools actually query. This funnel shape — many messy sources in, a few trustworthy marts out — is the closest thing dbt has to an industry-standard project structure.

06. Materializations

view, table, ephemeral, incremental — and the newer microbatch strategy

A model file is just a SELECT. Its materialization is the setting that decides what dbt actually builds from that SELECT — and it's the single highest-leverage decision you make per model, because it trades off build cost against query cost and freshness.

MaterializationWhat gets builtRebuild costBest for
view (default)A SQL view — no data stored, query re-runs the SELECT every timeFree to "build" (just DDL)Staging models; anything cheap to query and rarely reused
tableA real physical table, fully rebuilt (dropped & recreated) every runFull cost, every runMarts that need fast reads and don't grow unbounded
ephemeralNothing at all — inlined as a CTE into every model that refs itNone — no object existsIntermediate models nobody queries directly
incrementalA table that's only appended to / merged, not fully rebuilt each runCheap — only processes new/changed rowsLarge, append-heavy fact tables (section 07)
 
-- models/marts/dim_customers.sql
{{ config(materialized='table') }}

SELECT customer_id, first_name, last_name, signup_date
FROM {{ ref('stg_customers') }}

Newer addition: microbatch. Recent dbt Core releases add incremental_strategy: microbatch for very large, time-partitioned fact tables: instead of one big incremental statement, dbt splits the run into many small, independent per-time-slice batches — one per day, say — each processed and retried on its own. Backfills over months of history get dramatically more resilient, since one failed batch doesn't take down the whole run and can be retried individually.

❯ Short version

view stores nothing and re-runs on every query; table is fully rebuilt every run; ephemeral creates no object at all and is inlined into whatever refs it; incremental only processes new or changed rows on top of an existing table. microbatch is a newer incremental strategy purpose-built for large, time-partitioned tables, splitting a run into small, independently-retryable per-time-slice batches.

07. Incremental Models, Deep Dive

is_incremental() and the strategies for merging new data in

An incremental model's SQL file has to serve two different purposes depending on how it's run: on a full refresh (dbt run --full-refresh, or the model's very first run) it needs to select the entire history; on every run after that, it should select only new or changed rows and merge them into the table that already exists. The is_incremental() macro is how one file does both jobs.

-- models/marts/fct_events.sql
{{
  config(
    materialized='incremental',
    unique_key='event_id',
    incremental_strategy='merge'
  )
}}

SELECT event_id, user_id, event_type, event_time
FROM {{ ref('stg_events') }}

{% if is_incremental() %}
  -- this filter only applies on incremental runs, never on a full refresh
  WHERE event_time > (SELECT MAX(event_time) FROM {{ this }})
{% endif %}

Incremental strategies — how new rows actually get merged in

append just inserts the new rows — fastest, but unsafe if a row you already loaded can reappear with changed values (you get a duplicate, not an update). merge, the most common choice on warehouses that support it, does a real MERGE/upsert keyed on unique_key: existing rows update in place, new ones insert — safe against reprocessing the same time window twice. delete+insert deletes existing rows matching the new batch's keys then inserts the batch, a common fallback where there's no native merge. microbatch (section 06) computes no single incremental filter at all — dbt itself decides the time slices and runs one batch per slice.

Interview question: how do you identify new or changed records?

You need a column that reliably moves whenever a row is created or updated — usually a source-maintained updated_at / _loaded_at. The incremental body filters to rows past a watermark: WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }}). Pair that with unique_key and incremental_strategy='merge' so a row that reappears with a newer updated_at updates in place rather than duplicating. If the source only gives you an created_at that never changes on update, an updated_at-style filter can only ever catch inserts — you would need CDC, a snapshot (section 10), or the check comparison approach.

Interview question: what happens when historical data changes? If a row from last month is corrected in the source but its updated_at does not move, your updated_at > MAX(...) filter will never see it, and the incremental table quietly drifts out of sync with the source. Three real answers: (1) rely on the source bumping updated_at on every write and use merge on unique_key; (2) run a periodic dbt run --full-refresh (nightly or weekly) to fully rebuild and re-sync; (3) widen the filter to a rolling window (below) so recent history is always re-evaluated.

Interview question: how do you handle late-arriving data? An event with yesterday's timestamp that lands today is already older than MAX(event_time), so a strict > filter skips it forever. The standard fix is a lookback window: re-scan the last few days on every run and let merge de-duplicate. The wider the window, the more late data you catch and the more you reprocess each run — size it to your real lateness. The microbatch strategy formalises this with a lookback setting that re-runs the last N time slices automatically.

{% if is_incremental() %}
  -- lookback window: re-process a rolling few days so late-arriving
  -- and corrected rows are picked up; merge on unique_key de-dupes them
  WHERE event_time >= (SELECT MAX(event_time) FROM {{ this }}) - INTERVAL '3 days'
{% endif %}

The classic incremental footgun: schema changes. If an upstream source silently adds, removes or retypes a column, an incremental model's next run tries to merge new-shape rows into an old-shape table. on_schema_change decides what happens: ignore (the default, often wrong — it can silently drop or misalign columns), fail (stop and force a human to look, the safest default for anything important), append_new_columns, or sync_all_columns. Pick it deliberately per model.

❯ Short version

is_incremental() lets one model file behave differently on a full refresh vs. a normal run — normally filtering to only new/changed rows via a watermark on updated_at. The incremental_strategy (append, merge, delete+insert, microbatch) decides how those rows combine with what's there — use merge on a unique_key for anything that can change. Handle historical corrections with a periodic --full-refresh or a source that bumps updated_at; handle late-arriving data with a lookback window. Always set on_schema_change deliberately — the default can silently corrupt a table when an upstream schema changes.

08. Jinja & Macros

Why dbt files aren't quite plain SQL, and how to reuse logic across models

Every dbt model is a Jinja template that happens to render into SQL. {{ ... }} is an expression replaced with its rendered value ({{ ref('stg_orders') }} becomes a real table path); {% ... %} is a statement — an if, a for loop, a macro call — that controls what gets rendered but produces no output itself. That's what makes is_incremental() (section 07) and looping over column lists possible in something that's ultimately just a SQL file.

Macros — functions for SQL

A macro is a reusable, parameterized chunk of Jinja+SQL, defined once in your macros/ folder and called from any model. The most common motivating example is a repeated pattern you don't want to retype in ten different models — computing a surrogate key from several columns, standardizing a currency conversion, or generating a custom test (a macro is also how you write a custom generic test, section 09).

-- macros/cents_to_dollars.sql
{% macro cents_to_dollars(column_name) %}
    ({{ column_name }} / 100.0)
{% endmacro %}

-- used in a model:
SELECT
    order_id,
    {{ cents_to_dollars('amount_cents') }} AS amount_dollars
FROM {{ ref('stg_orders') }}

You rarely have to write every macro yourself. Packages — declared in packages.yml, installed with dbt deps — are shareable dbt projects made almost entirely of macros and sometimes models. dbt_utils (from dbt Labs) is the one nearly every project installs, for dbt_utils.generate_surrogate_key() (a stable hash of several columns, commonly the primary key for a snapshot or a table with no natural key) and dbt_utils.date_spine() (a row per day, week or month over a date range). dbt-expectations ports much of Great Expectations' test vocabulary into dbt-native generic tests.

# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.0

❯ Short version

dbt models are Jinja templates that render to SQL: {{ }} for expressions, {% %} for control flow. A macro is a reusable, parameterized snippet of Jinja+SQL you define once and call everywhere. Packages (installed via packages.yml + dbt deps) are shareable bundles of macros and models — dbt_utils is the one almost every project installs.

09. Testing in dbt

Generic tests, singular tests, and unit tests — three different questions, three different tools

A dbt test is fundamentally simple: it's a query, and if that query returns any rows, the test fails. Everything about dbt testing is built on that one idea, applied to three different kinds of questions.

Test typeAnswersDefined whereRuns against
Generic test"Does this column ever violate a simple, reusable rule?" (not_null, unique, accepted_values, relationships)schema.yml, applied to a columnReal data, after the model is built
Singular test"Does this specific, one-off business rule ever get violated?"One .sql file in tests/Real data, after the model is built
Unit test"Given this fake input, does my SQL logic produce the expected output?"tests: block in the model's YAML, with mock rows inlineFabricated rows, not your real data, and not the warehouse's real tables
 
# models/schema.yml — generic tests
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests: [unique, not_null]
      - name: customer_id
        tests:
          - relationships:
              to: ref('dim_customers')
              field: customer_id
      - name: status
        tests:
          - accepted_values:
              values: ['placed', 'shipped', 'delivered', 'cancelled']
-- tests/orders_total_matches_line_items.sql  (singular test)
-- fails if any order's stored total doesn't match the sum of its line items
SELECT o.order_id
FROM {{ ref('fct_orders') }} o
JOIN (
    SELECT order_id, SUM(line_amount) AS computed_total
    FROM {{ ref('fct_order_lines') }}
    GROUP BY order_id
) l ON o.order_id = l.order_id
WHERE ABS(o.order_total - l.computed_total) > 0.01

Unit tests — testing logic without touching real data

Generic and singular tests both run after a model is built, against whatever real data happens to be sitting in your warehouse — great for catching bad data, useless for testing a tricky piece of SQL logic in isolation, since you'd need real rows that happen to hit every edge case. A unit test gives a model a handful of hand-written fake input rows and asserts the exact output rows your SQL should produce — the same "arrange, act, assert" idea as a unit test in application code, finally available for SQL. It's the tool for "I refactored this CASE statement, prove it still does the same thing," not for catching bad production data.

# models/schema.yml — a unit test
unit_tests:
  - name: test_discount_tier_logic
    model: fct_orders
    given:
      - input: ref('stg_orders')
        rows:
          - {order_id: 1, order_total: 40}
          - {order_id: 2, order_total: 150}
    expect:
      rows:
        - {order_id: 1, discount_tier: 'none'}
        - {order_id: 2, discount_tier: 'gold'}

❯ Short version

Every dbt test fails if its query returns any rows. Generic tests (not_null, unique, relationships, accepted_values) apply a reusable rule to a column via YAML. Singular tests are one-off SQL files for a specific business rule. Both run against real, already-built data. Unit tests are different in kind — they feed a model fabricated input rows and assert on the exact output, testing your SQL logic in isolation rather than your production data's health.

10. Snapshots

Capturing change history from a source that only shows you "now"

Most operational source tables show only current state: a customers table's status column shows today's status, with no record of what it was last month. Asked "what was this customer's status on a given date in the past," the source table can't tell you — the row was overwritten in place. A snapshot is dbt's answer: on every run it compares current source data to the last snapshot it took and records any change as a new row, building up exactly the change history relational modeling calls Slowly Changing Dimension Type 2 (SCD Type 2).

-- snapshots/snap_customer_status.sql
{% snapshot snap_customer_status %}

{{
  config(
    target_schema='snapshots',
    unique_key='customer_id',
    strategy='timestamp',
    updated_at='updated_at'
  )
}}

SELECT customer_id, status, updated_at
FROM {{ source('shop_raw', 'customers') }}

{% endsnapshot %}

Two change-detection strategies

The timestamp strategy trusts an updated_at column the source already maintains — simplest and cheapest, but only as reliable as that column actually is. The check strategy instead compares a specific list of columns row-by-row on every run and considers the row changed if any of them differ — more expensive, but works even when the source has no trustworthy update timestamp at all.

❯ Short version

A snapshot captures change history (SCD Type 2) from a source that only shows its current state, by comparing new data against the last snapshot on every run and appending a new row for anything that changed. The timestamp strategy trusts an existing updated_at column; check compares specific columns directly when no trustworthy timestamp exists. The resulting table only grows, with dbt_valid_from/dbt_valid_to marking each version's validity window.

11. Documentation & the DAG

Turning your schema.yml descriptions into a browsable lineage graph

Every description you write in a schema.yml — for a model, a column, a source — isn't just a comment; it's structured metadata dbt renders into an actual documentation site. dbt docs generate builds that site from every model's compiled SQL, every test and every description, and dbt docs serve runs it locally. The centerpiece is the lineage graph: an interactive rendering of the exact DAG built from every ref() and source() in your project (section 02) — click any model and see everything upstream and downstream of it instantly, instead of grepping SQL files to reconstruct dependencies by hand.

# models/schema.yml
models:
  - name: fct_orders
    description: "One row per order. The core sales fact table used by every revenue dashboard."
    columns:
      - name: order_id
        description: "Primary key. Unique per order."

Exposures — extending the DAG past dbt's own models

An exposure declares something outside dbt — a Looker dashboard, a Tableau workbook, an ML feature pipeline — that depends on specific models, so it becomes a node in the lineage graph too. That closes an otherwise-invisible gap: without one, "who actually uses fct_orders" is tribal knowledge; with one it's a documented dependency, which matters enormously when deciding whether it's safe to change or deprecate a model.

❯ Short version

Descriptions in schema.yml aren't just comments — dbt docs generate turns them into a real documentation site, centered on an interactive lineage graph built from every ref()/source() in the project. Exposures extend that graph past dbt's own models to represent dashboards, ML pipelines, or anything else downstream that depends on a model, turning "who uses this" from tribal knowledge into a documented dependency.

12. dbt Commands

The handful worth knowing cold — and why production runs build, not run

Every dbt command takes an optional --select (which nodes to act on) and --exclude. The ones that come up day to day:

CommandWhat it does
dbt runCompiles and executes models only, in DAG order. Materializes each as view/table/incremental per its config. Does not run tests, seeds, or snapshots.
dbt testRuns tests against already-built models. Each test is a query; any rows returned = fail.
dbt buildRuns models, tests, seeds and snapshots together in one DAG-ordered pass, and stops downstream of anything that fails a test. The command production schedules.
dbt compileRenders every model's Jinja to plain SQL in target/compiled/ without touching the warehouse. Read these files to see exactly what dbt will send.
dbt seedLoads the CSVs in seeds/ into the warehouse as tables (section 04).
dbt snapshotRuns the snapshots in snapshots/, capturing SCD Type 2 change history (section 10).
dbt docs generate / dbt docs serveBuilds the documentation site and lineage graph from your project, then serves it locally (section 11).
dbt depsInstalls packages listed in packages.yml into dbt_packages/ (section 08).

dbt build vs. dbt run — the distinction interviewers ask about

dbt run only materializes models. If you want them checked, you run dbt test afterwards as a separate step — and in the gap between the two, a model that produced bad data has already been built, and its downstream children may have built on top of it before the test step flags the problem.

dbt build closes that gap: it walks the DAG once and, for each node, does the right thing in order — seed, snapshot, run a model, then immediately run that model's tests — and if a test fails, everything downstream of that node is skipped. Bad data never reaches a dependent model. That's why local development uses dbt run (fast iteration, you'll eyeball the result) and every production schedule uses dbt build.

❯ Short version

run = models only. test = checks against built models. build = run + test + seed + snapshot in one DAG pass, skipping everything downstream of a failed test — what production uses. compile = render SQL without executing. seed / snapshot / docs / deps do exactly what their names say.

13. dbt Core vs. dbt Cloud

Same modeling language, two ways to run it

Everything in sections 01-11 — models, ref(), tests, snapshots — is the same regardless of how you run dbt. What differs is the execution layer underneath.

dbt Core vs. dbt Cloud

dbt Core is the free, open-source, Apache-2.0 command-line tool: install it with pip, run dbt run/dbt test/dbt build yourself, and host and schedule it somewhere (section 14). dbt Cloud is dbt Labs' commercial, managed platform: a hosted IDE, a scheduler for production jobs, a hosted docs site, environment and secret management with no local profiles.yml, plus a few features that only exist there (the Semantic Layer API, the dbt Cloud CLI). Neither replaces the modeling language from sections 01-11 — dbt Cloud wraps management and orchestration around the same core engine.

Worth a one-line mention: the Fusion engine. dbt Labs is building a from-scratch Rust rewrite of the execution engine with real SQL comprehension (column-level lineage and type-checking before anything hits the warehouse), aimed at faster compilation and better editor tooling. Same SQL/YAML/Jinja authoring. It has been in preview since 2025 and rolls out warehouse by warehouse — check docs.getdbt.com for current status; you don't need its internals for a DE role.

❯ Short version

dbt Core is the free, open-source CLI — you host and schedule it yourself. dbt Cloud is dbt Labs' managed platform, adding a hosted scheduler, IDE, docs site, and secrets management on top of the same core engine. The Fusion engine is a newer Rust rewrite still in preview; know it exists, skip the internals.

14. Running dbt in Production

Who triggers dbt build at 3am, how CI stays fast, and where the warehouse bill goes

Every command in this guide so far (dbt run, dbt test, dbt seed) has implicitly assumed a human typing it into a terminal. Production is the opposite: something else has to trigger dbt, on a schedule or in response to an event, with nobody watching. That "something else" is the orchestrator, and it's a genuinely separate decision from anything covered so far — dbt itself has no built-in scheduler.

ApproachWhat triggers dbtBest fit
dbt Cloud jobsdbt Cloud's own hosted schedulerTeams that want scheduling, CI, and docs hosting without standing up separate infrastructure
Airflow / Dagster / PrefectA DAG task that shells out to dbt build (or uses a provider package with native task-per-model support)Teams that already run a general-purpose orchestrator for non-dbt pipelines too, and want dbt as one stage among many
Plain cron / CI scheduled jobA scheduled pipeline (e.g. GitHub Actions on a cron trigger) running dbt Core directlySmall teams/projects where a full orchestrator is more infrastructure than the job warrants

Production runs dbt build, not dbt run. It interleaves models, tests, snapshots and seeds in one DAG-ordered pass and stops downstream of anything that fails a test, so bad data never reaches a dependent model. Running dbt run then dbt test as two steps lets a broken model's children build on bad data before the test step catches it. Full command breakdown in section 12.

Slim CI — don't rebuild the whole project on every PR. A naive CI job runs every model and test on each pull request; past a few hundred models that is slow and expensive. Slim CI builds only what changed plus everything downstream: dbt build --select state:modified+ --defer --state ./prod-artifacts. state:modified+ diffs the branch against saved production artifacts and selects changed models and their descendants; --defer lets their unchanged parents resolve ref() to production's already-built tables instead of rebuilding the upstream DAG in a throwaway schema. A one-model change in a thousand-model project then builds in seconds.

Where the warehouse bill goes. Almost every dbt cost problem is one of: a full-rebuild table that should be incremental (section 07); an incremental filter that can't prune partitions because it filters a computed expression instead of a raw partitioned column; an ephemeral model ref'd by many others, so its SQL recomputes once per consumer per run; or a missing clustering/partition key on a large mart. Tag every query dbt sends (warehouse-native query tags) so "the bill spiked Tuesday" is a filtered lookup in query history, not a guess.

❯ Short version

dbt has no scheduler — an orchestrator (dbt Cloud jobs, Airflow/Dagster/Prefect, or a scheduled CI job) triggers dbt build, which runs models + tests + snapshots + seeds in DAG order and halts downstream of a failure. Slim CI (state:modified+ --defer) builds only what a PR changed plus its descendants, deferring the rest to production's tables. Cost problems trace back to materialization choice, un-prunable incremental filters, over-used ephemerals, or missing clustering keys.

15. How Deep to Go

You already use dbt — this is the intermediate-to-strong line, not a beginner tutorial

For a data-engineering role, you should be able to explain the full workflow and reason about incremental models under pressure. You do not need governance-platform depth.

Know cold

• The workflow: source → staging → intermediate → mart, and why each layer exists (section 05).

• The building blocks: models, sources, seeds, snapshots, tests, macros, documentation.

• Materializations: view, table, incremental, ephemeral — when and why each (section 06).

• Dependencies: ref(), source(), and that the DAG falls out of them for free (section 02).

• Data quality: unique, not_null, accepted_values, relationships, plus singular/custom tests (section 09).

• Incremental models (the interview favourite): how is_incremental() works, how you identify new/changed rows, what happens when historical data changes, and how you handle late-arriving data (section 07).

• Snapshots: SCD Type 2, and the timestamp vs check strategies (section 10).

• Macros: enough to answer "why would you use one" — reuse a pattern across models, write a custom generic test (section 08). You do not need to be a Jinja expert.

• Commands: run, test, build, compile, seed, snapshot, docs, and especially build vs run (section 12).

You do not need (yet)

• dbt Mesh / multi-project architecture — an org-scale ownership decision made once; you consume the result.

• The Semantic Layer & MetricFlow — real but uncommon in production, and it effectively needs dbt Cloud. Know the one-line pitch: define a metric once as code, every tool queries that definition.

• Data contracts & model versioning — know they exist (contract.enforced checks a model's output columns/types before build; versioning ships a breaking change as v2 while v1 keeps serving). Rarely needed until you have external consumers.

• The Fusion engine internals — a Rust rewrite in preview; know the name, skip the details.

• Deep Jinja — custom materializations, complex macro metaprogramming. Almost never interviewed, rarely needed day to day.

∎ The takeaway

dbt's core trick is small and easy to underestimate: turn your SQL transformations into a real, version-controlled project with dependencies, tests, and documentation, and let the warehouse keep doing what it already does well. Everything else — incremental strategies, Slim CI, contracts, the Semantic Layer, the Fusion engine — is infrastructure the ecosystem has built around that one trick as it scales from one analyst's laptop to a whole company.

For an interview, the centre of gravity is the source → staging → intermediate → mart workflow and incremental models: be ready to explain how one is built, how new and changed rows are identified, what happens when history changes, and how late-arriving data is handled. The rest you look up when you hit it.
